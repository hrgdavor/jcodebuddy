# Cooperative Codegen — Preserve User Tweaks

> **Status:** proposal, captured for [DEC-020](../architecture/decisions/DEC-020.md).

The full decision (rationale, alternatives, consequences, acceptance
criteria) lives in
[`doc/architecture/decisions/DEC-020.md`](../architecture/decisions/DEC-020.md).
This file is the **practical reference** for generator authors: the
hard user-facing rule, the default mechanism (implicit block
detection, not strict markers), the optional hint comment, the
reporting mode, and the patterns to make detection robust.

## The hard user-facing rule

> *If the user has not deleted a piece of generated code, do not
> rewrite it on the next pass. The user opts back into regeneration
> by deleting the block.*

That is the whole user contract. Everything else in this file is
about how the generator **finds** its previous output without
rewriting the file from scratch.

## Default mechanism: implicit detection, not strict markers

By default, generators recognise their previous output by
**structural shape** (the same shape they used to emit it), not by
looking for marker comments. The strict
`// generator:begin` / `// generator:end` pair is **discouraged** as
a default because it adds noise to every generated file for the
rest of the project's life.

Examples of "block I previously emitted" recognition:

- A **switch arm** keyed by the JSON-RPC method name
  (`case "users.get":`). The generator scans the `switch`, finds
  the arm, preserves its body.
- A **builder method** on a record builder, recognised by name,
  parameter type, and return type (`withName(String) →
  PersonBuilder`).
- A **scaffolding method** recognised by annotation, name, and
  parameter list (`@CoreChangeOnChange recomputeDerivedTotals(ProcessingUnit<OrderContext>)`).

In all three cases the user is free to edit the body. The
generator finds the block again on the next pass by the same
structural rule.

## Optional single-line hint comment

A generator MAY emit **one** optional comment at the top of a
block, as a user-facing hint:

```java
// generated by rpc-dispatcher — edit freely, delete to regen
case "users.get" -> usersService.get(req.params, req.id);
```

This is:

- a single line, scoped to the block,
- a **UX aid**, not a contract the generator relies on,
- not required for the generator to find the block on the next
  pass.

The generator MUST NOT depend on this comment for recognition. The
recognition rule (which AST shapes count as "mine") lives in the
generator's code, not in the file.

## Optional strict marker pair (discouraged, allowed)

A generator MAY choose to wrap its output in:

```java
// generator:begin <generatorId> <stableBlockKey>
... block body ...
// generator:end   <generatorId> <stableBlockKey>
```

This is **allowed but discouraged** as a default. Reasons a
generator might still choose it:

- The block cannot be reliably recognised by shape (free-form
  statements in the middle of a method body, mixed hand-written
  and generated code in the same block).
- A user has asked for stricter behaviour after observing a
  preservation bug.
- A future codegen policy decides that strict markers are the
  right default; this decision explicitly leaves that door open.

When a generator does use strict markers, the syntax is exactly
as above, with `<generatorId>` (a short namespaced id) and
`<stableBlockKey>` (a string that is stable across regenerations
of the same logical block).

## Reporting mode

A generator SHOULD support a `--report-preserved-blocks` (or
equivalent) mode that, after a normal regen pass, prints the set
of preserved blocks that differ from what the generator would
have emitted. Uniform format:

```
[generator:preserve] <generatorId> / <stableBlockKey>
  file:     <path>
  lines:    <startLine>–<endLine>
  reason:   <short description of what would have been emitted>
  opt-in:   delete the block to re-generate
```

A future LSP / CI can parse this format. The reporting mode is
the diagnostic surface that tells the user "I kept something you
might want to look at", without requiring the generator to
annotate every block.

## User actions and what they trigger

| User action                                                | Result              | Generator behaviour                   |
| ---------------------------------------------------------- | ------------------- | ------------------------------------- |
| Edit body, no markers used                                 | Preserved block     | Preserve edits.                       |
| Delete the block, no markers used                          | Block missing       | Re-emit at canonical location.        |
| Edit body, with the optional hint comment                  | Preserved block     | Preserve edits. Hint comment stays.   |
| Delete the hint comment, keep the body                     | Preserved block     | Preserve body. (Hint is optional.)    |
| Delete the body, keep the strict markers                   | Empty block         | Re-emit body between existing markers. |
| Delete body **and** strict markers                         | Block missing       | Re-emit at canonical location.        |
| Delete just the `// generator:end` marker                  | Dangling marker     | Re-emit the whole pair.               |
| Add `@GeneratedFrozen` / `// generator:freeze` on file     | n/a (DEC-018)       | Leave the whole file alone.           |

## Patterns to make implicit detection robust and usable

These are the patterns the project has explored or intends to
adopt so implicit detection is **reliable** in practice. Every
generator is expected to follow them.

### 1. Use AST-aware diffing, not text diffing

The patcher should run on a `CompilationUnit` AST and re-emit
exactly the block range, not text-replace ranges that may shift
when the user re-indents. JavaParser's
`LexicalPreservingPrinter` is the recommended primitive (see
`doc_knowledge/code.graph.md`).

### 2. Publish the recognition rule

Every generator's README MUST state, in plain prose, **which AST
shapes it considers "blocks it previously emitted"**. Examples:

- `rpc-dispatcher`: a `case "<method-name>":` arm inside the
  `switch` of `dispatch(JsonRpcRequest)`, where `<method-name>` is
  a method name the dispatcher knows about.
- `hipster-entity-builder`: a `with<FieldName>(<FieldType>)
  → <BuilderType>` method on the builder class.
- `business-logic-loop-guard`: a method annotated
  `@CoreChangeOnChange` whose name and parameter list match the
  canonical scaffolding for a given entity type.

Reviewers must be able to ask: "what is the block for this arm?"
and the answer must be in the generator's README, not just in
the code.

### 3. Idempotency check is a CI gate

CI MUST run the generator twice in a row on every generator and
fail the build if the second run produces a non-empty diff. This
catches the most common patcher bugs (forgetting to remove an old
emission, emitting a block with whitespace that does not match the
preserved version, etc.).

### 4. Preservation fixture is a CI gate

CI MUST also run the generator on a fixture file that contains
a known user tweak (e.g. a case arm with a custom log message, a
builder method with added validation) and assert that the tweak
is preserved verbatim after regeneration, and that the reporting
mode flags the difference. This is the only way to catch silent
drop-of-edits bugs before they ship.

### 5. Hint comment discoverability in the IDE

The LSP / IDE sidecar should:

- highlight the optional `// generated by ...` hint comment,
- show a hover with the generator's id, the block's recognition
  rule, and a "regenerate this block" hint,
- offer a code action "Regenerate this block" that deletes the
  current block and triggers the generator.

### 6. Reporting format is uniform

Every generator's `--report-preserved-blocks` output MUST match
the format above. The LSP / build log can parse it to surface a
summary.

### 7. Generator MUST refuse ambiguous matches

If a generator's canonical location for a block already has a
shape that does not match what the generator would emit (a
different annotation, a different parameter list, a different
case label), the generator MUST emit a diagnostic and **not
overwrite** the existing block. Mis-recognition is worse than
no recognition; let the user resolve it.

### 8. Generator source is reachable from the diagnostic

The diagnostic SHOULD include the location in the generator
source where this block is emitted, so a developer can jump from
the preserved block to the generator that owns it. This satisfies
DEC-019 (source-visible, IDE-navigable) for the **generator
side** of the same workflow.

### 9. A reusable recognition helper

Build a small helper (in the codegen module) that takes a
`CompilationUnit`, a canonical location, and a structural
predicate, and returns the existing block at that location if
the predicate matches. Every generator uses this helper instead
of re-implementing the recognition loop, so the patcher
diagnostics are uniform and the recognition semantics are
reviewable in one place.

### 10. Don't switch on marker style mid-file

A generator that uses strict markers in some blocks and implicit
detection in others is hard to reason about. A generator picks
one style (or makes a deliberate, documented split) and sticks to
it for the whole file. The split, if any, is recorded in the
generator's README.

## Worked example: detecting a "delete" without a marker

A user removes the entire `case "users.delete":` arm from the
dispatcher:

```java
// before
case "users.delete" -> usersService.delete(req.params, req.id);

// user deletes the line, leaving:
case "users.create" -> usersService.create(req.params, req.id);
```

The next regen pass walks to the `switch`, looks for an arm
labelled `case "users.delete":`, does not find it, and
**emits a fresh arm at the canonical location** (typically just
before `default`). The existing arms are not touched. The user
sees a diff that contains exactly the new arm, nothing else.

## Worked example: mis-recognition refusal

A user has hand-written a method on the builder:

```java
public PersonBuilder withName(String name) {
    return withName(name, "default");   // hand-written convenience overload
}
```

The canonical recognition rule is "method named `with<Field>`
with one parameter of the field's type, returning the builder
type". The user's `withName(String) → PersonBuilder` matches the
shape, so the generator recognises it as "the `withName` block I
emitted" and preserves the body. This is actually the desired
behaviour: the user is overriding the canonical body with a
custom one, and the generator is preserving their override.

If the user instead writes something that **does not match the
canonical shape** (e.g. they rename the method to
`setName`), the generator walks the canonical location, does not
find a match, and emits a fresh `withName` method at the
canonical location. The user's `setName` is left alone as a
hand-written method. The reporting mode flags: "expected a
`withName(String) → PersonBuilder` block; found a `setName`
method instead; emitted a fresh `withName`."
