## Context

**The generator is a full pass, and the only pass there is.** `EntityMetadataGenerator` walks every `.java` file
under the source root, parses it, builds the interface map, and emits every view's artifacts on every run. The
example's measured cost is **599 ms for 42 source files, 15 generated files and 315 locations**
(`codebuddy.md` § 5.6) — fast enough that a no-op is the first useful incremental result, slow enough that a
real project with hundreds of views will feel a full parse on every save.

Three pieces that *look* like an incremental pass already exist, and none of them is one:

- **`ClassIndex.changedSince(previous)`** computes `ADDED` / `CONTENT` / `REMOVED` / `RENAMED_TYPE`, and the pass
  prints one `[index] …` summary line. **The result is printed, not used** to decide what to emit.
- **`artifacts[].inputs`** was reserved in DEC-029, DEC-028 and the tooling README as "the other half of what an
  incremental pass needs". E3 now writes it **and** the per-view `views[].inputs` (see § 4), so the graph that
  says which views a changed file affects exists; E4 consumes it for selective emission.
- **`MetadataCache` / `FileMetadata`** (DEC-041) store one file's facts under `.jcodebuddy/cache/` keyed by
  content hash, and a warm scan parses nothing. **At the MVP's acceptance the entity pass did not consume it**;
  the post-MVP E10 step (**landed 2026-11-06**) now does, using the base entries and a counted parse fallback.

**Watch mode is out of scope.** `WatchedRegeneration` keeps an `fs-meta` trio under
`.jcodebuddy/cache/watch-fs-meta`, diffs it, ignores `TOUCHED` and republishes after a pass. That state exists
**only for watch mode**; there is no one-shot build state, and the cutover is `java-watch-to-fs-meta.md` **W7b**,
still open. This record starts no watcher, adds no event source, and does not touch `project-automation`.
What is missing is not a faster parser but a decision about **when a pass may skip work and still be provably
correct**, and what it may remember between runs.

## Decision

### 1. The full pass is the reference; incremental output must be byte-identical

An incremental pass over the same tree, generator and flags must produce **byte-identical output** to a full
pass: every generated `.java`, `classes.json`, metadata document and converter manifest. A difference is a bug,
not an acceptable reformat. The test is `ExampleRegenerationTest`'s shape — regenerate a copy and compare bytes —
extended to a full pass and an incremental pass over the same inputs.

The corollary is the design's safety rule: **the incremental state is a cache, never a correctness input.** A
missing, corrupt, older-format or unreadable state costs a full pass; it never changes an answer. The fallback
matrix follows from this rule rather than being bolted onto it.

### 2. State: one disposable `fs-meta` trio, published after a successful pass

> **Superseded by the 2026-11-07 amendment.** The state is now a `run.json` daemon-generation marker; there is
> no Java-published trio and no `FsMetaScanner`/`FsMetaDiff` state path. The paragraph below is the original
> 2026-11-05 decision, kept for history.

- **Location:** `<module>/.jcodebuddy/cache/entity-build/` — a new derived subdirectory beside `watch-fs-meta`,
  ignored like every other `cache/` subtree (DEC-026). It never holds `.java`.
- **Content:** the module-relative paths and content hashes of every `.java` file under the source root,
  **including generated files**. The pass scans with `FsMetaScanner.scan`, loads the previous pair with
  `FsMetaPair.loadIfPresent`, diffs with `FsMetaDiff.between`, ignores `TOUCHED`, and publishes with
  `FsMetaWriter.publish` **after** the pass completed successfully. A failed pass publishes nothing, so the next
  run retries rather than recording a half-state.
- **Excluding itself, and not git's view.** `FsMetaScanOptions.ignoring(".jcodebuddy")` keeps the state out of
  its own scan, and the scan deliberately **does not honour `.gitignore`**: the pass reads every `.java` under
  the source root, so a file a project happens to ignore is still part of the state. A trio whose recorded root,
  format or hash contract does not match is treated as **missing**, so a copied or stale `.jcodebuddy/` costs a
  full pass rather than a wrong answer.
- **The transitional writer, stated honestly.** `fs-meta`'s intended writer is the Zig daemon, and the Java
  `FsMetaWriter` is transitional until **W7b**. Using it lets a one-shot build work with no daemon; inventing a
  second tracker would violate the rule that `fs-meta` is the shared primitive. The use is confined to **one
  state class**, and W7b replaces the writer without changing the pass's inputs; daemon-or-writer is permitted.

### 3. Fingerprint: a generator or policy change is a full pass

The state records a fingerprint of what changes output **without changing a source byte**:

- generator identity/version, its artifact, and the JDK **major**;
- source root, metadata output, `--java-out`, package filter;
- every output-changing flag — `--adapters`, `--dto-projections`, `--mapper`, `--merge`, `--patch-appliers`,
  `--force` — and the validation policy.

A fingerprint mismatch forces a full pass — the "options are part of the fingerprint" rule the class index's
`hash` header follows. Separately the state records the publishing pass's validation **outcome** (`clean` /
`reported` / `not run`); it is not compared, because it licenses a no-op's validation skip (§ 5) rather than
deciding whether the tree changed.

### 4. Inputs are fully qualified names, resolved through the class index

A view may be skipped only if the pass can name **every file whose content can change that view's output or
metadata**: a set of FQNs resolved through the module's class index, **never paths** (DEC-029: an FQN is what an
IDE rename updates; a path is a fact about one checkout).

For each view, `views[].inputs` contains the view's own source file; the marker it derives from; every supertype
and addon it inherits fields from, transitively; every type named by a field's declared type, including generic
arguments; the generated artifacts belonging to the view (so a missing or hand-edited generated file is
detected); and mapper/merge partner views when those opt-in features are requested.

`artifacts[].inputs` is the **per-artifact** half — what the index promises about an artifact's
sources; in the MVP it repeats the view's set for each artifact. Both lists are FQNs, sorted, and resolved
through `classes.json`. An unresolved name is **reported, not silently dropped**, and a view with an
unresolved input is **always affected** — conservative, not a guess.

### 5. The fallback matrix

| Situation                                                                                   | Action                                                                                         |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| No content change and the fingerprint matches                                               | **No-op**: no parse, no validation, no writes                                                  |
| `TOUCHED` only (same bytes)                                                                 | no-op; content identity is unchanged, so the next run no-ops too                               |
| Existing `.java` files modified, in place                                                   | **Incremental**                                                                                |
| A file or type is added, removed or renamed                                                 | **Full pass**                                                                                  |
| Generator identity/version or any output-changing flag changed                              | **Full pass**                                                                                  |
| State missing, corrupt, unreadable, or an unknown format                                    | **Full pass**                                                                                  |
| A generated artifact is missing or its content hash differs from the state                  | **Full pass**, then report and regenerate: a hand edit cannot be attributed to one view safely |
| An incremental-unsupported emitter is enabled (`--adapters`, `--patch-appliers`, `--merge`) | **Full pass** in the MVP                                                                       |
| A source file cannot be parsed                                                              | **Full pass**, with the existing parse diagnostic                                              |
| `--validate=STRICT` and the state does not record a clean validation of the same tree/generator/policy | Validation runs over the whole tree; generation proceeds only if it passes          |
| `--full` / `--force`                                                                        | **Full pass**                                                                                  |
| A changed file cannot be mapped to a type FQN                                               | **Full pass**                                                                                  |

Two consequences are deliberate:

- **A no-op may skip validation only when the state records that the same tree, generator and policy already
  passed validation cleanly.** An explicit `validate` subcommand **always runs**, and a state recording a
  reported or skipped validation does not license a no-op — so `--validate=STRICT` cannot become a formality
  skipped exactly when it is cheap.
- **Incremental with `--validate=STRICT` still validates the whole tree.** Validation is a whole-tree question
  ("is this interface a view?"), so its cost is not avoided when some files changed; the no-op is the only case
  that can skip it safely.

**DTO projections and mappers are view-scoped, so they stay incremental.** `--dto-projections` emits a
`<View>Json` for a view marked `@View(dto = true)`, so it follows that view. `--mapper` emits a class between
two views, so it follows either endpoint. This matters beyond elegance: the example's own pass uses both, so a
blanket "optional emitters force full" would make the repository's canonical tree unable to demonstrate
incremental generation. The converter manifest remains complete because every mapper request is resolved
against the full interface map and the manifest is rewritten from that resolution whenever any mapper exists.
SQL adapters, patch appliers and merge stay full-pass in the MVP because they are either draft or family-wide.

### 6. What the incremental pass does

> **Superseded by the 2026-11-07 amendment.** The pass loads the `run.json` marker, asks the daemon for changes
> since the recorded generation within the module subfolder, and records the settled post-pass generation. It
> does not scan/diff a local trio; the numbered steps below describe the superseded 2026-11-05 mechanics.

1. Load the state and the previous class index / metadata / generated artifacts.
2. Scan the source root with `fs-meta` and diff against the state.
3. Apply the fingerprint and fallback matrix; on "full", run the existing pass unchanged and publish a fresh state.
4. Otherwise parse the whole source set, build the interface map, and compute affected views from the changed
   FQNs and the recorded inputs.
5. Emit only affected views; for every other view reuse its previous metadata and verify each generated artifact
   still exists with the recorded content. A missing or changed artifact makes the pass **full** in the MVP: a
   hand edit cannot be attributed to one view safely, so it is reported and the reference pass regenerates it.
6. Write the class index once, as today, and the converter manifest whenever mapper requests exist (resolved
   against the full interface map, so it is complete even when only affected mapper classes are written).
7. Publish the new state, including the generated files the pass wrote.
8. Report `mode`, `changed`, `affected`, `emitted`, `reused` and `fallbackReason` in the run record and pass log.

**The class index must stay complete even for views that were not emitted.** The pass either marks a walked file
as generated from its DEC-021 header or merges the previous rows for skipped views; E3/E4 decide which. The test
is that a no-op index is byte-identical and an incremental index still resolves every document.

**Command surface.** This record fixes semantics, not every default. `--incremental` and `--full` are the mode
switches; `--check` is a **full** pass into a temporary copy because it is a CI/verification command, not the edit
loop. Whether `--incremental` becomes the default is E5's call, gated by E6; `--full` remains the escape hatch.

### 7. Watch mode is not part of this decision

The watch path remains [`java-watch-to-fs-meta.md`](../../../plans/java-watch-to-fs-meta.md)'s **W7b**. When it
lands it feeds a batch to the **same** incremental pass and reuses `EntityBuildState`; it must not add a second
dependency graph or a second state directory. This record starts no watch loop and cuts no daemon over.

## Alternatives considered

- **Always run the full pass (today).** Correct and cheap at the example's 599 ms, but the MVP's promise ("run it
  again with no edits and have it do no work at all") would have no failing test, and a real project pays a parse
  on every save. Kept as the **reference**, which is stronger than one option among two.
- **Key the state by mtime instead of content hash.** Rejected for DEC-029 § 6's reasons: a checkout rewrites
  `mtime` while content is unchanged (a false miss), and a same-second edit can leave it unchanged (a false hit).
  A content hash has neither failure, and `fs-meta` is the shared way to compare one.
- **Reuse `MetadataCache` / per-file extended metadata as the state now.** Rejected for the MVP: parse reuse is
  a **cache** problem (E10), while selective emission is a **correctness** problem with a dependency graph; stale
  generated source is the failure this batch exists to prevent. A per-file *extended* cache is also DEC-041 D6's
  trap: it can be stale after an unrelated edit and cannot say so.
- **Require a daemon to hold the state.** **Chosen 2026-11-07 (Design B), replacing the original rejection.**
  The daemon root is the project root; a module filters to its source-root subfolder. A missing daemon is a full
  pass, so the original “one-shot command with no daemon” property survives as a safe fallback; what changes is
  that a **no-op requires** a daemon baseline. The format is a `run.json` generation marker, not a trio.
- **Use `classes.json` as the state.** Rejected: it is a **public addressing table** (DEC-029), not build state.
  It cannot record a file with no type (`package-info.java`), and treating a table a consumer may delete,
  relocate or regenerate as a correctness input would make an addressing artifact load-bearing for generation.
- **Record inputs as module-relative paths.** Rejected by DEC-029 and DEC-019: a path is a fact about one
  checkout, and a rename would leave the record stale in a way no IDE rename can update.
- **Skip validation on every no-op without recording the outcome.** Rejected: that turns `--validate=STRICT`
  into a one-time check and lets a tree that failed validation be treated as clean on the next no-op.

## Consequences

**Positive.** A no-op is a real, cheap result: no parse, no validation, no writes, and the state advances over a
same-content save. After E4 one view's edit rewrites that view's artifacts and leaves the rest untouched, with a
full-pass copy as the byte-equality oracle. There is one state directory, one format and one writer to replace at
W7b — not a second tracker. "I cannot prove this" is a **correct outcome** that does more work and names its reason.

**Negative, accepted.** The MVP still parses every file: the graph decides what to *emit*, not what to *parse*,
so a one-file edit costs a full parse plus one emission until E10. **E10 landed on 2026-11-06**: a warm pass
over the example parses zero files and a one-file edit parses one, with counted fallbacks for facts the base
layer cannot supply. The state is another derived artifact to
ignore and exclude from its own scan, and a foreign-format state costs a full pass rather than repair. The graph
may be wrong conservatively (an unresolved input makes a view always affected; an unmappable change makes the
pass full) — accepted, while the unsafe direction is not. Generation takes five shapes (no-op, incremental, full
on add/delete/rename, full on state/policy mismatch, full on an unsupported emitter), so the run record and tests
must carry mode and reason; a no-op that skips validation must be tested, not argued.

**Follow-up work.** E2 implements the state and the no-op; E3 the inputs; E4 selective emission; E5 the command
surface; E6 the tests; E7 the guide; E8 the clean-consumer acceptance; E9 the declaration. E10 (parse reuse)
landed on 2026-11-06; W7b (watch cutover) remains explicitly later.

## Out of scope

- Watch mode, an event source, a sidecar/LSP, and the daemon cutover (W7b).
- Multi-module or cross-module resolution, and any repository-wide index: one module, one source root, one
  class index.
- Incremental support for SQL adapters, patch appliers or merge; those force a full pass in the MVP.
- A Maven plugin, release to Maven Central, and any API-stability promise.
- The state's storage format beyond "an `fs-meta` trio in the module's derived cache"; moving it and what a
  daemon writes are W7b's business.
- Changing generated output, metadata shape or the class index format; this record adds a cache and a dependency
  record and changes no emitted byte by itself.
- The CLI default: whether `--incremental` is the default is decided in E5 and gated by E6.

## Acceptance criteria

The plan's E2–E9 gates, restated as the observable conditions this record is accepted against. For this record
itself (E0): the maintainer accepts it, it is indexed in both decision indexes, its matrix is the plan's § 3.5
matrix, and **no production behaviour changed** — implementation starts at E2.

1. **E2 — no-op.** `--full` then `--incremental` over an unchanged tree performs no pass and writes nothing
   (`git status` clean); a same-content save is a no-op; add, delete, rename, a corrupt state and a changed flag
   each fall back to full; tooling and example tests are green.
2. **E3 — inputs recorded.** Every view's metadata carries resolved inputs; the index resolves every FQN; two
   passes are byte-identical; a changed marker, addon, supertype or field type is reported affected; no path
   appears in an input list.
3. **E4 — selective emission.** One accessor edit emits only that view's artifacts; a full-pass copy is
   byte-identical; unaffected files are untouched; a second run is a no-op; the test asserts **which** views.
4. **E5 — command surface.** Two `gen.js` runs leave the second a no-op; `--check` exits 0 on the committed
   example and 1 after a deliberate edit, naming the file; `--full` regenerates; `--run-record` carries the six
   fields.
5. **E6 — the matrix is tests.** Every row has a test; every incremental result is byte-identical; the reason is
   named; the README and this record carry the same matrix; a write counter/mtime check proves no unaffected
   rewrite.
6. **E7 — the guide.** `user/incremental-build.md` covers the state directory, fallback rules,
   `--incremental`/`--full`/`--check`, and that watch mode is later and calls the same pass; the MVP surface page
   says what the gate exercises; links pass and tables are normalised.
7. **E8 — clean-consumer acceptance.** `scripts/check-entity-mvp.js` exits 0 from a clean local install, records
   durations and emitted/reused counts, and names a missing JDK 25, Maven or artifact.
8. **E9 — declared.** The recorded gate is green; docs links pass; roadmap and plan agree; watch and Maven
   Central remain out of scope.
