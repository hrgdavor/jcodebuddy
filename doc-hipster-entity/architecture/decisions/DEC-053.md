# DEC-053 — A live tool inside a project publishes a Unix socket in `.jcodebuddy/ipc/`

> **Status:** accepted, 2026-11-19.
> **Applies to:** every tool that runs inside an open project and has state or commands a person or a page
> should reach — today the IntelliJ incremental compiler, and any host that proxies it.

## Context

A live tool knows things a project cannot show from its files: what a compiler is doing right now, which
files failed, what it would do if asked to rebuild. Until now the only way to reach that was the tool's own
window: the IntelliJ plugin's log page has a log and ten buttons, and nothing outside the IDE can read either.

The obvious bridge is HTTP. It is also the bridge this ecosystem has spent the most effort containing: a port
must be chosen, published, claimed against another instance, pinned, discovered from a record, and probed to
answer "is a host there?" — `HostPortClaim`, `host.json`, DEC-032, DEC-033. That machinery exists because a
TCP port is a machine-wide, numbered, guessable resource. A tool inside one project is none of those things:
it serves exactly one directory, it is alive exactly as long as its process, and the operating system can
already answer "who may connect" for a file.

At the same time the webview product already has the presentation half: `/app/<tool>.html` is served from
`<project>/.jcodebuddy/app/` with the navigation bridge, and the page authoring rules, the token and the
allow-list are settled (`webview/doc/webview-app-contract.md`, `webview/doc/webview-host-api.md`). What is
missing is a **tool endpoint convention** — a place a tool publishes, and a way a host proxies it.

## Decision

**A live tool publishes one Unix domain socket under the served project's derived `.jcodebuddy/ipc/`
subtree, a descriptor next to it, and newline-delimited JSON-RPC 2.0 over the socket.**

1. **Paths.** `<project>/.jcodebuddy/ipc/<tool>.sock` and `<project>/.jcodebuddy/ipc/<tool>.json`, with
   `<tool>` a lowercase slug ({@code jcodebuddy-incremental-build}). `.jcodebuddy/ipc/` is a derived subtree
   in DEC-026's sense: machine-written, git-ignored, never configuration. When the conventional socket path
   exceeds the platform's `sockaddr_un` limit (108 bytes on Linux and Windows, 104 on macOS), the socket moves
   to the system temp directory and **the descriptor stays in the project and names the real path**. The
   descriptor is the authority; no consumer recomputes a socket path from a convention it might spell
   differently.
2. **Descriptor.** `{protocol, tool, title, ide, ideVersion, pid, socket, project, startedAt,
   capabilities}`, absolute and forward-slashed, written atomically. It carries **no secret** and makes **no
   liveness claim**: the descriptor outlives a crashed process, exactly like `host.json`, and liveness is
   answered by connecting.
3. **Protocol.** JSON-RPC 2.0, one JSON object per line, UTF-8, request/response on a connection. `tool.info`
   returns the descriptor and every endpoint answers it, because that is how a consumer proves liveness and
   how a host lists what a tool declares in `capabilities`. A tool's other methods are its business; a
   refusal carries a numeric JSON-RPC code, never only a message. v1 has no server-pushed events — a consumer
   polls a method that answers "everything after N" (the compiler's `build.log` carries a monotonic sequence).
4. **One endpoint per tool per project.** Two editor windows on one project are normal, and a consumer has no
   rule for choosing between two endpoints that answer for the same project, so the second one **does not
   bind**: `start()` reports the live occupant and the caller logs it. The test is a real connection, so a
   socket file left by a crashed process is removed and replaced.
5. **The socket is scoped by the filesystem, not by a token.** The socket is created with the owner's
   read/write mode on POSIX systems; on Windows it is a file only that user can reach. There is therefore **no
   token on the socket**. A host that proxies it over HTTP applies its **own** token and allow-list at that
   boundary (`/api/tools/<tool>/call` is token-only in `webviewd`; the list is origin-or-token) and never
   passes a socket credential on, because there is none.
6. **One implementation.** `jcodebuddy/jcodebuddy-ipc` is the library: `ToolProtocol` (the names), the
   descriptor, `ToolEndpoint` (server) and `ToolClient` (consumer). A tool does not implement the framing, and
   a host does not implement a second copy of it. Its tests are in the recorded gate, because the wire format
   is a contract every endpoint and every proxy has to follow.
7. **The page is a starting point, not a second UI project.** A tool that has a log page may ship a default
   served page built by Bun from `project-automation/` and written to `<project>/.jcodebuddy/app/`, so
   `/app/<tool>.html` already works with no host change. The compiler's page
   (`project-automation/compiler-console/`) is the first: the same log and buttons as the tool window, over
   `/api/tools/<tool>/call`. It reads its host token from its own URL (`?token=`), the mechanism the Eclipse
   host documents, and refuses to pretend it can work without one.

## Amendment 2026-11-19 — push, not only request/response

The first version was request/response: a page polled. That was enough to prove the endpoint, and wrong for a
log, where the interesting line is the one that arrives while you watch. The same socket now carries
notifications, so no second transport is added. This supersedes Decision 3's "v1 has no server-pushed events"
and the matching consequence below; both are left as written because a decision record is history.

- **`tool.subscribe`** (`{topic, since?}`) confirms a stream and turns that **connection** into an event
  channel: every later line is a JSON-RPC **notification** `tool.event` with `params = {topic, data}`, and the
  response to `tool.subscribe` is the last request/response message on it. A consumer that needs both opens
  two connections; a host opens one per SSE client.
- **Topics are declared** in the descriptor (`topics`), and `tool.subscribe` appears in `capabilities`, so a
  consumer knows a tool streams before subscribing. A tool with no topics implements neither and remains a
  valid endpoint.
- **The tool owns the backlog.** `subscribe(topic, since, sink)` replays retained events after `since` and then
  pushes live ones; the compiler's log replays under the same lock its writes take, so a line cannot fall
  between "what you have" and "what comes next". `since = null` means "from now".
- **A slow consumer is ended, not silently skipped.** Each subscription has a bounded queue; on overflow the
  tool sends `tool.event-error` (`reason: overflow`) and closes, and the consumer re-reads the missing lines
  from the tool's own method by sequence. A skipped event without a gap signal is the one outcome the format
  forbids.
- **The hosts expose SSE.** `webviewd`, the JetBrains host's HTTP bridge and the standalone Bun metadata server
  serve `GET /api/tools/<tool>/events?topic=&since=&token=`: token-only (EventSource cannot set a header, so
  the token is in the query), `text/event-stream`, one `event: tool-event` frame per notification with the
  data's `sequence` as the SSE `id`, a keep-alive comment every 15 s, and `Last-Event-ID` winning over the
  query's `since` so a reconnect resumes where the page stopped. A tool refusal is `400`, an unreachable tool
  `502`, an unknown tool `404`. The two Java hosts share `ToolProxy` in `jcodebuddy-ipc`; the Bun server is a
  port of that wire, and its tests hold it to the same statuses and frame.
- **The page uses it.** `project-automation/compiler-console` takes the retained tail once with `build.log`
  and then renders the stream; a lower sequence than it has seen means the tool restarted and the view
  reloads.

The wire stays `jcodebuddy-tool/1`: a consumer that never subscribes receives exactly what it received before,
and the two new frames are JSON-RPC notifications, which a JSON-RPC client is already required to ignore when
it did not ask for them. A later change that alters the meaning of an existing frame is a version bump; this
one adds frames.

## Alternatives considered

- **An HTTP port per tool.** Rejected: it recreates the numbering, claim, pin and discovery problem DEC-033
  exists to contain, for a resource that is per-checkout and user-scoped. A Unix socket is a file.
- **A Windows named pipe.** Rejected as a second transport: the JDK has supported `AF_UNIX` on Windows 10
  1803+, and two transports would be two contracts and two test lanes. A platform without Unix sockets
  exposes no tool endpoints; the tool still works in its own window.
- **One socket per host, with tools registering inside it.** Rejected: a host is not always running, and a
  tool must be reachable when one is not. Per-tool sockets also make the second-instance rule local (one tool,
  one project) instead of a registry's problem.
- **Token on the socket.** Rejected: it would be a second authentication model for a resource the OS already
  scopes, and a token file in the project is exactly the host state DEC-032 says belongs to a host, not to a
  tool.
- **Server-sent events over the socket in v1.** Deferred: polling a sequence-numbered log is enough for the
  first page, and a push protocol needs framing, reconnect and backpressure rules that are a decision of
  their own.

## Consequences

**Positive.**

- A tool is reachable without numbering anything, and a second IDE instance cannot create a second endpoint
  that answers for the same project.
- One framing, one descriptor, one client: a host proxies a tool it has never heard of.
- The page namespace, the bridge, the token and the allow-list are reused rather than reinvented; a tool page
  is a build output, and `/app/<tool>.html` needs no host route.
- Nothing about the socket is a secret, so there is nothing to leak in a descriptor, a log or a bug report.

**Negative, accepted.**

- The page cannot authenticate itself on a host that does not hand it a token; today that means the URL, and
  a `webviewd`-served page needs the token appended. The seamless form — a host injecting the token into the
  page it serves — is a host change with its own security decision and is not part of this one.
- The socket is local only. A remote caller needs a host, which is the point.
- v1 is request/response: a page polls. A future event channel is a new decision, not an extension by
  accident.
- The routes are served by the host itself rather than proxied to a `customServer`, so a project with a JS
  backend still reaches a tool on the host's own port; the JS backend serves the same routes for the pages it
  serves, which is one wire in two implementations rather than a second contract.

## Out of scope

- Remote access, TLS, or exposing a socket outside the machine.
- A push/event protocol on the socket.
- A registry of tools other than the directory listing (`*.json`), and any tool discovery outside a project.
- Replacing the host API's own editor routes; this contract only adds a tool namespace.

## Acceptance criteria

1. `jcodebuddy-ipc` binds, publishes and answers a descriptor over a real socket; a second endpoint for the
   same project is refused; a stale socket file is replaced; `stop()` removes the socket and the descriptor.
2. The IntelliJ incremental compiler publishes `jcodebuddy-incremental-build` while its build is enabled for a
   project, answers `tool.info`, `build.status`, `build.log`, `build.diagnostics`, `build.roots`, and accepts
   `build.rebuild`, `build.watch.stop`, `build.watch.start`, `build.refreshErrors`, `build.refreshRoots`,
   `build.listClasspath`.
3. `webviewd` serves `GET /api/tools` and `POST /api/tools/<tool>/call` (token-only), forwarding to the
   socket, with `400` for a tool refusal, `404` for an unknown tool and `502` for an unreachable one.
4. `project-automation/compiler-console/` builds `.jcodebuddy/app/incremental-build.html` with Bun, and the
   page renders the log and drives the same buttons through `/api/tools`.
5. The recorded gate builds and tests `jcodebuddy-ipc` and the contract has one implementation.
