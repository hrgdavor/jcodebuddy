## Context

DEC-024's runtime half landed: `ViewChangeTracking` exposes `changesDeep()`, `shallowPaths()` and `nestedTrackers()`,
`ChangePath` names a leaf, and `EntityUpdateTrackingArray` materializes both from an untyped `Object[]` — discovering
nesting with an `instanceof` on the value it already holds, which DEC-024 § 4 records as deliberate rather than a
sloppiness. Two things were explicitly left out, and DEC-024 says so in its own follow-ups:

1. **task 6.5, the generator wiring** — *"a generated tracking builder must detect that a field's declared type —
   including a generic collection of them — is itself a trackable `@View` type and emit the deep index, rather than the
   array path's value-level discovery."* Until it exists, the array path and a hand-written fixture are the only
   materializations that exercise the contract, so a *generated* view's deep path is whatever the interface's default
   gives it: the shallow level, and an empty `nestedTrackers()`.
2. **a patch applier** — *"Applying the deep document — including the collection operations — is a separate, testable
   piece."* The emission already exists (`EntityJacksonDeepChangeSerializer`, beside the shallow
   `EntityJacksonChangeSerializer`), so the document's shape is fixed: a list of operations carrying a `path` array
   (field names, with an integer at a collection level) and the leaf's `current` value, with no `previous` anywhere.

The second one has a question inside it that decides where the code lives, and it is the reason this record exists
rather than the work simply being done: **how does an applier set a leaf without reflection?** DEC-019 forbids routing a
request by string name into a `Map<String, Method>`, and a generated view's setters are **typed methods**
(`Write firstName(String value)`) — there is no set-by-name call to make generically. The three shapes available,
weighed: (a) **generated per view**, so the dispatch is the same direct-call switch the generated `forName` arms already
use; (b) **generic over the field enum's name mapper** plus a generated setter switch reached through metadata; (c) a
**`ViewWriter`-shaped SPI** that each generated view implements, which is the shape DEC-019 accepts for transport
routing. (b) and (c) both split one operation across a generic half and an emitted half, and (c) adds an interface to
the model to serve a consumer that is itself generated.

## Decision

1. **The generated tracking builder emits the deep index from its own typed fields** (task 6.5), for every field whose
   declared type — or whose `List<…>` element type — is a trackable `@View` type:
   - `nestedTrackers()` returning `Map<Integer, ViewChangeTracking<?, ?>>`, keyed by that field's **ordinal**, holding
     the child tracker the builder's typed field already references;
   - `changesDeep()` walking the shallow level and extending each nested field through the child's own `changesDeep()`,
     wrapping a child path as `new ChangePath(field, -1, childPath)` and reporting `ChangePath.of(field)` when a
     **reassigned** child shows no change of its own — because a reassignment is a change at this level even when the
     child has nothing to report, and the array path's code says so in the same words.

   The array path keeps its `instanceof` discovery: it has no declared field types to read. The template the emitter
   mirrors is `EntityUpdateTrackingArray.changesDeep()`/`nestedTrackers()`, so the two materializations answer the same
   question and the difference between them stays the one DEC-024 § 4 already explains.

2. **The applier is generated per view**: `<View>PatchApplier`, emitted beside the `<View>Write` interface it writes
   through. Its `apply(…)` takes the document and the view's own `Write` target, walks each operation's `path` array,
   and dispatches on the field **name** with a `switch` whose arms call the **typed setter** — the same direct-call
   shape the generated `forName` switch already has, so a reader with only the committed sources can follow a patch
   operation to the field it sets. A path that continues past this view's field recurses into the **nested view's own
   applier**, which is what makes the path array work end to end without any name lookup at runtime.

3. **An unknown field is skipped and reported, never guessed** (DEC-016): no `HashMap` lookup, no positional fallback
   presented as identity matching. The document's own `"fallback": true` marker is carried into the report rather than
   silently applied.

4. **Nothing about the runtime contract changes**: `changes()` stays shallow and single-level (DEC-012), `changesDeep()`
   stays pull, a child stays reusable and shareable, and the array path's behaviour is untouched. This record adds
   emitted code and one generated class; it moves no existing meaning.

5. **A nested or collection field: `setter` is implemented, `recursion` is not yet, and here is why it needs a decision
   rather than an implementation.** The implementing step measured the ground this record assumed when it said the
   applier "recurses into a nested view's own applier": **nothing generated implements `Write`** (`PersonSummaryBuilder`
   is `public final class PersonSummaryBuilder`, with no `implements` clause — the reference on those views is
   hand-written into the view itself), and `toBuilder()` yields that builder, so there is **no route from a view
   instance to a child's `Write`**. The nested write therefore cannot be reached by walking values, and the document
   describes a **leaf inside** the child (`["previousAddresses", 0, "city"]`), not the child's whole value — which the
   `ViewWriter` surface cannot supply either: its `set(String, Object)` / `get(String)` / `supports(String)` defaults
   write and read a **whole field value** through the writer's own field mapping, so they answer "what is this field"
   and not "what is this field's field".

   Two shapes remain, and the implementing step chooses with its eyes open:
   - **(a) a caller-supplied child-writer resolver** — the generated `apply` takes a function `(String field, int index)
     -> ViewWriter` (or the typed `<Child>.Write`) alongside the target, so the project says how a nested view's writer
     is obtained from the one it already has. Source-visible, no new model type, and the generated applier still
     dispatches with a `switch`; the cost is one more parameter and a caller that must wire it.
   - **(b) emit the child's whole current value** instead of paths into it, so the nested case becomes one
     `ViewWriter.set(field, value)` (or one typed setter) — the smaller applier and the smaller caller, at the price of
     a change to the **emitter**, which § 5 currently specifies as leaf paths, and of losing the information that the
     change was a leaf rather than a whole-value replacement.

   The reviewer's question for whichever is chosen is the one § 1 asks everywhere: *with only the committed sources and
   a stock IDE, can a reader follow a nested patch operation to the field it sets?* (a) answers it directly; (b) answers
   it only if the emitted value's own construction is navigable. Until this is settled, the generated applier emits an
   honest arm for such a field rather than a wrong call.

## Amendment, 2026-10-09 — § 5 settled, and the polymorphic family with it

**§ 5 is answered, and not by either listed shape.** The maintainer chose a third: **a generated builder implements its
view's `Write`**. `PersonSummaryBuilder` becomes `implements PersonSummary.Write`, so `view.toBuilder()` is the route
from a view instance to a writer, and it is the same route at every level. That is what § 5 measured as missing — the
builder had no `implements` clause and no generated class implemented `Write` at all — so the answer also closes a
long-standing gap rather than routing around it. It is preferred over (a) because a resolver parameter puts the model's
own structure into every caller's hands and a wrong resolver fails at runtime, and over (b) because losing "this was a
leaf change" is a real loss for a document whose purpose is to say what changed.

**Two consequences that follow, and one that was needed anyway.**

1. **Nested and collection recursion follows through the child's own applier.** Given a `Write` for the child, a path
   that continues past this view's field dispatches into `<Child>PatchApplier` exactly as § 2 specifies. Collection
   support is **element writes only**: applying an operation inside a list writes through the element's own applier,
   and an **index that no longer exists fails with a named finding** rather than being skipped — § Consequences already
   allows an applier to be stricter than its emitter, and a silent skip would drop part of a patch while reporting
   success. Add/remove/reorder wait for the runtime-bookkeeping reading the Follow-ups below still ask for.
2. **Polymorphic view roots get a generated dispatcher on the root family.** The convention already exists end to end
   for serialization and needed no invention: `@View(discriminatorField = "…")` on the root, a generated
   `discriminatorValue` per concrete view, and a generated `permittedSubtypes()` on the root's `META`. What was missing
   was only **apply-time** dispatch, so the generated dispatcher reads the value's discriminator through the root's
   `discriminatorField()` field enum, matches it against each permitted subtype's `META.discriminatorValue()`, and calls
   the matching concrete applier. This is the shape `PaymentMethodController` hand-writes in the example today; it is
   emitted instead, which is the difference DEC-019 exists to make.
3. **Scope: only views reachable from a patch target** get an applier and a dispatcher, so a project pays nothing for a
   polymorphic family it never patches.

**Honest note on cost.** Point 1 is an **emitter change to every generated builder**, not code beside them: every
generated `<View>Builder` gains an `implements` clause, which is visible churn in committed sources and a change to
what "committed == generated" means for them. It is taken deliberately, because the alternative is a route to a child's
writer that exists only in a caller's lambda.

**Still open after this amendment**: the generated applier's arm for a nested field remains the honest placeholder § 5
describes until the builder change lands, and how a **discriminated family member reachable only through a root-typed
field** is resolved when a permitted subtype is itself abstract is not addressed here — no such case exists in the tree
yet, and inventing a rule for it now would be a decision without a measurement.

## Consequences

**Positive.** A generated view's deep path stops depending on the interface default, so a nested-only change is
reportable from generated code with no hand-written fixture in the loop. The applier closes the round trip the emission
half opened, and it does so with code a stock IDE can navigate: `switch` arm → typed setter → field. The two
materializations (array, generated builder) answer `changesDeep()` the same way, which is what makes the contract one
contract rather than two behaviours with a shared name.

**Negative, and accepted.** A view with no nested trackable field gains nothing and emits nothing — the emitters must
therefore decide per field, and a mistake there is a silently missing deep path rather than a compile error. The
per-view applier is more generated code than one generic applier would be, and it must be emitted for every view that
can appear as a patch target, including nested ones.

**Neutral.** Collection levels: the document names a collection element by integer index, so applying an operation
inside a list means writing through the element's own view (and its applier) rather than mutating the list in place.
Which list operations the applier supports — and whether an index that no longer exists is a skip or a failure — is
left to the implementing step and must be settled by a test, because the document is a *description* of changes and an
applier is allowed to be stricter than its emitter.

## Alternatives considered

- **A generic, reflective applier** (`Map<String, Method>` populated by scanning the view's setters): rejected by
  DEC-019, and the rule's rationale applies exactly here — the program's flow would stop being visible in the committed
  sources.
- **A generic applier over the field enum's name mapper with a generated setter switch** (shape b): workable, but it
  splits one operation into a generic walker and an emitted switch, leaving the reader to assemble the flow from two
  files when one generated class can hold it.
- **A `ViewWriter`-shaped SPI the views implement** (shape c): the shape transport routing uses, but it adds a model
  interface whose only client is generated code, and it moves the typed setters behind one more indirection for no
  gain over emitting the applier beside them.
- **Overloading `changes()`/`changesDeep()` into one method once a view nests something**: rejected in DEC-024 and not
  revisited here.

## Follow-ups

- **Polymorphic view roots** in the deep path (DEC-024's third follow-up): a discriminated family member needs the same
  wiring as a plain view; the generator side of this decision is where that lands, and it is not exercised yet.
- **Collections in the deep index**: whether the generated builder needs runtime bookkeeping like the array path's
  collection trackers, or whether emission alone suffices — to be decided by reading the array path's collection pass
  first, and recorded either way.
- **Benchmarks** (DEC-024's second follow-up, task 6.9): `pullNoNestedChange`/`pullDeepNestedChange` are written and
  registered; the numbers have not been taken, and the pull model is revisited only if the no-nested-change case is not
  free.
