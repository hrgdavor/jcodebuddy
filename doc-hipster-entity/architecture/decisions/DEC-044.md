## Context

The maintainer's direction, kept as given:

> ok, fix the script so it definitely uses .gitignore properly and also skip unlikely files, it is too slow and is
> likely due to checking too many files. After that check any other broad script in this repo and centralize somewhere
> include file with logic to go through files while skipping gitignored files, but do so only for javascript scripts

and then, on the approach:

> using git sounds like overkill, I prefer you make for js a utility project that has that functionality that jcodebuddy
> ecosystem js utils can use. and make that as statement to be done also for java in watcher if needed at some point. do
> not implement java gitignore ATM

and, while that work was underway:

> also for such scripts that do a lot of work, report duration at the end of output, and make taht also a rule for
> utilities

**The measurement that made it a decision rather than a tidy-up.** `scripts/check-repo-links.mjs` walked the tree with a
hand-written skip list and filtered to Markdown *after* walking and reading everything, so it read every Java source,
every resource and every archive in a 25,293-file checkout to find about 270 Markdown files. The list was not wrong —
it named `node_modules`, `.vscode-test`, `.jsx6`, `proto`, `.tmp`, `.jcodebuddy` — it was the wrong *shape*: a list is a
promise somebody has to remember to update, and the cost of forgetting is paid in seconds on every run, invisibly.

## Decision

1. **One walker, for every JavaScript utility in this ecosystem.** `scripts/lib/file-walk/` is a small package under
   `scripts/lib/` — where this repository's shared JavaScript already lives — with its own `package.json`, no
   dependencies (DEC-027's rule for anything under `scripts/`), and a README that states its promise.
2. **`.gitignore` is the definition of "not ours".** Read from each directory as the walk enters it, so a nested file
   overrides its parent and a later line overrides an earlier one; an ignored directory is **not entered**, which is
   both the speed and git's own rule, because git cannot re-include a file below an excluded directory. Symlinks are
   not followed. Deliberately not consulted: `.git/info/exclude`, `core.excludesFile`, `.gitattributes` — those are a
   person's or a machine's opinion about a checkout, and a tool that behaves differently per machine is the failure
   this repository writes rules about.
3. **No `git` process.** `git ls-files` was considered and rejected as overkill and as an environment dependency: a
   utility then cannot run in an exported tarball, and its answer depends on a working tree rather than on files.
4. **A utility that does a lot of work reports its duration as the last line of its output**, through
   `scripts/lib/timing.js` so no two tools invent a format. **This is also a rule for utilities, written in
   `AGENTS.md` § 2**, because the reason is the same as the walker's: a tool whose cost is invisible cannot be noticed
   getting slower, and `time` is a shell builtin, which is precisely the platform-specific wiring § 2 rejects.
5. **`check-repo-links.mjs` uses it, and asks for Markdown during the walk** rather than filtering afterwards. It is
   the first consumer, not the only intended one: `fix-markdown-tables.js` and the other broad utilities are moved onto
   it in the same change.
6. **The Java side, in the watcher, is recorded and NOT built.** When the watcher needs gitignore semantics, they should
   be implemented once, in a Java type, against the same cases `scripts/lib/file-walk/index.test.js` states — and it
   should be written when something needs it, not now. The reason to wait is not effort: a second implementation of
   these semantics is a second place for them to be subtly wrong, and until a real consumer exists there is nothing to
   check the port against.

## Consequences

- A walk is a few hundred files in a few hundred milliseconds instead of tens of thousands of files in seconds, and the
  rule that decides it is a file in the repository rather than a list in a script.
- The walker is the repository's statement of what `.gitignore` means, so a script that disagrees with it is wrong by
  construction rather than by accident — and its tests are the cases a Java port would have to satisfy.
- One more small package under `scripts/lib/`, which is a place this repository already keeps shared JavaScript.
- **A latent divergence is now visible rather than hidden**: if a directory is ignored by a mechanism the walker does
  not read (a global excludes file), a script will visit it. That is the deliberate choice in clause 2, and it is
  written down where someone debugging it will look.

## Alternatives, and why not

| Alternative                                              | Why not |
| -------------------------------------------------------- | ------- |
| `git ls-files` (with `--others --exclude-standard`)      | Git's answer is authoritative and fast, but it makes every utility depend on a `git` process and a working tree; the maintainer called it overkill, and a script that cannot run from an exported tarball is a script that fails somewhere else |
| Keep the hand-written skip list, add the missing entries | This is the status quo that failed. The next directory somebody adds is the next silent slowdown, and nothing fails |
| A `.jcodebuddy`-style config listing directories to skip | A second place to declare what `.gitignore` already declares, with no mechanism to keep the two in step |
| Port it to Java now, for the watcher                     | Nothing needs it yet, and a second implementation of ignore semantics written against nothing is a second set of bugs |
