# DEC-032: `.jcodebuddy/` in two scopes — the project's and the user home's

- Status: Accepted

## Context

DEC-026 answered what a `.jcodebuddy/` directory means **inside a project**: it is the
per-module marker "this module applies `project-automation`", it holds the tool's reports,
caches, specs and run records, and generated `.java` never goes in it. That decision is
unchanged and is not revisited here.

Two things have since pushed the name outside a module, and neither had a rule:

1. **Hosts that serve a project they do not own.** `webviewd` publishes the port it bound in
   `<project>/.jcodebuddy/webview/host.json` ([DEC-033](DEC-033.md)), and the two IDE hosts
   now do the same. Publishing is *project-scoped state written by a tool that is not the
   project's build* — a case DEC-026 did not name.
2. **Settings that belong to a person, not to a checkout.** An editor plugin, a CLI and a
   generator all want the same handful of defaults in every project on one machine: which
   port to prefer, an allow-list, a token, a formatter's idea of line width. There is
   currently no defined place for them. The two available answers were both wrong: putting
   them in each project's `.jcodebuddy/` means every new clone must be configured again, and
   inventing a second dot-directory (`~/.config/jcodebuddy`, `~/.jcodebuddy.d/`, …) means the
   product has two names for one concept.

The name is already decided, and it is a good name for both scopes: `.jcodebuddy/` is
"JCodeBuddy's directory". What was missing is the rule for **which** `.jcodebuddy/` a tool
may read, which one it may write, and what each may hold.

## Decision

### 1. There are exactly two scopes, and the scope is the meaning

| Scope | Path | What it is |
| --- | --- | --- |
| **project** | `<project>/.jcodebuddy/` (a module per DEC-026; the project root for a host that serves one) | the project's own JCodeBuddy output, state and specs |
| **user** | `~/.jcodebuddy/` (`user.home` on the JDK; `%USERPROFILE%` on Windows) | the user's own **global defaults and configuration** — settings that are not about a project at all, and **never a port** (§ 2) |

The user-home directory **MUST NOT** be read as a project marker, and a project directory
**MUST NOT** be read as a source of the user's defaults. A tool that needs both reads both and
applies § 3's precedence.

### 2. What each scope may hold

**The project's `.jcodebuddy/`** keeps DEC-026's layout and its track policy (as amended:
`conf/` is the reserved, tracked subtree; everything else is derived and ignored by default) and
gains the one subtree the hosts made necessary:

    .jcodebuddy/conf/        TRACKED   configuration this project wants committed and shared
    .jcodebuddy/webview/     ignored   local HOST STATE: host.json, token, checkpoints

A worked example of the first, because the two are easy to confuse: the port a project **defaults** to is
configuration and lives in `conf/webview.json` (`{ "port": 18882 }` — optional, read by every host, and there
so a fresh clone asks for something sensible, DEC-033 § 6), while the port a **checkout is currently on** is
local state and lives in `webview/host.json` — together with the `sticky` flag that pins it **for this
checkout only** (DEC-033 § 5). The current port outranks the default, so a checkout that had to take the next
free port keeps it; a committed pin would pin every worktree of the project at once, which is precisely the
collision the pin exists to avoid.

`webview/` is **local state**: it records which port this checkout is on, the token a caller must present, the
pin if the user set one, and a page's undo journal. It is machine-written, ignored by git, and it **outlives
the host that wrote it** — the record is the project's port, not the process's, and deleting it on shutdown
would change an ephemeral port on every restart and throw the pin away (DEC-033 § 1). It is per **project**
rather than per module, because a port serves the directory a host was pointed at; in this repository, the
project root.

**Configuration and host state are different things, and they live in different places.** This is
the distinction that decides where a port goes:

| | configuration | host state |
| --- | --- | --- |
| what it is | a *choice* a person or a project makes, meaning the same thing to everyone: "these origins may call me", "a fresh checkout asks for 18882" | a *fact about one checkout on one machine*: "this directory is served on 18882 right now (pid 4312, since 09:12)" |
| where it goes | `<project>/.jcodebuddy/conf/` (tracked) — and, for settings that are not about a project at all, `~/.jcodebuddy/config.json` | `<project>/.jcodebuddy/webview/host.json` (ignored, and it outlives the host) |
| who may read it | anyone who reads the repository | any reader may *use* it, and nothing may *trust* it: liveness is asked of the port, never of the file |

So a **let-later-readers-find-the-port record is host state, not configuration**, and it **MUST NOT** be
written into `conf/` or into any `config` file, in either scope. It is local to one served directory on one
machine — two checkouts of one project are on different ports — and it is meaningless in a clone.

**A port *preference* is configurable, but only per project — never in the user home.** A port
names a socket on one machine for one served directory, so it is a property of the **project** (and,
for a pin, of one checkout of it); the fact that a *person* is running the host changes nothing
about which port is free or which page expects which URL. A machine-wide port default would apply to
every project on the machine at once — two projects both asking for 18882 by default — which is a
collision the user home can neither express nor resolve. The user-home scope therefore **MUST NOT
carry any port setting**: not a reservation, not a preference, not a "usual port". The only
project-independent thing about a port is the host's own built-in default, and that is code.

**The user's `~/.jcodebuddy/`** holds configuration only — defaults that genuinely do not belong to
any one project:

    ~/.jcodebuddy/
    ├── README.md      what this directory is, and what may not go in it
    └── config.json    the user's global defaults (one file, or one per tool)

Four prohibitions are the substance of this section:

- **No project output.** No reports, no caches, no indexes, no run records. Two projects'
  reports in one directory is how a report gets attributed to the wrong project.
- **No host state, and no current port of any kind.** No port record, no pid, no token, no checkpoint
  journal — that is `.jcodebuddy/webview/` in the project it belongs to — and no preferred or usual port
  either: a port *default* is configuration but belongs to the project's `conf/` (above), because it means
  the same thing to everyone who clones that project, and a machine-wide one would have every project on the
  machine ask for the same port at once. A port only means something to the directory being served.
- **No generated or committed artifacts of any kind.** Generated `.java` is `src/main/java`
  (DEC-019); everything a repository tracks lives in a repository. `~/.jcodebuddy/` is never
  in git, so an artifact that lands there is invisible to every reviewer.
- **No secrets that belong to a project.** A project's token stays in that project's
  `.jcodebuddy/webview/token`, where it is scoped to what it grants. A *user-level*
  credential, if one is ever needed, is a `config.json` value with a stated scope — not a
  copy of a project's token.

### 3. Precedence, and who may create it

A setting is resolved in this order, first match wins:

1. an explicit command-line argument or IDE setting for this run;
2. the **project's** `.jcodebuddy/` (per DEC-026's marker resolution: nearest marker, never a
   nearer `pom.xml`);
3. `~/.jcodebuddy/config.json` — **never consulted for a port**, which has no project-independent
   meaning (§ 2), so a port's resolution ends at step 2 and falls through to the built-in default;
4. the built-in default.

The project wins over the user home **on purpose**: a project file is reviewed by the team
and travels with the checkout, while the user's file is that person's convenience. Where they
genuinely disagree, the shared artifact is the one that must be explainable.

Two creation rules follow:

- A **build MUST NOT** read `~/.jcodebuddy/`. A Maven or Gradle build that produced different
  output for two people on one commit is not a build, it is an environment; a build may read
  the project's own `.jcodebuddy/` (its generators already do).
- A build MUST NOT create `~/.jcodebuddy/` either. Only a user-facing tool — an editor
  plugin, a CLI run by the user, `--write-user-config`-style commands — may create it, and
  only to write something the user asked for. **A missing `~/.jcodebuddy/` is the normal
  state**, and every consumer MUST work without it.

### 4. The project scope is unchanged, and the user scope adds no layout

DEC-026 § 1 (per module, never a repository-wide default), § 2 (marker before `pom.xml`, as refined
by that decision's final amendment: a directory holding only tool state is not a marker), § 4 (the
tracked/ignored split, whose default is `conf/` tracked and everything else ignored), § 5 (no
generated `.java`) and § 6 (every scanner excludes `.jcodebuddy/**`) apply verbatim to the project
scope and are not amended here. The user-home scope has no subfolder taxonomy of its own: it is a
configuration file and a `README.md`, and inventing `~/.jcodebuddy/metadata/` is exactly what § 2
forbids.

## Alternatives considered

- **One repository-wide or machine-wide `.jcodebuddy/` for everything.** Rejected. It is the
  alternative DEC-026 already rejected for the project scope, and it is worse for the user
  scope: a report in a shared directory cannot say which project it came from.
- **A second directory name for the user scope** (`~/.config/jcodebuddy`, `~/.jcodebuddy.d`,
  `~/.jcb/`). Rejected. The product would then have two names for one concept, and every
  document would have to say which one it means. The scope in the path already says it.
- **Put the user's defaults in each project's `.jcodebuddy/` and commit them.** Rejected. It
  makes one person's preference the team's policy, and a fresh clone has no defaults at all.
- **Read the user's `.jcodebuddy/` from the build.** Rejected: it makes a build's output
  depend on whose machine ran it (§ 3).
- **Let the user-home directory hold caches, for speed.** Rejected. A cross-project cache
  needs a key that identifies the project anyway, and the honest place for a project's derived
  data is that project's own ignored subtree, where `mvn clean`-style disposal and review both
  already work.
- **Put a port preference in the user home**, so a person configures 18882 once and every project
  uses it. Rejected, and worth stating as its own alternative because it looks convenient: a port
  belongs to one served directory, so a machine-wide port default would have every project on the
  machine ask for the same port by default — a collision the user home cannot resolve — and the
  committed per-project preference (DEC-033 § 6) already gives a fresh clone a sensible start. The
  user-home scope therefore carries no port setting at all.
- **Do nothing and let each tool decide.** Rejected. Two tools disagreeing about where a project's
  port preference or reservation lives is the failure this decision exists to prevent, and it is
  exactly the drift DEC-033 had to fix for `/health`.

## Consequences

- A tool that needs a per-project port, token or report has one defined place to look, and a
  human reading a checkout sees the state that belongs to it (DEC-033).
- A user's defaults are stated once per machine, in a file that is plainly not part of any
  project — and a project can still override them, because the project wins. A **port** is the one
  thing that cannot be a user default, because it is not a personal preference: it names a socket
  for the directory being served, so it is stated per project (and, when pinned, per checkout).
- Configuration and host state cannot be confused, because they differ in all three of the ways
  that matter: who writes them, whether they survive a commit, and whether they mean anything in
  another checkout. A port reservation in `conf/` would be a committed lie the moment the process
  exits.
- `.jcodebuddy/` in a project remains a *marker*, and its palette is open: a tool adds a subfolder
  without amending a decision, because the default is closed and only `conf/` is reserved.
- **Negative:** the same directory name now means two things, and the difference is the
  **scope** — a tool that resolves "the nearest `.jcodebuddy/`" for a *user* setting would
  silently read a project's. The rule that keeps this safe is that a user-scope read is always
  `user.home`-anchored and never a directory walk; § 3 states it, and the tests for a consumer
  of it must include "no project above this one has a `.jcodebuddy/`".
- **Negative:** `~/.jcodebuddy/` is invisible to code review. That is why § 2 forbids anything
  a repository should track from living there.
- **Follow-up:** the hosts and tools that read user defaults must be given the resolved
  precedence in one place per language rather than each re-implementing it; the first such
  reader is the port preference of the webview hosts, which currently reads only the project
  setting.

## Out of scope

- **DEC-026's layout, ignore policy and marker semantics inside a project.** Unchanged there; this
  decision only states that host state lives inside that scope, in an ignored subtree.
- **Where repository-level documents live** (`plans/`, `docs/`, `doc_knowledge/`,
  `doc_research/`). DEC-026 already left them out, and this decision does not move them.
- **Secrets management in general.** § 2 states the scope rule for a token; a credential store
  is a separate problem this decision does not solve.
- **A concrete `config.json` schema.** Each tool owns its own keys; this decision fixes the
  file's location, its scope and its precedence, not its contents.

## Acceptance criteria

1. Every project-scoped JCodeBuddy output resolves to a path under **that project's**
   `.jcodebuddy/`, and the resolution never walks to another `.jcodebuddy/` above it for a
   user-scope setting — a test that runs with a `.jcodebuddy/` in an ancestor directory
   asserts the user-scope answer is unchanged.
2. No build step reads or creates `~/.jcodebuddy/`; a test or a documented manual check shows
   a build succeeding with the variable that points at it set to a non-existent path.
3. The published host state is `<project>/.jcodebuddy/webview/host.json`, carries no secret, is
   ignored by the project's `.jcodebuddy/.gitignore`, and **no host state is written into
   `conf/` or into any `config` file** — a repository-wide search finds no writer of a port, a
   pid, a token or a checkpoint journal under a `conf/`-like path, in either scope. A fresh start
   and a killed process both leave the next start possible (DEC-033's acceptance criteria carry
   the behavioural half).
4. `git status` in any project a host serves lists no file from `webview/`: the state directory
   carries its own `.gitignore` (`*`), so this holds for a project that has no JCodeBuddy ignore
   policy of its own, not only for a converted module.
5. Every other `.jcodebuddy/` subfolder is ignored by default, and only `conf/` (plus the
   top-level `README.md` and `.gitignore`) is tracked — `git check-ignore` on a file placed in
   `conf/` and on one placed in `cache/` gives the two different answers this decision states.
6. A repository-wide search finds no code that writes generated `.java`, a report or a cache
   into a `~/.jcodebuddy/` path.
7. **No port setting is read from, or written to, a user-home path.** A repository-wide search
   finds no reader of a port preference anchored at `user.home`, and the webview hosts' resolution
   is: explicit flag/IDE setting → the project's `.jcodebuddy/conf/webview.json` → the built-in
   default, with the user-home scope absent from the list (DEC-033 § 6). The hosts' own tests run
   with no `~/.jcodebuddy/` at all and do not change their answer.
