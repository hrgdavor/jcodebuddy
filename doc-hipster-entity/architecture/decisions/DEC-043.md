## Context

The maintainer's direction, kept as given:

> plugin must allow opening .md files on right click and in addressbar but render clickable html, is sohuld not
> require manual rendering, also it must resfresh wehn markdown is saved in editor. Also must use
> https://tanstack.com/highlight/latest and vanillajs for the markdown render ad make it singlepage

Then, on being asked to look before building:

> stop, and look if we have already html render for markdown somewhere in jcodebuddy

The answer was that the repository already has both halves, and had for longer than this task:

1. **A Markdown renderer**: `scripts/markdown-view/render.js`, `renderMarkdown(markdown, context)`, vanilla,
   tested, and already emitting the `data-open` location links of plan 9.7. No third-party Markdown renderer
   exists anywhere in the tree (`marked`, `markdown-it`, `flexmark`, `commonmark`: zero matches), and no Java
   one does either.
2. **A highlighter**: `webview/kit/examples/with-assets/assets/microlighter.js`, microlighter 2.2.0 (MIT),
   vendored verbatim with its provenance, asset form — a plain `<script>` exposing `window.microlighter`, no
   module loader, no bundler — with seven grammars inlined: **javascript, json, java, html, markdown, css,
   yaml**. It is what the kit's own self-contained example highlights with.

DEC-042 was written before that search, and it decided on `@tanstack/highlight` — correctly observing that
TanStack ships **no Java grammar**, and resolving that with a `cpp` approximation. The search showed the
premise was incomplete: the repository already ships a Java-capable highlighter, in the exact shape DEC-027
asks for, so the approximation was never necessary.

The maintainer's decisions, both taken on 2026-10-04 in answer to that finding:

> A. Reuse microlighter — already in the repo, Java included
>
> reuse the renderer but make is a separate package in jcodebuddy to formalize it. So we have a readymade
> renderer that can produce markdown views via single page inlined and via relative path assets

## Decision

1. **microlighter is the highlighter.** It is already in this tree, MIT, reviewed, and it covers Java — the
   language this repository is mostly made of. Nothing new is adopted, so DEC-027's clause about a library
   for a specific output is not needed at all: the page stays a plain vanilla page with no dependency to
   justify.
2. **`@tanstack/highlight` is not adopted**, and the dependency declared in the root manifest on
   2026-10-04 is removed with this decision. A build step to bundle and inline a second highlighter is
   machinery for a problem the tree does not have.
3. **The Markdown view becomes a package**, not a folder of scripts: `scripts/markdown-view/` gets its own
   `package.json` with explicit entry points, so that consuming it is a decision about an API rather than
   about a file path. It declares **no dependencies** and has no `node_modules`, because DEC-027's vanilla
   rule applies to it (a vanilla renderer lives under `scripts/`, which stays dependency-free).
4. **The package produces a Markdown view two ways, from the same renderer**, because a page's situation
   differs and the caller should choose:
   - **inlined**: one self-contained file — renderer, highlighter, theme and client inlined, nothing fetched,
     openable from a file manager and shippable by a host that cannot serve assets (this is the mode the
     JetBrains plugin uses, where a page is loaded from memory by the IDE);
   - **assets by relative path**: a small page that references the package's own files next to it
     (`<script src="…/render.js">`), for a page that will be served, or written next to the assets — one
     copy of the renderer on disk instead of one copy per page.
   Both modes are the same code path; only the assembly differs. That is the reason to formalize the
   package at all: one renderer, two assemblies, no second implementation to keep in step.
5. **microlighter's grammar gap is stated rather than hidden**: it ships no **Kotlin** grammar, so a Kotlin
   fence falls back to escaped plaintext, exactly as TanStack would have. Java is covered in both.
6. **The vendored copy is checked, not trusted.** The package carries its own copy of microlighter (a package
   cannot reach into `webview/kit/examples/`), and a test asserts that copy is byte-identical to the kit's, so
   the two cannot drift apart in silence.

## Consequences

- **No build step for the plugin's page**, so no Bun prerequisite for the Gradle build and nothing to
  install: the plugin assembles the page from resources it already ships, and the page is inlined.
- **One renderer for both worlds**: the generated per-module pages and the plugin's page use the same
  module, so a link behaves identically in both, and plan 9.7's navigation cannot be fixed in one and
  broken in the other.
- **The page's colours depend on the CSS Custom Highlight API** (microlighter registers ranges on
  `CSS.highlights` and colours them with `::highlight()` rules, never wrapping tokens in `<span>`s). It
  guards for a missing API, so an engine without it loses colour and keeps working — the failure mode is
  cosmetic, which is the right one for a documentation page. Whether the IDE's JCEF is new enough is
  measured in the plugin when the wiring lands, not assumed.
- **A package under `scripts/` is a new shape here**: `scripts/` has held single-purpose scripts. The rule
  it must keep is DEC-027's — no dependencies, no `node_modules` — and its README states the two modes so a
  reader does not have to infer them from the code.

## Alternatives, and why not

| Alternative                                                     | Why not |
| --------------------------------------------------------------- | ------- |
| TanStack Highlight, as first decided in DEC-042                 | It would have been a second highlighter in a tree that has one, for the price of a build step and a library decision — and its Java coverage is exactly what the existing one already provides |
| Keep both: microlighter for Java, TanStack for the rest         | Two highlighters, two theme systems and two markup shapes in one page. The colour is not worth the machinery |
| Leave the renderer as loose scripts and copy it into the plugin | Two copies of the renderer, which is how the plugin's Markdown links and the generated pages' links drift apart. The package exists to prevent that |
| Only the inlined mode                                           | Simpler for us, worse for a served page: every page would carry its own copy of the renderer, and a bug fix would mean regenerating every page |
