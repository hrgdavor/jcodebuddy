# DEC-023: R1 — Field enums are append-only ordinal ledgers

## Context

Every entity view has a generated **field enum**: one constant per
view field, whose name is the field's accessor name. That enum is not
only a metadata lookup table. Its **ordinal is the positional index**
into the backing array that the whole runtime is built on:

- `EntityReadArray`, `EntityUpdateArray` and
  `EntityUpdateTrackingArray` hold field values in `Object[]`, where
  `values[field.ordinal()]` is that field;
- the change-tracking bitset is indexed by the same ordinal;
- `ViewMeta.create(Object[])` maps the array positionally onto the
  generated record's components;
- any writer that emits `INSERT`/`UPDATE` fragments in that order — the
  draft SQL generator (`--adapters`, opt-in and not a supported generator;
  see `plan.dsflash.notes.md` D-17) or your own code.

Because arrays, patches and snapshots built on those ordinals are
**persisted** — written to a database, queued on a message bus, stored
in a cache — the ordinal layout is a data format. Reordering the enum
constants silently reinterprets every stored array: what used to be
`firstName` is now read as `lastName`, with no error and no migration.

The natural failure mode is a **generator**, not a human. A code
generator that regenerates a field list "canonically" — for example
from a re-sorted view, from a merged addon interface, or from any
generic "sort the fields for readability" step — will happily insert a
new constant in the middle or move an existing one. Human renames are
another vector: renaming an accessor so its constant sorts differently
is enough to shuffle the ledger.

`@FieldSource` and `FieldKind` do not help here. They classify a field's
*origin* (`COLUMN` / `DERIVED` / `JOINED`), not its position. Nothing in
the type system prevents a reorder; the only defence is a rule plus a
checker that can read two revisions and refuse the change.

## Decision

### 1. The rule

> Once an entity's field enum has been generated, every subsequent
> generation step that finds new fields must **respect the order of the
> existing constants and append the new ones after them**. Existing
> constants are never reordered, never moved, and never inserted
> between.

**The constant order of a generated field enum IS a persisted ordinal
layout.** It is a data format, not a presentation choice. In
particular, a new constant is **never re-inserted into a "canonical"
position** — not even when that position is what the generator's own
field-sorting logic would have produced from scratch. A fresh
generation of a brand-new view is free to choose any order (there is no
persisted data yet); the rule binds from the second pass onwards.

The rule is deliberately **not** a policy that "should" be followed and
can be waived by a migration: there is no in-place migration story.
An ordinal, once assigned, is permanent.

### 2. The marker: `entityFieldEnum:true`

The rule must apply to *generated field enums* and to nothing else. A
repository contains many enums — hand-written ones, third-party ones,
and the tooling's own internal property enums. A checker cannot decide
from the name alone whether `Person_` is a persisted ledger or an
ordinary enum that merely happens to be named `X_`.

The marker therefore **rides the class-file header mechanism of
[DEC-021](DEC-021.md)** — a second key in the same single-line JSON5
config blob, with no new comment syntax:

```java
// {@link hr.hrg.hipster.entityexample.person.entity.PersonSummary} Field metadata for the PersonSummary view.
// {enabled:true, entityFieldEnum:true, blockMarker: "implicit"}
public enum PersonSummary_ implements FieldDef {
```

- `entityFieldEnum: true` is emitted by the generator on **every** field
  enum it produces.
- **Opt-in is by absence:** an enum without the marker is ignored by the
  checker entirely. That covers hand-written enums, third-party enums,
  and the tooling's own internal property enums — the checker must not
  flag any of them.
- The marker must be read by **parsing the comment**, not by
  string-matching the file: parse the `CompilationUnit`, locate the
  header comment above the `package` declaration, and decode the pinned
  JSON5 subset of DEC-021 § 4. A malformed marker is a **diagnostic**,
  not a silent skip — and the safe failure mode is "treat as marked"
  (refuse to drop constants), never "treat as unmarked" (delete a live
  ordinal). Silently skipping would defeat the rule.
- The same marker scopes the **generator's** preservation behaviour: an
  enum that already carries it is preserved and tombstoned; an existing
  enum that does not is bootstrapped as a fresh ledger (§ 5 below).
  "Once an entity's field enum has been generated" therefore means
  *once the generator's own output carries the marker* — not "once a
  file with that name exists".

The marker is a **refactor-insensitive explicit label**: the IDE rename
refactor must not touch it, exactly as
[DEC-022](DEC-022.md) requires of explicit API labels.

### 3. Why the constant list is treated differently from every other generated block

[DEC-020](DEC-020.md) is the cooperative-codegen rule: the generator
recognises its own previous output **by structural shape** and preserves
it verbatim (including user edits), so a user opts back into regeneration
by deleting the block. That works because the blocks it recognises — a
`case "…":` arm, a `withXxx(...)` builder method, a `@CoreChangeOnChange`
scaffold method, a nested `record`, a nested `interface Write` — are
identified by the *shape* they have, and their **position is
irrelevant**. A `case` arm means the same thing wherever it sits in the
`switch`; a builder method means the same thing wherever it sits in the
class.

The field enum's **constant list is not such a block**. It is
semantic *and position-bearing*: two enums with the same constants in a
different order are **different data formats**, not two spellings of the
same one. "Recognise by shape, then re-emit canonically" is therefore
exactly the wrong algorithm here — canonical re-emission is what
reorders. The two rules do not conflict, because they answer different
questions:

| | DEC-020 (cooperative blocks) | R1 (this decision) |
|---|---|---|
| Scope | any recognized generated block | the field enum only |
| Guarantee | *user edits survive regeneration* | *ordinals are permanent* |
| Recovery | user deletes the block → generator re-emits it | user may not reorder; additions append |

An implementer must not let DEC-020's recognise-and-re-emit logic touch
enum constant order. The generator's own comparison of a field enum must
be **order-sensitive** even though every other block's comparison is
not.

### 4. Removed fields: tombstoning, not deletion

When a view loses an accessor, the generator **must not delete the
corresponding enum constant**. Deleting it shifts every following
ordinal — precisely the corruption R1 exists to prevent. The constant is
kept, in place, as a **tombstone**:

```java
/** @deprecated no longer an accessor on PersonSummary; retained to preserve ordinals. */
@Deprecated
middleName(String.class),
```

The tombstone's generated override of `FieldDef.retired()` returns
`true`:

```java
// hipster-entity-api, hr.hrg.hipster.entity.api.FieldDef
default boolean retired() {
    return false;
}
```

`FieldDef.retired()` has a `default` returning `false` in
`hipster-entity-api`, so every existing hand-written and generated enum
keeps compiling unchanged; only a tombstone overrides it.

**A tombstone is reserved but dead.**

- **The invariant is preserved.** `values.length ==
  fieldValues().length` still holds, and `values[f.ordinal()]` is still
  the value of `f`, for *every* `f` — including tombstones. The ordinal
  array contract's central promise is not weakened for retired fields.
- **The record keeps a component for the tombstone** (a nullable field
  of the retired field's type), and it is `null` for rows that no longer
  carry the column. Consequence, stated plainly: **a tombstoned field
  stays in the generated record forever.** That is the deliberate price
  of never renumbering; there is no automatic compaction.
- **The builder and `Write` interface do not get a setter for it.**
  Tombstoning only ever applies to a field that was writable, and per
  the S1 rule a field with no accessor is not writable.
- **Writers skip retired constants; readers stay tolerant.**
  `FieldDef.retired()` gates **writes only**. Every generated writer —
  the `Write`/builder setters, the `set(int)`/`set(String)` arms, the
  draft SQL generator's binder and `INSERT`/`UPDATE` fragments (opt-in;
  see D-17), and the mapper's
  source field list — skips a retired field. `FieldKind` alone cannot
  express this: an unannotated constant defaults to `COLUMN`, and a
  tombstone has no accessor left to carry `@FieldSource`, so without
  `retired()` the retired column would silently reappear in generated
  SQL.
- **A retired slot may be `null` or non-null.** A row that still has the
  column may still carry a value; a row written after the column was
  dropped does not. Both are legal array contents.
- **`forName("middleName")` still resolves**, so an incoming payload
  that still carries the field is accepted rather than silently dropped.
- **Real removal** requires the `allowReorder` escape hatch (§ 7) plus a
  data migration, and is out of scope. Dropping tombstones and
  renumbering — **compaction** — is a deliberate, separately invoked
  operation that may only run when no persisted array, patch or snapshot
  survives.

Tombstones are only reachable through the **enum-preserving
regeneration path**: that is the only place the generator sees an enum
constant with no matching accessor. A fresh generation of a brand-new
view never produces one, so the tombstone logic is independently
testable without touching the general emission path.

### 5. The bootstrap path: a marker-less enum is pre-R1

R1 protects a *committed ordinal contract*. An existing enum **without**
the marker has no such contract, so it is treated as **pre-R1** and
**bootstrapped as a fresh ledger**:

1. the constant list is rebuilt from the view's resolved field list, in
   ordinal order;
2. constants that no longer correspond to any accessor **are dropped**,
   not tombstoned;
3. the DEC-021 header (including `entityFieldEnum:true`) is written in
   the same pass, so the *next* generation of that file is protected by
   R1.

The drop is reported as the DEC-022 divergence
**`enum_constant_removed`** with action `bootstrap`. It is not a reorder
of a committed ledger, so it does **not** require the `allowReorder`
escape hatch — but it must be reported rather than happening silently.

This is the difference between the two removal kinds, stated so it is
not confused:

| Situation | Behaviour | Divergence |
|---|---|---|
| Marked enum loses an accessor | keep the constant, add `@Deprecated`, emit `retired()` → `true` | `ordinal_drift`/deprecation entry for the tombstone |
| Marker-less enum has a stale constant | **drop** it; the file is a fresh ledger | `enum_constant_removed`, action `bootstrap` |

**Opting a hand-written enum into R1 is manual.** A consumer that
already persists positional arrays but has not adopted R1 adds
`entityFieldEnum:true` to the header **by hand** before the first
generation pass. That puts the enum under R1 and forces tombstoning
instead of dropping. The generator never infers a ledger from a
pre-existing file.

A malformed or unparseable header is **not** "unmarked": per § 2 the
safe failure mode is to treat the file as marked and refuse to drop
constants.

### 6. The checker contract

The rule needs an enforceable gate, so that a shuffled ledger fails a
build instead of reaching a database. The checker is implemented in
`hipster-entity-tooling`, under the existing `validation` package, so it
plugs into the existing `EntityRulesValidator` rule registry rather than
becoming a parallel tool.

**`hr.hrg.hipster.entity.tooling.validation.EnumConstantOrderChecker`**
— the reusable half. It parses a Java file with JavaParser, finds the
enum that carries the `entityFieldEnum:true` marker in its DEC-021
header, and returns its constant names in declaration order. It has **no
git dependency** — it takes two parsed enums and compares them — so it
is unit-testable in isolation. It reads the header by parsing the
comment (never by string-matching the file), and it fails safe toward
"marked".

**`hr.hrg.hipster.entity.tooling.validation.EntityFieldEnumOrderRule`**
— the build-time rule. In its in-place form it verifies the
self-consistency of one revision (the marker is present, the header is
decodable, the enum is not empty, and `allowReorder` is surfaced as a
warning). **It does not check that the constants are unique** — an
earlier revision of this paragraph claimed it did; the rule's checks are
the four listed here, and a duplicate constant is a compile error in
Java long before any rule sees it. `compareRevisions(baseline,
target)` drives the cross-revision order comparison. It is registered in
`EntityRulesValidator`'s rule list, alongside `MarkerEntityRule`,
`ViewInterfaceRule`, `ViewAnnotationRule` and `AuditableRule`, and it
**skips every enum without the marker** (opt-in by absence).

**`hr.hrg.hipster.entity.tooling.validation.EnumConstantOrderCli`** —
the CLI, reachable from the tooling entry point next to
`EntityMetadataGenerator.main` as the `enum-order` subcommand:

```text
java -jar hipster-entity-tooling.jar enum-order --repo <path> (--baseline <git-ref> | --diff <file>) [--target <ref>] [--strict]
```

| Flag | Meaning |
|---|---|
| `--repo <path>` | the repository root to read (default: the working directory) |
| `--baseline <git-ref>` | the reproducible baseline: `HEAD`, a commit, or a PR base such as `origin/main`. **Required unless `--diff` is given** |
| `--target <ref>` | the revision to compare; default `WORKING_TREE` |
| `--strict` | promote warnings (an `allowReorder` escape hatch being present) to a failure |
| `--diff <file>` | a unified diff to use as the baseline instead of a git ref — what a PR check has when the branch is not fetched locally. It is reverse-applied to `--repo` through `git apply -R` on a scratch copy, and a diff that does not apply exactly is refused with exit 2 rather than approximated. **Mutually exclusive with `--baseline`** |

**Exit codes: `0` = ok, `1` = violation, `2` = usage or environment
error.** A non-zero exit on a violation is what lets the checker gate a
build and a PR check. Warnings go to stderr without failing unless
`--strict` is given.

The baseline must be reproducible from the repository — a git ref or an
explicit file. It is **never** "remember the previous run".

**The comparison is a "removal then queue-jump" rule.** A plain "is the
baseline a subsequence of the target" test does **not** catch a middle
insertion:

```text
baseline [id, firstName]   target [id, email, firstName]
```

is a valid subsequence, yet `firstName` moved from ordinal 1 to 2, which
corrupts every persisted array. The implemented rule is stronger and
still satisfies append-only intent:

1. **Removal first.** Every baseline constant must still exist in the
   target. If not, the missing constant is reported as
   `enum_constant_removed` and the comparison stops, so a delete is not
   mis-reported as a reorder of everything after it. (A delete is a hard
   error; the fix is to keep the constant and mark it `@Deprecated`, per
   § 4.)
2. **Then order.** Every constant that is still present in the target
   and stands *before* the current baseline constant must itself be an
   *earlier* baseline constant. A constant that jumps the queue — a new
   constant inserted before it, or a later baseline constant moved ahead
   — means the current constant's ordinal changed, and **the moved
   constant** is what gets reported, with its old and new index.

An addition is allowed **only at the end**. An addition in the middle is
reported as a reorder, because that is what it is from the bitmask's
point of view.

The comparison uses JavaParser on both revisions and compares the parsed
constant **names in declaration order**; it never compares raw text, so
comments and formatting cannot affect the verdict.

### 7. The escape hatch: `allowReorder`

Real reordering is occasionally legitimate — early development of an
unreleased module, or a deliberate migration with a data conversion.
`allowReorder: true` in the DEC-021 JSON5 config blob is the **explicit,
hand-set escape hatch** that permits it:

```java
// {enabled:true, entityFieldEnum:true, allowReorder: true}
```

Every pass reports it. The checker emits a **warning-level
`enum_reorder_allowed` diagnostic whenever the flag is present**, so the
escape hatch is always visible; under `--strict` that warning fails the
build. This is what makes it impossible to leave the flag in by
accident. `allowReorder` is available only while an enum has no
committed consumers, and it must be set by hand — the generator never
emits it.

### 8. The two R1 divergence kinds

The checker reports both kinds in the uniform
[DEC-022](DEC-022.md) format —
`kind, location, cause, current, canonical, action`:

| Kind | Severity | Meaning | Action |
|---|---|---|---|
| `enum_order_shuffled` | error | a constant's ordinal changed relative to the baseline (a swap, a middle insertion, or a later constant moved ahead) | restore the baseline order and append the new constant at the end; or set `allowReorder: true` plus a migration |
| `enum_constant_removed` | error | a constant present in the baseline is absent from the target | keep the constant and mark it `@Deprecated` with `retired()` → `true` (tombstone); or, on the bootstrap path, acknowledge the pre-R1 drop |

A third, warning-level kind belongs to the same family but is not a
violation: `enum_reorder_allowed`, emitted whenever
`allowReorder: true` is present (§ 7).

## Consequences

### Positive

- **The persisted layout cannot silently change.** A reorder or a
  deletion fails a build and a PR check instead of corrupting a
  database, a queue or a cache.
- **The rule is enforceable, not aspirational.** The marker scopes it to
  generated field enums, so the checker has no false positives on
  hand-written or third-party enums.
- **Removal has a safe path.** Tombstoning keeps the ordinal, keeps the
  record's positional mapping straight, and keeps `create()` a plain
  positional copy.
- **The escape hatch is visible.** `allowReorder` cannot be left in
  silently; every pass reports it.
- **The order contract is discoverable on its own.** It is recorded
  here, not as an amendment of the header mechanism, so a reader can
  find "field enums are append-only" without first reading the
  generator-header decision. It rides
  [DEC-021](DEC-021.md)'s header and reports through
  [DEC-022](DEC-022.md)'s format, so no new mechanism is introduced.
- **It composes with DEC-020 without contradiction.** Shape-recognition
  still governs every other block; R1 governs only where a new constant
  may go.

### Negative

- **A tombstoned field stays in the record forever.** Its slot cannot be
  reclaimed without a compaction migration, so `fieldCount` grows
  monotonically and the record carries a nullable dead component.
- **A generated record gets wider over time**, which costs a little
  memory per row and a nullable check per retired field in the paths
  that still read it.
- **An escaped reorder is not automatically detected across a bootstrap
  commit.** The checker skips an enum unmarked in the baseline, so the
  very commit that first adds the marker is not guarded — the *next*
  commit is. A mistake made in that one window is not caught by the
  checker.
- **The gap between the plan's plain-subsequence wording and the
  implemented queue-jump rule** is a source of confusion unless read
  together; § 6 states the implemented rule explicitly.
- **Compaction is required for real removal**, and it is a separate,
  carefully gated operation rather than a normal generation pass.

### Follow-up

- The generator's field-enum emission path must be asserted to be a
  **fixed point**: running it twice on the same tree must be
  byte-identical, and must never reorder an existing constant list.
- The tombstone path carries an end-to-end test, and the
  `retired()`-skip has coverage in the draft SQL generator's binder
  (opt-in; `--adapters`) as well as in the field enum.
- ~~Fully specify the `--diff <file>` baseline form, or remove the flag
  from the documented surface, so the usage text and the implementation
  agree.~~ **Done** — `--diff` is implemented: the unified diff is
  reverse-applied to the working tree through `git apply -R` on a scratch
  copy, and a diff that does not apply exactly is refused with exit 2
  rather than approximated. It is **mutually exclusive** with
  `--baseline`, and `--baseline` is required only when `--diff` is absent.
  The flag surface is in
  [`hipster-entity-tooling/README.md`](../../../hipster-entity-tooling/README.md).
- Wire the `enum-order` subcommand into the build and the PR check so
  the rule gates on every change, not only when run by hand.

## Out of scope

- **Automatic compaction.** Dropping tombstones and renumbering is a
  deliberate, separately invoked operation that may only run when no
  persisted array, patch or snapshot survives. It is not part of a
  normal generation pass.
- **Reverse migration of already-corrupted data.** R1 prevents
  corruption; repairing an ordinal layout that was already shuffled
  before the rule existed is a data-migration project of its own.
- **Non-generated enums.** The rule applies only to enums carrying the
  `entityFieldEnum:true` marker.
- **Enum constant *names*.** R1 governs position. Renaming a constant is
  a field rename and follows the refactor-sensitivity rules of
  [DEC-022](DEC-022.md); the field-name contract itself is published in
  [`hipster-entity-tooling/README.md`](../../../hipster-entity-tooling/README.md).

## Acceptance criteria

- A generated field enum's constant order MUST never change between two
  generation passes; a new field's constant MUST be appended at the end.
- Every generated field enum MUST carry `entityFieldEnum: true` in its
  DEC-021 header, and the checker MUST ignore every enum that does not.
- A removed field's constant MUST be retained in place, marked
  `@Deprecated`, and MUST override `FieldDef.retired()` to return
  `true`.
- `FieldDef.retired()` MUST have a `default` returning `false` in
  `hipster-entity-api`, so existing enums compile unchanged.
- Every generated writer MUST skip a retired field; readers MUST tolerate
  its slot being `null` or non-null.
- `EnumConstantOrderChecker` MUST compare parsed constant names in
  declaration order against a reproducible baseline source, MUST report
  the moved constant for a queue-jump, and MUST NOT compare raw text.
- `EntityFieldEnumOrderRule` MUST be registered in
  `EntityRulesValidator` and MUST skip unmarked enums.
- `EnumConstantOrderCli` MUST accept
  `--repo --baseline [--target] [--diff] [--strict]` and MUST exit
  `0` on success, `1` on a violation, and `2` on a usage or environment
  error.
- An `allowReorder: true` flag MUST produce a warning-level
  `enum_reorder_allowed` diagnostic on every pass.
- `enum_order_shuffled` and `enum_constant_removed` MUST be reported in
  the DEC-022 `kind, location, cause, current, canonical, action`
  format.
- A marker-less existing enum MUST be bootstrapped as a fresh ledger,
  its stale constants dropped, and the drop reported as
  `enum_constant_removed` with action `bootstrap`.
- A malformed header MUST be treated as marked, never as a bootstrap.

## Appendix note — Phase 8 of the rewrite migration (2026-09-22)

**The rule is untouched; the way the checker reads a file is not.**

§ 1 (the append-only ledger) and § 6 (the checker contract) stand exactly as written. What changed is the reader behind them: [`EnumConstantOrderChecker`](../../../../hipster-entity-tooling/src/main/java/hr/hrg/hipster/entity/tooling/validation/EnumConstantOrderChecker.java) no longer parses "a Java file with JavaParser" — it reads the unit through OpenRewrite's LST and takes positions from javac. `EntityFieldEnumOrderRule`, `EnumConstantOrderCli` and `EnumCompactionCli` sit beside it in `.../tooling/validation/` and read through the same classes.

The verdict is still the parsed constant **names in declaration order**, never raw text, so comments and formatting cannot affect it, and the header is still read by decoding the DEC-021 comment rather than by string-matching the file.

The representation decision is [DEC-030](DEC-030-openrewrite-source-representation.md) and the reader's guide is [`doc_knowledge/code.graph.md`](../../../doc_knowledge/code.graph.md).
