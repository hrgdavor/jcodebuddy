## Context

The project is exploring DTO interfaces used as read markers for SQL and NoSQL queries, including direct JSON output paths that bypass full entity materialization.

## Decision

Treat projection-based reads, streaming JSON output, and low-allocation mapping as an explicit architecture track rather than an incidental generator optimization.

## Accepted notes

The `hipster-entity-jackson` module is the realization of this decision. It provides:
- `EntityJacksonViewSerializer` / `EntityJacksonViewDeserializer` as the projection-oriented fast path
- Boilerplate and positional deserializers as the lower-level fast paths (benchmarked)
- `EntityJacksonMapper` as the ergonomic single-call API
- JMH benchmarks and file-scan benchmarks as the acceptance evidence

### The DTO marker and the generated projection writer (plan step 6.5, 2026-10-09)

The decision's "projection contracts separate from write-path assumptions" half is now a marker the
generator reads, rather than a shape a project has to remember:

- **The marker is `@View(dto = true)`.** It is an annotation attribute rather than a naming convention
  (`*Dto`, `*Projection`) so the pass decides from committed source, and so an IDE rename refactor
  cannot silently change whether a view is a projection. A view without it is unaffected by everything
  below — the marker changes what the *projection pass* does and nothing else, which is why it is a
  separate component of `ViewAttributes`/`ViewMeta` and not a value folded into `gen`.
- **The emitter is `ViewJsonGenerator`, and it is opt-in.** It runs only when a pass carries
  `--dto-projections` **and** the view carries the marker; either half alone emits nothing. It writes
  `<View>Json` into the view's own package, carrying DEC-035's `@generated file` header and the
  whole-file freeze check (DEC-018/DEC-021 § 6), exactly like the other whole-file emitters.
- **The shape is a direct call per field**, on the view's own accessor:
  `gen.writeNumberProperty("id", source.id())`. There is no reflection, no `Map<String, Method>`, and
  no positional array. That last part is the decision's own point: the ordinal serializers walk
  `ViewReader.get(ordinal)`, so a source that is not a `ViewReader` (a SQL row, a Mongo document) has
  to be materialized into one first — the materialization a projection exists to avoid.
- **Field order is the ledger order**, emitted as a `FIELDS` literal, so the JSON keys and the field
  enum's ordinals cannot drift apart; the test derives its expected document from the enum rather than
  from a golden string, because a golden string would keep passing if they did drift.
- **A composite field goes to the caller's codec** (`writePOJOProperty`). The JSON shape of a
  collection is a decision the caller's `ObjectMapper` owns; a generator that guessed one would be
  wrong the first time a caller configured a different one, and wrong silently.
- **Where the pattern is demonstrated:** `hipster-entity-example`'s `PersonDto` carries the marker and
  the committed `PersonDtoJson` is its generated writer. The test is
  `ViewJsonGeneratorTest` (6 tests: the marker, the flag, the emitted shape, compilation, the document
  compared against the field enum, and the composite case).

What this does **not** do, stated rather than implied: it does not generate SQL, a query, or a result-set
mapper — the adapter pair under `--adapters` is a separate, still-draft exploration (see the
`ViewAdapterGenerator` notes). The projection writer emits the JSON half only, and the caller supplies
the values.

## Consequences

- Encourages design work around performance, memory usage, and GC pressure early.
- Keeps developer ergonomics in scope instead of optimizing only for throughput.
- Needs follow-up design on adapter APIs, driver integration points, and benchmark criteria before acceptance.
  **Status 2026-10-09:** the adapter API half is closed by the DTO marker and the generated projection
  writer above (plan step 6.5); the benchmark criteria and the driver integration points were already
  answered by this record's Accepted notes and remain as they stand.

## Out of scope

- Write-path behavior — this decision covers read paths only; write semantics are covered by DEC-005.
- Specific driver integration (JDBC, R2DBC, MongoDB) — integration points are follow-up design work, not resolved here.
- Caching or result memoization — projection responsibility ends at mapping; retention strategy is separate.
- Benchmark tooling infrastructure — benchmarks are a prerequisite for acceptance but are not defined within this decision.

## Acceptance criteria

- Read-path design MUST explicitly define projection contracts separate from write-path assumptions.
- The chosen approach SHOULD support SQL and NoSQL read use cases.
- Adapter API and benchmark criteria MUST be documented before acceptance.
