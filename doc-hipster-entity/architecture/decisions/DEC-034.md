# DEC-034: Entity relations are key references, never object references

## Context

`hipster-entity` models an entity as an **array-backed view**: a field is a slot, read through a generated
`ViewMeta` and a `FieldNameMapper`, and the read path never touches a graph. The materialization levels are
an ordinal array, a proxy over it, or a generated record — none of which is a bean.

Nothing so far has said what a relation between two entities looks like. That silence has a cost, because
the industry default is the opposite of what this model wants: JPA and most ORMs let an entity hold a
**direct reference** to another entity (`Order.getCustomer()` returning a `Customer`), and a developer who
arrives expecting that will reach for it here. On this model that choice is not merely unfashionable, it is
structurally wrong:

- A direct reference makes the **read set unbounded**. Reading `Order.customer()` becomes a second read
  with its own query, its own cache, and its own failure mode. The projection contract — "a view is an
  ordinal array of columns this query selected" — can no longer be honoured, because one slot's cost
  depends on data the query did not choose.
- A direct reference makes the **view type recursive**, so the metadata, the field enum, the JSON, and the
  change-tracking path all have to describe a graph. `hipster-entity`'s metadata describes a flat field
  list with a `javaType`, and DEC-024's deep change tracking already walks nested tracked views by hand; a
  general graph would push that into everything.
- A direct reference **breaks the array contract**. `EntityReadArray` holds `Object[]`; a nested entity in a
  slot means a nested array, and `ViewMeta.create(Object[])` would need a recursive materialization step
  that the whole design exists to avoid.
- A direct reference makes **write-back ambiguous**. If `Order.customer` is a `Customer` object, then
  loading and storing an order implies cascading into the customer — the "cascade" behaviour every ORM has
  and every reviewer has learned to fear.

`@FieldSource(kind = JOINED, relation = "department.name")` exists today (DEC-005) and is the right
instinct, but it is **not a specification of a relation**. It names a path in the shape `<table>.<column>`
and leaves the rest to inference: which entity is being joined to, which column is the primary key, which
local column is the foreign key, what cardinality the relation has, and what happens when the relation
crosses a join table. The generator's own documentation admits this — the brainstorm's SQL sketch annotates
its join clause as *"inferred from relation path"* — and a key that is inferred from a string is a key that
a rename silently breaks.

### The Hibernate motivation: object references are where visibility goes to die

A large part of why this decision exists is the accumulated experience of what entity relations do in
Hibernate and JPA, and the honest summary is that **the feature's main effect is to make more things
hidden**. It is worth naming the mechanisms rather than gesturing at "ORM problems", because each one is a
thing this project refuses on purpose:

- **`@ManyToOne` / `@OneToMany` getters that issue SQL.** `order.getCustomer()` looks like a field read and
  is a query. Nothing at the call site says a database round trip is about to happen, so a method that was
  pure becomes I/O, and a loop over orders becomes N+1 queries — the single most common production
  performance defect in JPA codebases, discovered by a profiler rather than by reading the code.
- **`FetchType.LAZY` / `EAGER` is a hidden routing decision.** Whether a read costs one query or two is
  decided in an annotation on a field, far from the code that pays for it, and it can be overridden at query
  time by an entity graph or a fetch join. The read set of a method is therefore not deducible from the
  method.
- **`LazyInitializationException` is the failure mode of that hiddenness.** A read that used to work throws
  depending on whether a transaction happened to be open — a bug whose location and whose cause are in
  different files, and the reason "open session in view" exists as an anti-pattern.
- **Cascade policies hide writes.** `CascadeType.ALL` and `orphanRemoval` mean that persisting one object
  writes others. A reviewer reading `repository.save(order)` cannot see how many rows that statement will
  touch, or which, and a missing cascade silently loses data.
- **Dirty checking hides the write entirely.** There is no `update` call to find: mutating a managed object
  and committing flushes an `UPDATE` nobody wrote. The code that changes state and the code that persists it
  are not the same code, and neither one points at the other.
- **Proxies make the object lie about its own type.** `order.getCustomer()` may return a subclass with
  nothing in it, so `instanceof` and `equals` behave in ways the source does not show — a substitution the
  compiler cannot warn about because it is a runtime-generated subclass.
- **The session and the identity map are a hidden lifetime.** Whether two reads give the same instance,
  whether a change is visible to a later read, and when an object detaches are all properties of a scope
  that appears in no signature.

Every one of those is the same defect stated differently: **the code does not say what it does.** That is
precisely what this project's source-visibility rule exists to prevent — DEC-019 requires that a developer
with the committed sources and a stock IDE can follow the program flow from entry point to leaf without
running the application, and a relation that turns a getter into a query is a step of that flow which is
*nowhere in the source*. A JPA-style relation is therefore not merely a different design; it is
**antithetical to the project's stated goal**, and no amount of convenience makes hidden I/O acceptable in a
library whose central claim is that the wiring is visible.

The position this decision takes is a consequence, not a preference: **if the read is not in the source,
the read must not happen.** A caller who needs the customer writes the read, and the read is a line of code
a reviewer can see.

The cost of that position is real and should be stated plainly: callers do more work, and some of the
convenience that makes JPA pleasant to write is gone. What is bought is that a method's cost, its queries
and its writes are all deducible from its body — which is the property the rest of this architecture is
built to preserve, and which a relation introduced for convenience would quietly destroy.

This decision fixes the direction and the shape. It is `Proposed` rather than `Accepted` for one honest
reason: the **key markers do not exist yet** (§ Decision 2). The prohibition in § Decision 1 is what the
current model already implies and can be enforced; the metadata in § Decision 2 is the design that needs
building before this can be called accepted.

## Decision

**An entity never references another entity. A relation is data — a key that identifies the other row — and
the marking of which key is the primary key and which is the foreign key.**

### 1. Direct entity references are prohibited

Let an entity view be any interface reaching `EntityBase<ID>` (DEC-001), and let an *entity type* be a view
that is a root entity (it extends `Identifiable<ID>`, DEC-017). Then:

1. A field on an entity view **MUST NOT** have an entity type — no `Customer customer()`, no
   `List<OrderLine> lines()`, no `Optional<Customer>`, however convenient each looks.
2. A field **MUST** be a flat value: a scalar, a value object with no identity of its own, an array or
   `List` of such, or another entity's **key** (`Long customerId`).
3. A view **MUST NOT** declare a method whose return type is a type parameter bound to a view, and the
   generator **MUST** report one that does.
4. **Flat, identity-free value objects remain allowed and are not relations.** An embedded address, a money
   amount, a `List<String>` — a type that is not a view and has no `Identifiable` contract is a *value*, not
   a related entity. This is the boundary the rule turns on, and it is DEC-017's `EntityBase<Void>` case
   arriving from the other direction: what makes something an entity is that it has an identity to point at,
   so a type with no identity is data.
5. The prohibition is a **generator-level diagnostic**, not a compile-time one. A view interface *can*
   declare `Customer customer()` and javac will accept it; nothing in the type system can forbid it without
   a marker that says "this type is an entity" — which does not exist and is not what `EntityBase` is for
   (DEC-017 deliberately keeps it minimal). So a violation is reported by the generator with the diagnostic
   vocabulary DEC-022 already defines, and it is a violation rather than a warning.

### 2. Keys carry the relation, and both ends are marked

Relation metadata is attached to the **key fields**, which is the change that makes a relation checkable:

1. **The primary key is marked on the entity, not by name.** A root entity view declares which of its fields
   is the primary key. The generated `ViewMeta` exposes it (a `primaryKey()` accessor, or an equivalent on
   the field enum — the concrete API is open, § Open questions). Relying on a field that happens to be
   called `id` is not marking: DEC-017's `Identifiable<ID>` already establishes that identity is a
   *contract*, and this decision makes the key's location part of the metadata rather than a convention.
2. **A foreign key is marked on the referencing view**, and it names the relation it participates in.
3. **The relation names both ends.** A relation is declared once, with two ends: the foreign key's view and
   field on one side, the referenced entity and its primary key on the other. The relation is a
   **first-class metadata record**, not a string path embedded in one field's annotation:

   ```java
   public interface OrderLine extends EntityBase<Long>, Identifiable<Long> {
       @PrimaryKey                     // this view's identity is this field
       Long id();

       @ForeignKey(entity = Order.class, referencedBy = "id")   // <- shape, not final spelling
       Long orderId();

       String sku();
       int quantity();
   }
   ```

   The **spelling** above is illustrative and open. What is decided here is that the *relationship* is
   declared by naming the entity and the key it points at, so a generator can emit the join clause without
   inferring anything, and so an IDE rename refactor moves the entity reference with the code.
4. **`relation = "department.name"` is not deleted, it is demoted.** It remains a useful human-facing label
   for a join whose target is outside the entity set (a table that has no view here), and DEC-005's
   `JOINED` classification keeps its meaning. What it may no longer be is the *only* description of a
   relation between two entities this project generates — a path string cannot be verified, renamed or
   type-checked.

### 3. Cardinality is declared, not inferred

A relation **MUST** state whether it is to-one or to-many, because the two produce different read shapes and
different change-tracking paths (DEC-024), and inferring cardinality from the field's Java type
(`Long` versus `List<Long>`) conflates "a list of keys" with "a relation to many rows". Cardinality is a
property of the relation, so it is declared with it.

### 4. Serialization writes keys, and never nests

The same rule applies to every codec (DEC-027's JSON, `hipster-entity-jackson`, JDBC row adapters):
an entity serializes as its own fields, and a related entity appears as its **key value**, or as an extra
column projected by an explicit join. It is never nested as an object, and never loaded implicitly. A
consumer that needs the related row issues its own read or declares its own projection — which is the whole
point: **the read set is what the query selected, not what the object graph implies.**

### 5. Composition stays legal, and is a different thing

An entity may be composed of value objects, and a view may nest views that are **not** entities in the sense
of § 1.4 — DEC-017's embedded sub-document case. A nested view is a *part of* its parent, not a *pointer to*
another row: it has no identity, it is materialized with the parent, and it lives and dies with it. That is
composition, and nothing here forbids it. The test is whether the type has an identity of its own: if it
does, the parent holds its key; if it does not, the parent may hold it.

### 6. Diagnostics

| Kind | Meaning | Severity |
| ---- | ------- | -------- |
| `entity_reference_field` | a view field whose type is an entity view (§ 1.1) | violation |
| `primary_key_missing` | a root entity declares no primary key (§ 2.1) | violation |
| `foreign_key_target_unknown` | a marked foreign key names an entity or key this module cannot resolve (§ 2.3) | violation |
| `relation_path_only` | a relation between two generated entities is described only by a `relation` path (§ 2.4) | warning, until § 2 lands |
| `joined_field_without_relation` | already defined by `field-type-divergence.md` V-6 | warning |

Diagnostics use DEC-022's format (`kind`, `location`, `cause`, `current`, `canonical`, `action`) and are
reported by the entity pass and by `validate`.

## Alternatives considered

- **Direct references, JPA-style** (`Customer customer()`). The industry default, the most ergonomic to
  write, and the reason this decision is needed at all. Rejected: it makes the read set unbounded, forces a
  graph into a flat metadata model, breaks the array contract, and makes write-back cascade implicitly. The
  cost is real and honest — a caller who wants the customer **must now issue a second read**, and there is
  no lazy-loading magic to hide it. That cost is the feature: an unbounded read is what makes a service slow
  in a way nobody can find.
- **Lazy references (a proxy that loads on access).** Preserves the ergonomics and hides the read. Rejected,
  and this is the clearest case in the list: a lazy reference is a getter that performs I/O, which is
  `order.getCustomer()` issuing SQL in every JPA codebase — an N+1 query born in the one place a reviewer
  looks for a field access. It is also a runtime-generated subclass, so the object lies about its own type
  in a way the compiler cannot report. JCodeBuddy rejects invisible wiring by rule (DEC-019); a lazy
  relation is that rule's exact antithesis, and the project's visibility goal is the reason, not a
  preference for simplicity.
- **Keep `relation = "path.to.column"` as the whole answer.** Rejected as *sufficient*: it cannot be
  verified against the entity set, cannot be updated by an IDE rename, carries no cardinality, and leaves
  the join clause to inference — a mistake that surfaces as a wrong query rather than a build failure.
  Retained as a label for joins to tables outside the entity set (§ 2.4).
- **Infer primary and foreign keys by naming convention** (`id`, `<entity>Id`). Rejected: hipster-entity
  already treats identity as an explicit contract (DEC-017), and the R1 lesson (DEC-023) is that a
  *positional* fact must be recorded rather than assumed. A convention that a rename can break silently is
  the same defect in a different place.
- **A separate relation-description file** (a schema document the generator reads). Rejected: it moves the
  relation out of the interface that owns the field, so the two can drift, and it makes the relation
  invisible to the IDE — the failure DEC-019 and DEC-022 exist to prevent.
- **Join-less entities** (no relations at all; every join is application code). Rejected as unnecessarily
  weak: a declared key relation can be checked, reported and used to emit a join, which is strictly more
  than nothing, and § 1's prohibition is what keeps it honest.

## Consequences

**Positive**

- The read set is bounded by the query, so a view's cost is a property of its projection and not of the
  data it happens to point at. This is the property the whole projection design exists for.
- Metadata stays **flat**: a field has a name, an ordinal, a `javaType` and possibly a kind. No recursive
  `ViewMeta`, no graph traversal in a deserializer, no cascade policy.
- A relation becomes **checkable**. The generator can verify that a marked foreign key points at a marked
  primary key, report the ones that do not, and emit a join clause without inferring it.
- Serialization cannot accidentally embed a graph, so payload size and read amplification stay predictable.
- The rule is teachable in one sentence: **an entity holds the other entity's key, and the key is marked.**

**Positive (the visibility half, which is the reason this decision exists)**

- **A method's cost is deducible from its body.** No getter issues a query, so the read set of a method is
  the reads written in it. This is the property DEC-019 is built on, and a relation is where an ORM
  normally trades it away.
- **No lazy proxies, so no object that lies about its type.** A view is what it says it is, so `instanceof`,
  `equals` and an IDE's type hierarchy all mean what the source says.
- **No cascade and no dirty checking, so no hidden writes.** Every write is a described effect in the unit
  and a dispatcher statement — `repository.save(order)` cannot silently touch four other tables, because
  there is no cascade to touch them with.
- **No N+1 by accident.** A loop over orders cannot acquire a query per iteration from a field access,
  because a field access is a field access.

**Negative**

- A developer wanting `order.customer().name()` writes a second read or an explicit projection. This is more
  work, and it is the deliberate trade. It is also where a team that has only used JPA will push back, so the
  reasoning above — not the rule alone — is what has to be communicated.
- Conveniences that a JPA user expects are simply absent and will be asked for: lazy loading, cascade
  delete, automatic dirty flush, a second-level cache keyed by entity. Each is a separate decision, and
  each would reintroduce the hiddenness this one rejects, so "no" is the default answer rather than a
  temporary gap.
- Marking keys adds annotations to every entity and a metadata surface that has to be generated and kept
  stable — and the key's location becomes part of the R1-shaped ordinal contract, so moving it is a
  migration.
- The prohibition cannot be enforced by the compiler (DEC-017's minimal `EntityBase` is why), so it depends
  on the generator diagnostic running. A project that never runs `validate` gets no protection.
- Adopting `@PrimaryKey` / `@ForeignKey` means a **new metadata block per view**, which the HTML report and
  the class index will want to show (DEC-027, DEC-029) — follow-up work, not free.

**Follow-up work**

- Define the marker annotations and the relation record, and generate them into `ViewMeta`.
- Add the `entity_reference_field` and `primary_key_missing` rules to `EntityRulesValidator`, with the
  DEC-022 diagnostic format.
- Emit join fragments from a marked relation, so the join clause stops being inferred from a path.
- Extend `<Marker>.metadata.json`, the HTML report and the class index with the key and relation facts.
- Decide whether `JOINED` gains a sibling that means "this field *is* the foreign key" as opposed to "this
  field came from the join", or whether the two roles stay separate (see Open questions).

## Out of scope

- **Join execution.** This decision says how a relation is *described*; whether the store performs a join,
  a second query, or a batch load is the persistence layer's business (DEC-005 already puts this out of
  scope, and it stays out).
- **Cascade semantics.** With no object graph there is nothing to cascade, which is the point; a delete that
  must also delete children is business logic, and in this project's vocabulary it is a
  `@CoreChangeOnChange` step.
- **Polymorphic relations.** `hipster-entity` has a polymorphic-view mechanism, and a relation pointing at a
  polymorphic root needs a discriminator; how that composes with a marked foreign key is open.
- **Referential integrity enforcement.** Whether the database has a foreign key constraint is a schema
  concern, not a view concern.
- **Reverse navigation.** A convenience `Order → List<OrderLine>` accessor generated from the other side's
  foreign key would be a *query*, not a reference, and whether the generator should emit one is open.
- **Lazy, batch or eager loading strategies.** There is no loading to strategize: the caller reads.

## Acceptance criteria

- The generator reports `entity_reference_field` for a view field whose type is an entity view, and the
  entity pass fails under `--validate=STRICT`.
- A root entity view that declares no primary key is reported as `primary_key_missing`.
- `ViewMeta` (or the field enum) exposes the primary key of a root entity, and the foreign keys of a view
  with the entity and key each points at.
- The generated metadata for a view with a marked relation contains the relation as **structured data**, not
  as a path string alone, and the HTML report renders it (DEC-027).
- A serializer round-trips an entity with a foreign key as a **key value**, and a test asserts that no
  generated serialization nests a related entity.
- Renaming a referenced entity's type updates the relation in generated output through an IDE-visible
  reference (DEC-022), and the operation is covered by a test.
- No view in this repository's example declares a field whose type is an entity view.
