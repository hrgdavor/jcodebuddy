# DEC-037: One metadata engine in `jcodebuddy-core`

- Status: Proposed — the direction is the maintainer's (2026-10-02), and the two points that remain open are
  named below; everything else in this record is settled
- Date: 2026-10-02
- Owners: project
- Related docs: [DEC-004 — Generated metadata over runtime reflection](DEC-004.md), [DEC-026 — `.jcodebuddy/`, the per-module output root](DEC-026.md), [DEC-029 — the class index](DEC-029.md), [DEC-030 — OpenRewrite is the one source representation](DEC-030-openrewrite-source-representation.md), [DEC-031 — project-automations are living code](DEC-031-project-automations-are-living-code.md), [DEC-W006](../../../doc/architecture/decisions-watch/DEC-W006.md) / [DEC-W008](../../../doc/architecture/decisions-watch/DEC-W008.md) / [DEC-W009](../../../doc/architecture/decisions-watch/DEC-W009.md) (watch metadata, its parse, the arena index), [`AGENTS.md`](../../../AGENTS.md) § 1 and § 2, [`doc/architecture/module-map.md`](../../../doc/architecture/module-map.md), [`plans/unified-plan.md`](../../../plans/unified-plan.md) steps 3.0a–3.0k

## Context

The maintainer's direction, kept as given:

> Metadata parsing and representation should all move to `jcodebuddy-core` and `jcodebuddy-codegen-api` is
> questionable if needed. All of the codegen and code analysis and code reporting and any other code
> utilities like LSP sidecar … all of that will need fresh metadata, that is updated also in watch mode that
> fires events, indexes and allows search. We need one dedicated core engine that is backbone for all others
> in this big project.

And, confirming the two things that were still open (2026-10-02, kept as given):

> jcodebuddy-core should hold the main engine, and what others need. it is ok we merge jcodebuddy-codegen-api
> into it to simplify.

**Confirmed (2026-10-02):** `jcodebuddy-core` holds the main engine **and what consumers need** (the model,
the queries, the generator SPI, and the watch/freshness contract they subscribe to), and
`jcodebuddy-codegen-api` is merged into it to simplify. Two points remain open and are named below; the
rest of this record is settled.

Today the pieces that sentence describes are spread across six modules, and each separation has a real
reason — but none of those reasons is a reason a *backbone* should be scattered:

| What | Where it is today | Why it is there |
| --- | --- | --- |
| file-scoped metadata representation, and the one parse path | `hipster-entity-tooling` (`meta/SourceMetadata`, `SourceReader`/`TreeQueries`, `meta/*`) | DEC-030's one representation, owned by the entity tooling |
| the class index | `hipster-entity-tooling` (`index/ClassIndex`, `ClassRecord`, `TypeFacts`) | DEC-029; written as part of an entity pass |
| file watching and checksums | `java-watch-core` (`BatchedFileWatcher`, `ManagedFileWatcher`, `ChecksumDatabase`, `ChangeSet`, `DirectoryScanner`) | the watch subsystem's own module |
| providers, JSON-RPC, transports | `metadata-server` (`MetadataProvider`, `WatchMetadataProvider`, `MetadataRpcService`, `RpcDispatcher`, `HttpTransport`, `UnixSocketTransport`, `ForyCodec`) | it serves metadata to editors |
| index storage | `metadata-arena` (`LongToLongsIndex`, the mmap formats, the arenas) | off-heap work, DEC-W009 |
| the generator-facing SPI | `jcodebuddy-codegen-api` (exactly five types) | promoted out of `project-automation` so that AGENTS.md § 1.1 holds |
| reporting | Bun renderers under `scripts/` (entity, merge, markdown) | DEC-027/029: the generator is not the model |
| the consumers | `project-automation` (dev-time passes), `java-watch-agent` (watch tools), `hipster-ioc-tooling`, the webview hosts and `webviewd`'s `ProjectEventStream`, and an LSP sidecar to come | each is a *consumer* of metadata, and each needs it fresh |

Three facts in the tree make this a decision rather than a detail, and each is verified rather than assumed:

1. **`jcodebuddy-core` is a leaf by design, and being a leaf is its stated reason to exist.** It holds three
   types (`GeneratedCodeMarkers`, `GeneratedCodeParser`, `GeneratedBlock`), its POM declares nothing but
   JUnit in test scope, and [`module-map.md`](../../../doc/architecture/module-map.md) records why: "a tool that
   only wants to know where generated code stops should not resolve any of that" — the OpenRewrite LST, the
   Jackson metadata model, the entity type system. It is also **inside the recorded gate**
   ([`scripts/lib/gate.js`](../../../scripts/lib/gate.js) names it deliberately, "being in the gate is a
   decision, so it is written down"). An engine in that module gains OpenRewrite and Jackson: that is the
   point of this decision, and it is also the property this record has to replace deliberately rather than
   quietly.
2. **The recorded gate covers none of the migration's other modules.** `GATE_MODULES` is `jcodebuddy-core`
   plus the six `hipster-entity`/`hipster-entity-example`/`hipster-entity-test` modules.
   `jcodebuddy-codegen-api`, `hipster-ioc-tooling`, `java-watch-agent`, `project-automation`,
   `metadata-server`, `metadata-arena` and `java-watch-core` are all outside it, so a move across them is
   visible in **no** gate run unless the step that makes it says how it is verified.
3. **The SPI cannot be implemented where its data lives, and one engine removes that by construction.**
   `jcodebuddy-codegen-api` holds `TypeResolver`/`TypeDefinition` and already depends on
   `hipster-entity-tooling` — for `SourceMetadata`, one type — while the class index it would have to read
   lives in that same module. An implementation next to the index is a cycle; an implementation above both is
   a second copy of the model. This is the same conclusion the maintainer reached from the other end.

## Decision

**1. One engine, in `jcodebuddy-core`.** The engine owns, as one library with one lifecycle:

- **parsing** — through the repository's one source representation (DEC-030), never a second parser;
- **representation** — the metadata model a consumer reads: a type, its kind and modifiers, its members,
  its relations (supertypes, interfaces, implementors), the file it is declared in, and its checksum;
- **indexes** — including the relations and their reverse direction (DEC-029's class index grows into this);
- **freshness** — the watch loop: change detection, checksum-based invalidation, and **events** emitted when
  the model changes;
- **search** — the queries a consumer asks: by fully qualified name, by kind/modifier, by relation, by
  annotation, by member, by package.

**2. `jcodebuddy-codegen-api` dissolves into the engine.** Its five types are not one thing, and the split
says where each belongs:

- `TypeResolver`, `TypeDefinition` — **engine** metadata queries, next to the model they describe;
- `CodeGenerator`, `CodeContext`, `CodeContextImpl` — the **generator SPI** the engine publishes, because a
  generator is a consumer of the engine, not a peer library of it;
- the `SourceMetadata` edge disappears: the engine holds the representation, so nothing needs to reach into
  the tooling module for one type.

**3. The engine is a library, and watch state is not a second source of truth.** `metadata-server` becomes a
**transport and adapter over the engine** (JSON-RPC/MCP and the transports it already has) rather than the
owner of providers; an editor, a CLI, a pass and an LSP sidecar are all *readers* of the same engine. A
second index — a per-tool cache, an editor-side model, a pass-local map — is the failure this decision exists
to prevent, and a consumer that wants freshness subscribes to the engine rather than watching files again.

**4. Consumers migrate onto it; none of them keeps a private metadata path.** The dev-time passes
(`project-automation`), the watch tools (`java-watch-agent`), the generators (`hipster-ioc-tooling`, the
entity pass) and reporting (the Bun renderers, which read the engine's JSON) are the migration.

**5. The recorded gate grows with the engine.** As consumers migrate, the modules that carry the engine's
contract join `GATE_MODULES`; until then each migration step records its own build and test evidence,
because fact 3 above means the gate is silent about them today.

## Open points — the two that remain

These are the maintainer's calls, and each changes code rather than wording. *(The third and largest one —
whether `jcodebuddy-codegen-api` is merged in — is settled: yes, to simplify, confirmed 2026-10-02.)*

- **What stays a leaf.** Recommendation: the marker vocabulary and its parser move to a small leaf module of
  their own (they are consumed by tools that must parse generated regions *without* resolving OpenRewrite),
  and `jcodebuddy-core` becomes the engine. The alternative — keep the three types in the engine — is
  cheaper and is a defensible reading of "core holds what others need"; it gives the linter/agent case the
  dependency the leaf exists to avoid. **Measured, so the choice is informed:** `jcodebuddy-core` is 6 files
  today (3 main, 3 test) and the marker leaf would be exactly those 3 types moved, not a new body of work.
- **How far the watch side is absorbed — two halves, answerable together.** Recommendation for
  `metadata-server`: keep it as the transport/adapter over the engine and re-point its providers, which
  preserves DEC-W006–W009's serving shapes while removing their ownership of the model (absorbing the module
  entirely is the stronger reading and a bigger change to those records). Recommendation for
  `java-watch-core`: its watcher and checksum work becomes the engine's freshness implementation — the engine
  owns the *contract*, the module may stay as the implementation — since DEC-W006's cache and DEC-W009's
  rebuild protocol are exactly the freshness semantics the engine must publish.

## Alternatives considered

- **Leave it scattered and give each consumer a path to the pieces it needs.** Rejected: it is the present
  state, and it is why the same question ("who extends whom") is answered three ways today — by the merge
  tool's classpath resolution, by the entity tooling's index, and by hipster-ioc's sibling-file lookup. It is
  also what made the annotations in this repository look reliable while a file that was never read looked
  exactly like a file with nothing in it.
- **A new module named for the engine (`jcodebuddy-metadata-engine`).** Rejected for now: the maintainer's
  direction names `jcodebuddy-core`, and a second new name would add a module without changing anything the
  decision is about. Revisit only if the marker leaf makes "core" a misleading name.
- **The engine inside `metadata-server`.** Rejected: a server is a lifecycle with a socket and a port; every
  other consumer would then depend on that lifecycle to read a type. The engine must be usable in a test
  with no server running.
- **Keep `jcodebuddy-codegen-api` as the generator SPI and let the engine implement it.** Rejected: it keeps
  the dependency inversion that fact 3 describes, and it leaves `TypeResolver` — a metadata query — outside
  the module that owns metadata.

## Consequences

- **Positive.** One model, one parse path, one index, one freshness contract; a consumer (a report, a
  generator, an editor, an LSP sidecar) reads the same facts and cannot drift from them; the cycle in fact 3
  disappears; `TypeDefinition` can finally express a relation and be implemented.
- **Negative.** `jcodebuddy-core` stops being a leaf and gains OpenRewrite and Jackson, so the
  linter-side property must be re-established deliberately (the leaf above) or given up; the migration is
  large and mostly outside the recorded gate (fact 2), so it is scheduled as steps with their own evidence;
  DEC-029, DEC-W006–W009 and `module-map.md` all need amending as the code moves rather than before.
- **Neutral.** The engine is still a library, not a service, and the watch loop is still explicit: DEC-030's
  "one representation", DEC-026's per-module `.jcodebuddy/` output and AGENTS.md § 1's source-visible wiring
  are unchanged by this record.
