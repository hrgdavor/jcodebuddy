## Context

Generated code is committed source in this project (DEC-019), and it is **cooperative**: a member
belonging to an earlier revision of the generator survives regeneration, which is what lets a developer
edit generated output and keep the edit (DEC-020). Both properties mean a file in this repository can be
partly generated, partly hand-written, and the boundary between the two is currently knowable only to the
generator itself — because the recogniser *is* the generator.

That was acceptable while the only consumer was the generator. It is not acceptable now, for three
consumers that all need the same answer without that knowledge:

1. **An external static parser** — a linter, a migration tool, a diff policy, an IDE inspection. It has
   the file and no access to this module's internals.
2. **An AI agent** reading the source to make a change. It has to know which parts it may edit freely and
   which parts its edit will be overwritten by, or it will make a change that silently disappears on the
   next pass.
3. **A reviewer** in a pull request, who is reading a diff and needs to see at a glance whether the
   changed lines are the developer's or the generator's.

Today the markers exist but only at one granularity, and only for wholly-generated files. Every generator
here emits DEC-021's two-line file header, and nothing else:

```java
// {@link hr.hrg.hipster.entity.tooling.ViewTrackingBuilderGenerator} Tracking builder for the PersonSummary view.
// {enabled:true, blockMarker: "implicit"}
```

Measured on this tree: **11 emission sites, all file-level, all the same shape** (seven generators, plus
the variants that share a header builder). There is no method-level marker, no region marker, and no way
for a parser to say "I found a marker whose rules I do not implement". A file that is half generated and
half hand-written — which DEC-020 makes the normal case — has no visible boundary in it at all.

### What is wanted, and what is not

The goal is **recognisability by structure and a small fixed vocabulary**, not exhaustive annotation. The
failure mode to avoid is the opposite of the one above: marking every generated line, every `case` arm and
every setter, so that the markers become the noise a reader learns to skip. A `switch` statement that
routes REST endpoints is already delimited by its own braces; marking each arm adds nothing a parser did
not already have, and adds a line to every arm forever.

So: mark at the granularity where the generator's ownership boundary actually is, and rely on the
language's own delimiters everywhere below that.

## Decision

### 1. The vocabulary is closed at four markers, and each has one job

A marker is a **Java line comment whose payload begins with `@generated`**, followed by a keyword that
names the marker's scope. Nothing else about a comment makes it a marker: a parser does not need to know
which generator wrote it, what it was configured with, or how it recognises its own output.

| Marker | Scope it claims | Where it appears |
| ------ | --------------- | ---------------- |
| `// @generated file <generator>` | **The whole file.** Everything below belongs to the generator. | First line of the file, above `package` |
| `// @generated member <generator>` | **The next declaration and its body.** Everything from the annotated declaration to its closing brace. | Immediately above a method, constructor, field or nested type |
| `// @generated region begin <id>` … `// @generated region end <id>` | **The lines between the pair.** | Anywhere inside a body |
| `// @generated block` | **The next statement or block, as delimited by the language.** | Immediately above a statement whose body has its own braces |

The fourth exists for the case named in the context: a generated `switch` over routes, a generated
`if/else` chain, a generated `try`. The marker says "the statement that starts here is generated"; the
statement's own braces say where it ends. **A generator MUST NOT emit a marker per `case` arm, per
`else` branch or per line** — that is the noise case, and the language already carries the boundary.

The payload after the keyword is **advisory**. A parser that does not care which generator emitted a
region ignores it; a human reading the file gets jump-to-source for free.

### 2. The file header keeps its DEC-021 shape, and gains the file marker

DEC-021's two-line header is not replaced. Its first line already carries the generator's fully qualified
name, which is what a parser or a person needs to find the generator, so the file marker is expressed by
**adding `@generated file` to that line** rather than by a third line:

```java
// @generated file hr.hrg.hipster.entity.tooling.ViewTrackingBuilderGenerator — tracking builder for the PersonSummary view.
// {enabled:true, blockMarker: "implicit"}
```

Two consequences worth stating, because they are the migration:

- The header's first line already began with `// {@link <fqn>}`. The `{@link …}` is a **javadoc tag in a
  line comment**, which javadoc ignores there, so it was never producing a link for a reader; the `{@link`
  spelling is retained only where it does something. The marker keyword replaces it because being
  *recognisable* matters more than looking like javadoc.
- **The JSON5 config line is unchanged**, and stays the place for per-file options. A parser MUST NOT have
  to parse JSON5 to find a boundary: the boundary is the marker, and the config is for the generator.

### 3. Placement rules, and why each is a rule rather than a preference

- **A marker is a line comment, alone on its line**, at the indentation of the declaration or statement it
  annotates. Not a trailing comment on the same line as code: a parser scanning line-by-line must be able
  to decide "is this line a marker" without parsing what precedes it.
- **`@generated file` is the first line of the file**, above `package`. It covers the whole file, so no
  `member` or `region` marker inside such a file adds information — a generator SHOULD NOT emit them
  there, and a parser MAY stop reading markers once it has seen it.
- **`@generated member` is the line immediately above the declaration**, with no blank line between, and
  it covers the declaration and its body. A blank line between the marker and the declaration breaks the
  association, deliberately: "immediately above" is checkable, and a rule that allowed an arbitrary gap
  would need a parser to guess how far up to look.
- **`@generated region` is a pair with a matching `<id>`**, and regions do not nest with the same id. The
  id is what makes a pair match; it is a short stable token, not a description. A region whose end marker
  is missing is a **broken marker**, which a parser MUST report rather than silently extend to the end of
  the enclosing block.
- **`@generated block` annotates a statement that has its own braces.** If the next statement does not,
  the marker is a broken marker: the parser has nothing to bound it with, and guessing a boundary is
  worse than reporting one missing.
- **A generator MUST NOT emit a marker for a construct it does not fully generate.** Half-marked code is
  the one outcome worse than unmarked code, because a parser will believe the marker.

### 4. The rule that makes the vocabulary extensible: unknown markers MUST be reported

This is the part that lets the set of rules grow without breaking a parser that has not caught up, and it
is the reason the vocabulary can be extended at all:

> **A parser that meets a marker it does not implement MUST warn, naming the marker and its location, and
> MUST NOT treat the code as hand-written.**

The three failure modes are not equivalent, and only one keeps the design honest:

| What the parser does on an unknown marker | Consequence |
| ----------------------------------------- | ----------- |
| Treats the code as hand-written | **Wrong, and silently.** The parser will happily edit or migrate generated code, and the edit is lost on the next pass. This is the outcome the whole decision exists to prevent |
| Treats the code as generated | Safe for edits, but the parser will not do what the marker asked, and nothing says so |
| **Warns, and refuses to decide** | Correct: the code's status is unknown, and the operator is told which marker they need to support |

So a marker is **self-describing enough to be refused**. `@generated <anything>` is recognisable as a
marker by shape alone — the `@generated` keyword and a following word — which means a parser can report
`unsupported marker: @generated patchwork at line 412` without knowing what a patchwork is. A parser that
sees `@generated` and does not know the keyword MUST NOT fall through to "not generated".

The same applies to the parameters of a known marker: a `region` id it can pair is fine, a marker with a
shape it cannot parse is an unknown marker, not a known one to be ignored.

### 5. AI agents are the reason the vocabulary is described, not just enforced

An agent has no parser to fail; it has a description. So the vocabulary is stated in prose a reader can act
on — this table, and the generated-code section of the user documentation — and the rule for an agent is
the same as for a parser, expressed differently:

- code under a marker is the generator's: **an edit there will be overwritten**, and the correct change is
  to the generator (DEC-020's rule, and this project's whole expectation while it is pre-1.0);
- code outside every marker is hand-written and safe to edit;
- code under a marker whose rules the agent does not know should be **left alone and said out loud**,
  rather than assumed hand-written.

## What this changes in the generators

Nothing in this decision is retroactive work by itself: the four markers are the vocabulary, and the
generators adopt them as they start emitting partial code. Concretely, and in order:

1. **The file header** (all 11 sites today) gains `@generated file`. This is mechanical and immediately
   makes every generated file recognisable to a parser that implements nothing else.
2. **`CooperativeCodegen`** — the component that decides which members it owns — gains a marker reader, so
   "the members the generator owns" and "the members a marker claims" are checked against each other
   rather than being two independent notions that can drift.
3. **A generator that emits into a hand-written file** — which none does yet, and which is the reason
   markers 2–4 are specified before they are needed — emits `member` or `region` at the boundary, and
   `block` where the construct has its own braces.

The third is deliberately not being implemented speculatively. Specifying the vocabulary now and
implementing it when the first partial emission appears is what keeps the rules honest: a marker set
invented ahead of its use gets the granularity wrong.

## Alternatives considered

- **A registry mapping generator ids to their markers.** Rejected: it makes recognition depend on data
  that lives outside the file. A parser reading a file must be able to decide from the file.
- **Machine-readable block markers only (`// generator:begin` / `// generator:end` on every block).** This
  is what DEC-020 calls *discouraged* as a default, and the reason applies here too: it is two lines per
  block forever. The cooperative recogniser does not need them, and for a reader they are noise. They
  remain allowed for a block that cannot be recognised by shape.
- **Marking every `case` arm in a generated dispatch.** Rejected in the context above: the switch's own
  braces already bound it, and per-arm markers are the noise case.
- **A marker that encodes the generator's config (blockMarker, maxMethods, …).** Rejected: it would make a
  boundary depend on parsing JSON5, and would put a generator's private options in a file every parser
  reads. The config stays on the second header line, where DEC-021 put it, and a parser never needs it.
- **Requiring `@generated` to be the first token of the comment, with nothing before it.** Chosen, and it
  is a real constraint: it means `// NOTE: @generated` is not a marker. A parser scanning for `@generated`
  at the start of the comment text is trivial; a parser searching for the substring anywhere will match
  prose about markers, including this document.

## Consequences

- Positive: a file's generated regions are recognisable from the file, with no generator internals; the
  vocabulary can grow without a parser that is behind becoming *wrong*; the partial-emission case that
  DEC-020 makes normal finally has a visible boundary; an AI agent has a stated rule for what it may edit.
- Negative: a new marker shape costs a parser an update, and until it does, the parser warns on every file
  that uses it — noisy, but the correct direction, and the alternative is silence.
- Negative: `@generated` is not a javadoc tag, so a reader who expected `{@link}` to be clickable loses
  nothing but may be surprised. The header's generator FQN is still there in plain text, which is what a
  jump-to-source actually needs.
- Follow-up: implement § 1 for the 11 existing file headers; then the marker reader in
  `CooperativeCodegen`; then the first partial-emission generator, whichever needs it first.

## Acceptance criteria

- A parser can decide, from a single file and no other input, that it contains generated code and which
  lines are covered — for each of the four markers.
- A parser that implements only `@generated file` still recognises and reports the other three as
  unsupported, rather than treating them as hand-written.
- Every wholly-generated file in this repository carries `@generated file`.
- No generator emits a marker for a construct it does not fully generate.
- No generator emits a marker per `case` arm, per branch or per line.
- The vocabulary, the placement rules and the agent-facing rule are described in prose a reader who has
  never seen a generator can follow.
