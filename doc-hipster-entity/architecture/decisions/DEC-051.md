# DEC-051 — wildcard matching follows git's `wildmatch`

> **Status:** accepted, 2026-10-23.
> **Applies to:** every place in this ecosystem that matches a name against a wildcard pattern — the `.gitignore`
> matcher, any tool that filters files by pattern, and every port of either.

## Context

Wildcard matching appears in several places and had no shared definition. Each implementation grew its own subset of
"glob": one supported `**`, another treated `*` as crossing `/`, a third added brace expansion because it was
convenient. The results looked plausible and disagreed at the edges, which is the worst combination: a filter that is
subtly wrong silently includes or excludes files, and the disagreement only surfaces when two tools maintain the same
tree.

At the same time, the ecosystem's dominant use of wildcards is **`.gitignore`**, which means git's semantics are
already the ones users are trained on, already documented, and already implemented in a reference C file:
`wildmatch.c` in git's own tree. `.gitignore` is not a convention this project invented; it is the convention it must
interoperate with, because the trees it describes are git worktrees.

## Decision

**The wildcard syntax of this ecosystem is git's `wildmatch`, as git uses it for `.gitignore` patterns.** A matcher
here means: one pattern against one path segment sequence, with `*` never crossing `/`, `?` matching one byte, `[...]`
character classes, `\` escapes, and the three `**` forms. The `.gitignore` layer on top of it — anchoring, a trailing
`/` for directories only, `!` negation, last match wins, a deeper file beating a shallower one, an excluded directory
not being entered — is part of the same definition, not a local extension.

Concretely:

- **The reference is the `gitignore` project** ([`gitignore/README.md`](https://github.com/hrgdavor/gitignore/blob/main/README.md)), which owns the
  matcher, the chain and the conformance vectors. `fs-meta` and anything else consume it rather than carrying a second
  implementation.
- **Correctness is measured against those vectors** (`gitignore/conformance/gitignore-vectors.json`) and, when a
  disagreement is found, against `git check-ignore` on a real checkout. A port that disagrees with git is wrong, not
  different.
- **Performance work keeps the semantics.** The segment dynamic program in `src/gitignore.zig` exists because the naive
  recursive form was exponential on `**`; it computes the same language, and a faster implementation is welcome only if
  the vectors still pass. A "faster" matcher that changes what matches is not a faster matcher.
- **Missing features are not added locally.** If a tool needs something `wildmatch` does not have, the options are, in
  order: express it as several patterns; translate the user's input into `wildmatch` patterns and say so; or open the
  decision again with evidence. It is never "just this one extension in this one tool".

## Consequences

**Positive.**

- One vocabulary: a user who knows `.gitignore` knows what every filter here does.
- One test corpus, reusable across Zig, Java and JavaScript; a port is comparable before it is optimised.
- Interoperation by construction: a tree that git ignores the same way this ecosystem filters it, which is what a
  watcher and an indexer need in order to agree.
- The subtle rules have one owner and one place to fix: `**` forms, `[]` with `]` first, escaped `#`/`!`, trailing
  spaces, CRLF tolerance.

**Negative, accepted.**

- `wildmatch` is quirky where glob is usually generous: no brace expansion (`{a,b}`), no `extglob`, no case folding,
  and `*` stopping at `/` surprises people who come from shells. A tool whose users expect braces must translate, and
  the translation is its own behaviour to document.
- The "less defined glob syntax" that some libraries offer is easier to satisfy at first and impossible to agree on
  later. This decision pays that cost once.
- Performance work is constrained: the obvious shortcuts (a regex translation, a hash of the whole pattern) must be
  re-validated against the vectors, because they tend to change `**` semantics.

## Non-goals

- **No brace expansion, no `extglob`, no PCRE** in any matcher here. A tool that needs them translates at its own edge.
- **No reading of `$GIT_DIR/info/exclude` or `core.excludesFile`.** Those are per-clone configuration; a tree
  description is not. This is a `.gitignore`-only decision and is recorded in `gitignore/README.md`.
- **No new dialect for JSON or other formats.** A JSON path, a YAML key and a `.gitignore` are matched with the same
  language when a pattern is involved.

## Migration

- `fs-meta` already depends on the `gitignore` project instead of carrying the matcher (commit `c50b720`).
- The Java and JavaScript ports of the matcher must be measured against `gitignore/conformance` rather than their own
  expectations; a disagreement is a bug report against the port, or — if git agrees with the port — a vector to fix
  here with the reasoning recorded.
- Any tool that currently accepts patterns with braces should translate them into alternatives at its boundary, and
  document that the expansion happens before matching.
