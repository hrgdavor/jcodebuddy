## Context

The maintainer's direction, kept as given:

> metadata needs to define a strict subset where all of it is derived from file alone, so that result can be
> serialized in cache per Java source file, so rebuilding the full metadata cache and extended metadata per Java
> File can reuse it. That base set must include a hash so we know it is up-to date with source

Today the engine has the **facts** this asks for and not the **shape**. `TypeFacts.of(declaration, …)` and
`TreeQueries.importLines(unit)` already read a single file and produce exactly a file's worth of metadata, and
`ClassIndex` already writes a checksum per row — but the only thing that is ever *serialized* is the module-level
table, and the per-file result is thrown away when the pass ends. Three consequences, all of them the cost this
record is about:

- **A rebuild re-parses everything.** Nothing on disk says "this file's facts were computed from these bytes", so
  the second pass over an unchanged tree does the same work as the first, and there is no unit to reuse.
- **A watch edit invalidates a module.** The table is one artifact for the whole module, so one changed file
  rewrites all of it. A watch loop that knows exactly which file changed (DEC-W006) has no per-file result to
  recompute, and no way to express "these rows are still good".
- **The layers are unnamed, so nothing keeps them apart.** A consumer cannot tell which facts came from *this*
  file and which came from resolving names against others, so a cache built by a consumer either re-derives
  everything or risks keeping a cross-file fact that a later edit to another file invalidates.

The distinction the direction draws is not tidiness; it is the difference between a cache that can be trusted and
one that lies. A fact derived from one file is invalidated by exactly one file. A fact derived from two files is
invalidated by either, and a per-file cache holding it is **stale after an unrelated edit** — which is DEC-040's
central concern (a stored copy cannot announce that it is stale) one level up.

## Decision

**D1 — Two layers, named, and the boundary is "one file's bytes".**

- **Base metadata** is every fact derivable from **one Java source file's bytes alone** — no other file, no index,
  no classpath, no environment, no clock.
- **Extended metadata** is everything else: name resolution, reverse indexes, cross-file and cross-module answers,
  freshness verdicts, reports. It is **derived** from base metadata plus its declared external inputs.

The direction's word is *strict*: a fact that needs a second file is not base, however convenient it would be
there (D6).

**D2 — The base set is closed and enumerated; adding to it is a format decision.**

The base set is exactly these facts, and each is file-local for a stated reason:

| fact                                          | why it is file-local                                                                            |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `path` (module-relative)                      | the entry's key: an entry is *about* a file, so the file is its identity, not a fact it holds   |
| `checksum`, `size`                            | computed from the bytes themselves (DEC-029 § 4)                                                |
| `generated` (the DEC-021 file marker)         | read from the file's own header                                                                 |
| the type declarations                         | FQNs come from the package clause plus the nesting the file writes, kind, modifiers, line, span |
| annotations, as written                       | a name and its arguments, in the file that writes them                                          |
| members, as written                           | names, kinds, types-as-written, parameters, modifiers, annotations, positions                   |
| relations, **unresolved**                     | the supertype *as the file spells it* (`ChildContext<AppContext>`) and its range                |
| the file's import lines                       | a property of the compilation unit (DEC-029's `imports.json`)                                   |

Everything in that table is already produced by one parse of one file today; the change is that it becomes a
**stored unit** with a name and a version. The D1 facts DEC-040 still owes (`permits`, `throws`, enum constants,
initialisers, has-a-body) join this table when they land, and they are file-local by construction, which is why
they were worth listing before implementing.

**A base entry holds ranges, not source text** (DEC-040 D2) — and that matters more here than anywhere else,
because a per-file cache is exactly where storing the text becomes tempting: the file is right there, and "we
already read it" is a strong argument. It is still refused. The entry carries positions, the hash says whether the
file they point into is the one the entry describes, and `SourceSlice` is the read. So an entry is small (a
thousand-line file's facts are kilobytes, not its source), it cannot disagree with the file *textually* because it
holds no text, and the repository's guard that no metadata row carries content (DEC-029, and the
`noRowCarriesContent` invariant) applies to this serialized form exactly as it applies to the table.

**D3 — Every base entry carries the hash of the content it was computed from, and a mismatched entry is never
used.** The hash is `Wyhash64` over the LF-normalised content (DEC-029 § 4) — the identity this repository already
uses, not a second one. An entry that does not match its file's current hash **must be recomputed**, and no answer
may be served from it. That is what makes reuse safe rather than merely fast, and it is DEC-040 D2's rule at the
cache: a pointer or a copy that cannot detect staleness is the bug, and a hash makes the detection free.

**D4 — Extended metadata is a pure function of the base set** (plus inputs it declares, such as a classpath for
resolution). Consequences, all of them required: a full rebuild can always be produced from base entries alone;
any *cached* extended artifact must be discardable without changing an answer; and an extended answer that cannot
be reproduced from base is a bug rather than a convenience.

**D5 — Invalidation is per file.** A file's change invalidates exactly its base entry; the extended layer is
re-derived (or invalidated by D4's rule). The unit of recomputation is the file, which is the unit a watch loop
already reports, so a watch edit becomes "recompute one entry, refresh the derived views" rather than "rewrite the
module".

**D6 — A fact that needs a second file must not be stored in a base entry, even when it is cheap there.** No
resolved FQN, no reverse edge, no "who implements this", no freshness verdict, no cross-module fact. The reason is
D1's and it is measurable: a base entry for file *A* must be **byte-identical** whether file *B* exists, is
edited, or is deleted. An entry that changes when another file changes is not base, and the acceptance criteria
below make that a test rather than a promise.

**D7 — One entry per Java source file, in the module's derived subtree, and an unreadable entry is recomputed
rather than fatal.** The entry is JSON in the same one-spelling metadata format, versioned like the table, and
written under the module's `.jcodebuddy/` (DEC-026: derived, ignorable, never committed). A missing, corrupt or
older-format entry costs a parse; it never fails a pass and never changes an answer.

**D8 — The class index becomes a projection of the base entries.** `classes.json` stays the *addressing* table
consumers are told to read (DEC-029), and a pass may produce it **from** base entries — including a pass that
parses nothing at all when every entry is current. It must not become a second place where a fact is invented: a
value in the table that the base entries do not imply is a bug D4 names.

## Where this sits beside the decisions that already exist

- **DEC-029 § 6** established the pattern at the module level (an `mtime` cannot be committed; `imports.json`
  cannot be repeated per row). This record does the same thing for the *subject* of the metadata rather than a
  sidecar: a fact's storage scope follows the scope of the fact.
- **DEC-W006** chose per-hash invalidation for the watch cache. This is the same rule, one layer down and in the
  engine: the hash decides whether a stored result may be reused at all.
- **DEC-037** said there is one model. There is still one model — this record says it has **layers**, and that the
  layer boundary is the file.

## Alternatives considered

- **Keep only the module-level table (today).** Rejected: it is the status quo whose cost is the Context section —
  a rebuild re-parses, a watch edit rewrites the module, and no consumer can reuse a per-file result.
- **Cache the *extended* model per file.** Rejected, and it is the trap this record exists to name: extended facts
  depend on other files, so a per-file extended cache is stale after an unrelated edit and cannot say so.
- **Key the cache by mtime instead of hash.** Rejected for DEC-029 § 6's reason: an `mtime` is a working-tree
  fact, so a checkout rewrites it while the content is unchanged (a false miss), and a same-second edit can leave
  it unchanged (a false hit). A content hash has neither failure, and the direction asks for one.
- **Store base facts only inside the table (which partly happens today).** Rejected as the *primary* form: the
  table is one artifact per module, so it cannot be the unit a per-file rebuild reuses. It stays as the projection
  D8 describes.
- **Recompute everything every time; cache nothing.** Correct but wasteful, and it is what the direction asks to
  fix. It also keeps the parse cost per file permanently on the critical path of every consumer run.

## Consequences

**Easier.** A rebuild reuses every unchanged file's entry and re-parses only what changed; a watch edit has a
unit to recompute; per-file facts can be computed in parallel because nothing in a base entry depends on another
file; a consumer can cache per file with the hash as its invalidation key; and the boundary gives a fact a natural
home — the question "is this base or extended?" now has an answer that does not depend on who is asking.

**Harder.** There is a second serialized form to version and keep honest, and the *strictness* needs enforcing or
it decays: the moment a resolved name is stored "because it was already computed", the cache is a per-file copy
of a cross-file fact. That is the failure DEC-040's guard lesson describes — the invariant is what catches it, not
the intention.

**Follow-ups.** The implementation is plan step 3.0u: the entry model, its writer and reader, `ClassIndex`
consuming entries so a current tree parses nothing, and the test that a base entry for file *A* does not change
when *B* does. DEC-040's remaining D1 facts land in the same layer, and the extended layer's own cache policy (if
any) is explicitly not decided here.

## Acceptance criteria

> **Progress 2026-10-03.** Step **3.0u-a**: the entry model exists (`FileMetadata`), the table's row reader/writer
> are shared with it, and criteria **1** and the substance of **4** are asserted by `BaseLayerTest` — an entry for
> file `A` is byte-identical whether `B` exists, is edited or is deleted; a stale entry is refused by the hash it
> carries; no source text is stored; and the document is deterministic across rebuilds.
>
> Step **3.0u-b** closed the list the same day. `MetadataCache` stores one entry per source under
> `.jcodebuddy/cache/`, decides reuse with the content hash alone, and counts hits and misses so "a warm rebuild
> parses nothing" is a measurement rather than a claim; `ClassIndex.absorb(FileMetadata)` takes an entry's rows and
> imports without reading the file, which is D8 in code — the table as a projection of the entries. All five
> criteria now have tests: the warm rebuild reports **3 hits, 0 misses** over three files and its table is
> **byte-identical** to the cold one; one edit rewrites **exactly one** entry; deleting the whole cache produces an
> **identical table**; a stale entry is refused; and no entry moves because a neighbour did.
>
> One boundary worth stating rather than implying: the *engine* can do all of this and proves it, while the passes
> adopt the cache in step **3.0j** — a cache nobody calls is still a cache that lies about being used.

1. **A base entry is independent of every other file.** Edited, added or deleted neighbour ⇒ the entry's bytes are
   unchanged. This is D6 as a test, and it fails the moment a cross-file fact is added to the base set.
2. **A warm rebuild parses nothing for unchanged files** — measurable with a parse counter — and produces a table
   **byte-identical** to a cold rebuild. Same input, same bytes: the projection adds no information.
3. **One edit, one entry.** Changing one file recomputes exactly that entry and leaves the others byte-identical.
4. **A stale entry is never used.** Mutating a file under an unchanged entry ⇒ the answer reflects the new
   content, and the stale entry is recomputed rather than trusted.
5. **Deleting the whole cache changes no answer, only the time taken.** A cache is allowed to be an optimisation
   and nothing else.

## Out of scope

- The base entry's storage *format* beyond "JSON in the metadata spelling, versioned" — whether a later revision
  moves it to `metadata-arena` (2.3/DEC-W009) is that decision's, not this one's.
- The extended layer's own caching policy, and any consumer's cache.
- Incremental *within* a file (a member-level entry) — the file is the unit this record defines, and DEC-026's
  `cache/` may hold whatever granularity a later decision chooses.
- Bodies and statements: DEC-040's Out-of-scope section already says why they are not metadata, base or extended.
- The watch agent's protocol and the sidecar's session model (DEC-038), which consume this layer rather than
  define it.
