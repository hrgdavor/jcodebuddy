## Context

The maintainer's direction, kept as given:

> plugin must allow opening .md files on right click and in addressbar but render clickable html, is sohuld not
> require manual rendering, also it must resfresh wehn markdown is saved in editor. Also must use
> https://tanstack.com/highlight/latest and vanillajs for the markdown render ad make it singlepage

Three facts constrain how that can be done.

1. **A page opened by a host cannot run our tooling.** The renderer under `scripts/markdown-view/` is run by Bun at
   *build* time today; the IDE plugin is Java, so a Markdown file opened in the webview has to become HTML without a
   shell command. The Markdown text therefore travels into the page and the page renders it there.
2. **DEC-027's vanilla rule is about view time, and it is strict**: one self-contained file, no bundler, no
   `node_modules`, no CDN, no `<script src>`, no network. A *build* step is how the `jsx6` pages already work — the
   rule's words are about what the page loads, not about how its bytes were produced.
3. **That rule also has an escape hatch, and this decision is it**: "when `jsx6` or `nodditor` cannot do something a
   page needs … a critical gap is a decision about an additional library for that specific output, taken with the
   evidence and recorded as its own decision rather than assumed" (DEC-027). Highlighting code fences in a
   documentation page is exactly such an output.

The candidate, read from the published package rather than from memory (`@tanstack/highlight` 1.0.0, MIT, no runtime
dependencies, `dist/core.js` ≈ 10 KB): a synchronous, class-based highlighter whose output is one `<pre><code>` tree
with stable `th-*` token classes and **no inline styles**, with isolated entries for each language and theme, and its
own published measurements (3.84 KB minified core with no languages; 16.04 KB for its nine-language docs set).

## Decision

1. **Adopt `@tanstack/highlight` 1.0.0 for code fences only.** It highlights code; it does not render documents. The
   Markdown itself stays this repository's own vanilla renderer (`scripts/markdown-view/render.js`), which owns lists,
   tables, links, headings and the `data-open` navigation of step 9.7.
2. **The library is bundled at build time and inlined.** A Bun script under `scripts/` (esbuild, the same shape the
   `jsx6` page uses) produces one JavaScript bundle, which is inlined into one HTML page together with the theme CSS
   and the bridge client. **At view time there is still no bundler, no `node_modules`, no CDN and no network**, which
   is what DEC-027 actually requires.
3. **Only the languages a documentation page can fence are registered**, from the library's isolated entries. Java and
   Kotlin are **not** among the thirty it ships; see the next clause, because silently falling back would be the kind
   of quiet lie this repository writes decisions to avoid.
4. **Java fences are highlighted with the `cpp` grammar, as an explicit approximation.** Java and C++ share the
   comment, string, keyword and numeric shapes a documentation fence shows, and the alternative is escaped
   plaintext — no highlighting at all. The mapping is written where it lives, in one place, with this decision as its
   reason; it disappears the day the library ships a Java grammar. **Kotlin falls back to plaintext**: the C-family
   approximation would mislead more than it helps there, and an approximation that misleads is worse than none.
5. **The theme is the library's own**, `github-light` and `github-dark` through `createThemeCss`, inlined with a
   light/dark selector so the page can follow the IDE. Its output contract — semantic classes, no inline styles — is
   what our page CSS targets.

## Consequences

- **The plugin build gains a prerequisite**: Bun and `bun install` at the repository root, because the page bundle is
  built rather than committed. That is recorded in the plugin's README and in the webview README, next to the build
  steps a reader already follows.
- The page grows by a few kilobytes, once, for every document it shows.
- A third-party library now has a say in how code looks in our pages. Pinned to `^1.0.0` in the root manifest, and its
  output contract is the small surface we depend on — classes, not markup structure.
- When the library ships a Java grammar, clause 4 collapses to a deletion: remove the mapping and register `java`.

## Alternatives, and why not

| Alternative                 | Why not |
| --------------------------- | ------- |
| A CDN `<script src>`        | DEC-027 forbids a network reference at view time, and it is the one rule that keeps these pages greppable and offline |
| Shiki                       | Larger and slower by the package's own published comparison (4.6 ms vs 182 ms over its 334 fixtures, and ~3.4× the HTML) — their measurement, quoted as theirs, and the deciding factor is that we need fragments of a docs page, not a TextMate engine |
| Writing our own highlighter | Out of scope for a documentation page, and a grammar runtime is exactly what this repository should not maintain |
| Shipping no highlighting    | The maintainer asked for this library by name, and unhighlighted Java in a Java repository's own documentation is a poor reading experience |
