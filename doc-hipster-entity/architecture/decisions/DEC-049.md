## Context

Step 3.8 built the dependency-graph page: `hipster-ioc/hipster-ioc-graph/` bundles a `jsx6` application with Bun
and writes **one self-contained HTML** into the module's derived subtree
(`hipster-ioc/hipster-ioc-test/.jcodebuddy/metadata/hipster-ioc/graph.html`), with the generator's `contexts.json`
**inlined** because a `file://` page may not fetch a sibling. The page renders contexts as blocks, but **clicking
one does nothing**: it has no source positions, and it does not call the host.

The ROADMAP lists three things as not built — "editor-agnostic context navigation", an "embedded light HTTP server"
for the graph, and the browsable page. The third now exists, and the exploration of 2026-10-09 (plan commits
`f32d430`, `3f3c0f4`) established that the first two need no new mechanism, because the webview suite already
provides both halves:

- **a frozen, versioned page contract** — `window.openFile(path, line, column)` plus `window.__jcbWebViewBridge`
  as the version probe (`InjectedBridge`, `VERSION = 1`), with the transport deliberately left to the host: an
  image beacon to `/open` for `webviewd`, a `JBCefJSQuery.inject(...)` call for JetBrains, `postMessage` for a
  mirroring host. Under it sit `EditorHost.openFileAt` (one method per host), `Navigator` (the one funnel: rate
  limit → resolve → jail → host), `LocationFragment`/`LocationResolver` (the location grammar of step 9.7), and
  `LspHost`, which is editor-agnostic by construction through `window/showDocument`;
- **a served HTTP path for a process that is not the browser** — `webviewd` registers `GET /open` with
  `filePath`, `line` and `column`, answered with `200`, `400` (no path), `403` (outside the project), `404` (a
  location the file does not have), `405` and `429` (rate-limited). So a live application does not need a custom
  agent on our side.

What was missing is the **join**, in two places:

1. **The page's model has no positions.** `contexts.json` carries a context's name, implementation, dependencies
   and beans — no path and no line. `.jcodebuddy/index/classes.json` (DEC-029) carries `path`, `line`, `kind`,
   `relations`, `members`, `annotations` per **fully qualified name**, and it sits one `../index/` away from the
   page. The join was verified against the real files rather than assumed: `hr.hrg.hipster.ioc.test.CtxMain` →
   `src/test/java/hr/hrg/hipster/ioc/test/CtxMain.java`, declaration line **7**, and
   `hr.hrg.hipster.ioc.test.CtxMainImpl` → `CtxMainImpl.java`, declaration line **12**. It does not cover
   everything: `contexts.json` records the bean `mapper` with the type **`ObjectMapper`**, and the index is keyed
   by FQN, so a simple name is not resolvable through it at all.
2. **The page does not call the host, and cannot be reached by one.** A `file://` document has no injected bridge,
   so a page that navigated unconditionally would be broken for the person who double-clicks it — which is the
   standalone rule root `AGENTS.md` § 2 states ("a UI must be usable standalone even without webview, the webview
   is not a requirement for many tools").

The maintainer's requirement of 2026-10-09 decides the shape: **both integration paths stay open** — the page must
be navigable **served over HTTP** *and* **inside an IDE host** — "as I want to enable integrating into the IDE for
example from a live app, so I need both paths open". Neither path may be closed, and neither needs to be invented.

## Decision

1. **The graph page becomes a consumer of the webview page contract, and nothing more.** It calls
   `window.openFile(path, line, column)` **after feature-detecting it**, and defines no navigation API, no route,
   no capability key and no second attribute of its own. The transport under the call stays the host's business,
   exactly as the frozen contract intends.

2. **Source positions are joined at build time from the module's class index, not fetched at view time.** The
   page's build (`hipster-ioc-graph/src/build.js`) reads `../index/classes.json` beside the generator's
   `contexts.json` and extends the inlined model with `{path, line}` per FQN. Build-time is forced by the
   standalone rule — a `file://` page cannot fetch — and it keeps the page's existing property that nothing is
   fetched when it is opened.

3. **A name the index does not resolve is reported, never guessed and never dropped.** The model gains a
   `locationless` list beside the `missing` list `model.js` already keeps for a dependency naming a context that
   is not in the file; the page shows the absence, and a build that silently omitted the entry would be the
   failure DEC-040's D4 names ("an omission is reported as a limit, never answered as *none*"). Concretely today:
   both context FQNs resolve; the bean type **`ObjectMapper` is reported** rather than mapped, because the index
   holds no row for a simple name and inventing a candidate would be the confident-wrong-answer failure the same
   rule forbids.

4. **Bean type resolution is settled as the page's rule, and the generator half stays open.** The page resolves
   an FQN **only**; it does not resolve simple names through imports, and it never guesses among same-simple-name
   candidates. If bean navigation is wanted, the fix is upstream — `IocGeneration` emits the bean's **FQN** in
   `contexts.json`, a projection change a consumer may ask for — and that is scheduled as a separate, optional
   step (3.11c) rather than assumed here. Until then a bean is **named but not navigable**, and the page says so.

5. **Both integration paths are reused, and the second is now documented.**
   - **in a host**: the page is served through `/page/`, gets the bridge appended, and calls `window.openFile`;
     the transport differs per host and the page never learns which one it is talking to;
   - **from outside the browser**: a live application calls `GET /open?filePath=…&line=…&column=…` directly. It
     discovers the port and the token through the project's **published host state**: read
     `<project>/.jcodebuddy/webview/host.json`, which names the port and a `tokenPath` **but never the token**;
     probe that port with `GET /health` (credential-free) and require `plugin`, `port` **and** `project` to name
     the directory being served; fall back to the project's committed default
     (`<project>/.jcodebuddy/conf/webview.json`) when no descriptor exists or the probe fails. A descriptor
     **outlives the process** that wrote it (DEC-032/033), so the probe — never the file — is what answers "is a
     host there". The **token is the file at `tokenPath`**, read only for the routes that require it; a host may
     publish an empty `tokenPath` (the VS Code host keeps its token in editor settings), and then a live
     integration must be told the secret rather than discover it. `Navigator`'s rate limit (20 per 20 s) is part
     of the contract a caller must respect, not an obstacle to route around.

6. **The navigation spelling is the position, not a fragment.** The graph's join yields a **file and a line**, so
   the page passes them through the three-argument call — the one spelling the frozen contract has always had,
   needing no amendment. The location grammar of step 9.7 (a member or region name in a `data-open` fragment) is
   the *link* spelling and is already reachable for a live caller by putting the fragment inside `filePath`
   (`Navigator.open` splits it there, because the frozen contract calls that attribute a path). This decision
   therefore adds **no new argument** and does not bump `bridgeVersion`.

7. **"Editor-agnostic" is an acceptance test, not a claim.** A page that works in one host and not another means
   this answer was wrong; the test is written out in **Acceptance criteria** below.

## Alternatives considered

- **An embedded HTTP server in `hipster-ioc`** (the ROADMAP's literal wording). Rejected: the suite already has one
  host per project that serves pages and navigates (`webviewd`), with a port claim, a published descriptor, a
  token, a jail and a rate limit — a second server would be a second way for one page to be served and a second
  bridge to keep in step, and the module's own `README` would then document a port the maintainer never chose.
- **A second navigation abstraction for the graph** (a bespoke `ctx.open` or a postMessage protocol). Rejected:
  the contract is frozen and versioned precisely so a page does not learn which host it is in; a second
  abstraction would have to be implemented by every host, and the page would stop working the day a host forgets.
- **Fetching `classes.json` at view time.** Rejected: `file://` refuses a sibling fetch (measured in step 3.8),
  so the page would work only when served — closing the standalone path the maintainer requires to stay open.
- **Resolving a simple bean type against the index anyway** (matching `ObjectMapper` by simple name). Rejected:
  the index is keyed by FQN and a simple name may have several rows; a guess is a wrong jump that looks like a
  working link, which is the failure mode DEC-040's D4 and DEC-016's "never a guessed position" exist for.
- **Marking this item `[-]`** (dropping navigation). Legitimate per step 3.11's own Done-when, and rejected
  because the join is small, the data already exists next door, and both transports are already built.

## Consequences

- Positive: the graph page gains source navigation **without a new API, server or host**; the live-application
  entry point (`/open` + the port/token discovery story) is documented where an integrator reads, which it was
  not before; the standalone property is preserved by construction; and the same page is exercised by two hosts,
  which is what makes "editor-agnostic" a test rather than a slogan.
- Negative: the page's `locationless` output will list bean simple names until (and unless) the generator emits
  FQNs, so the page shows a limitation rather than hiding it; the join adds a build-time read of a derived file,
  so the graph build fails loudly when the index is missing or older than `contexts.json` (that failure is
  deliberate: a page built from a stale index points at lines that moved).
- The `InjectedBridge` javadoc was corrected on 2026-10-09 (there is no `POST /api/v1/open`; navigation is
  `GET /open`), because a reader following that comment found a 404 — it is the entry-point documentation the
  live-app path needs (plan step 3.11b).

## Out of scope

- The graph's **diagram layout**, `nodditor` capabilities and any further page UI (step 3.8's subject).
- The **generator emitting bean FQNs** — scheduled as optional step 3.11c, taken only if the maintainer wants
  beans navigable.
- Any **change to the frozen page contract** (`window.openFile`, `bridgeVersion`, `/open`'s parameters).
- A **navigation API for the sidecar/LSP** beyond what `LspHost`/`window/showDocument` already does.

## Acceptance criteria

1. The page opened as a plain `file://` document **still works**: it renders, nothing is fetched, and it says
   navigation needs a host rather than failing when `window.openFile` is absent.
2. The **same unmodified page** navigates in a host-served context — served by `webviewd`, a click lands the caret
   on the joined line — and in a **JetBrains** tool window, with the difference confined to the transport the host
   injects.
3. **From outside the browser**, `GET /open?filePath=…&line=…` navigates to a known file and line, with the port
   and token resolved by the discovery order in Decision 5, and the documented statuses are what a caller sees.
4. A context, implementation or bean FQN the index does not know appears in the page's `locationless` report
   (never silently absent, never aimed at line 1), and `bun scripts/ioc-gen.js` plus the graph build remain green
   as a no-op when nothing changed.
5. The javadoc/documented route set contains **no** `POST /api/v1/open`, and `webview/README.md` or the host API
   document names `GET /open` as the outside-the-browser entry point.
