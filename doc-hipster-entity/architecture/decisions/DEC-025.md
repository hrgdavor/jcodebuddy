# DEC-025: Field-enum compaction is a deliberate, acknowledged ordinal migration

## Context

DEC-023 makes a generated field enum an **append-only ordinal ledger**:
its constant order is a persisted positional layout, a removed field's
constant is kept as a tombstone, and a new constant is always appended.
That rule is what stops a stored `Object[]`, a change-tracking bitset, a
JSON patch or a JDBC row from being silently reinterpreted.

It also means the enum only ever grows. A field that was designed,
shipped, and later removed leaves a `@Deprecated` tombstone behind
forever: it occupies an ordinal, a nullable slot in the positional
array, and a component in the generated record. For a view that has
churned a few times this is visible — `fieldCount` counts fields nobody
can read, `get(int)` returns dead slots, and the generated record's
constructor takes arguments no caller can supply meaningfully.

That is the correct trade while data exists. It stops being the correct
trade once it does not: a project that has drained its positional
arrays, replayed or discarded its queued patches, and rebuilt its
snapshots can reclaim the ordinals. Doing so is a **migration**, not a
cleanup, and it is the only operation in this subsystem that deliberately
mutates a persisted ordinal layout.

The failure mode this decision is written against is compaction that
happens **by accident or by habit**: a generator "tidying" a ledger
during a normal pass, a script run from a copy-pasted command, or a
single `--force`-style flag typed from muscle memory on the wrong tree.
Each of those turns a documented layout into a silent one, and the
damage is only discovered when a stored array is read back with the
wrong field in every slot after the change.

## Decision

### 1. Compaction is never a default behaviour

No generation pass compacts. The generator's ledger planner keeps
tombstones and appends new constants (DEC-023); compaction is reachable
only through the dedicated `enum-compact` subcommand of the tooling's
entry point, and never through a flag on a normal run. A subcommand was
chosen over a flag precisely so that it cannot be reached by adding an
argument to an existing command line.

### 2. Two acknowledgements, neither implied by the other

The command refuses to act — exit code `2`, nothing written — unless
**both** of these are present:

| flag | what the operator is asserting |
| --- | --- |
| `--allow-reorder` | the ordinal layout of this enum may change |
| `--acknowledge-drained-data` | no persisted positional array, JSON patch or snapshot survives that was built on the old layout |

The redundancy is the point. `--allow-reorder` is a statement about the
*schema*; `--acknowledge-drained-data` is a statement about the *data*.
A run that has drained its data but has not thought about the layout is
as unsafe as the reverse, and one flag invites typing the other by
reflex. `--target` restricts *which files* are considered and implies
nothing.

### 3. Only tombstones are dropped, and only when they are recognisable

A constant is removed only when it is **both** annotated `@Deprecated`
**and** declares `retired()` returning `true` — exactly the shape the
generator emits for a tombstone. Either half alone is not enough:

- a `@Deprecated` constant without `retired()` may be a developer
  documenting an ordinary deprecation, and dropping it would move every
  ordinal after it;
- a `retired()` returning `true` without `@Deprecated` is a shape the
  generator does not emit, so it is treated as a hand edit and left for
  a human.

A file that cannot be parsed is refused rather than rewritten. A partial
compilation unit has no reliable constant list, and rewriting one is
strictly worse than leaving it alone.

### 4. Compaction removes; it never shuffles

The compacted constant list must be a **subsequence in order** of the
original. The command verifies exactly that before writing, and refuses
the file if it fails.

The verification is deliberately **not** the R1 checker's comparison.
The checker reports a removal as `enum_constant_removed`, which is its
whole purpose: a normal generation pass must never drop a constant from a
marker-carrying enum. Compaction is the single sanctioned exception, so
asking the checker here would refuse the one operation it exists to
allow. What the checker is still good for is the *report*: run against
the pre-migration baseline it names every dropped constant, which is
precisely the migration record, and from the migration commit onward it
is clean again.

### 5. The report is the migration record

Every dropped constant is reported with the ordinal it held, and every
surviving constant whose ordinal changed is reported with `from → to`.
That report, plus the generator pass that follows the compaction, is the
migration record.

`allFields` in the generated `*.metadata.json` carries a field's name,
type, classification and the views that declare it — but **no ordinal**,
so there is no ordinal-shaped value in it to rewrite. What changes is its
membership: a compacted-away field has no accessor any more, so the next
generation pass drops it from `allFields` naturally. The procedure is
therefore *compact → regenerate → commit*, and the regeneration diff is
the reviewable artifact.

### 6. The enum stays a ledger

Compaction removes the `entityFieldEnum:true` marker from nothing. The
compacted enum still carries DEC-021's header and the marker, so it is
still guarded by the R1 checker from that point on: the reclaimed layout
is immediately frozen in its new shape. Reclaiming ordinals is a
one-time migration, not an opt-out.

## Consequences

- A project can reclaim ordinals, but only by an explicit, twice-acknowledged,
  separately-invoked migration whose every movement is printed.
- The compaction command is testable in the direction that matters: the
  tests are dominated by what it refuses (missing acknowledgement, a
  deprecated-but-not-retired constant, a marker-less enum, an unparseable
  file, build outputs and second checkouts), not by the happy path.
- Compaction's output is not byte-identical to the generator's canonical
  emission — the file is reprinted through a parser. The documented
  procedure therefore ends with a generation pass, which rewrites it
  canonically, and the committed diff is that pass's output.
- Tombstones are the only thing compaction reclaims. A field that was
  never released is never compacted away, and there is no "compact to
  the interfaces" mode: that would be a silent renumbering with extra
  steps.
- **Compaction is not reversible by re-adding the accessor.** Once a
  tombstone has been compacted away, restoring the field it stood for
  creates a *new* constant appended at the end, with a new ordinal and a
  new slot. The old ordinals are gone from the ledger, so the data that
  was written under them cannot be reached by putting the accessor back —
  which is exactly why decompaction is not offered as a mode and why the
  drained-data acknowledgement is about data that no longer exists rather
  than data that could be re-read later. A migration that needs the field
  again extends the compacted ledger rather than undoing the migration;
  `CompactionRoundTripTest` asserts that sequence.
- `hipster-entity-core`, `-jackson` and the runtime are untouched by this
  decision. Compaction edits generated source and nothing else.

## Follow-up

- The exclusion list for the directory scan (`target/`, `.kilo/worktrees/`,
  `tmp/`) is shared in spirit with the R1 order checker's. A third
  location holding a copy of the tree — the untracked `tmp/` directory
  noted in `plan.dsflash.notes.md` D-13 — was added to both after it was
  found to defeat a repo-scoped check.

## Out of scope

- Compacting a ledger whose data has *not* been drained. That is not a
  mode, it is the failure this decision exists to prevent.
- Migrating stored arrays. The command reports what moved; turning that
  into a data migration for a particular store is the operator's job and
  depends on the store.
- Reclaiming ordinals in a marker-less enum. Such an enum has no
  committed ledger; a normal generation pass bootstraps it (§ 4.5/G7 of
  the execution plan), which is already a rebuild.

## Acceptance criteria

1. `enum-compact` with neither acknowledgement, or with only one, exits
   `2` and writes nothing.
2. A tombstone in the middle of a marker-carrying enum is dropped, the
   survivors keep their relative order, and the report names every
   ordinal that moved.
3. A `@Deprecated` constant that does not declare `retired() == true` is
   not touched.
4. A marker-less enum and an unparseable file are skipped with a named
   reason, and are not rewritten.
5. The compacted constant list is a subsequence in order of the original;
   the command verifies this itself, and the R1 checker's verdict against
   the pre-migration baseline names exactly the dropped constants.
6. The compacted enum still carries `entityFieldEnum:true`.
