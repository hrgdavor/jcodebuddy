# DEC-012: Update-array and change-tracking semantics

- Revised: [Revision — no previous value is kept (supersedes D2)](#revision--no-previous-value-is-kept-supersedes-d2) — the `previousValue` half of the original change-tracking model is reversed; the no-op rule below is unchanged

## Context

Builder workflows need efficient mutable storage during composition and update flows. The project needs clear semantic models for overwrite, presence tracking, dirty flag behavior, and patch-oriented persistence.

## Decision

Provide two array-backed storage primitives with explicit change-tracking semantics:

**EntityUpdateArray (baseline):**
- Store latest assigned values by property ordinal
- Overwrite semantics: last write wins
- No intrinsic knowledge of whether value changed from original
- Suitable for full replace workflows

**EntityUpdateTrackingArray (tracking variant):**
- Track whether fields were touched during builder operations
- Enable patch-oriented writes and selective persistence
- Two specialized implementations based on field count:
  - `EntityUpdateTrackingArray64`: single `long` field for entities with fewer than 64 fields (no array allocation)
  - `EntityUpdateTrackingArray`: `long[]` for entities with 64 or more fields

**Dirty tracking behavior:**
- Touched flag tracked via bitmask indexed by field ordinal
- Explicit null assignment: touched bit set with null value
- Same-value assignment is a no-op: does not set the touched/updated bit
- Changed-value assignment sets the touched/updated bit

**Merge behavior:**
Explicit mode naming required to avoid ambiguity:
- Overwrite-all: incoming values always replace
- Non-null overwrite: only non-null incoming values replace
- Touched-only merge: only fields marked touched in source apply

## Accepted notes

All four storage classes implemented in `hipster-entity-core`:
- `EntityUpdateArray` — baseline overwrite semantics
- `EntityUpdateTrackingArray` — abstract base with bitmask change tracking
- `EntityUpdateTrackingArray64` — single `long` bitmask for ≤64 fields (concrete subclass)
- `EntityUpdateTrackingArrayLarge` — `long[]` bitmask for >64 fields (concrete subclass)

Factory method `EntityUpdateTrackingArray.create(ForNameOrdinal forNameOrdinal, F[] universe, Object... values)` selects the concrete variant automatically based on field count. Proxy handler (`UpdatableHandler` in `ArrayBackedViewProxyFactory`) routes `changes()` and `clearChanges()` to the tracking array; other zero-arg calls go through `FieldNameMapper`.

## Revision — no previous value is kept (supersedes D2)

**Status of this revision: accepted.** It reverses the *previous-value*
part of the original change-tracking model, i.e. D2's answer to its own
question — the "D2" resolution recorded in `plans__p1/plan.dsflash.md`
§ 4.2, whose decision-table row read:

> | D2 | Must `previousValue(ord)` exist? | **Yes** (§ 4.2). New `ChangeRecorder` in `hipster-entity-core`, where the contract already lives (S3 deferred). Previous values are **shallow references** — documented and pinned by test. |

The answer is now **No**: `previousValue(ord)` does not exist, and neither
does the `ChangeRecorder` that stored it.

Every rule below that concerns *whether* a field is marked — the no-op
rule, explicit null, the bitmask — is **unchanged** and still in force.
Note that D2 is *not* the unrelated "shallow-reference hazard" (assignment
to a reference marks the field, mutating the pointee does not), which is a
property of shallow bit tracking and is untouched by this revision.

### What was reversed

The tracker used to remember the value a field held before its first
write, and exposed it:

- `ViewChangeTracking.previousValue(int)` and `hasPreviousValue(int)` —
  **removed**; they do not exist anywhere.
- `ViewChangeTracking.diff()` — **renamed** to `changedValues()`, which is
  now the only name for the operation.
- `FieldChange<E>` — was
  `record FieldChange<E>(E field, Object previous, Object current)`, is now
  `record FieldChange<E extends Enum<E>>(E field, Object current)`. The
  `previous` component is gone.
- `hr.hrg.hipster.entity.core.ChangeRecorder` — **deleted**. It existed
  only to store previous values, together with a parallel `boolean[]` so a
  recorded `null` was distinguishable from "nothing recorded".
- `EEnumSetBuilder` — lost `addOrdinalChange(int, Object, Object)`,
  `previousValue`, `hasPreviousValue` and `clearPreviousValues`. It is
  now a **plain ordinal set**: `addOrdinal`/`removeOrdinal`/`has`/
  `toImmutable`, and no value state at all.
- The Jackson API followed: `EntityJacksonChangeSerializer.serialize(tracking, gen, boolean includePrevious)`
  is now `serialize(tracking, gen)`, and
  `EntityJacksonMapper.toJsonChanges(meta, tracking, writer, boolean)` is
  now the three-argument form.

### Why

Ownership. The old value belongs to whoever still holds the instance the
write started from. A tracking mutable is built *from* another mutable or
*from* an immutable, and that source is the caller's object — the tracker
never owned it and only copied it. Storing a copy meant:

- **duplicated state** the caller already holds, with "did this change?"
  answerable from two places that can disagree;
- a **stale shallow reference**: a value copied at first write keeps
  reflecting later in-place mutation of a `Map`/`List`, so the reported
  "previous" value could silently be a value the field never held at the
  time it was overwritten. The old design had to document this as a hazard;
  with no stored previous value the hazard is **impossible by
  construction**, not merely documented.

### Where the comparison actually happens now

The DEC-012 no-op rule (compare before marking) is **unchanged**, but the
comparison moved **to the write site**:

- the generated tracking setter is
  `if (!java.util.Objects.equals(this.firstName, value)) { this.firstName = value; mf.addOrdinal(1); }`;
- `EntityUpdateTrackingArray.set(int, Object)` compares the slot it holds
  before marking.

### Accepted consequences

1. **An equal write marks nothing** — unchanged: a write whose value
   equals the one the field currently holds marks nothing.
2. **A write back to the original value leaves the field marked.** There
   is no stored baseline that could unmark it. Relative to the state the
   tracker saw, the field *was* written with a different value, and that is
   the whole of the tracker's claim. This is the one behaviour a reader of
   the old model is most likely to get wrong, so it is stated flatly.
3. **"Does this differ from my baseline?" is a caller-side comparison.**
   The consumer compares the current instance with the baseline instance
   the caller still holds — the mutable was built from another mutable or
   from an immutable, and the caller owns both sides. `changedValues()`
   supplies the new half; the library supplies nothing for the old half,
   by design.
4. **No presence-flag array is needed for a written `null`.** The marked
   ordinal itself answers presence: a field never written is unmarked, a
   field written as `null` is marked and reports `current == null`. The
   `boolean[]` that existed to distinguish "previous value was null" from
   "nothing recorded" has no remaining purpose.
5. **The change set is a plain ordinal set.** `EEnumSetBuilder` carries no
   value state, which is what lets `changes()` / `changesBuilder()` stay
   two views over one piece of state (S5) instead of two structures to
   keep in sync.
6. **The patch document is a JSON Merge Patch of current values.** It is
   not an audit trail: `{"firstName":"Grace"}`, not
   `{"firstName":{"previous":"Ada","current":"Grace"}}`. A caller that
   wants old → new pairs builds that document itself from its baseline.

### What deep tracking keeps — the one baseline that remains

Reversing the value baseline does **not** reverse the collection
baseline. `ListChangeTracker` / `ListDelta` still detect add, remove and
reorder, and for that they retain an **identity** baseline — each entry's
`Identifiable.id()` — and never an element's field values.
`ListDelta.previousIndex()`, `identity()`, `kind()` and `fallback()` are
unchanged. Identity is not a copied value: it is the key the caller
already uses to recognise an entry, and without it a reorder is
indistinguishable from a removal plus an addition. See
[DEC-024](DEC-024.md).

## Consequences

- Provides efficient mutable storage without redundant boolean arrays (bitmask as canonical touched tracking).
- Supports both full-replace and patch-update workflows with the same interface.
- Compact single-word representation for common case (64 fields or fewer).
- Explicit merge modes prevent ambiguity in update semantics.
- Tight coupling between array variant and field count; transition between variants requires recreation.
- Adds memory and logic overhead versus baseline (EntityUpdateArray) due to change tracking.

## Out of scope

- Converter implementation or transformation pipeline (handled separately).
- Write-path SQL generation or query planning (integration layer concern).
- Diagnostics and validation beyond change-tracking state (covered by broader builder validation).

## Acceptance criteria

- `EntityUpdateArray` and `EntityUpdateTrackingArray` implementations MUST be available in `hipster-entity-core`.
- Bitmask-based touched tracking MUST be the canonical implementation for tracking arrays.
- Merge behavior MUST require explicit mode naming to avoid silent semantic mismatches.
- Storage variants MUST specialize for 64-field threshold to keep common case compact.
- No-op same-value assignment behavior MUST be clearly documented and tested.
