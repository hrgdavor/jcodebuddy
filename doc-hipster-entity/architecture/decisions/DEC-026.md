# DEC-026: `.jcodebuddy/` — the per-module output root, and its tracked/ignored split

## Context

JCodeBuddy writes more than source. A generator pass emits a metadata report,
the watch agent keeps a checksum cache and an audit trail of every edit it
applies, and a watched run drops further reports. Before this decision those
outputs were spread across two unrelated conventions:

| output | location before this decision |
| --- | --- |
| entity metadata report (generation pass) | `<module>/target/entity-metadata/` (at the time, written by a generator bound to `generate-sources`; that binding was later removed — see `hipster-entity-example/codebuddy.md` § 3) |
| entity metadata report (watched run, `EntityRegenerationWatcher`) | `<module>/target/entity-metadata`, system temp when no `pom.xml` was found |
| watch-agent checksum cache | `<root>/.watch/metadata/<toolSet>/metadata.db` |
| watch-agent audit trail | `<root>/.watch/metadata/<toolSet>/audit/<timestamp>_<action>/` |

Three problems follow from that.

**The locations are unrelated and undiscoverable.** `target/` is Maven's
directory, so a JCodeBuddy output that lands there is indistinguishable from
build output, is deleted by `mvn clean`, and carries no statement about what
it is. `.watch/` is the watch agent's private state directory. Neither name
says "JCodeBuddy produced this", and neither is documented anywhere a reader
of a converted module would look.

**Derived output and valuable output are mixed.** A metadata report is
reproducible from source; an audit trail records *what an agent changed and
why*, which is not reproducible and is sometimes the only record of a
deliberate edit. Filing both under `target/` (deleted on `clean`) or both
under an ignored dot-directory treats them as equally disposable, which they
are not.

**There was no rule about what may be committed.** Nothing said whether a
metadata report belongs in git. A project that wanted the report as a
reviewable contract had no defined place to put it, and a project that did
not had no defined place for it to be ignored.

The pressure behind the decision is that `JCodeBuddy` is a code generation
tool, so its output layout is part of what it offers. A layout that a
consumer cannot predict is a layout they will work around.

## Decision

### 1. `.jcodebuddy/` is per-module, not per-repository

A `.jcodebuddy/` directory **MUST** be read as the marker "this module applies
`project-automation`". It is the output root of the modules that use
JCodeBuddy, and only of those.

- A module that uses JCodeBuddy **MUST** have its own `.jcodebuddy/`, beside
  its `pom.xml`.
- A module that does not use JCodeBuddy **MUST NOT** have one, and no tool
  **MUST** create one on its behalf.
- The repository root **MUST NOT** carry a `.jcodebuddy/` by default. It
  **MAY** do so in the rare case of a repo-wide generator; with no such
  generator, the root has none.

At the time of writing the only converted module is `hipster-entity-example`.

### 2. Resolution: the marker wins over `pom.xml`; `pom.xml` is only a fallback

A tool that needs a module's output root **MUST** walk up from the source root
looking for the nearest `.jcodebuddy/` directory, and **MUST** fall back to the
nearest `pom.xml` only when no marker exists anywhere above the source root. A
plain `pom.xml` closer to the sources **MUST NOT** shadow a marker further up:
a freshly converted submodule of an aggregator has exactly that shape.

When neither is found — a source tree outside any Maven project — the report
**MUST** go to a location outside the tree being watched. The system temporary
directory is the current choice. The invariant this protects is that a watched
run never drops untracked `*.metadata.json` files next to the entities, where
they could be mistaken for a source change.

The resolved location is exposed as `EntityRegenerationWatcher.JCODEBUDDY_DIR`
and `EntityRegenerationWatcher.METADATA_ENTITY_DIR` so the literals appear
once.

### 3. The subfolders are fixed, and each says what it is for

> **Amended (2026-09-26):** the palette is no longer fixed. `conf/` is reserved and tracked; every
> other subfolder is derived and ignored by default, and projects may add subfolders without
> amending this decision. See "Amendment — `conf/` is reserved, and the palette is open" at the end
> of this document, which is current where it disagrees with the list below.

    .jcodebuddy/
    ├── README.md      the layout contract for that module
    ├── context/       module-scoped specs and invariants for its generators
    ├── metadata/      derived, machine-written
    │   ├── entity/    <Entity>.metadata.json
    │   ├── watch/     the watch agent's metadata.db and audit/ trail
    │   └── project/   whole-project metadata indexes (index.fury and friends)
    ├── index/         derived, machine-written: the module's index
    │   └── files.json id → module-relative source path
    ├── reports/       run records kept for a human reader (gates, baselines)
    └── agent-state/   scratch: run logs, probes, temp copies

| subfolder | purpose | who writes it |
| --- | --- | --- |
| `context/` | hand-written material belonging to this module's generators: specs, invariants, naming contracts, examples of acceptable output | a human |
| `metadata/entity/` | one `<Entity>.metadata.json` per entity and view | `EntityMetadataGenerator` (a generation pass — manual or watched) |
| `metadata/watch/` | `<toolSet>/metadata.db` checksum cache, and `audit/<toolSet>/<timestamp>_<action>/{manifest.json,summary.md,before/,after/}` | `MetadataCache`, `AuditManager` |
| `metadata/project/` | whole-project metadata passes, reserved so a project-wide pass has a defined home instead of inventing a root directory | whole-project passes |
| `index/` | the module's index: the addressing tables a metadata document references and (reserved) content hashes for watcher/incremental use | `ModuleFileIndex` (the same generation pass that writes `metadata/entity/`) |
| `reports/` | records of runs that are evidence rather than noise | a human, from tool output |
| `agent-state/` | disposable run logs, probes, temporary copies | any tool |

Each subfolder carries a `README.md` stating its purpose, so the taxonomy is
readable from the tree itself.

### 4. Three track policies, encoded in `.jcodebuddy/.gitignore`

> **Amended (2026-09-26):** the default is now **closed** — everything under `.jcodebuddy/` is
> ignored except the top-level `README.md`/`.gitignore` and the reserved `conf/` subtree. `context/`
> and `reports/` are no longer tracked *by default*; a module that wants them tracked writes the
> opt-in, which the example module does. The mechanism below (the `!` opt-in, the narrowness rule)
> is unchanged. See the final amendment.

The ignore file, not this prose, is the authority.

| subtree | policy | why |
| --- | --- | --- |
| `context/`, `reports/` | **tracked (MUST stay visible)** | the "why" and the evidence; small, text, reviewable, and the part that is lost when untracked |
| `metadata/` | **ignored by default (MAY be opted in)** | machine-written and regenerable, so a whole-tree commit is churn — but a project that wants its metadata as a **contract** opts a subtree back in with a `!` rule |
| `index/` | **ignored by default (MAY be opted in)** | derived like `metadata/`, and **coupled to it**: a metadata document names source files by ids that resolve only in `index/files.json`, so an opt-in for the metadata subtree **MUST** carry `index/` too, or the committed documents reference an uncommitted table |
| `agent-state/` | **ignored (MUST NOT be committed)** | scratch, never a deliverable |

The default-ignored subtree is deliberately not an all-or-nothing choice. The
opt-in that makes a subtree tracked looks like this, and it is the documented
escape hatch rather than a new convention:

```gitignore
!metadata/entity/
!metadata/entity/**
```

Because the two are coupled, a project that opts the metadata subtree in adds
the index in the same breath:

```gitignore
!index/
!index/**
```

Two details of the encoding are normative, because both were observed as real
failure modes:

- Each ignored subfolder keeps a tracked `README.md` (`!metadata/**/README.md`
  after `metadata/**`). An entirely ignored directory vanishes from
  `git status`, so without this the tree cannot document itself and a reader
  cannot tell an empty subtree from an absent one.
- The opt-in rule **MUST NOT** be written so broadly that it would carry
  generated `.java` files. A hand-run generator pass that omits `--java-out`
  writes generated source into its report directory — that debris has been
  seen in this repository. Generated `.java` belongs under `src/main/java`
  (§ 5), so the report directory is not a place any source file may be
  committed from. The generation pass itself emits only `.json`.

### 5. Generated `.java` is **not** in `.jcodebuddy/`

This decision moves reports, never the generated program source. Generated
Java **MUST** stay under `src/main/java`, regenerated in place, because
DEC-019 and `AGENTS.md` § 1 require generated wiring to be committed,
IDE-navigable source. A dotted directory is conventionally tool state; putting
program source there would break jump-to-definition and find-usages for a
developer with a stock IDE.

Correspondingly, `--java-out src/main/java` is not a detail a consumer may
omit, and `hipster-entity-example/README.md` documents the flag as the one
adopters most often forget. `.jcodebuddy/` holds the *reports about*
generation, not the generated code that is part of the program.

### 6. Tool output is excluded from every scanner that walks a converted module

Any file filter, scanner or directory walk that a generator, watcher or
validator uses over a converted module **MUST** exclude `.jcodebuddy/**`. The
report now lands inside the module that the entity watcher watches, so a walk
that does not exclude it re-enters its own output.

The sites carrying this exclusion are the entity watcher's `FileFilter`, the
watch agent's `ToolSetAgent` (both the directory skip and the path check),
`ProjectScanner`, `ProjectWatcher`, and the two enum tooling checkers
(`EnumConstantOrderCli.readWorkingTree`, `EnumCompactionCli.isExcluded`).

## Amendment — `index/` joins the fixed subfolder list

DEC-028 gave the metadata a central, per-module addressing table: a `<Marker>.metadata.json` no
longer contains a source path at all — it names each file by a short **id**, and
`index/files.json` is the one place that states the path behind that id. The table therefore
needs a defined home, and § 3's fixed subfolder list gains one:

> `index/` — the module's index: the addressing tables a metadata document references and
> (reserved) content hashes for watcher/incremental use.

The rules attached to it:

- **It is derived, and ignored by default, exactly like `metadata/`.** It is machine-written by
  the generation pass (`ModuleFileIndex`) and reproducible from the sources, so committing a
  whole changing tree of it is churn (§ 4).
- **The opt-in is coupled and MUST be written together.** A metadata document that is committed
  while the table that resolves its ids is not is a document full of dangling references, so a
  project that re-includes the metadata subtree **MUST** re-include `index/` in the same
  `.gitignore` — the two snippets above, side by side. A one-sided opt-in is a broken contract,
  not a partial one.
- **It keeps a tracked `README.md`, like every other subfolder** (§ 3, § 4). The pass creates
  `.jcodebuddy/index/README.md` when it is absent and **MUST NOT overwrite** an existing one:
  the file is tracked, i.e. owned by a human, and clobbering it on every pass would silently
  revert an edit — the failure mode DEC-020 forbids for generated blocks. Only an index that
  lives inside a real `.jcodebuddy/` gets that README; the fallback location a report directory
  outside any `.jcodebuddy/` produces (`<report dir>/index/`) holds `files.json` alone.
- **It is the module's, never the repository's.** The paths in it are module-relative, so a
  repository-wide table would be meaningless in every module but one (§ 1).

DEC-028 owns the table's format, its `format` version, the id scheme, and the reserved tables
(`hashes.json` and per-artifact dependency edges) that the directory exists to make room for.

## Alternatives considered

- **One `.jcodebuddy/` at the repository root for all modules.** Rejected. It
  makes `JCodeBuddy` a repository-wide convention rather than a per-module
  tool, and it forces every module's output into one tree regardless of which
  module actually uses the tool. It also creates the question this decision
  exists to avoid: what does the directory mean for a module that does not use
  JCodeBuddy at all.
- **Keep `<module>/target/entity-metadata`.** Rejected. `target/` is Maven's,
  a `clean` deletes it, and nothing in the name says the report is a
  JCodeBuddy artifact or that a project may want to commit it.
- **Generalise `.watch/` and put everything there.** Rejected. `.watch/` is
  the watch agent's state directory; it does not cover the Maven-time
  generator, and naming the generator's reports after the watcher would be
  wrong for every project that does not run the agent.
- **Track nothing, ignore everything.** Rejected. It throws away the audit
  trail and the metadata-as-contract option, which are the two things a
  consumer of a code generator most often wants in version control.
- **Track everything, including `metadata/`.** Rejected as a default. A
  regeneration rewrites the reports, so every pass would produce a diff; the
  interesting diffs would be buried. Kept as a per-project opt-in instead.
- **Put generated `.java` under `.jcodebuddy/` too.** Rejected outright;
  see § 5 and DEC-019.
- **A central registry of output locations.** Rejected. The marker directory
  *is* the registry: adding a module means adding its directory, and no
  manifest can drift from the tree.

## Consequences

- Output location is predictable and self-describing: a `.jcodebuddy/`
  directory means "this module uses JCodeBuddy", and the subfolder a file is
  in states whether it is curated, derived or disposable.
- Resolution order is total: marker, then `pom.xml`, then temp. A converted
  module always wins over an aggregator, and a tree outside any project is
  still safe.
- A normal build no longer leaves untracked files anywhere: the report lands
  in an ignored subtree, and generated `.java` continues to be rewritten in
  place under `src/main/java`.
- The split is reviewable per subtree. Opting `metadata/entity/` into git is a
  one-line change whose consequence is confined to that subtree.
- The tree is self-documenting: every subfolder has a `README.md` that survives
  in git even where the contents do not.
- **Negative:** the default ignoring of `metadata/` means a report that
  *should* be reviewed is invisible until a project opts in. The opt-in rule
  is the release valve, and § 4 requires it to be written narrowly.
- **Negative:** a marker can be deleted by mistake, at which point resolution
  silently falls back to the nearest `pom.xml` and the output moves with no
  error. This is a deliberate fail-soft choice; a consumer that wants the
  invitation for its own module to be honoured deliberately has to keep the
  directory in version control, which the tracked `README.md` encourages.
- **Negative:** resolution walks the filesystem per generation pass. It is
  bounded by the directory depth and happens once per pass.
- Known residue, recorded rather than hidden: a report directory can hold
  stale `.java` debris from an earlier hand-run pass that omitted
  `--java-out`. § 4's narrow opt-in rule ensures it can never be committed
  from there, and deleting the residue is the fix.

## Out of scope

- **Repository-level planning, research and knowledge documents.** Plans,
  specs, `docs/`, `doc_knowledge/` and `doc_research/` are agent and human work
  products, not JCodeBuddy tool output. They are not moved into `.jcodebuddy/`
  and this decision says nothing about their layout.
- **Deleting existing scratch.** `tmp/`, `sync_test/`, `test_sort/` and
  `native-image.log` are unaffected by this decision.
- **`target/`, Gradle `build/`, and `.kilo/`.** Build-tool output and
  tool configuration respectively; only JCodeBuddy's own outputs move.
- **Cleanup of the pre-existing stale `.java` debris** described under
  Consequences. The report tree is correct without it.
- **The `project-automation` module's own code layout.**
- **A repo-wide `.jcodebuddy/`.** Not needed today; § 1 permits it if a
  repo-wide generator ever appears.

## Acceptance criteria

1. Running the example module's generation pass (`bun scripts/gen.js`; the module POM's
   explicit, phase-less `exec:java` goal; or a watched run) writes
   `<module>/.jcodebuddy/metadata/entity/*.metadata.json`, and no
   `.metadata.json` remains under any `target/`. No Maven build writes it: the
   generator is not bound to a lifecycle phase.
2. `EntityRegenerationWatcher.Config.defaultReportDir(sourceRoot)` returns
   `<marker>/.jcodebuddy/metadata/entity` when the marker is present —
   including when a plain `pom.xml` sits closer to the sources — and falls
   back to the nearest `pom.xml`'s module root when it is absent.
3. A watched run's report directory is never inside the watched source root.
4. The watch agent writes its cache to
   `.../metadata/watch/<toolSet>/metadata.db` and its sessions under
   `.../metadata/watch/audit/<toolSet>/`.
5. A green build over a converted module leaves no new untracked file in the
   working tree.
6. `git add -A` on a converted module stages only its `.jcodebuddy/README.md`,
   `.jcodebuddy/.gitignore` and the subfolder `README.md` files — no
   `.metadata.json`, and no generated `.java`.
7. Every scanner, filter and walk listed in § 6 excludes `.jcodebuddy/**`, so a
   pass that writes a report does not observe its own output as a change.

## Amendment — the table inside `index/` is now `classes.json`

The `index/` subfolder keeps the meaning and the track policy the amendment above gave it: it is the
module's own derived subtree, ignored by default, opted into git together with `metadata/`, and its
tracked `README.md` is created when absent and **never overwritten** (DEC-020's rule for a human-owned
file). What changed is the table it holds. DEC-028's readable id → path table `files.json` is replaced by
**DEC-029's class index**:

> `index/` — the module's index: the class index a metadata document references, and its
> working-tree sidecar.

- **`classes.json` is the addressing table.** One row per **type** the module compiles, keyed by the
  type's **fully qualified name**, each row carrying the declaring file's module-relative `path`, its
  `size` and `checksum`, the `hashCalculatedAt` instant that checksum was calculated, and the type's
  `kind`, sorted `modifiers`, `line`, `depth` and `enclosing`. Every `file` value in a
  `<Marker>.metadata.json` is an FQN that resolves here, so § 3's and § 4's rule — **a path is stated
  once, in `index/`, and nowhere else in the metadata tree** — is unchanged; only the spelling of the
  reference changed. The layout line in § 3 therefore reads `classes.json` where it says `files.json`.
- **`mtimes.json` is the sidecar, and it is ignored like the rest of the subtree.** FQN → the file's
  last-modified time in epoch milliseconds. It exists because an `mtime` is a property of a *working
  tree* and cannot survive a checkout: writing it into a table a project may commit would make the
  committed table differ from a regenerated one on every machine (DEC-029 § 6). A watcher may use it as a
  cheap pre-filter; nothing may treat it as a correctness input, and a missing or unreadable sidecar
  simply costs a full hash. It is derived output and carries no `README.md` of its own.
- **The file name inside the fallback directory changed with the table.** When the report directory is
  not inside a real `.jcodebuddy/`, the fallback is `<report dir>/index/classes.json` (plus
  `mtimes.json`), and it still gets **no** `README.md` — a fallback `index/` is not a DEC-026 subfolder,
  which is what keeps "a report directory holds JSON only" true.
- **The `.gitignore` rules do not change.** `index/**` with `!index/**/README.md` ignores whatever tables
  the subfolder holds, so the two opt-in snippets above remain exactly as written and stay **coupled**:
  a committed metadata document whose FQNs resolve only in an uncommitted `classes.json` is a broken
  contract, not a partial one.
- **It is the module's, never the repository's**, for the reason § 1 gives: the paths in it are
  module-relative, so a repository-wide table would be meaningless in every module but one.

DEC-029 owns the table's format, its `format` and `hash` headers, the FQN key, the row shape, the
checksum rule and the reserved work (`generator`, the per-artifact dependency edges, and the generated
artifact's pointer to its index row) that the directory exists to make room for. Where this amendment and
the one above disagree — and they do on exactly one point, the table's file name — this one is current;
the one above remains the history of how `index/` came to exist, and DEC-028 owns the decision it records.

## Amendment — `conf/` is reserved, and the palette is open

§ 3's list of subfolders read as a closed taxonomy and § 4's table gave three different track policies
to four names. Both were too specific for what the directory turned out to be: a place **any** tool in
the ecosystem keeps its per-project material, in a palette that is still growing (`metadata/`,
`index/`, `cache/`, `reports/`, `agent-state/`, `webview/`, …). A new tool had to either reuse a name
that did not fit or amend this decision, and the second option is how a taxonomy rots. The rules are
therefore reduced to two, and they do not need to know the palette:

> **1. `conf/` is reserved: it holds what must be preserved across a commit.**
> **2. Everything else under `.jcodebuddy/` is derived, machine-written and machine-local, and is
> ignored by default.**

    .jcodebuddy/
    ├── README.md      tracked   the layout contract for this module
    ├── .gitignore     tracked   the authority for the split below
    ├── conf/          TRACKED   what must survive a clone and a commit
    └── …              ignored   whatever a tool writes: metadata/, index/, cache/, reports/,
                                 agent-state/, webview/, and anything added later

The default `.jcodebuddy/.gitignore` is **closed**, and this is its shape:

```gitignore
*                       # derived and machine-local: not committed unless a project says so
!.gitignore
!README.md
!conf/                  # the one reserved subtree; a project may add its own opt-ins above these
!conf/**
```

- **A tool does not have to be listed to be ignored; it has to be listed to be tracked.** That is what
  makes the palette open: adding `cache/` or a future `artifacts/` is a change in a tool, not a change
  in this or any decision.
- **What belongs in `conf/`** is anything that has to survive a clone: shared settings a project's
  contributors and tools agree on, a naming contract, an invariant. It is the *only* subtree whose
  purpose is to be committed, which is why it is the only one re-included by default.
- **The opt-in shape is unchanged, and it is now the norm rather than the exception.** A project that
  wants `metadata/entity/`, or just a subtree's `README.md`, writes the `!` rules itself. § 4's two
  rules still govern them: **re-include the directory before anything inside it** (git never
  re-includes a file whose parent directory is excluded), and **keep the rule narrow enough not to
  carry generated `.java`** (§ 5). `hipster-entity-example/.jcodebuddy/.gitignore` is the worked
  example of both — it opts in the explanation of every subtree and one hand-written spec in
  `context/`, and no generated content.
- **`context/` and `reports/` are no longer tracked by default.** They are the same kind of thing as
  the rest — material that a project *may* want in git — and the example module opts both in. § 4's
  table is history on this point; this amendment is current.
- **Superseded wording.** Where § 3 says the subfolders are fixed, and where § 4's table gives
  `context/`/`reports/` the tracked policy by default, this amendment is current. § 1 (per module),
  § 2 (marker before `pom.xml`), § 5 (no generated `.java`) and § 6 (every scanner excludes
  `.jcodebuddy/**`) are unchanged.
- **One refinement the hosts forced, recorded here because it is about the directory rather than
  about hosts.** A `.jcodebuddy/` whose whole content is **tool state** — `webview/` (a page host's
  published port, DEC-032/DEC-033) or `merge-history/` (the merge tool's per-branch state) — is **not**
  a project-automation marker, and marker resolution (§ 2) skips it and keeps walking up.
  `JcodebuddyDirectory` owns that rule, with `JcodebuddyDirectoryTest`; without it, a browser pointed
  at an unconverted repository would create a marker at the root and move a module's report directory
  one level up. Adding a tool-state subfolder means adding its name there in the same change.
