# DEC-036: hipster-ioc context generation — the generated shape, and where the generator lives

- Status: Trial
- Date: 2026-10-01
- Owners: project
- Related docs: [hipster-ioc ROADMAP](../../../hipster-ioc/doc/ROADMAP.md), [hipster-ioc architecture and design](../../../hipster-ioc/doc/architecture-and-design.md), [DEC-009](DEC-009.md) (source-visible generation), [DEC-019](DEC-019.md) (source-visible wiring), [DEC-020](DEC-020.md) (cooperative codegen), [DEC-021](DEC-021.md) (the class-file header), [DEC-022](DEC-022.md) (naming contract and diagnostics), [DEC-026](DEC-026.md) (where generated output lives), [DEC-030](DEC-030-openrewrite-source-representation.md) (the LST), [DEC-035](DEC-035.md) (markers)

### Context

`hipster-ioc` was folded into this repository with an API but no generator. The API is five leaf types in
`hipster-ioc-api` — `@HipsterContext`, `ChildContext<P>`, `@Circular`, `DynamicResource<T>`,
`StableValuePolyfill<T>` — and the only contexts that exist are hand-written, in `hipster-ioc-test`
(`CtxMain` extends `CtxMainModule`, whose `default ObjectMapper buildMapper()` customises one bean's
creation).

The reactor already contains `hipster-ioc-tooling`, whose POM describes it as "Code generator and
dependency graph computation for hipster-ioc" and which has **no `src/` at all**: it compiles to an empty
jar. Its ROADMAP asks for the generator, the dependency graph, and a browsable presentation of it, and the
integration plan that asked for this record named a decision number that another decision had already
taken — so the module has been an intention rather than a decision until now. The generator cannot be
written without fixing the output shape first: every one of the questions below is a generated-code
contract a consumer will build on.

### Decision

**1. One generated class per context interface, named `<Context>Impl`, committed as ordinary Java.** The
class is written into the marker interface's own package, under the consuming module's `src/main/java`, and
carries DEC-035's two-line header (`// @generated file <generator-fqn> — <description>` plus the JSON5
config line). It MUST NOT be written under `.jcodebuddy/` (DEC-026) and MUST NOT be emitted at runtime
(DEC-009, DEC-019).

**2. It implements the context interface directly.** Every abstract no-arg method that is not a `default`
method becomes a bean accessor backed by a `private final` field. No proxy, no reflective lookup, no
`Map<String, Object>` registry: a reader with a stock IDE MUST be able to follow `ctx.mapper()` to the
field that holds it (DEC-019).

**3. Creation order is derived from the dependencies and is visible in the source.** The generator computes
a topological order over the declared `dependencies()` contexts, the module's `default` factory methods,
and each bean's parameter/field type, and emits creation in that order. The same order drives the
`init*` methods, so the two never disagree.

**4. A bean with no dependencies SHOULD be created in a field initializer**, per the design document's
rule; a bean with dependencies is created in the constructor. The rule exists because a field initializer
cannot see a constructor parameter, and the difference is visible to whoever debugs the context.

**5. `@Circular` breaks a cycle with a settable field.** A cycle marked `@Circular` MUST be generated as a
field assigned after the other beans exist. A cycle the user did not mark is a **generator diagnostic in
DEC-022's format** (`circular_dependency_unmarked`), never silently emitted as code that cannot run.

**6. `ChildContext<P>` gets explicit parent plumbing:** a field, `getParent()`/`setParent(P)`, and — when a
declared dependency is a `ChildContext` — the parent assignment emitted where the child is created.

**7. `@HipsterContext.impl` disables creation code for that bean.** When `impl` names a class, the
generator MUST NOT emit creation code for it: the bean is taken from the module's factory, and the
reference is emitted as a `{@link}` in the field's javadoc so the choice is navigable. A bean that has an
`impl` and no way to be built is a diagnostic, not an empty field.

**8. `DynamicResource<T>` and `StableValuePolyfill<T>` are the lazy seam, and laziness is opt-in.** A
dependency declared as `Supplier<Bean>` or `DynamicResource<Bean>` MUST be emitted through the API's own
holder type rather than by calling the supplier per use; eager creation stays the default, matching the
design document's "beans in context are created immediately" and its stated non-goal of general lazy
loading. A `StableValuePolyfill` is used until a JDK `StableValue` is available; the choice is a generator
option, not a fork in the generated API.

**9. Markers are emitted only where they add information.** Region markers (`region begin <id>` /
`region end <id>`, DEC-035's `region` scope) are emitted for the three sections the design document names —
instance fields, exposed beans, factory methods — **and only when the section exceeds its threshold**
(fields > 5, exposed beans > 3, factory methods > 3), because below that the language's own boundaries
already delimit the code and a marker per small section is noise forever. Cooperative preservation
(DEC-020) applies: a member the generator does not own is carried through verbatim, and `enabled:false` in
the header freezes the whole file (DEC-021 § 6, implemented 2026-10-01).

**10. The dependency graph is JSON metadata, and the page is rendered by Bun.** The generator writes
`.jcodebuddy/metadata/hipster-ioc/contexts.json` (derived, ignored) describing each context, its beans,
their dependencies and their order. A browsable presentation is a JavaScript renderer under `scripts/`
reading that JSON — never HTML emitted by the generator (DEC-027), one self-contained framework-free file,
every link verified before it is written (DEC-029).

**11. Module boundaries.** `hipster-ioc-tooling` MUST NOT depend on `project-automation` (AGENTS.md § 1.1);
it is driven by the dev-time pass and by a CLI. It MUST read the annotated interfaces through the
repository's one source representation — OpenRewrite's LST via `hipster-entity-tooling` (DEC-030), which its
POM already declares — and MUST NOT add a second Java parser.

**12. Naming contract (DEC-022).** `<Context>` → `<Context>Impl` is **refactor-sensitive**: the generated
class wires the relationship with `{@link}`/`@see` and the POM publishes the table entry, so an IDE rename
of the interface reaches the generated class. The bean accessor names are the interface's own method names
and are therefore refactor-sensitive too. Nothing here is an API label (no JSON-RPC name, no audit event),
so nothing is refactor-insensitive.

### Alternatives considered

- **Annotation processing (JSR 269).** Rejected: it puts generation inside the compiler, regenerates on
  every build, and produces the invisible wiring DEC-019 forbids. The design document states the same
  objection at length ("The Annotation Processor Overhead").
- **Dagger-style generated factories, one per bean.** Rejected: class bloat with no reader benefit; the
  whole point of a hand-checked context is that one file shows the object graph.
- **Reflection or a runtime container.** Rejected by DEC-019: if the connection is not in the source, it
  does not exist.
- **Runtime bytecode generation.** Rejected: not navigable, not committable, not reviewable.
- **Generating an interface plus an implementation** (`<Context>` + `<Context>Impl`). Rejected for now: the
  marker interface already *is* the contract and the user owns it, so a second generated interface is one
  more name to keep in step for no gain. Revisit if a context ever needs a generated-shaped public type.
- **Deriving the graph only as metadata, with no generated class.** Rejected: the context must be ordinary
  Java a debugger can step through; metadata describes the graph, it does not replace it.

### Consequences

**Positive.** The tooling module stops being an empty jar with a description. The generated context is
readable, debuggable and reviewable; creation order is explicit; the dependency graph has one machine
representation that both the generator and a report can consume. The decision also fixes the questions a
second consumer would otherwise have to guess: the class name, the package, the header, the markers, and
where laziness is allowed.

**Negative.** A generated context is more code than a reflective container, and the `init*`/creation order
becomes something a user can break by editing the generated file — which is precisely why the file carries
a header and why the freeze exists. Generating Java also means the generator must be re-run (and the result
committed) rather than being invisible; that is the accepted cost of DEC-019.

**Follow-up.** The CLI and the report renderer are separate work; `hipster-ioc-tooling`'s POM comment about
`project-automation` is the boundary this record restates, and the module's README must publish the naming
contract table (DEC-022) when § 12 is implemented.

### Acceptance criteria

- `hipster-ioc-tooling` compiles with sources, and generates `<Context>Impl` for a context in
  `hipster-ioc-test`, which compiles.
- Generated output carries the DEC-035 file marker and honours `enabled:false` (DEC-021 § 6).
- A context whose beans have dependencies is created in topological order, and the order is asserted by a
  test rather than by reading the file.
- An unmarked cycle is a `circular_dependency_unmarked` diagnostic in DEC-022's format.
- The graph is written as JSON under `.jcodebuddy/metadata/`, and no HTML is produced by the generator.
- The module's POM still does not depend on `project-automation`.
