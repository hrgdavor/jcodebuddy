# DEC-036: hipster-ioc context generation — the generated shape, and where the generator lives

- Status: **Accepted** (2026-10-01) — **moved from `Trial` on 2026-10-03**, when plan step 3.0e part two made the
  generator consume the metadata model instead of reading sources: the condition the plan's step 3.10 named
  ("Schedulable when DEC-036 is `Accepted`") is met, and the hand-written module interface it described is retired
- Date: 2026-10-01
- Updated: 2026-10-03 — **the generator is model-driven.** `ContextReader` takes a class-index row and an index,
  not a file; `IocContextGenerator` no longer implements the file-scoped `CodeGenerator` SPI (the category error
  the tooling README described); `hipster-ioc-test` no longer carries a hand-written `CtxMainModule` — its
  `default ObjectMapper buildMapper()` was the last hand-written wiring, and the regenerated `CtxMainImpl`
  constructs the bean directly instead. Regenerating the committed example after the rewrite produced the **same
  bytes except that one line**, which is the evidence that reading the model says what reading the source said.

### Context

`hipster-ioc` was folded into this repository with an API but no generator. The API is five leaf types in
`hipster-ioc-api` — `@HipsterContext`, `ChildContext<P>`, `@Circular`, `DynamicResource<T>`,
`StableValuePolyfill<T>` — and the only contexts that existed were hand-written, in `hipster-ioc-test`
(`CtxMain` extends `CtxMainModule`, whose `default ObjectMapper buildMapper()` customised one bean's creation).
**As of 2026-10-03 that module interface is retired**: the context interface is the only hand-written input left,
and `CtxMainImpl` is generated from the model.

The reactor already contains `hipster-ioc-tooling`, whose POM describes it as "Code generator and
dependency graph computation for hipster-ioc" and which has **no `src/` at all**: it compiles to an empty
jar. Its ROADMAP asks for the generator, the dependency graph, and a browsable presentation of it, and the
integration plan that asked for this record named a decision number that another decision had already
taken — so the module has been an intention rather than a decision until now. The generator cannot be
written without fixing the output shape first: every one of the questions below is a generated-code
contract a consumer will build on.

### Decision

**1. One generated class per context interface, named `<Context>Impl`, committed as ordinary Java.** The
class is written into the marker interface's own package, under the consuming module's `src/main/java`, and
carries DEC-035's two-line header (`// @generated file <generator-fqn> — <description>` plus the JSON5
config line). It MUST NOT be written under `.jcodebuddy/` (DEC-026) and MUST NOT be emitted at runtime
(DEC-009, DEC-019).

**2. It implements the context interface directly.** Every abstract no-arg method that is not a `default`
method becomes a bean accessor backed by a `private final` field. No proxy, no reflective lookup, no
`Map<String, Object>` registry: a reader with a stock IDE MUST be able to follow `ctx.mapper()` to the
field that holds it (DEC-019).

**3. Creation order is derived from the dependencies and is visible in the source.** The generator computes
a topological order over the declared `dependencies()` contexts, the module's `default build<Bean>(...)`
methods, and each bean's parameter/field type, and emits creation in that order. The same order drives the
`init*` methods, so the two never disagree.

> **Amended 2026-10-03, on implementing them (plan step 3.5).** This clause presupposed `init*` methods without
> saying what one is, and that gap is why nothing emitted any. Settled as follows, and the shape is chosen so that
> **no generated code lands in a user's edit path**:
>
> - **An `init*` method is the user's own hook, declared on the module interface** — the same place the
>   `default build<Bean>(...)` factories live. A hook is a `default` method whose name starts with `init`, that
>   returns `void`, and that takes exactly one parameter whose type is the type of a bean this context builds.
>   Being `default` is what makes it inheritable by the generated class, which is what makes the call compile —
>   the mechanism the factories already rely on.
> - **The generated constructor calls each hook immediately after that bean's field is assigned.** So the
>   guarantee is: a hook runs after its own bean exists, and before anything that depends on it is created. The
>   beans are still created by generated code; the *initialisation* is the user's, which is what this clause's
>   "the same order drives them" was always describing.
> - **Anything else named `init*` is left alone** — no parameter, a non-`void` return, or a parameter type that
>   names no bean. The generator only ever *adds* a call to code it can place, so a helper of the user's that
>   happens to start with `init` is not swept into the seam.
> - **Two hooks for one bean are reported** as `init_hook_ambiguous`, and the first declared one is used: which
>   initialiser runs is not a question to answer by declaration order, so it is asked rather than assumed.
> - **One boundary, stated rather than discovered:** a hook for a bean whose factory takes a
>   `@Circular Supplier<...>` (clause 5) runs before that supplier's target exists, so the hook must not call it.
>   The supplier is exactly what makes the cycle work later; calling it during construction is the one thing the
>   two-phase form cannot make safe.
>
> A bean created in a field initializer (clause 4) would have no hook position at all, which is the second reason
> the implementation creates every bean in the constructor: the clause's "SHOULD" is satisfied by an order that
> can be followed, and a field initializer cannot be interleaved with hooks.

> **Where the module interface is read from (clarified 2026-10-01, when it was implemented).** The module
> interface is the context's own supertype, and in practice it is a **sibling file** — `CtxMain.java` beside
> `CtxMainModule.java`, which is the shape `hipster-ioc-test` already has. The first implementation looked
> only inside the context's own compilation unit and therefore found no factories at all for that shape; the
> reader now resolves a supertype to the file named after it beside the context, and takes **both files'
> imports** into the generated class (a factory's parameter type is usually named only in the module file).

**4. A bean with no dependencies SHOULD be created in a field initializer**, per the design document's
rule; a bean with dependencies is created in the constructor. The rule exists because a field initializer
cannot see a constructor parameter, and the difference is visible to whoever debugs the context.

**5. Cycles are refused, and that is a limitation of the first implementation.**
> **Amended 2026-10-01, on implementing it.** This clause originally required a cycle marked `@Circular` to
> be generated "as a field assigned after the other beans exist". That is not implementable against the
> current API, and the amendment is recorded rather than the clause being quietly ignored: closing a cycle
> after construction needs the dependency to be resolved *later* — a `Supplier<Bean>` parameter the
> generated code can hold, or a setter on the user's class the generator may call — and `@Circular` today
> marks a plain parameter of the factory, which is read before the bean exists. So the generator **refuses**
> a cycle either way, and the two cases get different diagnostics:
>
> - `circular_dependency_unmarked` — no parameter is marked, so no order exists;
> - `circular_dependency_marked_unsupported` — the user did mark it, and the two-phase form that would
>   honour the mark is not implemented.
>
> Both leave the file untouched, which is the "never silently emitted as code that cannot run" rule this
> clause was written to state. The `Supplier`-parameter form is the follow-up that would make the marked
> case generate.
>
> **Amended again 2026-10-03, on implementing that follow-up (plan step 3.4).** The spelling is settled, and it
> is the one this amendment named: **a marked edge is written `@Circular Supplier<Bean>` as the factory
> parameter**. The annotation keeps its meaning — the user says this edge closes a cycle — and the JDK type says
> how it is resolved, which is what the first amendment lacked. Concretely:
>
> - a marked parameter is **not an ordering edge**, because the supplier is only called after the context
>   exists; that is what breaks the cycle rather than working around it;
> - the generated constructor passes `() -> bean()` — a call to the context's **own accessor** for the bean it
>   supplies, so the deferral is visible source a stock IDE can navigate (DEC-019), not reflection or a lazy
>   proxy;
> - a marked parameter that is **not** a `Supplier`, or whose supplied type names no bean this context builds,
>   is handled without guessing: the first is refused with **`circular_dependency_needs_supplier`**, and the
>   second becomes an ordinary constructor parameter of the context, so the caller supplies the supplier.
>
> `circular_dependency_marked_unsupported` is therefore **retired**, and `circular_dependency_unmarked` is
> unchanged: a cycle nobody marked is still refused, because accepting it would mean guessing which edge the
> user meant. The generated form is proven by `IocContextGeneratorTest`, which compiles the cycle fixture and
> then runs it: each bean's supplier resolves to the other bean the context built.
>
> One boundary worth stating: `Supplier<Bean>` written **on the context interface** is a different, older
> thing — a lazy bean accessor (clause 8) — and the two positions do not overlap, because the marked form is a
> factory *parameter* and the lazy form is an accessor of the context itself.

**6. `ChildContext<P>` gets explicit parent plumbing:** a field, `getParent()`/`setParent(P)`, and — when a
declared dependency is a `ChildContext` — the parent assignment emitted where the child is created.
> **Amended 2026-10-03 (step 3.7: what a declared dependency *is*).** The clause above said the plumbing and the
> parent assignment exist; it did not say how a context **receives** another context, and until step 3.7 the
> generator recorded `dependencies()` in `contexts.json` and used it for nothing at all. Three decisions settle it:
>
> 1. **A dependency is received, never constructed.** The generated implementation takes each entry of
>    `@HipsterContext(dependencies = …)` as a **constructor parameter**, in declaration order and ahead of the
>    parameters the context cannot answer at all, and keeps it in a `private final` field. **Who constructs it is
>    the caller** — the generator does not know the other context's own dependencies, and inventing a factory for one
>    would be exactly the invisible wiring DEC-019 rejects. The dependency's own generated implementation is adopted
>    where it is received instead: when it is a `ChildContext`, the constructor calls `setParent(this)` on it, which
>    is clause 6's "assignment where the child is created" for a child the generator did not create.
> 2. **A dependency's beans become resolvable.** A factory parameter whose type matches one of the dependency's beans
>    is satisfied by calling that context's own accessor — `buildReport(dataContext.rows())` — so a bean may be
>    assembled from another context's bean without either context knowing the other's internals. This context's own
>    beans win a tie; a parameter that **two** dependencies could each answer stays the caller's, because the
>    generator does not choose silently; and a dependency the index cannot resolve is reported
>    (`dependency_context_not_indexed`) rather than skipped, since the alternative is generated code that does not
>    compile.
> 3. **Types are compared without package qualifiers.** A factory parameter is source text (`List<String>`) while a
>    bean's type comes from the index, which resolves it (`java.util.List<java.lang.String>`). Comparing the two
>    literally matched nothing, and the parameter then silently became an extra — code that compiles only if the
>    caller happens to supply it, which is the worst available outcome. The boundary is deliberate: two same-named
>    types in different packages compare equal, and a context declaring both disambiguates with an explicit factory
>    parameter name.

**7. `@HipsterContext.impl` suppresses generation for the whole context.**
> **Amended 2026-10-01.** This clause was written as "disables creation code for that bean", and reading the
> API changed it: `impl` is an attribute of the **context** annotation, not of a bean, and its own javadoc
> says it exists so that "if an implementation already exists, disable auto-build and give reference to it
> for documentation purposes". So when `impl()` names a class the generator emits **nothing** for that
> context and reports `context_implementation_present` naming the class — the reference is the diagnostic,
> which is the navigable form of "for documentation purposes". Competing with an implementation that already
> exists is the one thing this generator must not do.

**8. `DynamicResource<T>` and `StableValuePolyfill<T>` are the lazy seam, and laziness is opt-in.** A
dependency declared as `Supplier<Bean>` or `DynamicResource<Bean>` MUST be emitted through the API's own
holder type rather than by calling the supplier per use; eager creation stays the default, matching the
design document's "beans in context are created immediately" and its stated non-goal of general lazy
loading. A `StableValuePolyfill` is used until a JDK `StableValue` is available; the choice is a generator
option, not a fork in the generated API.

**9. Markers are emitted only where they add information.** Region markers (`region begin <id>` /
`region end <id>`, DEC-035's `region` scope) are emitted for the three sections the design document names —
instance fields, exposed beans, factory methods — **and only when the section exceeds its threshold**
(fields > 5, exposed beans > 3, factory methods > 3), because below that the language's own boundaries
already delimit the code and a marker per small section is noise forever. Cooperative preservation
(DEC-020) applies: a member the generator does not own is carried through verbatim, and `enabled:false` in
the header freezes the whole file (DEC-021 § 6, implemented 2026-10-01).

> **Implemented 2026-10-03 (plan step 3.6), with the ids and one interpretation named.** The three ids are
> **`fields`**, **`accessors`** and **`factories`** — short stable tokens, as DEC-035 requires of a region id —
> and each pair is emitted at the section's own indentation, around the bean declarations, the bean accessors,
> and the bean creations inside the constructor respectively.
>
> The one thing this clause left open: the design document says "**BeanFactory methods** (count > 3)", and a
> generated context has no factory method of its own — it *calls* the module's `default build<Bean>(...)`
> factories. The generated section that corresponds to that threshold is therefore the **creation block**, and
> `factories` delimits exactly the statements that call those factories. A stricter reading would make the
> threshold apply to a section that never exists in the file being generated, which cannot be what the clause
> meant; the reading is recorded here rather than left to whoever reads the generated file next.
>
> The thresholds are counted over the context's beans, and the field region counts the bean fields — the
> extra-parameter fields and a `ChildContext` parent field are outside it, because they do not grow with the
> object graph the markers exist to make navigable. The example context in `hipster-ioc-test` has one bean, so it
> is below every threshold and the committed example is unchanged by this step.

**10. The dependency graph is JSON metadata, and the page is rendered by Bun.** The generator writes
`.jcodebuddy/metadata/hipster-ioc/contexts.json` (derived, ignored) describing each context, its beans,
their dependencies and their order. A browsable presentation is a JavaScript renderer of its own reading
that JSON — never HTML emitted by the generator (DEC-027) — and **not a resident of the root `scripts/`**:
this is the page DEC-027's 2026-10-01 amendment classifies as **interactive/advanced**, so it is built with
**`jsx6`** and its diagram with **`jsx6`/`nodditor`** rather than as one framework-free vanilla file, while
`scripts/` stays dependency-free for the vanilla renderers — a built page gets a home that may declare its
own dependencies (DEC-027's 2026-10-02 note on where a `jsx6` page's build lives). Every link is still
verified before it is written (DEC-029) and the JSON is still the only source of the model.

**11. Module boundaries, and what this generator consumes.** `hipster-ioc-tooling` MUST NOT depend on
`project-automation` (AGENTS.md § 1.1); it is driven by the dev-time pass and by a CLI.

> **Amended 2026-10-01 — the input is metadata, not source.** This clause originally required the generator
> to read the annotated interfaces through OpenRewrite's LST (DEC-030) and never to add a second parser. The
> second half stands; the first half named the wrong actor. **hipster-ioc is a project-wide generator and
> extracting metadata is not its job** — it consumes the project's type relations (who extends whom, who
> implements what, what is assignable) to produce IoC code, and the *metadata layer* is what reads sources,
> through the repository's one representation (DEC-030), and indexes them. `hipster-ioc-tooling` therefore
> keeps its `hipster-entity-tooling` dependency only as far as the shared metadata types go, and the
> contract between the two sides is `plans/unified-plan.md` steps **3.0a–3.0k**, which since 2026-10-02 means
> one metadata engine in `jcodebuddy-core` ([DEC-037](DEC-037.md)) with this generator as one of its consumers
> (the seam already exists and
> is empty: `jcodebuddy-codegen-api`'s `TypeResolver`/`TypeDefinition`, where `TypeDefinition` currently
> carries fields and **no relations**, and nothing implements `TypeResolver` but `EmptyTypeResolver`).
>
> **Amended 2026-10-03 — where the seam went.** The sentence above says the seam "already exists and is empty:
> `jcodebuddy-codegen-api`'s `TypeResolver`/`TypeDefinition`". Both halves stand, and both moved: step **3.0i**
> dissolved that module into the engine, so the seam is `hr.hrg.jcodebuddy.engine.query` and the SPI this
> clause assigns to `hipster-ioc-tooling`'s reader side is `hr.hrg.jcodebuddy.engine.codegen` — in
> `jcodebuddy-core`, which is the module the clause above already names as the contract's home. **It is still
> empty**: nothing implements `TypeResolver` but `EmptyTypeResolver`, `TypeDefinition` still carries no
> relations, and `IocContextGenerator` still implements the file-scoped `CodeGenerator` that the next
> paragraph calls a category error — steps **3.0d** and **3.0e/3.0j** are unchanged by the move.
>
> **Why a project-wide generator cannot be a file generator.** It is not a difference of appetite: "who
> extends whom" is in no single file, so a generator reading one file and following what it references
> either misses relations or invents them. The prototype did both halves of that failure: its first
> implementation looked for the module interface only inside the context's own compilation unit, found
> nothing, and reported **no factories** — an empty-wiring implementation rather than an error, because a
> file it never read looks exactly like a file with nothing in it. That is why the plan's rule § 2.8 now
> says **metadata that cannot be resolved is reported, never inferred as absent**.
>
> **The prototype's `CodeGenerator<GeneratedContext>` implementation is a category error, not a
> classification question.** `CodeGenerator`/`CodeContext` is the *file-scoped* SPI — its javadoc promises
> that "the cost of asking is the predicate, not a parse", i.e. that one file is all that matters — and this
> generator both needs the project and (through its pass) writes a whole-tree artifact. Plan step **3.0e**
> removes that implementation instead of re-labelling it: hipster-ioc becomes metadata in, code out. Step
> **7.8** is what makes the two kinds visible to a caller holding a generator list. Until 3.0e lands, treat
> `bun scripts/ioc-gen.js` (which runs it over a root) as the supported entry point and do not offer this
> generator to an isolated file.
>
> **Amended 2026-10-03 (step 7.8: the two kinds are now a type).** Both halves of the paragraph above have
> happened: step **3.0e** removed the file-scoped implementation (`IocContextGenerator` no longer implements
> `CodeGenerator`, parses nothing, and is handed the model), and step **7.8** made the distinction enforceable
> rather than documentary. `hr.hrg.jcodebuddy.engine.codegen` now holds **two unrelated interfaces**:
> `CodeGenerator`/`CodeContext` is the **file-scoped** kind, and `ProjectGenerator`/`ProjectContext` is the
> **project-scoped** one — metadata in, code out, handed the class index and the typed queries and never a single
> file. Neither extends the other, which is what makes "offer this generator to every file" impossible to write by
> accident rather than merely discouraged: a caller holding a list of file-scoped generators cannot be handed a
> project-scoped one, and the compiler says so.
>
> Two consequences worth stating where the classification lives. **A wrapper's kind is its delegate's**, and exactly
> one kind — a wrapper implements the interface of the kind it forwards to, and nothing implements both (the one
> wrapper that existed, `ActionToolAdapter`, was deleted in step 3.0s, so this is a shape to hold to rather than a
> class to fix). And **a generator's kind is what it reads, while a pass's kind is what it writes**: this generator
> returns text and has no side effects, while `IocGeneration` writes the graph and the generated files — a rule
> calling a thing's kind by what it touches would have named the same generator two kinds depending on which half
> you looked at. The classification of each generator is stated on its own README
> (`hipster-ioc-tooling`: project-scoped; `hipster-entity-tooling`'s `EntityMetadataGenerator`: project-scoped by
> construction, no per-file entry point to walk through).

**12. Naming contract (DEC-022).** `<Context>` → `<Context>Impl` is **refactor-sensitive**: the generated
class wires the relationship with `{@link}`/`@see` and the POM publishes the table entry, so an IDE rename
of the interface reaches the generated class. The bean accessor names are the interface's own method names
and are therefore refactor-sensitive too. Nothing here is an API label (no JSON-RPC name, no audit event),
so nothing is refactor-insensitive.

### Alternatives considered

- **Annotation processing (JSR 269).** Rejected: it puts generation inside the compiler, regenerates on
  every build, and produces the invisible wiring DEC-019 forbids. The design document states the same
  objection at length ("The Annotation Processor Overhead").
- **Dagger-style generated factories, one per bean.** Rejected: class bloat with no reader benefit; the
  whole point of a hand-checked context is that one file shows the object graph.
- **Reflection or a runtime container.** Rejected by DEC-019: if the connection is not in the source, it
  does not exist.
- **Runtime bytecode generation.** Rejected: not navigable, not committable, not reviewable.
- **Generating an interface plus an implementation** (`<Context>` + `<Context>Impl`). Rejected for now: the
  marker interface already *is* the contract and the user owns it, so a second generated interface is one
  more name to keep in step for no gain. Revisit if a context ever needs a generated-shaped public type.
- **Deriving the graph only as metadata, with no generated class.** Rejected: the context must be ordinary
  Java a debugger can step through; metadata describes the graph, it does not replace it.

### Consequences

**Positive.** The tooling module stops being an empty jar with a description. The generated context is
readable, debuggable and reviewable; creation order is explicit; the dependency graph has one machine
representation that both the generator and a report can consume. The decision also fixes the questions a
second consumer would otherwise have to guess: the class name, the package, the header, the markers, and
where laziness is allowed.

**Negative.** A generated context is more code than a reflective container, and the `init*`/creation order
becomes something a user can break by editing the generated file — which is precisely why the file carries
a header and why the freeze exists. Generating Java also means the generator must be re-run (and the result
committed) rather than being invisible; that is the accepted cost of DEC-019.

**Follow-up.** The CLI and the report renderer are separate work; `hipster-ioc-tooling`'s POM comment about
`project-automation` is the boundary this record restates, and the module's README must publish the naming
contract table (DEC-022) when § 12 is implemented.

### Acceptance criteria

- `hipster-ioc-tooling` compiles with sources, and generates `<Context>Impl` for a context in
  `hipster-ioc-test`, which compiles. — **Capability delivered and asserted on a fixture tree in
  `IocContextGeneratorTest` (the generated file is compiled by the JDK running the test); generating the
  committed example in `hipster-ioc-test` is step 3.3's job, because that needs the CLI to be the entry
  point.**
- Generated output carries the DEC-035 file marker and honours `enabled:false` (DEC-021 § 6). — **Both
  asserted.**
- A context whose beans have dependencies is created in topological order, and the order is asserted by a
  test rather than by reading the file. — **Asserted, and the fixture's generated file is compiled.**
- An unmarked cycle is a `circular_dependency_unmarked` diagnostic in DEC-022's format. — **Asserted, with
  the marked case reported separately as `circular_dependency_marked_unsupported` (§ 5).**
- The graph is written as JSON under `.jcodebuddy/metadata/`, and no HTML is produced by the generator. —
  **Asserted; the graph goes under the *module* root, which is why `IocGeneration.generate` takes the module
  root separately from the source root.**
- The module's POM still does not depend on `project-automation`. — **Holds; the generator implements the
  shared `CodeGenerator` SPI instead.**
- No factory parameter is ever passed as a `null`: a parameter the context cannot provide becomes a
  constructor parameter of the generated class, so the caller decides what it is.
