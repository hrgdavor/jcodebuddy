## Context

DEC-028 gave the metadata a central, per-module addressing table and a field's every location. What it
did not give it was any statement about **the classes those locations live in**, and the few file facts
it did carry were shaped for one generator's need rather than for a consumer that wants to join against
the tree:

1. **The only name a document had for a file was a readable id** (`PersonSummaryBuilderTracking`,
   `entity.Person`) resolved through `.jcodebuddy/index/files.json`. That id is derived from *the whole
   set of paths one pass happened to index*, so adding an unrelated file can lengthen an existing id and
   invalidate every document that used it. It is a good human id and a poor join key, and — because it is
   a fact about the pass rather than about the code — it is the one reference a Java IDE's rename
   refactor cannot update in a text file.
2. **Nothing in the tree knew a file's content identity.** A generator that wants to skip work, a watcher
   that wants to know whether the bytes changed, and a report that wants to say "this file is stale" all
   had to re-read and re-hash the tree themselves. `hashes.json` was *reserved* for exactly this in
   `plans__p1/plan.metadata-locations.md` § 2.3.2 and never built.
3. **Nothing recorded a type's kind, modifiers, size or declaration line**, so every generator re-derived
   those facts, per generator, by walking and parsing the same sources again.

The plan that closes all three is `plans__p2/plan.class-index.md`, and this decision records the contract
it produced; the plan is the specification and this document is the decision, in the same relationship
DEC-028 has to its own plan. One earlier draft of that plan — the now-deleted
`plans__p2/plan.sourcemap-locations.md` — proposed re-expressing the location payload as a source-map v3
file. That file format is **withdrawn** here and § 13 records why, together with the five source-map
*conventions* that are adopted.

## Decision

### 1. `.jcodebuddy/index/classes.json` is the module's class index

A pass writes **one** table for the whole module, beside the documents that reference it:

```jsonc
// <module>/.jcodebuddy/index/classes.json
{
  "format": 1,
  "module": "hipster-entity-example",
  "sourceRoot": "src/main/java",
  "hash": { "algo": "wyhash64", "normalize": "lf", "of": "content" },
  "classes": {
    "hr.hrg.hipster.entityexample.person.entity.PersonSummary": {
      "path": "src/main/java/hr/hrg/hipster/entityexample/person/entity/PersonSummary.java",
      "kind": "interface", "modifiers": ["public"], "line": 14, "depth": 0,
      "size": 1837, "checksum": "3f2c8d91a4b7e601", "hashCalculatedAt": "2026-05-14T09:12:33Z" }
  }
}
```

- There is **one row per type** the module compiles: every `*.java` file under the module's source root
  **and** every artifact the pass writes. **Member types are their own rows** (`…PersonSummary.Record`),
  so every reference in the tree can be a type name; a member type therefore repeats its file's facts,
  which is accepted deliberately (§ 2).
- It is written by the `hipster-entity-generator` pass, in the same pass that writes the documents: the
  index is **derived output and follows the same track policy as `metadata/`** — ignored by default, and
  opted into git together with the metadata subtree (DEC-026's amendment).
- Location rule: `<nearest .jcodebuddy above the report directory>/index/`; when the report directory is
  not inside a `.jcodebuddy/` at all (a temp directory in a test), `<report dir>/index/`. That is why each
  document carries an **emitted** `classIndex` pointer rather than assuming the layout (§ 13, convention 3).
  Only an index inside a real `.jcodebuddy/` gets a `README.md`; the fallback gets the table alone, which
  keeps "a report directory holds JSON only" true.
- `format` is the table's own version, an integer. A consumer that does not recognise it **MUST** refuse
  the table and say why — never guess. `1` is the only value in use.
- `module` and `sourceRoot` are diagnostics, so the file is self-describing when opened directly.
- `hash` is the content-identity contract: `algo`, `normalize` and `of`. A table whose contract is not the
  reading build's **MUST** force a full pass (§ 9).
- `classes` is keyed by FQN and written in ascending key order, so an unchanged tree is byte-identical
  pass to pass and the file's order is a property of the names rather than of `Files.walk`.

### 2. The key is the fully qualified type name, and there is deliberately no surrogate id

The row's key is the type's **fully qualified name**: package-qualified, member types joined with `.`
(`hr.hrg.hipster.entityexample.person.entity.PersonSummary.Record`). `TypeFacts.of` derives it from the
unit's package declaration plus the enclosing chain walked through JavaParser's parent nodes — there is no
classpath at generation time, and the parent chain is all an FQN needs.

**There is no id anywhere in this design.** Not a 4-byte hash, not a counter, not a positional index, not
a "local id for compactness" in a document:

- An id is a fact about **the writing pass**: it changes when a file moves, when a row is inserted, when
  the scheme is salted, and it means nothing to a tool that cannot run our writer.
- An FQN is a fact about **the code**, and it is the one reference a Java IDE's rename refactor updates
  everywhere it appears — **including in text files that are not Java**. This repository's generators
  write committed Java that must stay navigable under a stock IDE (`AGENTS.md` § 1, DEC-019, DEC-022); a
  surrogate id in a text file would be exactly the class of silent stale reference those decisions exist
  to prevent.
- The disambiguation DEC-028 hand-encoded survives for free: the three `Person` types in the example are
  now distinguished by their packages rather than by a manufactured `entity.Person` / `iface.Person` /
  `record.Person` suffix. One scheme — the language's own — replaces two.

**The cost, stated honestly:** an FQN is longer than a hash, and **a package or type rename changes the
key**. A reference in a document is stale until the next pass regenerates it. That is the correct
behaviour for generated output — the pass reads the renamed Java and emits the new name — but it is a real
consequence, and `ClassIndex.changedSince` reports it rather than hiding it (§ 12): the old FQN is a
`removed` row, the new one is `added`, and when the **same path** appears under a different FQN the change
is reported as `renamedType`.

### 3. What a row carries

| field | meaning |
| --- | --- |
| `path` | the declaring file, **module-relative with forward slashes**, never absolute, never `..`, never project-relative |
| `kind` | `class` / `interface` / `enum` / `record` / `annotation`, from the tooling's single `MetadataLocations.kindOf` resolver |
| `modifiers` | the declaration's Java modifier keywords, **sorted**, restricted to `public`, `protected`, `private`, `abstract`, `static`, `final`, `sealed`, `non-sealed`, `strictfp` (a reordered modifier list must not be a diff; adding a keyword is a format change) |
| `line` | the declaration's **name** line, 1-based |
| `depth` | `0` for a top-level type, the number of enclosing types otherwise |
| `enclosing` | the FQN of the enclosing type — **written only when non-null** |
| `generated` | `1` when the pass wrote the file (it carries a DEC-021 header) — **written only when true** |
| `size` | the file's size in bytes, as hashed |
| `checksum` | 16 lowercase hex characters — `Wyhash64` over the file's content with CRLF normalised to LF first (§ 4) |
| `hashCalculatedAt` | the ISO-8601 UTC instant that checksum was calculated, second precision (§ 5) |

`enclosing: null` and `generated: 0` are omitted because they are the common case for a top-level
hand-written type, and writing them would add a line per row to a table whose purpose is to be read. The
file's last-modified time is **not** in the table (§ 6).

### 4. The checksum is `Wyhash64` over LF-normalised content, vendored into the tooling

```
bytes    = Files.readAllBytes(file)
bytes    = normaliseCrLfToLf(bytes)      // \r\n → \n and a lone \r → \n
checksum = String.format("%016x", Wyhash64.hash(0, bytes))
```

- **The algorithm and the normalisation are the repository's existing ones.** `java-watch-core`'s
  `ChecksumDatabase` and `java-watch-agent`'s `MetadataCache` already hash text files this way, and
  `plan.metadata-locations.md` § 2.3.2 reserved **one** content-identity table for the whole repository.
  Using the same algorithm and normalisation is what makes the index and the watch tables agree about what
  "the same content" means. LF normalisation is not optional: without it a CRLF checkout and an LF checkout
  of identical content disagree, and the checksum becomes a property of the developer's git configuration
  rather than of the code.
- **How the tooling obtained it: by vendoring, not by a dependency.** `hr.hrg.wyhash:wyhash:1.0.0` is
  copied byte-for-byte from the library's sources jar as `…/tooling/index/Wyhash64.java`, with the
  upstream artifact and version named in the file header. The tooling's dependency set is asserted by
  `DependencyBoundaryTest` (DEC-W003), and adding a Maven dependency for one 128-line class would have
  widened it.
- **The accepted risk, and its mandatory mitigation:** a copy can silently diverge from the library, and
  then two tables disagree about "the same content" — the exact failure the single-hash reservation
  existed to prevent. `ContentHashTest` therefore pins the copy to **vectors produced by the library
  itself**, not by the copy: the empty array, `"a"`, an LF / CRLF / CR triplet of the same text, and
  inputs of exactly 16, 17, 48 and 49 bytes and 10 800 bytes (the short-input, first-block, full-block and
  multi-block paths). If `Wyhash64` is ever regenerated from a newer upstream release, those vectors and
  the `hash.algo` header must be regenerated with it.
- **The rejected alternative** was adding the `wyhash` dependency to `hipster-entity-tooling`: cheaper to
  keep in sync, and rejected to keep the tooling's dependency surface unchanged. If the copy ever proves
  hard to keep honest, that is the option to revisit.
- **Never a correctness input.** A missing, unreadable or contract-mismatched table forces a full pass; the
  `hash` header is the licence to skip, and a mismatch is reported rather than guessed.

### 5. `hashCalculatedAt` changes if and only if the row's `checksum` changes

The instant is decided at **write** time, in `ClassIndex.stampFileFacts()`, by comparing the row's freshly
computed checksum against the previous table's. `ClassIndex.merge(previous)` only *remembers* the previous
table — it stamps nothing, because at that point no row has a checksum yet and the pass may not have
written the file the row describes.

The rule, applied per row: **if the checksum is unchanged, `hashCalculatedAt` is the previous table's;
otherwise it is this pass's instant** (and a new row is stamped now). This is what makes the table
byte-identical across two passes on an unchanged tree, and therefore **committable and reviewable in a
diff**. Stamping every pass would make every pass a diff and destroy the determinism
`ExampleRegenerationTest` and the bun tests depend on. The clock is injectable, so a test can assert bytes
across two passes with a fixed clock and with an advancing one.

### 6. The file's last-modified time is **not** in the table: `.jcodebuddy/index/mtimes.json`

```jsonc
// <module>/.jcodebuddy/index/mtimes.json
{ "format": 1, "of": "classes.json", "mtimes": { "<fqn>": 1757000000000 } }
```

- An `mtime` is a property of **a working tree**, not of the source: it cannot survive a fresh checkout or
  a branch switch, so writing it into a committable table would make a committed table differ from a
  regenerated one on every machine — the opposite of what this table is for. The sidecar is derived and
  git-ignored with the rest of `index/`.
- A watcher **may** use it as a cheap pre-filter ("compare a timestamp before hashing a file" — the use
  `plan.metadata-locations.md` § 2.3.2 asked for). **Nothing may treat it as a correctness input**: a
  missing, unreadable or mismatched sidecar simply costs a full hash.
- The sidecar's value is also **carried forward while the checksum is unchanged**, for a stated reason: a
  generated artifact is rewritten on every pass, so its filesystem mtime moves even when its bytes do not.
  The value therefore means "when this row's *content* last changed, as this pass saw it", which is what a
  pre-filter needs and is stable across passes that changed nothing.

### 7. A file that declares no type contributes no row

The table's key space is **types**, so a file with none has no key — and none is invented:

- A `package-info.java` (or a file of only comments) is registered as **type-less** and the pass reports it:
  `[index] no type declared in …, so the class index has no row for it (the table's key space is types)`.
  It is remembered rather than silently dropped, so the pass's own record names it.
- **A file the parser cannot read** contributes no row either. The pass's walk reports it through its own
  `source_not_parsed` divergence (F-23's fail-safe), so an unreadable file is visible without the index
  inventing a checksum for bytes nobody could parse. A **generated** artifact the pass cannot read back is
  remembered as type-less for the same reason.
- **A row whose file has vanished is fatal**: `ClassIndex.write()` raises an `IOException` naming the FQN
  and the path, because a row whose size and checksum describe a file nobody read is worse than no row.
- Registering a path that is not module-relative is refused (`ClassIndex.isModuleRelative`, moved here from
  DEC-028's `ModuleFileIndex`): a path with a drive letter, a backslash, an absolute prefix or a `..`
  segment cannot be indexed, and a file outside the module has no honest path at all.

### 8. A duplicate FQN from two paths is a fatal diagnostic

`ClassIndex.put` throws an `IllegalStateException` naming **both** paths:

> two files declare `<fqn>`: `<path A>` and `<path B>`. A fully qualified name is unique in Java, so this
> is two source roots holding the same type — resolve it (drop one root, or rename one type) rather than
> letting the pass pick a winner by iteration order.

Never "last one wins": that is the F-44 failure this repository has already paid for. FQN keys are unique
by the language's own rules, so this is the only collision the design can suffer and no hash-collision
machinery is needed.

### 9. Reading is strict about the format and the hash contract, lenient about extra keys

`ClassIndex.read` refuses a table — and therefore forces a full re-read and re-hash — when it is absent,
unreadable, not valid JSON, carries a `format` this build does not know, or was hashed with an
`algo`/`normalize` this build does not write. Each refusal comes with a reason, which the pass reports as a
`class_index_ignored` divergence in DEC-022's format. Unknown *extra* keys are ignored, so a table from a
newer minor revision is still readable when its contract matches.

The previous table is used for exactly three things: carrying `hashCalculatedAt` (and the sidecar's
`mtime`) forward on unchanged content, reporting `changedSince`, and nothing else. It is never a
correctness input.

### 10. Documents address types by FQN, and `classIndex` replaces `fileIndex`

Every `markerFile`, `views[].file`, `properties[].file`, `allFields[].file` and `artifacts[].file` value is
now an **FQN**, and the root pointer key changed from `fileIndex` to **`classIndex`** — the table's path
relative to the document's own directory, emitted by `ClassIndex.pointerFrom(documentDir)`. The keys
themselves do not change, so the renderer's document shape is untouched and resolution is one table lookup
by name.

**The Java model is unchanged in shape.** `EntityMeta.markerSourcePath`, `ViewMeta.sourcePath`,
`Property.sourcePath` and `ArtifactMeta.file` all still hold module-relative paths for every Java caller
and test; `toJson(entityMeta, classIndex)` and `fromJson(json, fqnToPath)` are the **single conversion
point**. A `file` value with no row is a **bug**, not a fallback: `ClassIndex.fqnForPath` and the writer
fail loudly rather than letting a path leak back into a document. `fromJson` without a table leaves
references **unresolved** (`null`) rather than inventing a path.

### 11. Legacy reading, for one revision

`fromJson` accepts, for one revision, three spellings; **nothing emits two**:

| spelling | how it is read |
| --- | --- |
| the current one | `classIndex` pointer + FQN keys, resolved through `classes.json` |
| the DEC-028 one | `fileIndex` + readable ids, resolved through `files.json` when it is present (`ClassIndex.legacyPathsById`) |
| the pre-index one | `markerSourcePath` / `sourcePath` path strings, read as they always were |

The renderer keeps its two-route lookup (module root first, then the document's own pointer), so a document
written before this decision still renders. The reader is tolerant; the writer is not.

### 12. The pass reports what changed since the previous table

`ClassIndex.Change` is `(kind, fqn, path)` with `kind ∈ {ADDED, REMOVED, CONTENT, RENAMED_TYPE}`:
`ADDED`/`REMOVED` by FQN, `CONTENT` when an FQN is present in both tables and its checksum differs,
`RENAMED_TYPE` when the same path appears with a different FQN in the two tables. `kind`, `modifiers` and
`generated` are deliberately **not** change signal of their own — a change to any of them also changes the
file's content, which `CONTENT` already reports. The pass prints one line:

```
[index] 42 type(s) in classes.json — a added, c content change(s), r removed, n renamed
```

It goes to the pass log, not into the divergence report: it is a fact about what the pass saw, and the
divergence counts are what `gen.cmd` asserts on. This is the kernel an incremental pass needs, answered
without walking and parsing the tree; it is deliberately not a second generation path.

### 13. The source-map **conventions** are adopted, the source-map **format** is rejected

This is the explicit direction from the project owner, and it is a requirement of the change rather than a
rationale: these are the conventions that make a source map usable by many unknown consumers, and they are
what `files.json` implemented only halfway.

| # | Convention (from source maps) | What this index does | Test |
| --- | --- | --- | --- |
| 1 | **One table states a path once; everything else addresses it indirectly.** | `path` appears once per type in `classes.json`, reached through the FQN key, and nowhere else in the metadata tree: a document names a type, never a path. | `ClassIndexTest`, `MetadataFileIdsTest` |
| 2 | **Paths are root-relative and never absolute or `..`.** | The `sourceRoot` header plus the rule that a row's `path` is module-relative with forward slashes, no drive letter, no `..` — enforced by `ClassIndex.isModuleRelative`. | `ClassIndexTest`, `MetadataSourcePathTest` |
| 3 | **The pointer is emitted, not assumed** (`sourceMappingURL`). | Every document carries `classIndex`, the table's path relative to the document's own directory, computed by the writer — so a consumer never guesses the `.jcodebuddy/` layout and the fallback layout needs no special case. | `ClassIndexTest`, `MetadataFileIdsTest`, the bun tests that stage a wrong and a relocated pointer |
| 4 | **Content is never carried** (`sourcesContent` exists; a correct producer leaves it out). | The index records a checksum, a size and a name — never text, and never a `content`/`sourcesContent` key. | `GeneratorGuardTest`, `ClassIndexTest` |
| 5 | **The table is content-addressed, so an unchanged tree produces identical bytes.** | `hashCalculatedAt` is preserved while the checksum is unchanged, keys are derived from names, rows are written in key order, and there is no pass-level timestamp. | `ClassIndexTest`, `MetadataFileIdsTest`, `ExampleRegenerationTest`, the bun determinism test |

**The source-map v3 file format itself was rejected**, for three recorded reasons:

1. **It solves a problem we do not have.** A source map is a *positional join for an ordered reader with a
   program counter* — a debugger walking generated lines in order. Our readers ask a **random-access**
   question ("the row for `…PersonSummary.age`") and a **set** question ("what changed since the last
   pass"). Base64 VLQ delta columns are optimal for the first access pattern and hostile to the second:
   you cannot skip, index or binary-search a delta-encoded string.
2. **Its interoperability benefit does not survive.** The mapping would not be standard anyway: a stock
   consumer would still have to be taught `generatedColumn = artifactId × 9 + roleOrdinal` and the
   extension keys (`x_jcodebuddy.roles`, `x_jcodebuddy.ids`). It would read the envelope and nothing else,
   and a hand-written decoder in Java *and* in JavaScript is a second private format wearing a public name.
3. **It has nowhere to put the facts this index exists to record.** Checksum, `hashCalculatedAt`, `size`,
   `kind`, `modifiers` are not positional mapping data; every one of them would end up smuggled into
   `x_jcodebuddy.*`, which is the tell that the format is a host rather than a fit.

Two source-map ideas are deliberately not used, and saying so is part of the decision: **section offsets**
exist to compose maps whose generated line spaces would collide, while our key space is FQDNs that cannot
collide, so there is nothing to compose; and the FQN key is **not** a `sources`-style *positional* table —
in a source map `sources` is positional because the body is numeric, whereas here the key **is** the name.
A positional table would be a surrogate id by another name.

`plans__p2/plan.sourcemap-locations.md` is **withdrawn** and has been deleted by the change that landed
this decision, so this repository holds one plan for the index and none that contradicts it.

## Alternatives considered

- **Any surrogate id — a 4-byte hash, a content hash, a counter, a positional index.** Rejected (§ 2): an
  id is a fact about the writing pass, its brevity buys a private key space that only our writer can
  maintain, and it is precisely the reference an IDE rename refactor cannot update in a text file. A
  4-byte id does not survive the content it names either: 2³² values over a module's types buys nothing
  the FQN does not already give, and adds a collision case that must be detected and reported.
- **Add `hr.hrg.wyhash:wyhash:1.0.0` as a Maven dependency instead of vendoring it.** Rejected: cheaper to
  keep in sync, but it widens the tooling's dependency surface, which `DependencyBoundaryTest` (DEC-W003)
  exists to hold. Recorded as the fallback if the copy ever proves hard to keep honest.
- **Write `mtime` into the table.** Rejected (§ 6): it is a working-tree property that cannot survive a
  checkout, so a committed table would differ from a regenerated one on every machine. It lives in the
  `mtimes.json` sidecar, which nothing may trust as a correctness input.
- **Keep `files.json` beside `classes.json`.** Rejected: `classes.json` states every path `files.json`
  stated, so keeping both would state every path twice — the exact failure DEC-028 § 3 exists to prevent.
  DEC-028's `files.json` is gone from the layout; only its *reading* survives for one revision (§ 11).
- **The source-map v3 file format.** Rejected for the three recorded reasons in § 13.
- **Give a file that declares no type a row, and an unparseable file a row with a `parseError`.** Rejected
  (§ 7): the key space is types, an invented key would be a surrogate by another name, and a checksum for a
  file nobody could parse is a claim about content that was never read. Both cases are reported instead.
- **Factor the repeated file facts into a `files` legend keyed by path.** Not taken: with 2 member types
  against 37 top-level ones in the example the repetition is two `path` strings and two hashes, and a
  legend would reintroduce indirection (and, if the reference were positional, something id-shaped) to save
  bytes nobody is short of. Recorded as the change to make first if a nested-heavy module ever makes the
  repetition visible — and the reference must then be the **path string**, never an index.
- **A binary or `metadata-arena` encoding.** Rejected: the table's value is that it is diffable,
  greppable and reviewable in a pull request. Off-heap formats remain `metadata-arena`'s business.
- **A separate `index` command, or an IDE plugin owning the table.** Rejected: the table is derived from
  the same walk the pass already performs, so a second entry point would either duplicate that walk or make
  the index stale with respect to the documents it serves. Derived output with the same track policy as
  `metadata/` is the DEC-026-consistent answer.

## Consequences

- **One table, one statement of a path, one reference scheme.** Every module-relative path appears once per
  module; a document cross-references an FQN; and the index answers "does this type exist, what is it, has
  it changed" for any generator, not only the entity one.
- **References are refactor-safe and human-readable.** An IDE rename of a referenced type updates the
  metadata's FQNs like any other text occurrence, and a human reading a diff sees the language's own names
  instead of a manufactured id. `MetadataSourcePathTest.renamingATypeUpdatesEveryReferenceThePassWrites`
  performs that rename end to end and asserts that no document keeps the old name.
- **Size, measured honestly — the documents GREW.** `files.json` was **4 301 bytes**; `classes.json` is
  **14 615 bytes** for **42 rows**. The three `*.metadata.json` documents went from **50 993 bytes**
  (DEC-028, readable ids) to **56 097 bytes** (FQNs) — a rise of **5 104 bytes ≈ +5.1 KB (+10.0 %)** —
  because an FQN is longer than the short id it replaced and 112 file references pay for it. The table is
  inside the plan's 12–15 KB projection; the document growth is **≈3.5× the plan's ≈1 450-byte estimate**,
  which assumed ≈30 characters per FQN where the real names run to 70.
  `index/README.md` also grew, 2 699 → 5 325 bytes, because it now describes a row shape rather than a
  single id → path map, and `mtimes.json` adds 3 634 bytes of git-ignored sidecar.
  **This is not a size optimisation and must never be sold as one.** It buys (a) a class manifest with
  content identity, kind, modifiers, declaration line and a checksum timestamp that every generator
  currently re-derives by walking and parsing, (b) the `hashes.json` reservation of
  `plan.metadata-locations.md` § 2.3.2 cashed in, and (c) one addressing scheme — the language's own —
  where there were two.
- **The plan's own budget was revised rather than met.** `plan.class-index.md` § 5.2 proposed "the three
  documents ≤ 55 KB"; the measured 56 097 bytes exceed it. The bun budget test now asserts documents
  < 60 KB, the class index < 20 KB and their sum < 80 KB, with a comment stating that the point is to
  catch a *shape* regression — a fact repeated once per view, per field or per location again — rather
  than to police a byte. The counterfactual is unchanged: stating a path inline per location instead of
  once per type plus a grouped `at` map would cost tens of kilobytes more.
- **Where the implementation differs from the plan**, recorded so the plan can be reconciled rather than
  read as describing something else:
  - `line` is the declaration's **name** line (`declaration.getName().getBegin()`), not the declaration's
    begin line as the plan's § 4.1 wrote it. For a declaration carrying annotations these differ, and the
    name line is what the other recorded lines mean and what a page link must open.
  - `hashCalculatedAt` is decided in `ClassIndex.stampFileFacts()` at write time; the plan's § 4.3 put the
    decision in `merge(previous)`. `merge` can only remember the previous table, because at merge time no
    row has a checksum.
  - `mtime` moved out of the row into the `mtimes.json` sidecar (§ 6), the plan's own stated fallback if
    the churn of a committed value were objected to. `ClassRecord` still carries an `mtime` component, but
    it is `-1` on both read and write — the sidecar is authoritative — so the record field is a leftover
    rather than a second source of truth.
  - An unparseable source file gets **no** row and a `source_not_parsed` divergence, where the plan's § 2.4
    specified a row with its checksum and size and a `parseError` string.
  - Generated artifacts are registered by `MetadataLocations` (`index.addTypes(moduleRelative,
    read.unit(), true)`) at the moment their locations are extracted, which is after the emitter has
    written them. `ClassIndex.addGeneratedArtifact` exists as the plan's helper for that job and is
    currently unused.
- **The table is deterministic and committable.** Rows in FQN order, no walk order, no pass-level
  timestamp, and a timestamp that moves only with the content: two passes over an unchanged tree produce
  byte-identical bytes, which is what lets a project commit the table and review a change to it in a diff.
- **A consumer that finds a reference it cannot resolve has found a bug, not a missing fallback.** A
  document that cannot resolve an FQN is a broken document; the writer raises rather than writing a path.
- **Negative:** the sidecar is a second file in the directory, and a consumer that mistakes it for a
  correctness input would get a stale answer on a machine whose mtimes moved without a content change. The
  contract says otherwise (a missing or mismatched sidecar costs a full hash), and nothing reads it as a
  gate.
- **Negative:** a rename produces churn — the old FQN as a `removed` row, the new one as `added` — and any
  document committed as a contract carries stale names until the next pass rewrites it. That is the price
  of a reference an IDE can maintain, and `changedSince` names it.
- **The index directory is a DEC-026 subfolder with a track policy**, so the change reaches the layout and
  the `.gitignore` coupling rule, not just the code (DEC-026's amendment).
- **Follow-up work has a defined home.** A generated artifact may one day carry a pointer to its index row
  in its DEC-021 header (tentatively DEC-030), the per-artifact dependency edges (`artifacts[].inputs`)
  are reserved with a stated shape, and the parse-skip optimisation has a correctness rule rather than an
  implementation — all three without changing any consumer's contract (see Out of scope).

## Out of scope

- **A generated-Java pointer to the index row** in an artifact's DEC-021 header — the
  `//# sourceMappingURL`-equivalent idea. It changes emitted Java, so it needs the DEC-021 header and
  DEC-022 naming contracts revisited, a full regeneration and a moved `ExampleRegenerationTest`
  baseline. Tentatively **DEC-030**; deliberately not built here.
- **The per-artifact dependency edges** (`artifacts[].inputs`): the file ids an emitted artifact was
  generated *from*. They are the other half of what an incremental pass needs, and the README reserves
  them.
- **Cross-module index mirroring.** The index is per module; a foreign class is either absent or, in
  future, carried with its module name. A merged repository-wide table is not this decision.
- **The parse-skip optimisation.** A pass *may* skip re-parsing a file whose checksum is unchanged, but
  only if that is provably equivalent (the previous row's type facts are present and no parse error is
  recorded). It is an optimisation with a correctness precondition, not part of this table's contract, and
  if in doubt the answer is to parse.
- **Source content, in any form.** Never. The index records a hash, a size, a name and a timestamp.
- **Replacing `metadata/watch/<toolSet>/metadata.db`** with the class index. The watch agent's cache and
  the generator's inspectable record are different artifacts; consolidation is a later decision.
- **A binary or arena encoding of the table**, and **a repository-wide index**.
- **The withdrawn source-map v3 format**, and any VLQ decoder in either language (§ 13).

## Acceptance criteria

1. **The pass writes `<module>/.jcodebuddy/index/classes.json`**, once per pass, per module — with its
   `format` (`1`), `module`, `sourceRoot`, `hash` contract and a `classes` table in ascending key order —
   never at the repository root and never in another module's tree. *Asserted by* `ClassIndexTest`
   (`theTableDescribesItself`, `everyTypeGetsARowKeyedByItsFullyQualifiedName`) and `IndexLayoutTest`.
2. **One row per type**, member types included, each carrying its declaring file's `path`, `size`,
   `checksum` (16 hex) and `hashCalculatedAt` (ISO-8601 UTC) and the type's `kind`, sorted `modifiers`,
   `line`, `depth` and `enclosing`; **no row carries content**, in any spelling. *Asserted by*
   `ClassIndexTest` (`everyTypeGetsARowKeyedByItsFullyQualifiedName`, `noRowCarriesContent`),
   `TypeFactsTest` and `GeneratorGuardTest`.
3. **There is no surrogate id** — not a short hash, a counter or a positional index, in the table or in a
   document — and same-named types are distinguished by their packages. *Asserted by*
   `ClassIndexTest.theTableCarriesNoSurrogateId` and
   `MetadataFileIdsTest.sameNamedTypesAreDistinguishedByTheirPackage`.
4. **A source path is written once per module, and a document references types by FQN.** Every
   `file`/`markerFile` value resolves in `classes.json`, no module-relative path string or `.java` suffix
   appears anywhere in a document, and each document's `classIndex` pointer resolves to the table.
   *Asserted by* `MetadataFileIdsTest` (`everyReferenceResolvesAndTheIndexDescribesItself`,
   `noSourcePathAppearsOutsideTheIndex`, `everyDocumentPointersAtTheIndex`) and by
   `MetadataSourcePathTest.thePathsAreInTheIndexAndSurviveBeingReadBack`.
5. **A member type resolves.** A reference to `…PersonSummary.Record` has its own row, and a member type's
   row names its enclosing type and shares its declaring file's facts. *Asserted by*
   `MetadataFileIdsTest.memberTypesHaveTheirOwnRows` and `ClassIndexTest`.
6. **Every recorded path is module-relative and true**: forward slashes, no drive letter, no `..`, not
   project-relative, resolves to a file under the module root that declares the type it is attached to —
   an inherited or addon field names its own declaring file, a view outside its marker's package keeps its
   own path, and a generated artifact whose `--java-out` is outside the module is absent from the inventory
   and reported as `artifact_outside_module`. *Asserted by* `MetadataSourcePathTest`
   (`everyIndexPathIsModuleRelative`, `everyRecordedPathIsModuleRelativeAndDeclaresItsOwner`,
   `anInheritedOrAddonFieldCarriesItsOwnDeclaringFile`, `aViewOutsideItsMarkersPackageKeepsItsOwnPath`).
7. **A rename reaches every reference the pass writes.** Renaming a referenced type updates every document
   the pass writes and the index with it — no document keeps the old FQN. *Asserted by*
   `MetadataSourcePathTest.renamingATypeUpdatesEveryReferenceThePassWrites`.
8. **The checksum is the library's**, pinned vector for vector: the empty input, `"a"`, the LF/CRLF/CR
   triplet of one text, and the 16-, 17-, 48- and 49-byte and 10 800-byte inputs all reproduce
   `hr.hrg.wyhash:wyhash:1.0.0`'s own values, CRLF and LF forms of the same content hash equal, and two
   different contents hash differently. *Asserted by* `ContentHashTest`.
9. **`hashCalculatedAt` changes if and only if the checksum changes.** Two passes over an unchanged tree
   with an advancing clock are byte-identical, and editing one byte moves exactly that file's rows'
   `checksum` and `hashCalculatedAt`. *Asserted by*
   `ClassIndexTest.anUnchangedTreeIsByteIdenticalAndAnEditMovesOneRow`,
   `MetadataFileIdsTest.theIndexIsDeterministic` and `ExampleRegenerationTest`.
10. **`mtime` is not in the table.** The sidecar is a separate, git-ignored file that carries an entry per
    row, and the table's bytes do not depend on it. *Asserted by*
    `ClassIndexTest.theMtimeSidecarIsSeparateAndNotACorrectnessInput` and `IndexLayoutTest`.
11. **A duplicate FQN fails loudly, naming both paths** — never "last one wins". *Asserted by*
    `ClassIndexTest.twoFilesDeclaringOneTypeIsAFatalDiagnostic`.
12. **A file that declares no type contributes no row and is reported**; an unparseable file contributes
    no row and is reported by the pass. *Asserted by* `ClassIndexTest` (its fixture includes a
    `package-info.java`, and `everyTypeGetsARowKeyedByItsFullyQualifiedName` asserts the table has three
    rows and the file appears in `typeLessFiles()`).
13. **An unrecognised table is refused with a reason**, so the pass re-reads and re-hashes rather than
    half-believing it. *Asserted by* `ClassIndexTest.anUnknownTableIsRefusedWithAReason` and by the bun
    test "an unrecognised index format is refused rather than guessed".
14. **The renderer reads `classes.json` and resolves the documents' FQNs through it**: a wrong document
    pointer is survived by the module-root route, a relocated table is found by the pointer, and a missing
    table is a loud `html_index_missing` error with nothing rendered. *Asserted by*
    `HtmlRenderBoundaryTest.theRendererExistsAndReadsTheMetadataJson` and the bun tests in
    `scripts/entity-html/entity-html.test.js` under "the module index".
15. **A document written before this decision still reads and still renders**, in both legacy spellings,
    with references left unresolved rather than guessed when no table is supplied. *Asserted by*
    `MetadataSourcePathTest` (`aLegacyDocumentIsStillRead`, `withoutTheIndexReferencesStayUnresolved`) and
    by the bun test "renders a pre-class-index document, references and all absent".
16. **`.jcodebuddy/index/` holds `classes.json`, `mtimes.json` and `README.md` and nothing else** — the
    reserved work is not built prematurely, the DEC-028 `files.json` is gone, the README is created when
    absent and **never overwritten**, and a fallback `<report dir>/index/` gets the table and no README.
    *Asserted by* `IndexLayoutTest` (all three of its cases).
17. **Nothing else regressed**: `ExampleRegenerationTest` stays byte-identical (no emitted `.java`
    changed), `GeneratorGuardTest` stays green (no `.java` under any `.jcodebuddy/`, a report directory
    holds only JSON), `HtmlRenderBoundaryTest` stays green, `DependencyBoundaryTest` still passes — the
    assertion that vendoring replaced a Maven dependency rather than adding one — and the bun suite
    reports the page unchanged and inside its shape budget. *Asserted by* those tests and by
    `scripts/entity-html/entity-html.test.js`.
