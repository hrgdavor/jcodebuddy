# DEC-024: Deep (nested) change tracking — pull over push

## Context

A view field whose value is itself a tracked view gets exactly **one bit** from shallow change
tracking: "this reference was reassigned". That bit cannot express the case that matters most in a
partial-update flow — *the reference is unchanged and a field inside it changed*:

```java
PersonSummary person = load();
person.address().city("Berlin");   // no field of `person` was written
person.changes();                  // empty: nothing at this level changed
```

The change is real and a consumer needs it: a JSON patch, an audit trail, an optimistic-locking
check, or an event payload all have to know that `address.city` moved. `DEC-012` deliberately
defines `changes()`/`changesBuilder()` as a single-level bitset, so this is not a gap in that
contract — it is a second feature, deep (nested) tracking, and it needs its own record.

Three properties of the existing design constrain the answer, and none of them is negotiable in
this release:

1. **The ordinal array is the storage model.** `EntityUpdateTrackingArray` holds an `Object[]` and
   a bitset indexed by ordinal (`DEC-012`, the [Ordinal Array Contract](../../user/patterns/ordinal-array-contract.md)).
   A tracked value is a plain Java object in a slot; there is no wrapper around it and nothing is
   registered when it is stored.
2. **`changes()` and `changesBuilder()` are one shared state with two accessors.** Adding a second
   *meaning* for `changes()` — "changed, considering descendants" — would break every existing
   caller, every test and the `DEC-012` no-op rule, which is defined on one field at a time.
3. **Pay only for what you use** (`DEC-014`). A view that nests nothing must not pay for deep
   tracking, and a view that nests something must pay only in proportion to what it actually nests.

The section below records the decision; the implementation is Phase 6 of
`../../../plans` § 11, and this record is task 6.1 — it is written before tasks 6.2–6.10
so the contract exists first.

## Decision

### 1. Pull, not push

> **Propagation is pull.** A view that can see into its own fields walks into every field whose
> value is itself a `ViewChangeTracking` when it is asked for the deep result, and ORs the child's
> state into the *reported* result — never into its own bitset. The child is asked; the parent is
> not told.

The deep accessor is a **third** method with the same immutable/mutable discipline as the shallow
pair:

| Method | Returns | Mutability |
|---|---|---|
| `changes()` | the changed fields, this level only | immutable snapshot |
| `changesBuilder()` | the same state, live | mutable |
| `changesDeep()` | the changed **paths**, this level and every level below | freshly built list |

`changes()` and `changesBuilder()` are **never overloaded and never made context-dependent**. A
caller that wants the shallow answer keeps getting it, unchanged, with the same cost. A caller that
wants the deep answer asks a differently-named method, so which one is being used is visible at the
call site.

`changesDeep()` reports **`List<ChangePath>`**, one entry per changed leaf.

**Why pull wins.** A push model — the child holds a back-reference to the parent plus its own
ordinal and calls `parent.mark(ordinal)` on every change — is genuinely zero-cost when nothing
changed. It was rejected for three reasons:

1. **It contradicts the ordinal-array design.** For a child to call back, *every* tracked value in
   *every* slot must be wrapped in a notifying proxy at the moment it is stored. That is a
   per-value allocation and an indirection on every read, paid by every view, changed or not — the
   opposite of `DEC-014`'s discipline. It also means the value in the slot is no longer the value
   the caller stored.
2. **It destroys sharing and reuse.** A pushed child can have exactly one parent, because it holds
   one back-reference. Under pull a child can be held by any number of parents and reports the same
   answer to each; the state-sharing requirement of `S5`/`DEC-012` extends to nesting for free.
   A child cannot be moved between parents, cached, or compared across two loaded versions under
   push.
3. **It is invisible control flow.** A `mark()` call issued from inside another object's setter is
   exactly the kind of hidden wiring `DEC-019` rejects. The pull walk is a concrete, IDE-navigable
   method body — a developer can read `changesDeep()` and see every hop.

The cost pull accepts is a walk on read. § 6 records the benchmark that measures it: pull on a view
with **no** nested change should be free, and the decision would only be reopened if it were
materially worse there.

### 2. The `ChangePath` shape

```java
public record ChangePath(FieldDef field, int listIndex, ChangePath next) { }
```

- `field` — the field at this level.
- `listIndex` — the index inside a `List` field, or **`-1`** for "this level is not a collection
  element".
- `next` — the rest of the path, or **`null`** at the leaf, i.e. at the field that actually
  changed.

A shallow change says *which* field changed; a path says *where*, and a chain of paths is a
navigable description of every deep change. It is an ordinary record with public accessors, not an
opaque handle: walking it is a direct Java call (`next()`, `leaf()`, `depth()`, `render()`), so the
control flow is visible in source (`DEC-019`).

`render()` produces `outer.inner[3].leaf` — the field names, with a bracket only where a level is a
collection element. The list index is an **integer in the path**, never a field name, so an element
index can never be confused with a document member.

### 3. The collection semantics

A field whose value is a `List` of tracked views is the hard case, and it is decided here in full.
Such a collection changes in **two independent ways** and both have to be reportable *distinctly*:

| Finding | Representation |
|---|---|
| an entry that stayed put changed inside | a `ChangePath` with `listIndex` set, or `ListDelta.kind() == FIELD_CHANGED` |
| an entry appeared, disappeared or moved | `ListDelta.kind() == ADDED` / `REMOVED` / `REORDERED` |

The value type is a small record in `hipster-entity-core`:

```java
public record ListDelta(ListChangeKind kind,
                        int index,
                        int previousIndex,
                        Object identity,
                        List<FieldChange<?>> fieldChanges,
                        boolean fallback) { }
```

- `index` is the entry's index in the **current** list, except for `REMOVED`, where it is the index
  it occupied in the baseline.
- `previousIndex` is where the entry was before, or `-1` when it was not there (an addition).
- `identity` is the entry's `Identifiable.id()` when it has one, else `null`.
- `fieldChanges` is the per-entry field delta, non-empty only when there is an element to compare
  against — an added or removed entry has no previous state to diff.
- `fallback` is `true` on a delta produced by the positional fallback (§ 3.2).

The kind enum is closed and explicit: `UNCHANGED`, `FIELD_CHANGED`, `REORDERED`, `ADDED`,
`REMOVED`, `REPLACED`. A structural change is **never** encoded as a field delta, and a field delta
is never encoded as a structural change.

#### 3.1 Reorder detection requires a stable identity

Reorder detection *is* "same identity, different index". Comparing entries by `equals` answers a
different question (content equality, not identity) and would report a reorder every time two
entries happen to be equal and every time an entry is edited into equality with its neighbour. The
element type must therefore be **`Identifiable`** (`DEC-017`).

Given identities, "did this entry move?" is answered **relative to the entries that survived**, not
against absolute indices:

> An entry is reported as `REORDERED` when it is not part of the **longest run of surviving entries
> that is still in baseline order**.

This distinction is not cosmetic; the two obvious alternatives are wrong in both directions:

- **Comparing each entry's index with its own baseline index** reports every survivor that merely
  shifted down when an earlier entry was removed. They did not move — the removal alone accounts
  for the change — and reporting them turns one removal into "a removal plus *N* spurious
  reorders", which is a structurally wrong patch.
- **Comparing only the surviving relative order** is complete but reports an entry whose absolute
  index never changed: reversing three entries reports the middle one, which stayed exactly where it
  was.

Keeping the longest in-order run also makes the report *small*: a two-entry swap reports one move
(either entry can be the one left in place), a three-entry reversal reports two, a single entry
moved to the front reports one, and a stable prefix is never reported. Where several runs are
equally long the earliest is kept, so the answer is deterministic rather than merely correct.

#### 3.2 No identity means a diagnostic and a fallback, never a guess

If the element type is not `Identifiable` — or if two entries report the **same** identity, which
makes an identity name more than one position — the tracker refuses to guess. It:

1. reports positional deltas only, marking each `fallback = true` and using the honest
   `REPLACED`/`ADDED`/`REMOVED` kinds a positional comparison can actually support;
2. raises a `CollectionDiagnostic` (`collection_element_not_identifiable` or
   `collection_duplicate_identity`) reachable from the contract, so the limitation is visible to the
   caller and to the JSON patch;
3. **never** pairs entries by index and calls the result a move.

The identity objects are compared **directly** — there is no name→ordinal `HashMap` anywhere in the
path, per `DEC-016`.

#### 3.3 The baseline

A tracker takes the identity list of the collection as its **baseline**. The baseline is taken by
the first question asked of the tracker rather than at construction time, because an array-backed
view is built from its positional array and its list field may legitimately be filled after that
array was handed over; a construction-time baseline would call those entries "added" and report a
change on a view nobody has touched. `clearChanges()` / `snapshot()` move the baseline forward on
demand, which is how a caller says "this is the version I loaded".

A field write that installs a *different* list instance is reported to the tracker, so the content
difference between the old and the new list is what gets reported. A wholesale replacement with no
entry in common is therefore a removal of every baseline entry plus an addition of every new one,
which is exactly what happened.

#### 3.4 What the deep walk reports for a collection

- one `ChangePath` per element that changed in place, carrying that element's `listIndex`;
- **one** summary path naming the field itself when the collection changed structurally, because a
  structural change has no single field to point at; the kinds are read from
  `collectionDeltas()`.

A collection is walked **whether or not its own field was marked**: mutating an entry in place, and
adding or removing one, writes to no field of the parent, so the marked ordinals alone would never
reach it.

### 4. The nested-change index, and the `instanceof` on the array path

The nested-change index is allocated **only** for a field whose declared type (or generic collection
element type) is itself a trackable view. A view with no nested trackable field pays nothing: its
deep walk is a single loop over the same ordinals the shallow walk visits.

An **array-backed** view has no declared field types at runtime — it stores an `Object[]`. It
therefore discovers nesting with an `instanceof` test on the value it already holds, only for
marked ordinals (and, for collections, only for fields that hold a `List`). A generated builder
answers the same question from its own typed fields. Both satisfy "pay only for what you use"; the
difference is recorded here so a future reader does not read the `instanceof` as a design
violation. The `instanceof` is not reflection and it is not a lookup table: it is a test on the
value the field already holds, which is the only honest question an untyped slot can answer.

### 5. The JSON patch

`hipster-entity-jackson` emits the deep result as a nested RFC 6902-like patch document derived from
`changesDeep()` (`EntityJacksonDeepChangeSerializer`, reached through
`EntityJacksonMapper.toJsonDeepChanges`), **alongside** — not instead of — the shallow
`EntityJacksonChangeSerializer`. A leaf operation emits its `"current"` value and **no**
`"previous"` member anywhere, because the tracker keeps no previous value (`DEC-012` revision); an
audit-style old&nbsp;→&nbsp;new document is a comparison of two instances the caller holds. A deep
patch names the leaf through a path array whose collection
level is an integer index, so an addition at the end is not confused with a document member. A
field the view does not have is **skipped, never resolved through a `HashMap`** (`DEC-016`), and the
positional fallback is stated in the document (`"fallback": true` plus the diagnostic) rather than
silently presented as identity matching.

## Alternatives considered

- **Push propagation (child → parent back-reference + `parent.mark(ordinal)`).** Zero-cost when
  untouched, rejected: it requires wrapping every tracked value, it makes a child single-parent, and
  it hides propagation inside another object's setter. See § 1.
- **Overloading `changes()` to mean "deep" once a view nests something.** Rejected: it makes one
  method mean two things depending on the instance, breaks the `DEC-012` one-field no-op rule for
  every existing caller, and hides a cost change behind an unchanged call site.
- **Making `changesDeep()` a copy of the child's state ORed into the parent's bitset.** Rejected:
  that is push by another route — the parent's own `changes()` would start reporting descendants,
  `clearChanges()` semantics would have to cascade, and a shared child would acquire a parent.
- **Identity by `equals` on the element.** Rejected: content equality is not identity. It reports a
  reorder whenever two entries are equal and whenever an edit makes an entry equal to its
  neighbour.
- **Absolute-index movement for reorder detection.** Rejected: a removal then reports every
  following entry as moved. See § 3.1.
- **Element identity from a `Map<Object, Integer>` built per call.** Rejected by `DEC-016`: it
  allocates and hashes on every call, and the comparison is a direct `equals` over an array.
- **Deep tracking in `hipster-entity-api`.** Deferred for the same reason `S3`/`X1` were deferred:
  the accessors are typed on the `EEnumSet*` family, whose concrete implementations live in
  `hipster-entity-core`.

## Consequences

### Positive

- **Nested change is reportable without touching the shallow contract.** `changes()` keeps its
  meaning, its cost and its `DEC-012` semantics; a caller opts into the deeper view by naming a
  different method.
- **Children stay reusable and shareable.** No parent/child lifecycle coupling, no ownership
  question, and a child shared by two parents reports the same answer to both.
- **The walk is source-visible.** Every hop is an ordinary method call on a typed interface, so an
  IDE can follow the flow from `changesDeep()` to the leaf (`DEC-019`).
- **A view that nests nothing pays nothing.** The nested index exists only where a nested trackable
  field does.
- **The ambiguity is stated, not hidden.** Where reorder detection is impossible the tracker
  reports a diagnostic and a fallback rather than producing a patch that looks like a move.
- **The JSON patch was implementable from the contract alone.** The deep patch is derived from
  `changesDeep()` plus the collection deltas; no parallel schema and no reflection were needed.

### Negative

- **Pull costs a read-time walk.** The cost is proportional to the nesting depth and the number of
  live children, and it recurs on every call. § 6 measures it; it is the price of § 1's three
  benefits.
- **The array path cannot know a field's declared type.** It discovers nesting from the values it
  holds, so a view that momentarily holds `null` in a nestable field reports no path inside it. That
  is correct (there is nothing there to change) but it means "this view cannot nest" and "this view
  currently nests nothing" are not distinguishable at the array level.
- **A collection field is tracked positionally, so it allocates one tracker per list field.** The
  tracker is one object plus a baseline array per list field, allocated once, not per write.
- **Duplicate identities are a real hazard.** Two entries sharing an id silently degrade the whole
  collection to the positional fallback. The diagnostic makes it visible, but nothing prevents it
  at compile time.
- **A leaf inside a collection element is not typed by this view's type table.** A leaf inside a
  collection element is a field of the *element*, not of the view being serialized, so it is not in
  that view's type table; the leaf's **current** value is written as the POJO it is. No leaf carries
  a `previous` value — the tracker keeps none (`DEC-012` revision) — so there is no typed previous
  scalar to state, and nothing to lose by it not being typed.
- **`ChangePath` carries no value.** Only the path and the field are available; a consumer that
  needs the value must ask the element that holds it. That keeps `changesDeep()` allocation-light
  but means the JSON patch has to consult the element trackers for each leaf's **current** value.

### Follow-up

- **Task 6.5 (generator wiring)** is a Phase 6 task not covered by this record: a generated tracking
  builder must detect that a field's declared type — including a generic collection of them — is
  itself a trackable `@View` type and emit the deep index, rather than the array path's value-level
  discovery. Until then the array path and the hand-written fixture are the materializations that
  exercise this contract.
- **Benchmark the two axes and record the numbers.** Task 6.9 adds
  `pullNoNestedChange`/`pullDeepNestedChange` (plus their shallow counterparts) to
  `EEnumSetTrackingJmhBenchmark`. The benchmark is **not run** as part of this task — it is written
  and registered so it compiles. The decision above is only revisited if pull turns out materially
  worse on the no-nested-change case, where it should be free.
- **Polymorphic view roots in the deep path.** A discriminated root must be representable at every
  level of a `ChangePath`; the path itself is agnostic (it names fields), but the generator side of
  6.5 has to emit the same wiring for a family member as for a plain view. Not exercised here.
- **A patch *applier*.** This record specifies emission only. Applying the deep document — including
  the collection operations — is a separate, testable piece.

## Out of scope

- **Push propagation.** Rejected, not deferred. There is no flag and no future switch.
- **Deep tracking of values that are not tracked views.** A nested plain object, a nested `Map`, or
  a list of records is not tracked at any depth; the deep walk descends only into values that
  implement `ViewChangeTracking`. A collection of tracked views is the one container that is
  descended into.
- **A deep `changedValues()` analogue.** `changedValues()` remains the shallow list of this level,
  one `FieldChange` per marked ordinal carrying the value the field holds **now**. There is no deep
  previous/current pair to expose: an element's per-field delta carries the element's current values
  too, and an added or removed entry has no previous state to diff. A caller that wants an audit
  document pairs the patch with the baseline instance it holds (`DEC-012` revision).
- **Automatic reorder detection without identity.** There is no heuristic and no content-based
  matching; a non-identifiable element type gets the diagnostic and the fallback.
- **Persisting a `ChangePath`.** Paths are in-memory values. Nothing about their shape is a wire
  format; the JSON patch is the wire form.

## Acceptance criteria

- `changes()`/`changesBuilder()` MUST keep their `DEC-012` meaning and MUST NOT be overloaded or made
  context-dependent; the deep view MUST be a third method (`changesDeep()`).
- `changesDeep()` MUST NOT mutate the parent's own bitset: calling it MUST leave `changes()`
  unchanged.
- A child shared by two parents MUST report the same deep answer to both.
- `ChangePath` MUST use `-1` for "not a collection element" and `null` for "at the leaf", and its
  `render()` MUST show a collection index in brackets.
- A `List` field of tracked views MUST report an add, a remove, a reorder and an in-place field
  delta as four **distinct** findings.
- Reorder detection MUST report an entry only when the longest in-order run of surviving entries
  does not contain it; a removal MUST NOT produce reorder deltas.
- A non-identifiable element type MUST produce positional deltas marked `fallback` plus a
  `CollectionDiagnostic`; two entries sharing an identity MUST do the same.
- The nested index MUST be allocated only where a nested trackable field or a `List` field exists; a
  view with neither MUST report an empty `collectionTrackers()` and a deep walk equal to the shallow
  one.
- An `ArrayBackedViewProxyFactory` updatable view MUST produce the same `changesDeep()` result as a
  builder-side tracking holder for the same mutation sequence.
- The deep JSON patch MUST name the leaf through a path array whose collection level is an integer
  index, MUST emit add/remove/move as separate operations, MUST skip an unknown field, and MUST state
  the positional fallback when it applies. A leaf MUST carry its `"current"` value and MUST NOT carry
  a `"previous"` member.
- The deep-patch serializer MUST NOT introduce a Jackson dependency into `hipster-entity-core`.

## Invariants this record fixes

| # | Invariant |
|---|---|
| 1 | `changes()` and `changesBuilder()` are one shared state, shallow, and never context-dependent. |
| 2 | `changesDeep()` is a third accessor with the same immutable/mutable discipline. |
| 3 | `changesDeep()` never writes to the view it is called on, at any depth. |
| 4 | `ChangePath.listIndex` is `-1` outside a collection element; `ChangePath.next` is `null` at the leaf. |
| 5 | Structural collection change and per-entry field delta are always distinguishable. |
| 6 | Reorder detection requires `Identifiable`; without it, fall back and report — never guess. |
| 7 | Two entries with the same identity are treated as not identifiable, with the same fallback. |
| 8 | A view that nests no tracked view and holds no `List` allocates no nested index. |
| 9 | The deep result is identical on the proxy path and the builder path. |
| 10 | No name→ordinal `HashMap` is built anywhere in the deep path (`DEC-016`). |
| 11 | `hipster-entity-core` gains no Jackson dependency. |
