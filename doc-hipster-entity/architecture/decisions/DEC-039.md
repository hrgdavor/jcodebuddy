# DEC-039: The repository's top-level module groups

- Status: Accepted (maintainer's direction, 2026-10-02)
- Date: 2026-10-02
- Owners: project
- Related docs: [DEC-037 — one metadata engine in `jcodebuddy-core`](DEC-037.md), [DEC-038 — the modules around the engine](DEC-038.md), [DEC-026 — `.jcodebuddy/`](DEC-026.md), [DEC-031 — project-automations are living code](DEC-031-project-automations-are-living-code.md), [`AGENTS.md`](../../../AGENTS.md) § 2, [`module-map.md`](../../../doc/architecture/module-map.md), [`plans/unified-plan.md`](../../../plans/unified-plan.md) step 3.0o

## Context

The maintainer's direction, kept as given:

> now that I think of it we should start separating all the groups like we did for webview and move things
> into 4 folders — webview (already moved things into it), watch (move java-watch* here), hipster-entity
> (move hipster-entity* here), jcodebuddy (move jcodebuddy* here and jwa*). others to be decided. do this
> moving before we continue unified plan

And, on the `jwa*` modules being part of the watch lineage rather than its own thing:

> jwa* packages were prototype in java-watch* what is now intended to jcodebuddy and depends on java-watch.
> java-watch* are own project developed here together in this phase when many changes will be needed to
> reorganize

Ask a person where a module is today and the answer is "at the root", for twenty-eight modules, in a mixture
of four families that the names already imply. `webview/` was grouped first (`webview/core/webview-core`,
`webview/eclipse/webview-eclipse`), which is the shape this record extends.

## Decision

**1. Group the reactor by family, in four top-level folders.** `webview/` (done), **`watch/`** for
`java-watch*`, **`hipster-entity/`** for `hipster-entity*`, **`jcodebuddy/`** for `jcodebuddy*` — and, because
DEC-038 renames `metadata-server` to `jcodebuddy-meta`, for `metadata-*` and `jwa*` as well. "Others to be
decided" is honoured rather than pre-empted: `hipster-ioc*`, `merge-java` and `project-automation` stay at
the root until a later decision says otherwise.

**2. A module keeps its full name inside its group.** `hipster-entity/hipster-entity-tooling`,
`jcodebuddy/jcodebuddy-core`, `watch/java-watch-agent`. This matches `webview/core/webview-core`, and it
keeps the directory name equal to the artifactId, so every script, test and doc that names a module stays
greppable and a Maven error naming an artifactId still points at a path a reader can guess.

**3. `java-watch*` is its own library, developed here, and grouping it is not absorbing it.** The modules keep
their `hr.hrg.watch2.*` packages and their independence; `jcodebuddy-meta` (DEC-038) depends on them as
libraries. `jwa-builder`/`jwa-builder-api` go to `jcodebuddy/` because they are codegen parts — the direction
DEC-038 already records, including the duplicate `SourceSplicer` that absorption collapses.

**4. The layout is a fact the build reads, not a convention tests re-derive.** The root POM's `<module>`
entries are the one record of where a module is, so:
- the gate selects modules by `:artifactId` (`scripts/lib/gate.js`), which is location-independent;
- a test that needs a module's directory asks `CompileHarness.moduleDir(artifactId)`, which reads the root
  POM, rather than spelling out a path.

This is the part that matters beyond the move itself: before it, `CompileHarness.findRepoRoot()` guessed "the
nearest pom.xml whose directory starts with `hipster-entity-`", and the day the modules moved that guess
returned the *module* directory, so thirty test classes failed while every generated-source compile looked
for a classpath that cannot exist. A layout that tests re-derive is a layout that breaks them on every move.

**5. The move is scripted, and it is a migration artefact worth keeping.**
[`scripts/move-to-groups.js`](../../../scripts/move-to-groups.js) renames the directories, fixes each moved
POM's `<parent><relativePath>`, rewrites the root POM's `<module>` entries, rewrites path references in text,
and repairs what a flat rewrite cannot prove (a sibling link between two modules that moved together; a link
whose target did not move) — printing anything it cannot prove rather than guessing. It is idempotent, and it
keeps a `--dry-run`.

## Consequences

- **Positive.** The tree's top level says what the repository is made of; a module's location is derivable from
  its name and recorded in one place; tests no longer encode the layout; the next group move (and the "others
  to be decided") is a config change plus one script run.
- **Negative.** Every path reference moved with the modules (361 files in the first group alone), and the
  modules outside the recorded gate carry their own build evidence until step 3.0k grows it — the gate covers
  `jcodebuddy-core` and the six `hipster-entity` modules only. Two accidental tracked zero-byte files at the
  root (`hipster-entity`, `explicit`, from commit `28ad1d5`) had to be removed; one of them blocked the
  `hipster-entity/` folder.
- **Neutral.** No module's artifactId, package or behaviour changes in this record. DEC-038's renames
  (`jcodebuddy-meta`, `jcodebuddy-builder*`) are separate, later steps.

## Migration

Step **3.0o** in [`plans/unified-plan.md`](../../../plans/unified-plan.md): the four groups, in the order
`hipster-entity/` (done, gate green), `watch/`, then `jcodebuddy/`. Each carries the gate for what the gate
covers, a targeted build for what it does not, and a link check; each is one commit.
