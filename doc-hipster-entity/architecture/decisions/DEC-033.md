# DEC-033: One serving host per project — the published port, the `/health` identity, and the port claim

- Status: Accepted
- Date: 2026-09-26
- Owners: project
- Related docs: [DEC-026 — `.jcodebuddy/` as the per-module output root](DEC-026.md), [DEC-032 — `.jcodebuddy/` in two scopes](DEC-032.md), [`webview/doc/webview-host-api.md`](../../../webview/doc/webview-host-api.md), [`webview/conformance/bridge-decisions.json`](../../../webview/conformance/bridge-decisions.json), [`webview/PLAN-webview-suite.md`](../../../webview/PLAN-webview-suite.md) (D7, D8), [`AGENTS.md`](../../../AGENTS.md) § 1–2

## Context

Four hosts can serve one project over loopback HTTP and LSP: the standalone `webviewd`, the
JetBrains plugin, the VS Code extension, and the `jwa-sidecar`. They answer the same routes,
they are held to the same `/health` document by a conformance vector, and they each had their
own idea of a port:

| host | port before this decision |
| --- | --- |
| `webviewd` | ephemeral by default, published in `.jcodebuddy/webview/host.json`; a second start **refused** (exit 2) while the recorded pid lived |
| `webview-jetbrains` | a configured port (18881 by convention); a taken port logged a warning and the bridge stayed off |
| `webview-vscode` | a configured port (18882 by convention); `EADDRINUSE` produced an error notification and no bridge |
| `jwa-sidecar` | `jwa.sidecar.jumpPort`, default 7979; a taken port failed the jump service |

Four problems, and the fourth is the one that made this a decision rather than a bug fix:

1. **A page could not always find the port.** Only `webviewd` published it. The IDE hosts had
   to be told, which is why `data-bridge-port="18882"` is hard-coded in example pages and why
   the READMEs carry a table of "which port is which host".
2. **`/health` could not say who was answering.** It carried `plugin` (a reverse-DNS id),
   `port`, `allowedOrigins`, `tokenRequired`, `bridgeVersion` and `capabilities` — everything
   except *which editor* this is and *which project* it serves. A page that found a bridge on
   a port had no way to know what it had found.
3. **Two IDEs on one project is normal and was not modelled.** A debugger in one window and a
   diff in the other is how people work. With one fixed port each, the second editor either
   fails to bind or binds a second bridge for the same project.
4. **"The port is busy" was being treated as "a bridge is there".** It is not: the occupant may
   be an unrelated application, a bridge for a different project, or a stale record of a host
   that died. Acting on the wrong one of those either starts a duplicate bridge or refuses to
   start at all.

The cost of getting this wrong is not a failed request, it is a **silent mis-route**: an edit
proposed for one project applied into another IDE's buffer, and an undo that lands in the wrong
history. That is why the rule is written down once, implemented once per language, and asserted
against shared tests.

## Decision

### 1. Every host publishes the port it actually serves on

`<project>/.jcodebuddy/webview/host.json` — the file `webviewd` already wrote — is now written
by **every** host, with the same fields, in the project it was pointed at (DEC-032: project
scope, derived, git-ignored, no secret in it).

```json
{
  "plugin": "hr.hrg.jetbrains.webview",
  "ide": "IntelliJ IDEA",
  "pid": 4312,
  "port": 18881,
  "sticky": false,
  "project": "D:/wrk/java/jcodebuddy",
  "tokenPath": "D:/wrk/java/jcodebuddy/.jcodebuddy/webview/token",
  "capabilities": ["edit", "open", "select"],
  "startedAt": "2026-09-26T09:12:44.318Z",
  "host": { "name": "jetbrains", "available": true, "lineNavigation": "exact", "note": "…" }
}
```

The port is **the port that was taken**. It is also the port this **checkout** is now on: a later
start asks for it rather than for a fresh one (§ 6), which is what keeps a checkout that had to
move from colliding on every restart. The token itself is never in this file, only the path to it.

**The record outlives the host that wrote it.** A host that stops — cleanly or not — leaves it in
place, and `pid` plus `startedAt` are what it said about whoever wrote it last. Deleting it on
shutdown would make an ephemeral port change on every restart and would silently throw away a
`sticky` pin, so nothing deletes it automatically: a user removes the file to forget the port, and
`webviewd --no-sticky` clears only the pin. **"Is a host there?" is therefore never answered by
this file** — it is answered by asking the port (`HostPortClaim.occupantOf`), which is why a
record left by a stopped host misleads nobody.

**This is host state, not configuration, and it must not be filed as configuration.** The
port in the file is a fact about one served directory on one machine — meaningless in a clone,
wrong the moment the directory moves, and different for two worktrees — so it **MUST NOT** be
written into `.jcodebuddy/conf/`, the tracked subtree that holds what a project wants committed
(DEC-026's final amendment), and **MUST NOT** be written into a `config` file in either scope
(DEC-032 § 2). What *may* be configuration is the project's **default** port — "a fresh checkout
asks for 18882" — because that means the same thing to everyone; the current port and its pin do
not, which is exactly why they live in an ignored per-project file that any reader may use and
nothing may trust.

Two consequences follow and both are implemented: the state directory carries its own
`.gitignore` (`*`), so publishing a port never leaves an untracked file in a project that has no
JCodeBuddy ignore policy; and because the record survives a stop, two hosts for one project take
turns on one port without either of them erasing the other's record.

### 2. `/health` names the editor and the project

Two keys are **appended** to the document every host answers with, so a reader that walks the
keys in order keeps seeing the six it always saw:

```json
{ "plugin": …, "port": …, "allowedOrigins": …, "tokenRequired": …,
  "bridgeVersion": …, "capabilities": [...], "ide": "IntelliJ IDEA", "project": "D:/wrk/…" }
```

- `ide` is a **human** name (`"IntelliJ IDEA"`, `"Visual Studio Code"`, `"Zed"`), where
  `plugin` is an id. A host that has no name to give answers `"unknown"`; the key is never
  absent.
- `project` is the directory that endpoint serves, forward-slashed, and the **empty string**
  when the host does not know it yet (the sidecar before LSP `initialize`). The key is never
  absent either: "not known" and "no host" must not look the same.

Both are **required keys**: `HostHealth.REQUIRED_KEYS`, the TypeScript `HealthDocument`, and
`webview/conformance/bridge-decisions.json` → `healthKeys` are the one list, and the Java and
Node tests both assert against it. Neither value is a secret — both are already in the
project's `host.json`, which any process that can read the checkout can read.

### 3. The port claim: four cases, one rule

`HostPortClaim` (Java, `webview-core`) and `BridgePolicy.decidePort` +
`HostRegistration.claimPort` (TypeScript) implement one table:

| the requested port is… | and the occupant is… | what the host does |
| --- | --- | --- |
| free | — | **start** on it |
| taken | a webview host serving **this** project | **skip**: open no endpoint at all, and say so |
| taken | a webview host serving **another** project | **start** on the next free port |
| taken | anything else (an unrelated app, or nothing recognizable) | **start** on the next free port |
- **The occupant is asked, not inferred.** The port is probed with a plain
  `GET http://127.0.0.1:<port>/health` (no token: the endpoint is unauthenticated by design,
  and a token could not be presented to a host we have never spoken to). Only a document
  carrying both `plugin` and `port` counts as a webview host; JSON without them, a non-200, a
  refusal and a timeout all mean "not a host", which means "take the next port".
- **Twenty consecutive ports are tried** (`DEFAULT_ATTEMPTS`, identical in both languages).
  Exhaustion is not a crash: the host **serves nothing** and says which range it tried. Binding
  an arbitrary port, or falling back to the requested one, would be worse than not serving.
- **Port `0` is never probed.** An ephemeral port cannot conflict; the operating system picks
  one and `webviewd` keeps `--port 0` as its default.
- **The descriptor is checked first**, before the port loop, because a live host for this
  project may be on a port nobody asked about — probing only the requested port would find it
  free and start a second bridge for one project. A descriptor written by the host's **own**
  process is ignored, so a host can restart on its own published port; a descriptor whose port
  does not answer is not an occupant, because the file can outlive the process.
- **A host removes only its own descriptor** when it stops (`deleteIfOurs`). Hosts take turns
  on one port, and the one that shuts down last is not necessarily the one that wrote the file
  that is there now.
- **The claim binds.** A host that can bind its own server passes an attempt that binds and
  hands the bound server back, so the port reported free is a port already held. There is no
  check-then-bind window. `HostPortClaim.systemAttempt()` is the fallback for a host that
  cannot (it probes with a `ServerSocket` and releases it), and it is documented as the
  weaker of the two.

### 4. "Skip" is not "refuse"

A host that skips because another host serves its project opens no socket and **keeps running**:
the IDE keeps working, and the page keeps working against the host that is already there. The
skip is logged (and shown in the JetBrains settings pane) with the occupant's name and port, so
the state is discoverable rather than mysterious.

`webviewd` keeps its documented exit code: exit `2` when a live host already serves the
project (the caller usually wants that host's port, and the message says where to read it),
exit `1` when no port in the range could be taken.

### 5. A port can be pinned, and a pinned port is never moved

Moving to the next free port is the right default — a port is a deployment detail nobody wants to
think about — but it is the wrong answer when the port is the point. So a project may **pin** the
port it is served on, and every host must honour it:

> **`sticky` in `<project>/.jcodebuddy/webview/host.json`.** When it is `true`, that file's port is
> the only acceptable one: a host serves on it, skips when a host already serves this project on
> it, and **fails with an error notification** when anybody else holds it. It never moves.

- **It lives in `host.json`, not in configuration.** The pin is a *local property of the port this
  checkout is using*: per worktree, per machine, changed by hand or by a command. Configuration
  cannot hold it, because configuration is committed and shared (DEC-032 § 2) — and pinning a
  committed port would pin it for every worktree at once.
- **The case it exists for is several git worktrees of one project.** One repository checked out
  several times is several directories, each with its own `host.json`, all sharing one committed
  preference — so the second worktree must be free to take the next free port, while the worktree
  the user wants in a bookmark, a firewall rule or a second screen says `sticky: true` and keeps
  its port.
- **It is set by a person or a command, and it outlives the process that set it.**
  `webviewd --sticky` pins whatever port that project is served on (and can be run against a
  project another host is already serving, because the pin belongs to the port, not to the
  process); `webviewd --no-sticky` clears it; editing the file does both. Both flags take effect
  **even when the run cannot serve**, since a user who asked for a pin should not have to keep a
  host alive to keep it.
- **Two actions, not one.** A pinned port that already serves this project is `SKIP` (the state
  the pin asks for, not an error), and one held by anybody else is `FAIL` — a third
  `HostPortClaim.Action` you cannot get from the four-row table above. `webviewd` exits `2` on
  `FAIL`, the same code as a usage error: the run did not do what it was told.
- **"One bridge per project" still outranks the pin.** A live host already serving this project on
  *another* port means `SKIP`, because the pin is not an invitation to start a second bridge.
- **The sidecar cannot honour it.** Its port is chosen before its project is known (the project
  arrives with the LSP `initialize`), so its launcher's setting is the pinning mechanism there;
  this is the same limitation that already made it apply the port loop alone, and it is stated
  rather than papered over.

### 6. A project may name the port it prefers as a default, in committed configuration

A new checkout should start somewhere sensible without anyone configuring an editor, so a project
may state its **default** in the **tracked** configuration subtree:

```json
// <project>/.jcodebuddy/conf/webview.json  — committed, reviewed, shared by the whole team, and OPTIONAL
{ "port": 18882 }
```

The port a run should ask for is resolved in one place per language
(`HostConfig.requestedPort`, `HostRegistration.requestedPort`), first match wins:

| # | source | what it is | in git |
| --- | --- | --- | --- |
| 1 | the run's explicit flag or IDE setting | a decision by the person starting this host | — |
| 2 | `webview/host.json` → `port` | the port this **checkout** is currently on | **no** |
| 3 | `conf/webview.json` → `port` | the project's **default**, for a checkout with no record yet | **yes** |
| 4 | the host's built-in fallback | ephemeral (`webviewd`), or off (the IDE hosts) | — |

The current port beats the committed default, and that ordering is the substance of the two-file
model: a checkout that had to take the next free port (a second worktree, a colleague's process on
the conventional port) keeps it instead of drifting back and colliding there again on every start.
Deleting `webview/host.json` is how a user goes back to the default.

Five rules make it usable rather than a trap:

- **`conf/webview.json` is a default, never a pin, and it is optional.** Nothing stops a second
  worktree from taking the next free port, nothing stops a run from overriding it, and a project
  with no such file is the normal case — it gets its host's fallback. A project that wants a pin
  uses `sticky` (§ 5).
- **It is configuration, so it lives in `conf/`** — the reserved, tracked subtree — and never in
  the ignored `webview/` directory, which holds this checkout's current port, its pin, its token
  and its `pid` (DEC-032 § 2). Two files, two lifetimes, and no field in common.
- **The user-home scope is not consulted for a port at all.** Neither step 2 nor step 3 has a
  user-scope counterpart: a port names a socket for one served directory, so a machine-wide default
  would have every project on the machine ask for the same port at once (DEC-032 § 2).
- **A malformed default is reported and ignored.** Refusing to serve a project over a config typo
  would be a worse failure than serving it on the conventional port; a host logs the problem and
  moves to the next source in the table.
- **The IDE hosts read both files too**, which is the point: with no `webview.explorer.port`
  (JetBrains) or no explicit `webviewExplorer.port` (VS Code) setting, the checkout's current port,
  or failing that the project's committed default, starts the bridge. A setting the user *did*
  choose still wins, which is why the VS Code host reads its setting through `inspect` rather than
  `get` — a declared default is not a choice.

## Alternatives considered

- **Keep one fixed port per host and let the second editor fail to bind.** Rejected: it makes
  the second IDE's bridge silently absent, and the failure surfaces as a dead page link rather
  than as a statement about the project.
- **Refuse to start whenever the port is taken** (the `webviewd`-only rule this supersedes).
  Rejected as a general rule: "busy" is not "mine is already served", and refusing on a
  stranger's port means an unrelated application can deny the project its bridge.
- **Pick a random free port always.** Rejected: a stable port is what makes
  `data-bridge-port` and a firewall rule possible at all, and an unpredictable port is one no
  human can debug from a terminal.
- **Write the port into a user-home registry** (`~/.jcodebuddy/ports.json`). Rejected: a port
  means something to one project, and a shared registry adds a lock, a stale-entry problem and
  a cross-project leak for no gain. DEC-032 keeps the user-home directory to configuration that
  is not about a project, and a port is always about a project — so no user-home scope, registry
  or config file is consulted for one at all (§ 6).
- **Add `ide`/`project` to the manifest only** (`/.well-known/webview.json`) and leave
  `/health` alone. Rejected: the port claim runs before any page is served and must work
  against a host whose only guaranteed route is `/health`; and a page's own discovery ladder
  already reads `/health`.
- **Detect a neighbour by its descriptor rather than by probing.** Rejected as the only
  mechanism: the record outlives the host, so it can describe a port that answers nothing. It is
  used as a fast path, and the probe is the authority.
- **A machine-wide port lock file.** Rejected: it serializes what does not conflict, and it
  needs stale-lock recovery, which is the same problem as a stale descriptor with none of the
  locality.
- **Put the pin in the committed configuration.** Rejected: the pin is per checkout, and a
  committed pin would pin every worktree of the project at once — the exact collision the pin
  exists to avoid. Configuration holds the *preference*; `host.json` holds the *pin*.
- **Fail on a taken port always** (rather than only when pinned). Rejected: it makes an unrelated
  application able to deny a project its bridge, and it punishes the ordinary case — a second
  worktree, an IDE opened twice — for the sake of the rare one.
- **Move anyway when the pinned port is taken, and log it.** Rejected: a log line is not a
  notification. The user pinned the port for a reason outside the host (a bookmark, a firewall
  rule), so the host cannot judge whether moving is acceptable — and the failure is silent in
  exactly the place it matters.

## Consequences

- A page, a script or a second editor finds the port by reading one file at a known path, and
  the file names the editor and the project so the reader need not probe to find out what it
  found.
- Two IDEs on one project behave predictably: the first serves, the second declines and says
  who is serving. A page cannot reach the wrong IDE's buffer because there is only one bridge.
- An unrelated application squatting on a conventional port (18881, 18882, 7979) no longer
  costs the project its bridge; the host moves and publishes where it moved to.
- **Negative:** a page that hard-codes `data-bridge-port="18882"` is still wrong, and now
  wrong in a second way — the port may have moved. The fix is unchanged (read the descriptor or
  the manifest), and the examples and READMEs that hard-code a port must be read as the
  *default request*, not as the address.
- **Negative:** a host may now serve on a port the user did not configure, so a firewall rule
  or a bookmark can go stale. The descriptor is the answer, and the host logs the move.
- **Negative:** the claim costs up to twenty `/health` probes at startup in the worst case
  (each with a 400 ms connect timeout). In the ordinary case it is one bind, and the probe only
  runs on a port that is already known to be busy.
- **Follow-up:** the `ide` name of the JetBrains host comes from the platform
  (`ApplicationNamesInfo`), so it reads "PyCharm" or "RustRover" where the plugin id cannot.
  A host added later must supply its own name rather than reuse a constant.

## Out of scope

- **Which host *should* win** when several serve one project — the rule is "the first one
  keeps it", not an election or a hand-off. A takeover protocol (host A stops and hands its
  port and token to B) is not part of this decision.
- **Authenticating the `/health` probe.** It is unauthenticated in every host, by design, and
  this decision does not add a credential to it.
- **Remote or non-loopback serving.** Every host binds loopback only; the port claim assumes
  one machine.
- **The edit contracts themselves** (`/api/v1/*`), whose security rules are D8's and
  `webview/kit/doc/edit-api.md`'s.

## Acceptance criteria

1. A host that binds publishes `<project>/.jcodebuddy/webview/host.json` containing the port it
   actually bound, its `ide` name, its `plugin` id, its own `pid`, the project path, its
   capabilities and its `sticky` flag — and no token.
2. `/health` from every host carries `ide` and `project`, in the order the shared key list
   names; the Java `ConformanceVectorsTest` and the Node `BridgePolicy.test.js` both fail if a
   host adds a key alone.
3. Requested port free → served on it, no probe performed (asserted by a throwing attempt in
   the Java test and by the absence of an occupant in the TypeScript one).
4. Requested port held by a host for **this** project → no endpoint is opened at all
   (`HostPortClaimTest`, `HostRegistration.test.js`), and the reason names the occupant. End to end, two
   live `webviewd` processes on one project: the second exits `2` and names the port that is serving —
   `bun webview/tools/check-port-claim.js`.
5. Requested port held by a host for **another** project, or by an unrelated application →
   the host serves on the next free port and reports it; the same occupied port makes a **pinned**
   project fail instead (§ 5).
6. All twenty ports taken → the host serves nothing and says so; nothing is bound at random.
7. A live descriptor for this project on **another** port stops a second bridge; a descriptor
   owned by the calling process does not; a descriptor whose port answers nothing does not.
8. A stopping host **leaves** the record: nothing deletes it automatically, and the next start
   asks for the port it names — asserted end to end by `bun webview/tools/check-port-claim.js`
   (stop a host, restart it with no `--port`, and it serves on the same port again). Deleting the
   file is a deliberate act and returns the checkout to the project's default.
9. `webviewd --port 0` still publishes the operating-system-chosen port, and a second
   `webviewd` for the same project still exits `2` with a message naming the host that is there.
10. `webviewd --sticky` records `sticky: true` beside the port it bound, and the pin outlives the
    process that set it: with the pinned port held by another application, a later start exits `2`
    with a message naming the port and how to unpin it, and **nothing is republished**, while an
    identical project without the pin steps over the same occupied port. Both halves are asserted
    against live processes in `bun webview/tools/check-port-claim.js`, and the outcome is a third
    `HostPortClaim.Action.FAIL` asserted in `HostPortClaimTest` and in `BridgePolicy.test.js`.
11. The port to ask for resolves through the four sources in § 6, in order, in both languages —
    `HostConfigTest.requestedPort` and `HostRegistration.requestedPort` assert each step, and the
    gate asserts the first two end to end: a checkout with a live record asks for the port it is on,
    and a fresh checkout asks for the default in `<project>/.jcodebuddy/conf/webview.json`. The
    default file is optional: with neither file, the host's fallback (`0`, ephemeral, for
    `webviewd`; **off** for the IDE hosts) applies, and a malformed default is reported and skipped
    rather than fatal.
12. No part of that resolution reads a user-home path (DEC-032 § 2, acceptance criterion 7).
