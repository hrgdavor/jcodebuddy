# DEC-027: HTML reports are rendered by Bun from the generator's JSON metadata

## Context

The entity generator already writes a machine-readable model of a module's entities —
`<Marker>.metadata.json` in `.jcodebuddy/metadata/entity/` (DEC-026) — and
`hipster-entity-example/codebuddy.md` § 5.2 already states what it is *for*: "JS tooling
that renders HTML reports or interactive views of the codebase". No such consumer existed.
What was missing was a **reference page**: every entity in a module, every artifact generated
from it, and every field clickable through to the exact source line of every artifact —
readable from inside the IDE, which here means the JCEF tool window of the `webview-jetbrains`
plugin.

The question this decision answers is where such a report is *rendered*. Two homes were
available, and the first draft of this work implemented the wrong one (a Java emitter in
`hipster-entity-tooling`, since deleted). The facts that decide it:

- **A report renderer needs no compile-time knowledge.** Everything it reads (which views
  exist, their `gen` level, their fields, each field's `FieldKind`) is data the generator
  already produced. It is a *view over* the model, not part of the model.
- **Building HTML in Java buys nothing and costs recompiles.** Every presentation change —
  a column, a colour, a filter — would recompile the tooling and re-run the whole generation
  pass inside the reactor, and the tooling would grow an escaping/browser-scripting surface
  that no compiler checks.
- **The repository already has a JS runtime for exactly this kind of side tool.**
  `scripts/update-doc-includes.js` is Bun JavaScript (`import { Glob } from 'bun'`), and every
  developer machine here has `bun` on `PATH` (measured: 1.3.14). A Maven module has no JS
  toolchain, but `scripts/` does.
- **The JSON was written to be the consumer contract** (DEC-004: generated metadata over
  runtime reflection), and a second consumer is the cheapest way to find out whether the
  contract is actually sufficient.

It is not sufficient yet, and that is the second half of the context. The JSON carries **no
artifact inventory** — the files the pass emitted for a view — **no location of any member inside
those artifacts**, and its `allFields` array is a per-marker union rather than any one view's ordinal
order (DEC-023 owns that order, and the field enum is where it lives). A renderer that reads only the
JSON therefore cannot link a field into a builder, a record, or an enum at all. Any decision to
render from the JSON has to say what happens about that gap.

The one thing that gap originally included and no longer does is the *file a class is declared in*:
the amendment at the end of this document records that the generator now emits a module-relative
`sourcePath` for the marker, for every view, for every property and for every merged field. That is
the fact the renderer could not derive — an inherited field is declared in a different file than the
view that exposes it — and it is why § 4 below is written as "metadata first, scan for the rest".

## Decision

### 1. HTML is rendered in JavaScript, never by a Java generator

No Java class in `hipster-entity-tooling`, `hipster-entity-api`, `hipster-entity-core` or any
other module may write HTML, and no generator gains an HTML flag or subcommand. The renderer
lives in [`scripts/entity-html/`](../../../scripts/entity-html/README.md).

The boundary is the repository's existing one, extended by one step: the **generator** owns
the model and the committed Java source; the **renderer** owns presentation. A fact that is
missing from a report is added to the JSON by the generator, not scraped out of the report
side.

### 2. The generator's JSON metadata is the only source of the model

Which entities and views exist, a view's `gen` level, `addons`, `extends` and its own
properties, each field's type, `FieldKind`, column, relation and expression, and the views that
expose a field — all of it comes from `<Marker>.metadata.json`. The renderer **MUST NOT**
re-derive those facts by parsing Java; a change of model facts is a change to `toJson` and to
the Java model behind it (DEC-004).

**A record names a source file; it never contains one.** Where a report needs to say where a class
lives, it carries that class's **relative path** — and nothing else. Copying a file's text into a
metadata file or a page would create a second, stale copy of the tree whose owner is the committed
source (`AGENTS.md` § 1), and it is unnecessary: a path plus a line is what opens the file, in the IDE
and in the report. So `sourcePath` is a location, never a body; the page's cells hold a path, a line
and a role, never a code sample; and a report directory contains **metadata only** — a `.java` under
`.jcodebuddy/` is a mistake (DEC-026 § 5) whatever wrote it. `GeneratorGuardTest` asserts both halves
of that (a pass leaves only JSON in the report directory, and no `.jcodebuddy/` tree in the repository
holds a `.java`), and `MetadataSourcePathTest` asserts that every recorded path has the shape of a
path — `src/main/java/…java`, no newline, no body.

### 3. Bun is the runtime, vanilla JavaScript is the implementation, the page is one file

`bun run scripts/entity-html/index.js` (or `scripts\entity-html.cmd`) renders the page. The
output **MUST** be a single self-contained `.html` file with inline CSS and one inline script,
and that script **MUST** be framework-free vanilla JavaScript:

- no React, Svelte, Solid, Vue, Preact, Lit, Angular or jQuery — no framework global, no
  component model, no virtual DOM;
- no bundler, no `node_modules`, no npm dependency, no CDN, no `<script src>`, no linked
  stylesheet, no image;
- no network access at render time and none at view time — the page must work inside JCEF on a
  machine with no internet.

The reason is not austerity. The page is a *report*: it must be greppable, diffable, openable
from a file manager, and reproducible by anyone with Bun — and it must not require this Maven
repository to grow a JavaScript toolchain. A renderer that genuinely needs a dependency needs a
new decision, not a `package.json` entry.

### 4. Locations may come from the committed source, and every link MUST be verified

Because the JSON carries each class's declaring file (the amendment below) but **not** the artifact
inventory and **not** the line of a member inside a generated artifact, the renderer resolves those
from the committed Java: one line-oriented scan per run, with comments and string/char literals
blanked (so no line number can move), and with the DEC-021 header `// {@link <fqn>} …` used as the
artifact-to-view back-reference, because that reference is the generator's own navigable statement
of ownership.

Two rules make that safe rather than approximate:

1. **Prefer the metadata.** Where the JSON carries a location — the marker's and each view's
   `sourcePath`/`lineNumber`, each property's `sourcePath`/`lineNumber`, each `allFields` entry's
   `sourcePath`/`lineNumber` — the renderer **MUST** use it, and consult the scan only inside the file
   the metadata named. Requiring the metadata is deliberately *not* the rule: a JSON written before
   the amendment still renders, by falling back to resolving a view's file by name and a field's
   declaring file through the `extends` chain and the line the generator recorded.
2. **Verify every link before writing it.** A candidate is written only if the target file
   exists **and** the target line contains the member it claims — the one exception being the
   `@FieldSource` role, which is verified by the annotation on that line instead, since that
   line legitimately names no member. A candidate that fails is **dropped** and reported as a
   DEC-022 divergence (`kind=html_link_stale`), and the run **MUST** exit non-zero unless the
   caller passes `--soft`.

A page may therefore be incomplete. It never opens the wrong line.

### 5. The ordinal contract stays where DEC-023 put it

A view's field list and order come from its generated field enum — the ledger — not from the
metadata union. Where the metadata attributes a field to a view whose enum has no constant for
it, the page shows the field as a row **without an ordinal**, and the renderer reports
`kind=html_field_not_in_ledger` as a **warning**: it is a fact about the two sources
disagreeing, not a rendering defect, so it is visible on the page and does not change the exit
code. (The committed example has two such views; see Acceptance criteria 9.)

### 6. Report output stays in DEC-026's `metadata/` subtree

The page is written to `<module>/.jcodebuddy/metadata/entity/index.html`, beside the JSON it
renders: derived, regenerable, git-ignored, never a committed artifact. A generation pass
(`scripts\gen.cmd`) renders it as its last step. A missing Bun is reported and skipped — the
JSON is the pass's deliverable and the page is a view over it — while a *failed link check* is
fatal, because a link to the wrong line is worse than no link at all.

### 7. The page's link contract is the IDE's, declared once

In the JetBrains **WebView Explorer** the plugin injects
`window.openFile(path, line, column)` into every loaded page, and that is the primary path;
the plugin's HTTP endpoint (`http://127.0.0.1:<port>/open?filePath=…&line=…`) is the fallback
for a browser without the bridge, and clipboard-plus-toast is the last resort so a click never
loses information.

Link targets **MUST** be stored as `data-*` attributes holding paths **relative to one link
base**, never as `href`s and never as absolute paths; the page computes the absolute path from
its own `location`. That single choice is what makes the same page work whether the IDE project
is the example module or the repository above it, and it is what keeps a machine-specific path
out of a report that other machines will open. This is § 1 of `AGENTS.md` carried into the
browser: a developer reading the report must be able to reach the committed source.

## Amendment — `sourcePath` is now emitted, relative to the module

§ 4 said the JSON carries no file path, and that enriching `toJson` with one was the migration path.
That path has been taken in the same change, because the fact the renderer could not derive is the one
only the generator knows: **which file declares a class**, and for a field, which file declares the
*accessor* — an inherited field's is not the view's.

- Every `<Marker>.metadata.json` now carries `markerSourcePath`, a `sourcePath` on every view, a
  `sourcePath` on every property and a `sourcePath` on every `allFields` entry.
- Every one of those paths is **relative to the module root** — `src/main/java/…`, forward slashes,
  never absolute, never `..`, never project-relative. The module is the only base that is correct in
  every module of a multi-module build, because CodeBuddy's output lives in the module that holds the
  class (DEC-026) and no metadata file knows the project root. Resolving a path against an IDE project
  root — which is what the Bun renderer does with `data-link-base` — then lands in the right module
  whichever directory the IDE opened.
- The module root is resolved exactly the way DEC-026 § 2 resolves an output root: the nearest
  `.jcodebuddy/` above the report directory, then above the source root, then the nearest `pom.xml`,
  then the `…/src/main/java` convention, then the source root itself. A report directory outside the
  module (a temp directory in a test) therefore still produces module-relative paths.
- A path the generator cannot know stays `null` rather than being guessed: the inherited `id` comes
  from `Identifiable` in `hipster-entity-api`, so it has no source file here, and the page shows it as
  `inherited` with an enum-constant link and no accessor link.
- § 4.1 is now the normal case rather than a preference. What the JSON still does not carry is the
  **artifact inventory** and a **member's line inside a generated artifact**; those stay in the scan,
  and § 4.2 (verify every link) is unchanged and still mandatory.

The change is additive to the JSON and to the tooling's model records (`Property`, `ViewMeta`,
`InterfaceInfo`, `EntityMeta`, `EntityFieldMeta` all gained a `sourcePath`), so `fromJson` reads
metadata written before it and a consumer that ignores the new keys is unaffected.
`MetadataSourcePathTest` runs a real pass and asserts every recorded path is module-relative, resolves
to a file that mentions the class it is attached to, that an inherited or addon field names its own
declaring file, and that a view outside its marker's package keeps its own path.

What is recorded is the **path only**: the generator does not copy the file's text into the metadata,
and the renderer does not copy it into the page (§ 2). The residue that rule was written against — and
that § 2's guard now prevents — was thirteen generated `.java` files that an older tooling had dropped
into `hipster-entity-example/.jcodebuddy/metadata/entity/hr/…`; they were deleted, and the module's
`.gitignore` keeps a `.java` under `.jcodebuddy/` ignored even if a project opts the metadata subtree in
as a contract.

## Superseded — DEC-028

This document is accepted and remains the decision for *where a report is rendered* (Bun
JavaScript, one self-contained vanilla-JavaScript page, the `data-*` link contract, the renderer
boundary). Its **addressing and location half is superseded** by
[DEC-028](DEC-028.md), and the superseded text above is left in place as history:

- The amendment's `markerSourcePath`/`sourcePath` strings are replaced by `markerFile`/`file`
  **ids**, resolved through the module's central index `.jcodebuddy/index/files.json`. A
  document contains no source path at all; its one path-like value is the `fileIndex` pointer to
  that table.
- § 4.1's "the JSON carries each class's declaring file but not the artifact inventory and not
  the line of a member inside a generated artifact" is no longer true: `views[].artifacts[]` is
  the inventory and `views[].fields[].at` records **every** location of every field, as the pass
  that wrote the files recorded it. The renderer therefore **discovers nothing** from source;
  its scan is used only to verify a link.
- § 4.2 (verify every link before writing it) is **not** superseded: `MUST be verified` stands,
  and a rejected candidate is still `html_link_stale` and still fails the run unless `--soft`.
- § 5 (`html_field_not_in_ledger`) is not superseded either: a field the metadata attributes to a
  view whose ledger lacks it is still shown without an ordinal, as a warning. On the committed
  example the warning no longer fires only because the ledger is now read from the recorded
  locations rather than guessed by a line regex.
- **Acceptance criteria 10 and 11 are superseded as written**: their `sourcePath` assertions are
  now DEC-028's (ids, one path in the index, no path in a document). The rest of each criterion —
  module-relative, resolves to a file mentioning the class, path-not-content, no `.java` under
  `.jcodebuddy/` — still holds and is asserted by DEC-028's tests.
- **"Out of scope → Extending `<Marker>.metadata.json` with `sourcePath` and an artifact
  inventory" is superseded**: that extension has since been made, first by the amendment and then
  in the form DEC-028 defines.

## Alternatives considered

- **A Java HTML emitter inside `hipster-entity-tooling`** (the deleted first draft). Rejected:
  presentation churn would require recompiling the tooling and re-running the pass in the
  reactor; the module whose job is emitting Java would carry an HTML-escaping and
  browser-scripting surface that nothing checks; every launcher and POM would need a new entry
  point; and `mvn compile` would start to matter for a report. § 1's boundary is asserted by a
  test so the draft cannot come back by accident.
- **Render from the JSON alone, changing nothing.** Rejected as impossible on the facts: no
  file paths, no artifact inventory, no member lines, no per-view ordinal order — the page
  could not link a field into an enum or a builder, which is the entire point of the report.
- **Extend the JSON first, scan never.** Partly taken, and deliberately not finished. The class-level
  half is done (the amendment): every class the metadata is about now names its own file, because a
  renderer cannot derive it and a name search gets a cross-package view wrong. The rest — an
  `artifacts[]` inventory and a member line per artifact — is still deferred: it means teaching a
  2 800-line generator to record the line of each member it emits, in a file whose emitted bytes are
  pinned by a byte-identical-output test, for a page that already links every member correctly through
  a scan whose every result is verified. The pressure remains in the right direction (a renderer that
  needs more from the metadata is how the metadata improves), and the renderer prefers metadata
  wherever it exists, so finishing the job later is additive rather than a rewrite.
- **A framework (React / Svelte / Solid) for the page.** Rejected: this is a static document
  with a filter box and a click handler; a framework would add a package manager, a bundler and
  a build artifact to a Maven repository, and it would make the report ungreppable. § 3 pins
  vanilla JS, and `bun test` asserts the page has no framework global and no external script.
- **Commit the HTML.** Rejected: it is derived from JSON plus source, so every pass would churn
  it, and DEC-026 already classifies everything in `metadata/` as derived.
- **Have the renderer re-run a generation pass itself, or watch the sources.** Rejected: the
  renderer reads what a pass wrote. A stale JSON is *detected* (the link check fails and says
  so), which is a better signal than a renderer that silently regenerates the artifacts it is
  describing.
- **A server-backed or MCP-backed view.** Out of scope; see below.

## Consequences

- A generation pass gains a rendering step, and a link that no longer resolves fails the pass
  with a DEC-022-shaped diagnostic instead of producing a plausible-looking page.
- Iterating on the report is cheap: edit JavaScript, re-run `bun run`, no Maven, no Java
  rebuild, no reactor.
- Bun becomes a dev-time requirement for the report — not for the generator, not for the build.
  Its absence is reported by name in the pass log and does not fail the pass.
- The renderer reads committed source. That is a second source of location truth, narrowed by the
  amendment (every *class's* file now comes from the metadata) and mitigated by § 4.1 (metadata
  first) and § 4.2 (every link verified); a scan bug surfaces as a dropped link plus a divergence,
  never as a wrong link.
- The metadata now carries a module-relative `sourcePath` for every class it describes. That is a
  small widening of the JSON's contract with one sharp rule attached: **module-relative, never
  project-relative**, because in a multi-module build the module is the only base that is right
  everywhere — and it is the base the module's own `.jcodebuddy/` output already uses (DEC-026).
- The JSON's remaining gaps are recorded and load-bearing. A JS consumer that needs an artifact
  inventory or a member line inside an artifact must get it added to `toJson`, which is exactly the
  pressure DEC-004 wanted.
- Two `html_field_not_in_ledger` warnings are the steady state on the example module. They are
  a generator-level ledger/metadata disagreement that the renderer surfaces rather than hides;
  they do not fail the pass. If a later pass closes the gap, the warnings disappear by
  themselves.
- **Negative:** the report is ignored by git, so a reviewer of a pull request does not see the
  page in the diff; they regenerate it (`scripts\entity-html.cmd`) instead. This is DEC-026's
  deliberate split, not an oversight.
- **Negative:** the page's interactivity is deliberately small (filter, collapse, click-to-open).
  A richer view — diffing two passes, editing — would be a different artifact with a different
  lifetime, and § 3 would have to be revisited.

## Out of scope

- **Extending `<Marker>.metadata.json`** with `sourcePath` and an artifact inventory. Recorded
  as the migration path (§ 4.1), not done here.
- **The VSCode variant** (`webview-vscode`). The `data-*` link contract is transport-neutral and
  a VSCode webview consumer would translate the same attributes; wiring that up is not this
  decision.
- **Serving the page over HTTP, watching sources to re-render, or running a report server.**
  The artifact is a file an IDE opens.
- **Validating or evaluating the HTML in Java**, and **rendering Java documentation** (javadoc,
  architecture diagrams) — this decision covers generator-metadata reports only.
- **A general `scripts/` JavaScript style guide.** § 3's vanilla-JS rule is scoped to this
  report; it is not a claim about every script in the repository.

## Acceptance criteria

1. `scripts\gen.cmd` writes `<module>/.jcodebuddy/metadata/entity/index.html` as the last step
   of a pass, and its summary prints the renderer's `HTML entity index written to:` and
   `Link check: N links verified, M candidate(s) rejected` lines. A machine without Bun prints
   a skip line naming DEC-027 and the pass still exits 0.
2. `bun run scripts/entity-html/index.js` with **no arguments** finds the example module, its
   metadata directory and its source root, and writes that same file;
   `scripts\entity-html.cmd` does the same from any working directory in the repository.
3. The page is one self-contained file: no `<script src>`, no linked stylesheet, no image, no
   `https://` reference, no framework global, and an inline script that parses as valid
   JavaScript on its own. Asserted by `bun test` in
   `scripts/entity-html/entity-html.test.js`.
4. Every link in the page resolves to a file and a line that contains the member it claims (for
   the `field source` role: a line carrying `@FieldSource`). Asserted twice — by the renderer at
   build time (a failure is `html_link_stale` and exits 1) and by the test over the whole page.
5. No absolute path appears anywhere in the page, and the only absolute URL is the loopback
   bridge endpoint. Asserted by the test, which also resolves the page's own `data-link-base`
   the way the browser does and checks it lands on the link base.
6. Two runs over an unchanged tree produce byte-identical HTML. Asserted by the test.
7. Clicking an entity name, an aspect card, a column header and a field cell in the JetBrains
   WebView Explorer opens that file at that line. **Manual** — it needs the plugin
   (`webview-jetbrains`, `gradlew runIde`, then right-click the page in the Project view and
   choose "Open in WebView Explorer").
8. No Java source under `hipster-entity-tooling/src/main/java` writes HTML, and the renderer
   exists at `scripts/entity-html/index.js` and reads `*.metadata.json`. Asserted by a Java
   test, so the boundary survives a refactor.
9. The two views whose metadata attributes fields their ledger does not carry
   (`PersonUpdateForm`, `PersonUpdatableView`) appear with those rows marked `not in ledger`, no
   ordinal, and one `html_field_not_in_ledger` warning each — with the pass still green. This is
   the behaviour § 5 requires, and it is asserted.
10. Every `<Marker>.metadata.json` carries a `sourcePath` for the marker, each view, each property and
    each merged field, and every one of them is **module-relative** (`src/main/java/…`, forward
    slashes, no drive letter, no `..`, not prefixed with the module's directory name), resolves to a
    file under the module root, and points at a file that mentions the class or accessor it is
    attached to. An inherited or addon field names its own declaring file, a view outside its marker's
    package keeps its own path, and a field declared outside the source root (`id`) carries no path.
    Asserted by `MetadataSourcePathTest`, which runs a real pass rather than reading whatever is on
    disk.
11. What is recorded is a **path, not content**: every `sourcePath` matches
    `src/main/java/…java` (no newline, no body), a report directory holds only JSON after a pass, and no
    `.jcodebuddy/` tree in the repository contains a `.java` file. Asserted by `MetadataSourcePathTest`
    and `GeneratorGuardTest`, and a `.java` under `.jcodebuddy/` stays git-ignored even after a project
    opts its metadata subtree in as a contract.
