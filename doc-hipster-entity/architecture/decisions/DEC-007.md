## Context

One of the most promising design directions is using DTO interfaces as lightweight read contracts for SQL and NoSQL queries, potentially short-circuiting directly into JSON output without full entity or DTO object materialization. That direction has real performance upside, but it can also become unpleasant if the API is too low-level or fragile.

## Decision

If projection-based read paths are adopted, they must be designed as explicit developer-facing APIs, not only as an internal optimization path. Performance and low allocation matter, but the model must stay understandable and composable for application developers.

## Accepted notes

Two explicit paths exist and are benchmarked:
- **Ergonomic path**: proxy-backed views via `ArrayBackedViewProxyFactory` + `EntityJacksonViewDeserializer` (~1,131 ops/ms)
- **Fast path**: concrete implementations + boilerplate/positional deserializers (~1,268–1,278 ops/ms)
- File-scan benchmarks (30k records) confirm concrete positional path is ~14× faster than Jackson POJO at sustained throughput
- JMH suite (3 forks, 6wi, 8i) provides acceptance evidence

### The generated projection writer, and which path it is (plan step 6.5, 2026-10-09)

The decision asks that a projection path have a **developer-facing shape**. That half is now a generated
class rather than an API a developer assembles, and it sits on the *ergonomic* side of this record's
two paths — it is the shape a person writes, not the shape a hot loop is benchmarked against:

- **`<View>Json` is emitted for a view marked `@View(dto = true)`**, opt-in per pass with
  `--dto-projections` (DEC-003's Accepted notes carry the marker, the header and the freeze rule).
  `PersonDtoJson` in `hipster-entity-example` is the worked example.
- **It is reflection-free and direct**: `gen.writeNumberProperty("id", source.id())` per field, so the
  IDE navigates from the writer into the view (AGENTS.md § 1 / DEC-019). That is also why it is not a
  benchmark candidate in the way the fast path is: the numbers this record quotes are for
  **deserialization and materialization**, and the writer emits a document rather than reading one.
- **The two-path split is unchanged.** The fast path (`Record` materialization + positional
  deserializers) and the ergonomic path (proxy-backed views + `EntityJacksonViewDeserializer`) are the
  read paths; the projection writer is the *output* half that lets either of them — or a SQL row that
  never became either — reach JSON without a positional array in between.
- **No new benchmark is claimed here.** The writer was not benchmarked, and this record does not imply
  it was: what is asserted is its shape, its document equality with the field-enum ledger, and that it
  compiles (`ViewJsonGeneratorTest`). A number for it would be a separate measurement.

What this does **not** change: the proxy path, the concrete positional path, the JMH evidence, or the
ergonomic/fast split above. The writer is additive and opt-in, and a project that never marks a view
still gets exactly the two paths this record accepted.

## Consequences

- Keeps ergonomics in scope alongside throughput and memory use.
- Encourages stable APIs around projection binders, JSON sinks, or generated projection adapters.
- Requires benchmarks and examples to justify complexity before the ADR can be accepted.

## Out of scope

- SQL query optimisation or query plan control — projection adapters consume query results; they do not influence query shape.
- Caching or pooling of projection instances — out of scope until allocation patterns are established by benchmarks.
- Mutation operations — this decision covers the read path only; write semantics are addressed in DEC-005.
- Streaming pagination — how large result sets are paginated is a driver/query concern, not a projection-adapter concern.

## Acceptance criteria

- Performance-oriented projection APIs MUST have a developer-facing shape, not only an internal optimization path.
- The design SHOULD define at least one ergonomic materialization path and one lower-level fast path.
- Benchmarks and examples MUST exist before acceptance.
