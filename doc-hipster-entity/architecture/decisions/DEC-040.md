## Context

The maintainer's direction, kept as given:

> metadata should strictly avoid hiding any generics or relations that java might be hiding when compiling, we
> want to be better positioned than runtime code

Java removes things when it compiles. Generic type arguments are erased from the runtime representation; an
annotation survives only if its `@Retention` says so, so `@Retention(SOURCE)` is gone from a class file while
`CLASS` is gone from reflection; a parameter's name survives only under `-parameters`; and a `permits` list, a
bridge method or a default method is a class-file attribute whose reflective equivalent depends on the version
and the library doing the asking. A consumer that works from compiled code — a class loader, a framework, an
IDE's index of a jar — is therefore **strictly poorer** than the source, and the loss is not incidental: it is
the compiler's job.

The engine exists because every consumer should read **one** model instead of growing a path of its own
(DEC-037). If that model inherits the JVM's erasure, two things follow, and both are the failure this record
answers: the engine is no better positioned than a class loader, and a consumer that needs a fact the model
dropped has exactly one remedy left — parse the file itself, which is the second parse DEC-030 and DEC-037
exist to delete.

**Measured, 2026-10-03, while starting plan step 3.0e.** Two questions hipster-ioc asks of the model, and what
the row could answer:

| the consumer's question                                                                           | what the model said                                                       |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| the `P` of a `ChildContext<P>` supertype — what makes a child context emit its parent's accessors | `ChildContext`: `TypeRelation` drops type arguments **by design** ("it is source text, and this table's subject is names", `TypeFacts.withoutTypeArguments`) |
| `@Circular` on a factory's parameter — what decides how a bean is wired                           | nothing: a parameter was a type and nothing else (fixed by 3.0e part one) |

Neither was an accident; both were deliberate omissions, and each put a consumer back on the file. That is the
pressure: the model was deciding what a consumer may know, and it was deciding *less* than the compiler does.

## Decision

**D1 — What the compiler removes, the model MUST keep.** The model MUST record, as written, the facts erasure
destroys: type arguments wherever the source wrote them (on a relation, a member's type, a parameter's type), the
annotations on any declaration or member **regardless of their retention**, parameter names, declared kinds and
modifiers, and relations. It **MAY** omit a fact a class file still carries — enum constants, for instance —
because this rule is about erasure, not about copying everything the parse saw. An omission that a consumer
needs is still an omission: it MUST be reported as a limit (D4).

**D2 — "the name" and "the text as written" are two questions, and both MUST be answerable.** Matching wants
the bare name (`ChildContext`); fidelity wants the text (`ChildContext<AppContext>`). A field that keeps only
one of them is lossy, so a name the model carries MUST keep the form written in the source, and the bare name
MUST be **derivable** from it — never the other way round. Where both are stored, the text is the one that is
guaranteed to be present.

**D3 — Resolution MUST NOT replace the written text.** `List` resolving to `java.util.List` is a second fact,
not a better version of the first. Resolution needs the imports and the whole index, changes when an unrelated
type appears, and can fail; the written text is a fact about one declaration. Both MAY exist; only the text is
guaranteed here.

**D4 — An omission MUST be reported, never answered as "none".** A fact the model does not carry is a **gap**,
and a gap and a "no" must be distinguishable to a consumer. This is DEC-029's always-emitted rule and DEC-035's
marker rule, applied to the model as a whole: *not recorded* ≠ *none*, and a query that cannot answer says so
rather than returning an empty list.

**D5 — These questions MUST be answerable from the model alone.** No file parse, no class loader, no classpath:
a consumer of the engine answers "is this generic, and how is it spelled", "what does it extend", "what
annotates it" from a committed table, in a fresh checkout, deterministically. That is the "better positioned"
half of the direction: richer **and** available at generation time rather than at run time.

## Alternatives considered

- **Record the resolved or erased form, as reflection sees it.** Smallest rows, and it is what a runtime tool
  has. Rejected: it makes the engine no better positioned than a class loader, and it cannot answer either of
  the two measured questions.
- **Record neither, and re-parse a file when a consumer asks.** The fallback this record removes. Rejected: it
  is the second parse DEC-030 forbids, it makes an answer depend on the working tree at that moment, and it is
  what the two measured omissions already forced.
- **Serialize the parse wholesale — one row per file, shaped like the tree.** Rejected: the model's subject is
  the questions consumers ask, and a serialized AST grows without a contract while making every reader learn a
  second grammar. Generics and relations are facts; a tree is a representation.
- **Depend on a compiled model (bytecode, a jar, a class loader).** Rejected by construction: a class file is
  what erasure produced, so a model built from one is strictly poorer, and it would put a class loader inside
  the engine.

## Consequences

- **Positive.** Consumers are positioned strictly better than runtime code, from one committed table: generics
  and relations survive, annotations survive regardless of retention, and the answers are reproducible and
  diffable because a row is text. No consumer needs a file for a type question, which is what makes a generator
  a function of the model.
- **Cost.** Rows grow, and every added fact is a **DEC-029 format change** under the always-emitted rule. A
  consumer may read a name that resolves to nothing — deliberate, because resolution is a separate question
  with its own rules (3.0h), and a model that silently resolved would be the confident wrong answer this project
  keeps having to unlearn.
- **Debt this decision creates, measured rather than implied.** The `relations` field drops type arguments
  today (`TypeFacts.withoutTypeArguments`), so `X extends ChildContext<AppContext>` is recorded as
  `ChildContext`. Under **D2** that is a **defect**, not a design choice, and it is the first prerequisite of
  plan step 3.0e's remaining half — with the interface file's import lines the second (a file-scoped fact
  `ClassRecord` does not carry, which D1's spirit says to record rather than to replace with fully-qualified
  output). Both are written into `plans/unified-plan.md` 3.0e before that rewrite starts.
- **Follow-up.** A DEC-029 amendment for the relation text; the 3.0e generator rewrite; and the acceptance
  criteria below as tests, so the rule is enforced rather than remembered.

## Acceptance criteria

- A row for a declaration written `X extends ChildContext<AppContext>` carries the text
  `ChildContext<AppContext>`, the bare name `ChildContext` is derivable from it, and both survive a write and a
  read.
- A member field's and a parameter's generic arguments round-trip unchanged (`List<String>` in,
  `List<String>` out).
- An annotation that a class file would not carry (`@Retention(SOURCE)`) is present in the row.
- No consumer of the engine parses a source file to answer a type question — the test plan step 3.0e's gate
  names.
- A fact the model does not record is reported as a limitation, never returned as an empty answer.

## Out of scope

- **Not a promise to be a compiler.** The model carries facts as written; it does not type-check, fold
  constants, apply annotation defaults or resolve a name against a classpath. "Richer than runtime" is a claim
  about *fidelity to the source*, not about evaluation — and D3 is what keeps the two apart.
- **Not a promise to record everything the parse saw.** Bodies, initialisers and anything a reader can only
  interpret are out (DEC-029's member limits); D1 lists what must survive erasure, which is a shorter and more
  defensible list than "everything".
- **Not a change to what a consumer may do with a fact.** A generator still receives a snapshot
  (`TypeDefinition`) and cannot reach the file, the loader or the project through it.
