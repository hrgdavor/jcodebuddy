# DEC-022: Refactor-sensitivity rules for generated code and divergence reporting

- Status: Proposed
- Date: 2026-09-07
- Owners: project

## Context

JCodeBuddy generates source code that lives alongside hand-written
code. The generated code is source-visible (DEC-009), cooperative
(DEC-020), and carries a class-file header (DEC-021). But there is
a gap: **when a developer performs a normal IDE refactor on the
source types and methods that the generator depends on, the
generated code can silently diverge from what the generator would
have emitted.**

Concretely:

1. **Generated record for an interface.** A generator emits a
   `record OrderView(...)` for an `interface Order`. The developer
   renames the interface to `PurchaseOrder`. The generated record
   is still named `OrderView`. The IDE rename refactor did not
   reach it because the relationship is implicit (the generator
   "knows" but the IDE does not). The result is a disjointed
   codebase: the interface says `PurchaseOrder`, the generated
   record still says `OrderView`.

2. **Renaming an RPC method.** A generator emits a `case "users.get":`
   arm in a JSON-RPC dispatcher, keyed by the Java method name
   `getUser`. The developer renames the Java method to
   `fetchUser`. The IDE refactor renames the method declaration
   but does not touch the `case` arm, because the string literal
   `"users.get"` is not a Java identifier and is invisible to the
   IDE's rename refactor. The result: the dispatcher still handles
   `"users.get"` but the Java method it calls is now `fetchUser`.
   The developer expected the rename to be consistent; it is not.

3. **Implicit name derivation is the common cause.** Both cases
   share a root cause: the generator **inferred** a name (record
   name, case-arm label, builder method name) from a source
   identifier (interface name, Java method name) without making
   that inference explicit in a place the IDE can see. The IDE
   refactor is correct for the source; the generated code is
   correct for the generator; the two are now inconsistent.

This decision defines **refactor-sensitivity rules** for
generators: when generated code **must** track a source rename
(and how), when it **must not** track a source rename, and how
the generator **reports divergence** when an IDE refactor has
made the generated code inconsistent with what the generator
would have emitted today.

## Decision

### 1. What "refactor-sensitive" means

A piece of generated code is **refactor-sensitive** to a source
identifier if, after a standard IDE refactor (rename, move,
package change) on that source identifier, the generated code
**should** change to preserve the relationship that the
generator encoded.

A piece of generated code is **refactor-insensitive** if, after
the same refactor, the generated code **should not** change —
because the relationship is either not meaningful, or is
expressed through an explicit config that the refactor does not
see.

The rule is:

> *Refactor-sensitive generated code must be wired through a
> contract the IDE can navigate. Refactor-insensitive generated
> code must use an explicit API name that the IDE refactor does
> not touch.*

### 2. The two contracts: implicit derivation vs explicit API name

Generators MUST choose, for each derived name they emit, one of
two contracts:

**A. Implicit derivation (refactor-sensitive).**
The generated name is derived from a source identifier. The
relationship **must** be expressed through a contract the IDE
can navigate, so that a rename refactor reaches the generated
code.

Examples of implicit derivation:

- A generated record named `OrderView` derived from the source
  interface `Order`. The relationship is "record name = source
  name + suffix". The IDE must be able to navigate from the
  interface to the generated record, so a rename refactor on the
  interface can offer to rename the record.
- A generated builder method named `withTotal` derived from a
  source field `total`. The relationship is "method name =
  `with` + capitalised field name". The IDE must be able to
  navigate from the field to the method, so a rename refactor
  on the field can offer to rename the method.

How to make implicit derivation navigable:

- The generator MUST emit a **Java declaration** (class, method,
  field) whose **name** is the derived name. The IDE can
  navigate to it.
- The generator MAY emit a **`{@link …}` reference** (in a
  class-file header, a Javadoc, or a comment) from the source
  to the generated declaration, so the IDE's "find usages"
  reaches the generated code.
- The generator MAY emit a **`@SeeAlso` / `@GeneratedFrom`**
  annotation on the generated declaration pointing back to the
  source, so the IDE's "go to implementation" reaches the
  source.

Concretely, for the `Order` → `OrderView` example, the
generated record is:

```java
// {@link com.example.Order} Generated from Order; rename Order to rename this record.
// {enabled:true}

package com.example.order;

import ...

/**
 * @see com.example.Order
 */
public record OrderView(Long id, String name, BigDecimal total) { }
```

The `{@link}` and `@see` make the relationship navigable. The
IDE's rename refactor on `Order` can now reach `OrderView`
through the reference chain. The generator's class-file header
(per DEC-021) and the Javadoc `@see` are the two surfaces the
IDE can see.

**B. Explicit API name (refactor-insensitive).**
The generated name is **not** derived from a source identifier.
It is either hard-coded by the generator or configured
explicitly in the class-file header. The IDE refactor on the
source identifier does not reach it, and that is correct.

Examples of explicit API names:

- A JSON-RPC method label `"users.get"` in a dispatcher
  `switch`. The label is an explicit API contract with external
  clients; it MUST NOT change when a Java method is renamed.
  The relationship between the label and the Java method is
  expressed through the `case` arm body (`usersService.get(...)`)
  and the class-file header, not through name derivation.
- A builder method `withFullName` that does not correspond to
  any single source field. It is a hand-written convenience
  method (or a generator-emitted convenience method) whose name
  is explicit.
- A `NextStepTrigger` whose name `"shipment.create"` is an
  explicit workflow name, not derived from any Java identifier.

Concretely, for the RPC example, the generated dispatcher is:

```java
// {@link hr.hrg.codebuddy.RpcDispatcher} JSON-RPC dispatcher; method names are explicit API labels.
// {enabled:true}

package com.example.api;

import ...

public final class RpcDispatcher {
    public JsonRpcResponse dispatch(JsonRpcRequest req) {
        return switch (req.method) {
            case "users.get"    -> usersService.get(req.params, req.id);
            case "users.create" -> usersService.create(req.params, req.id);
            // generated from @RpcMethod declarations; API names are explicit,
            // Java method renames do not affect case labels.
            default             -> JsonRpcResponse.err(req.id, -32601,
                                            "Method not found: " + req.method);
        };
    }
}
```

The class-file header says "method names are explicit API
labels", and the `case` arm body calls `usersService.get(...)`,
so the relationship between the API label and the Java method
is clear to the reader. The IDE rename refactor on `get` →
`fetch` will rename the Java method call inside the arm body,
but will NOT touch the `"users.get"` label, which is the
correct behaviour.

### 3. The naming contract per generator

Each generator MUST publish, in its README, a **naming contract**
that says, for every derived name it emits, whether that name is
**implicitly derived** from a source identifier or **explicitly
assigned**. The contract is a table with one row per emitted
name:

| Emitted name                       | Derivation         | Refactor-sensitive? | IDE contract                                 |
| ---------------------------------- | ------------------ | ------------------- | -------------------------------------------- |
| `OrderView` record name            | implicit (source + suffix) | **Yes** | `{@link Order}` in header + `@see Order` in Javadoc |
| `withTotal` builder method name    | implicit (field name)      | **Yes** | method name itself is navigable; `@see` on field |
| `"users.get"` JSON-RPC case label  | explicit (`@RpcMethod.value()`) | **No** | case-arm body calls the Java method; header notes explicitness |
| `shipment.create` next-step trigger | explicit (workflow name)   | **No** | body references the workflow id; header notes explicitness |

The contract is part of the generator's public API and is
reviewed on changes. A developer reading the generator's README
must be able to answer: "if I rename the source interface/method,
what generated names will change?"

### 4. Divergence reporting

Even with explicit contracts, IDE refactors can diverge from
what the generator would emit. The generator MUST detect and
report divergence.

**When to report:**

- After any regeneration pass (a manual pass, a watched pass, or
  one a project has bound into its build), the
  generator compares the current generated output against what
  it **would** emit if it ran from scratch on the current
  source. Any difference is a **divergence**.
- The generator also compares the current output against what
  it emitted on the previous pass (DEC-020's reporting mode).
  Divergences that are not caused by source changes (e.g. the
  IDE renamed a method the generator's case-arm label does not
  track) are **refactor-divergences**.

**What to report:**

The generator MUST emit a diagnostic for every divergence.
The format is an extension of DEC-020's reporting mode:

```
[generator:divergence] <generatorId> / <file>
  kind:     refactor-divergence | source-change-divergence
  location: <path>:<startLine>-<endLine>
  cause:    <what the IDE refactor did>
  current:  <what is in the file now>
  canonical:<what the generator would emit today>
  action:   <suggested user action>
```

Two kinds:

- **source-change-divergence** — the source changed in a way
  the generator tracks (e.g. the `Order` interface was renamed
  to `PurchaseOrder`). The canonical output is the new derived
  name (`PurchaseOrderView`). The user should rename the
  generated record (or let the generator re-emit it).
- **refactor-divergence** — the IDE refactor changed something
  the generator does **not** track (e.g. the Java method `get`
  was renamed to `fetch`, but the JSON-RPC case label
  `"users.get"` is explicit and unchanged). The canonical
  output is the same as before (the label is still
  `"users.get"`), but the **body** of the case arm now calls
  `fetch` instead of `get`. This is a divergence because the
  generator's previous output called `get`. The user should
  review the case-arm body to confirm the rename is intentional.

**When to report (timing):**

- At **generation time**, the diagnostic goes to the pass log —
  the generator is a side-car in this project, so a pass is run
  on demand (`scripts\gen.cmd`) or by the watcher, never by a
  Maven build. A generator that a project *does* bind into its
  build would print the same diagnostic to the build log.
- At **sidecar / LSP time**, the diagnostic is surfaced as a
  warning in the IDE, with a code action to re-emit the
  affected block or to mark it as intentionally divergent.

### 5. The divergence report is the cooperative feedback loop

The divergence report is the user-facing signal that says: "the
IDE refactor changed something that affects generated code, and
the generator's view of the world is now different from what is
in the file."

This is the **same spirit** as DEC-020's diagnostic on preserved
tweaks, but it fires in a different scenario: not "the user
edited the block", but "the IDE refactor touched something the
generator cares about".

The user has three ways to resolve a divergence:

1. **Accept the generator's canonical output.** Delete the
   affected block (or the whole file, or just the header) and
   let the generator re-emit. This is the default for
   source-change-divergence.
2. **Keep the current file as-is.** The user edits the file to
   match the new source (e.g. renames the generated record
   manually, or updates the case-arm body to call the renamed
   Java method). The generator preserves the block on the next
   pass (DEC-020) and reports the divergence again on the next
   regen pass, because the file still does not match the
   generator's canonical output. The user must explicitly
   acknowledge the divergence (e.g. add a `// generator:keep
   divergent` comment, or set a `divergence_acknowledged: true`
   flag in the class-file header) to silence the report.
3. **Change the generator's contract.** If the divergence is
   caused by the generator inferring a name that should have
   been explicit (or vice versa), the user changes the
   generator's naming contract and re-emits. This is a
   generator-level fix, not a per-file fix.

### 6. Divergence reporting composes with DEC-020 and DEC-021

- **DEC-020 (cooperative blocks):** the divergence report
  identifies the specific block (case arm, builder method,
  scaffolding method) that has diverged. The user can delete
  that block to trigger regen.
- **DEC-021 (class-file header):** the generator MAY add a
  `divergences` key to the JSON5 config blob, listing the
  active divergences for this file. This makes the divergence
  visible without leaving the file. Example:
  `// {enabled:true, divergences: ["rename Order -> PurchaseOrder"]}`.
- **DEC-019 (source-visible wiring):** the `{@link …}` and
  `@see` references in the generated code make the source →
  generated relationship navigable, which is what allows the
  IDE refactor to reach the generated code in the first place.

### 7. What the generator MUST NOT do

- The generator MUST NOT silently rewrite a refactor-sensitive
  block without reporting the divergence. A rename refactor on
  `Order` → `PurchaseOrder` that silently leaves `OrderView`
  in place is a bug; the user must be told.
- The generator MUST NOT report a divergence for a
  refactor-insensitive block when the source changes in a way
  the block does not track. Renaming the Java method `get` to
  `fetch` MUST NOT produce a divergence report for the
  `"users.get"` case label, because the label is explicit and
  correct.
- The generator MUST NOT use `Method.invoke` or a
  `Map<String, Method>` to implement the IDE-navigable
  contract for refactor-sensitive names. The contract must be
  ordinary Java declarations and references, per DEC-019.

## Worked examples

### Example 1 — generated record for an interface (refactor-sensitive)

Source interface:

```java
package com.example.order;

public interface Order { ... }
```

Generated record (before refactor):

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generated view record for Order.
// {enabled:true}

package com.example.order;

import ...

/**
 * @see com.example.order.Order
 */
public record OrderView(Long id, String name, BigDecimal total) { }
```

Developer renames `Order` to `PurchaseOrder` via IDE.

The IDE sees the `{@link}` and `@see` references and offers to
rename `OrderView` to `PurchaseOrderView`. If the developer
accepts, the generated record is updated. If the developer
declines (or the IDE does not offer the rename), the generator
runs on the next build pass, compares the current output
(`OrderView`) with the canonical output (`PurchaseOrderView`),
and emits:

```
[generator:divergence] hr.hrg.codebuddy.RecordBuilder / OrderView.java
  kind:     source-change-divergence
  cause:    interface com.example.order.Order renamed to PurchaseOrder
  current:  record OrderView(...)
  canonical:record PurchaseOrderView(...)
  action:   rename the record or delete it to regenerate
```

### Example 2 — RPC method rename (refactor-insensitive)

Source method:

```java
public class UsersService {
    @RpcMethod("users.get")
    public User getUser(JsonValue params) { ... }
}
```

Generated dispatcher (before refactor):

```java
// {@link hr.hrg.codebuddy.RpcDispatcher} JSON-RPC dispatcher; method names are explicit API labels.
// {enabled:true}

package com.example.api;

import ...

public final class RpcDispatcher {
    public JsonRpcResponse dispatch(JsonRpcRequest req) {
        return switch (req.method) {
            case "users.get" -> usersService.get(req.params, req.id);
            ...
        };
    }
}
```

Developer renames `getUser` to `fetchUser` via IDE. The IDE
refactor renames the method declaration and the call inside the
case arm to `usersService.fetch(...)`. It does NOT touch the
`"users.get"` label, which is correct — the label is an explicit
API contract.

The generator runs on the next build pass. The canonical output
still has `case "users.get" -> usersService.fetch(...)`. The
current output has the same. **No divergence is reported**, because
the explicit API label did not change and the body was updated by
the IDE refactor to call the renamed method. The relationship
between the label and the Java method is maintained through the
case-arm body, not through name derivation.

### Example 3 — divergence when the IDE did NOT update the body

Same starting point as Example 2, but the developer renames
`getUser` to `fetchUser` **without** using the IDE refactor
(e.g. they edited the declaration by hand). The case-arm body
still calls `usersService.get(...)`.

The generator runs, compares the current output
(`usersService.get(...)`) with the canonical output
(`usersService.fetch(...)`), and emits:

```
[generator:divergence] hr.hrg.codebuddy.RpcDispatcher / RpcDispatcher.java
  kind:     source-change-divergence
  cause:    method UsersService.getUser renamed to fetchUser (not via IDE refactor)
  current:  usersService.get(req.params, req.id)
  canonical:usersService.fetch(req.params, req.id)
  action:   update the case-arm body or delete the arm to regenerate
```

### Example 4 — builder method derived from field name (refactor-sensitive)

Source view:

```java
public interface OrderView {
    BigDecimal total();
}
```

Generated builder method:

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generated builder for OrderView.
// {enabled:true}

public final class OrderViewBuilder {
    public OrderViewBuilder withTotal(BigDecimal total) {
        target.setTotal(total);
        return this;
    }
}
```

Developer renames the `total()` accessor to `grandTotal()` via
IDE. The IDE sees the method `withTotal(BigDecimal)` in the
builder and offers to rename it to `withGrandTotal(BigDecimal)`.
If the developer accepts, the builder method is updated. If not,
the generator runs, compares `withTotal` (current) with
`withGrandTotal` (canonical), and emits a divergence report.

## Alternatives considered

- **Option A — Treat all generated names as explicit API
  names.** Nothing is refactor-sensitive; every name is
  hard-coded or configured. Rejected: it forces the user to
  configure every generated class, which is the opposite of the
  project's "sensible defaults" goal.
- **Option B — Treat all generated names as implicitly
  derived.** Everything is refactor-sensitive; every rename
  refactor reaches every generated name. Rejected: it breaks
  legitimate explicit API names (RPC method labels, workflow
  trigger names, audit event names) and makes the generator
  fight the IDE.
- **Option C — No divergence reporting.** Let the user discover
  divergence on their own (tests fail, runtime errors, manual
  inspection). Rejected: the whole point of source-visible,
  cooperative codegen is that the generator tells the user
  what is wrong.
- **Option D — IDE plugin that intercepts refactors and
  rewrites generated code automatically.** Useful but
  orthogonal; the divergence-reporting mechanism in this
  decision is the on-disk contract that any IDE integration
  would have to honour anyway.

## Consequences

### Positive

- Developers have a clear mental model: "if I rename a source
  identifier, what generated names will change?" The naming
  contract in each generator's README answers that question.
- Refactor-sensitive generated code is wired through navigable
  Java declarations and references, so IDE rename refactors
  reach it.
- Explicit API names are stable across refactors, which is the
  correct behaviour for public contracts (JSON-RPC labels,
  workflow trigger names, audit event names).
- Divergence reporting gives the user a feedback loop: they
  always know when the IDE refactor has made the generated
  code inconsistent with what the generator would emit today.
- The divergence report is cooperative: it identifies the
  affected block, explains the cause, and offers the user a
  one-action escape hatch (delete the block to regen).
- The pattern composes with DEC-020 (cooperative blocks), DEC-021
  (class-file header), and DEC-019 (source-visible wiring)
  without contradicting them.

### Negative

- Generators MUST maintain and publish a naming contract for
  every derived name they emit. This is additional
  documentation and additional review surface.
- The IDE refactor reachability depends on the generator
  emitting navigable references (`{@link}`, `@see`,
  `@GeneratedFrom`). Generators that skip these references
  will produce refactor-sensitive code that the IDE cannot
  reach, and the divergence report will fire on every rename
  refactor even when the user expected the IDE to handle it.
- Divergence reporting adds a new diagnostic surface that the
  user must learn to interpret. The LSP / IDE sidecar SHOULD
  surface it as a warning with a code action, but a build-log
  diagnostic is the minimum.
- A bug in the naming-contract classification (a name the
  generator thinks is explicit but is actually implicitly
  derived, or vice versa) will produce either missed
  divergences (silently stale generated code) or false-positive
  divergences (noise on every rename refactor). The CI fixture
  for divergence reporting is the defence.
- The `divergences` key in the class-file header (suggested in
  § 6) adds another config key that generators must support.
  Generators that do not want to maintain it can omit it; the
  diagnostic is still emitted on every generation pass.

### Follow-up

- Each generator's README publishes its naming contract table,
  reviewed on changes.
- Provide a helper in the codegen module that compares a
  generated file against the canonical output and emits
  divergence diagnostics in the uniform format.
- Add a CI fixture per generator that renames a source
  identifier, runs the generator, and asserts the correct
  divergence is reported (or the refactor-sensitive block is
  correctly updated).
- Update the LSP / IDE sidecar to surface divergence warnings
  with code actions: "re-emit this block", "acknowledge
  divergence", "update generator naming contract".
- Evaluate whether the IDE plugin should offer "rename
  generated record" as part of the standard rename refactor
  flow, using the `{@link}` / `@see` references as the
  navigation contract.

## Out of scope

- **Runtime reflection to discover naming contracts.** The
  naming contract is published in the generator's README and
  enforced at generation time; runtime discovery is out of
  scope.
- **Cross-generator naming contracts.** If two generators
  consider the same type "theirs" and emit conflicting names,
  that is a generator bug in either or both; let the user
  resolve it.
- **Automatic IDE refactor integration.** The divergence
  reporting mechanism is the on-disk contract; building an
  IDE plugin that intercepts refactors is a follow-up.
- **Renaming of hand-written code.** The decision governs
  generated code only; how hand-written code refers to
  generated code is a separate concern.

## Acceptance criteria

- Every generator that emits a name derived from a source
  identifier (type name, method name, field name) MUST publish
  a naming contract in its README that classifies the name as
  refactor-sensitive or refactor-insensitive.
- Every refactor-sensitive generated name MUST be wired
  through a navigable Java contract (`{@link}`, `@see`,
  `@GeneratedFrom`, or the generated declaration itself) so
  that a standard IDE rename refactor can reach it.
- Every refactor-insensitive generated name MUST be an
  explicit API name (hard-coded or configured), not derived
  from a source identifier that the IDE might rename.
- After any regeneration pass, the generator MUST compare its
  current output against what it would emit today and emit a
  divergence diagnostic for every difference.
- The divergence diagnostic format includes kind, location,
  cause, current value, canonical value, and suggested action.
- The divergence report is surfaced on every generation pass and
  (where available) in the IDE via the LSP / sidecar.
- The class-file header (DEC-021) MAY include a `divergences`
  key listing active divergences for the file; the generator
  MUST preserve user edits to this key.
- A CI fixture per generator asserts that a source rename
  refactor produces the expected divergence report (or the
  expected regenerated output for refactor-sensitive names).
