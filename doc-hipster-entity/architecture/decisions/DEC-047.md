## Context

A generated view enum (`Person_`, `CreditCardPaymentMethod_`, …) is the **field metadata** of a view: one constant
per field, each an anonymous subclass of `FieldDef` that overrides `column()` and inherits every other answer as a
`default`. Nothing in the tree carries a field's **annotations** — the roadmap row (*"Annotation metadata exposure in
generated view enums (FieldAnnotation)"*) was open, and a grep for `FieldAnnotation` found nothing.

Two things already exist and shaped the decision:

- **The tooling already reads the annotations.** `FieldConstraint(String simpleName, String arguments)` carries
  `annotation()` (the source text, as written) and `qualifiedName()`, resolved where the accessor was parsed, with
  the declaring compilation unit's import table in scope. So the *facts* are known at generation time and the
  question is only what shape they take in the generated enum.
- **`FieldDef` is a defaults interface.** Every method below `name()` has a default that reproduces the behaviour of
  a plain field, which is why a generated enum only overrides what it must — and why adding a method with a default
  leaves **every existing generated enum compiling unchanged**.

The maintainer's decision of 2026-10-08, asked for by plan step 6.1 because the change alters generated output:

> annotations as metadata on the generated enum constant

## Decision

1. **`FieldAnnotation(String type, String arguments)` lives in `hipster-entity-api`**, beside `FieldDef`. `type` is
   the annotation's **qualified name** (`jakarta.validation.constraints.Size`) so a consumer needs no import table,
   and `arguments` is the **source text between the parentheses** — empty string when the annotation has none. The
   generator does **not** parse attributes into a model of its own: the semantics of `@Size(min = 1, max = 64)` belong
   to the validation provider, and a second, partial interpretation of them here would be a claim this repository
   cannot keep true.

2. **`FieldDef.annotations()` is a `default` returning `List.of()`.** An unannotated field — and every enum generated
   before this decision — answers "no annotations" without a line of emitted code, which is the same property the
   interface's other defaults have and the reason this change does not rewrite the world.

3. **The emitter writes an `annotations()` override only for a field that carries at least one annotation.** The
   override returns the annotations in **declaration order**, `@Override`-annotated, spliced as text (DEC-030) into
   the constant's anonymous body beside `column()`. A field with no annotations gets no override, so the example's
   diff is limited to the fields that have one.

4. **Metadata, not retained annotations.** The alternative — emitting the annotations themselves with
   `@Retention(RUNTIME)` so a consumer reads them reflectively — was rejected for three reasons that are all
   consequences of this repository's rules rather than taste: the annotations are written on the view **accessor**
   (the developer's own file) and not on the enum, so retaining them there would put a fact in one place and its
   consumer in another; a reflective read is exactly the invisible wiring § 1 rejects; and `arguments` kept as text
   is lossless, while a re-emitted annotation has to survive a format round-trip that buys nothing.

5. **The naming contract (DEC-022) gains a row**: `annotations` is the **API method's** name, and the emitted
   override is wired by `@Override`, so renaming the API method breaks the generated file's compilation rather than
   letting it drift. It is refactor-sensitive **by construction** — the strongest form the naming contract has — and
   the table says so rather than listing a name a generator derived.

## Consequences

**Positive.** A factory that builds a view from XML, JSON or a database row can see a field's constraints without
reading the interface source or reflecting over it: the facts are committed Java the IDE can navigate to. The change
is additive at every level — a new record, a new default method, one override per annotated constant — so nothing
that exists today changes behaviour, and a view with no annotations produces byte-identical output to before.

**Negative, and accepted.** Every annotated field's constant gains a method, so generated files grow where
annotations exist. The `arguments` string is unparsed, so a consumer that needs `min = 1` as a number parses it —
deliberately, because the alternative is this generator owning a validation-attribute model it does not have the
authority to define.

**Neutral.** The override is an ordinary member of an implicitly-recognised generated block (DEC-020), so a
developer may edit it and regeneration will report the divergence rather than silently overwriting it.

## Alternatives considered

- **Retain the annotations on the enum constants** (`@Retention(RUNTIME)`): rejected in § 4 — it moves the fact away
  from where it is written and needs reflection to read.
- **A static `Map<Field, List<String>>` inside the enum**: rejected because it splits each field's metadata in two
  and gives the IDE nothing to navigate; the constant is the field.
- **Put the annotations on the view interface's accessors and let consumers reflect**: rejected — the interface is
  the developer's file, and this generator does not add annotations to it.
- **A typed per-annotation model** (`SizeAnnotation(min, max)`, …): rejected as scope the plan does not ask for and
  the generator cannot own; a text `arguments` field is honest about what is known.
- **Expose only the simple name** (`Size`): rejected because a consumer resolving it would need the declaring file's
  imports — which is exactly the import-table problem the tooling already solved at parse time, and the qualified
  name is what it resolved.

## Follow-ups

- The consuming half — a factory or adapter that reads `annotations()` — is **not** part of step 6.1 and is not
  scheduled by it; the step's subject is the exposure, and this decision deliberately ends where the metadata becomes
  readable.
- If a consumer ever needs structured attributes, the change is to add a parsed accessor **beside** `arguments`, not
  to replace the text: the text is what makes the metadata lossless.
