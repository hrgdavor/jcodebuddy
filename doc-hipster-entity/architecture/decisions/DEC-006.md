## Context

Different views may intentionally expose the same logical field with different Java types. If converter requirements are discovered only at runtime, failures become harder to diagnose and may surface late in production-like flows.

## Decision

Detect type divergence during generation or build validation and require explicit converter coverage for incompatible source/target type pairs.

## Consequences

- Moves mapping failures earlier in the development cycle.
- Makes converter requirements visible and reviewable.
- Introduces additional generator diagnostics and converter registry design work.

## Out of scope

- Converter implementation — converters are declared and registered; this decision does not prescribe how conversion logic is written.
- Runtime type checking — validation is build/generation time only; runtime type mismatches are not addressed here.
- Nullability and null-propagation policy — null handling is a separate concern from type compatibility.
- Custom type mapping for third-party types — the registry contract is in scope; populating it for external libraries is follow-up work.

## Acceptance criteria

- Divergent source/target type pairs MUST be discoverable during generation or build validation.
- Missing required converters MUST fail with actionable diagnostics.
- Boxing/unboxing-only differences SHOULD not require semantic converters.

## Amendment 2026-10-08 — accepted, with two of the three criteria already met and the third located

Plan step 6.4 begins by accepting or amending this record, and it was measured against the tree rather than accepted on
its wording. The result is that this decision is **half implemented already**, which narrows what 6.4 has to build.

**Criterion 1 — already met.** `mapper_type_incompatible` is reported by `ViewMapperGenerator` in DEC-022's format
(`kind`, location, cause, current, canonical, action), alongside `merge_field_type_mismatch`, `type_mismatch`,
`type_ambiguous`, `type_unresolved` and `validation_constraint_type_mismatch`. A divergent source/target pair is
therefore discoverable during generation today.

**Criterion 3 — already met, and more carefully than asked.** The same generator's compatibility rule erases generics,
accepts an `Object` target, allows a primitive that widens (Java boxes and widens in one step), and **rejects** a
narrowing pair — for example a reference target where the source is a primitive — *because it would silently truncate on
overflow*, and rejects a reference-to-primitive target because a nullable field would become an unboxing failure. So a
boxing-only difference is not reported at all, and a narrowing one is reported with the reason rather than left to a
class cast.

**Criterion 2 — not met, and this is what 6.4 is for.** A missing converter is reported as a **divergence**, and a
divergence does not fail a pass: `scripts/gen.js` prints them and continues, which is why the example's committed run
reports three to five of them and still succeeds. "MUST fail with actionable diagnostics" therefore needs a decision the
record did not make, and the amendment makes it: a missing converter for an incompatible pair is a **contract-class**
finding, so it must fail a pass through the **policy machinery step 6.3 built** (a `Nature` per rule, `STRICT` failing on
`CONTRACT`) rather than through a second, parallel failure mechanism invented for it.

**What remains step 6.4's work, then**, and nothing else from this record: (a) a `TypeDivergence` type that names a
divergent pair and its converter requirement, so the finding is a value rather than a message string; (b) the
**converter manifest** — generated and committed, the shape the step's gate asks for — listing the pairs a converter
covers; (c) the contract-class wiring of (a) so a missing coverage fails a `STRICT` pass with the manifest as the
actionable diagnostic ("declare a converter for `A → B`").

**Out of scope, unchanged**: converter *implementation* (declared and registered, not prescribed), runtime type checking,
nullability policy, and populating the registry for third-party types.
