# Entity Companion Project: Data-Oriented Entity Handling

## Overview
The **Entity** project is a companion to the Java Hipster IOC framework. While the IOC project focuses on structural wiring and dependency management, the Entity project focuses on a **data-oriented paradigm** for handling persistent objects (entities) across SQL and NoSQL backends.

Traditionally, ORMs require exhaustive mappings of every field in a database table. Our approach is different: we focus on **Views** and **Metadata Extraction**.

---

## Core Philosophy: Data-Oriented Views

In this paradigm, an entity is simply data stored in a tabular or document form. Your application code shouldn't be forced to define every single field present in the underlying store.

### 1. Minimalistic Definitions
To define an entity, you only need:
- **Primary Key**: The unique identifier for the record.
- **Entity Name**: The name used in the backend store (e.g., table name or collection name).

### 2. Interfaces as Views (Record Pattern)
Instead of a monolithic Entity class, you define a series of **Interfaces** that act as specific "Views" of the data. 
- These views work like relational database views.
- **Record Pattern Naming**: Interfaces follow the modern Java `Record` pattern (e.g., `id()`, `name()`) instead of the legacy JavaBeans pattern (`getId()`, `getName()`).
- You only define the fields you actually need to access for a particular task.
- One underlying "Table" can be accessed through multiple, specialized interfaces depending on the context.

---

## Metadata Extraction & Reusable Patterns

The goal of the Entity project is to assist with extracting metadata from entity information across the entire codebase, driven by these access interfaces.

### Example: The Audit Pattern
Imagine you have an `Auditable` interface defined in your core library:

```java
public interface Auditable {
    String createdBy();
    Instant createdAt();
}
```

By marking an entity or a view as implementing `Auditable`, the sidecar can automatically:
1.  **Extract Metadata**: Recognize that this entity requires auditing logic.
2.  **Generate Behavior**: Augment the data access layer to automatically populate these fields during save/update operations.
3.  **Enforce Consistency**: Ensure that the same auditing pattern is consistently applied across different tables and backends within the project by pointing back to the same shared interface.

---

## 3. Writing and Implementation Strategies

### Writable Interfaces
If an interface is marked as **writable**, the Sidecar will automatically generate a boilerplate interface for writing operations. This keeps your read-only views clean while providing a consistent, generated path for data modification.

### Builders and Change Tracking
Record-style naming plays perfectly with **Fluent Builders**. The Sidecar enhances these builders with built-in **Change Tracking**. 
- Only modified fields are marked as "dirty".
- This enables **Partial Updates** (patching) to the database with zero friction—no more sending full record snapshots when only one field changed.

### DTOs as Clean Contracts
This approach turns DTO interfaces into lean, enforceable contracts for both reading and writing.
- **No Heavy Transformations**: Avoid the "DTO-to-Entity-to-Database" transformation overhead typical of heavy ORMs.
- **Bypassing Internals**: A form submission (via a DTO interface) can bypass internal entity classes entirely.
- **Parallel Updates**: The same DTO can be used to update internal VM caches and the persistent store in parallel, ensuring high performance without complex synchronization logic.

### Implementation Flexibility
The Entity project allows for ultimate flexibility in how these interfaces are backed:
- **Proxy**: Best for "throwaway" objects where high-volume processing happens on the database side. This reduces total source size and bytecode bloat.
- **Generated Bytecode**: A middle-ground optimization.
- **Generated Boilerplate Classes**: The best approach for performance-critical scenarios, such as high-frequency use of data or in-VM caching. 

The goal is to weigh **Runtime Performance** vs. **Compile Time** vs. **Source Size**. Using a proxy keeps the project lean, while boilerplate is generated only where the performance penalty of dynamic reflection/proxies is unacceptable.

---

## Why this approach?

1.  **Decoupling from Schema**: You are no longer "locked in" to matching your Java classes 1:1 with your database schema.
2.  **Virtual Tables**: Access virtual tables or complex joins as if they were simple entities via specialized view interfaces.
3.  **Sidecar Intelligence**: The LSP sidecar monitors these interfaces to build a global map of how data is used throughout your application, enabling smarter refactoring and documentation.
4.  **Agentic Ready**: Like our IOC approach, this data-oriented structure is highly predictable and easy for AI agents to reason about, as it relies on clean interfaces rather than complex, reflective ORM magic.
