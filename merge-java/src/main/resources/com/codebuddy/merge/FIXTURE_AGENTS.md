# AGENTS.md — working inside a merge-java fixture workspace

> Read this file completely before touching anything in this folder.
>
> This folder was generated by merge-java's `MergeFileTool` from a **real user's
> file with unresolved merge conflicts** (see `run.json` for the facts of the
> run). It is a workspace for turning each unresolved conflict into a new,
> tested resolver for the `merge-java` module — **without leaking the user's
> code**. The loop it drives: *anonymize → build the resolver on the anonymized
> fixture → re-verify the resolver on the original → report.*

## 0. Confidentiality rules (these override everything below)

Everything under `source/` and `cases/` is **proprietary user code**. It is here,
on this machine, only so that a resolver can be derived from its *shape*.

1. **Never** copy, quote, paraphrase or retype any part of `source/` or `cases/`
   into the merge-java repository — not into main sources, tests, test fixtures,
   docs, commit messages, branch names, or issue text.
2. **Never** send it to any external service beyond the LLM session already
   processing this folder: no web tools, no pastebins, no uploads, no issue
   trackers.
3. The only derivative that may leave this folder is the **anonymized fixture**
   you produce in §2, and resolver code, tests and docs derived *exclusively*
   from that anonymized fixture.
4. The `.gitignore` in this folder (containing `*`) is deliberate: it keeps the
   whole workspace out of version control even when the folder sits inside a
   repository. **Do not remove it, and never `git add` this folder.**
5. When in doubt whether something is derived from the original, treat it as
   derived and leave it out.

The anonymized fixture is a **firewall**. After §2, develop the resolver as if
the original did not exist — until §4, which *reads* the original to re-verify
but must never *write* anything based on its content into the repository.

## 1. What is in this folder

```
run.json                     facts about the run: file, branch, base source, per-block outcomes
.gitignore                   contains `*` — deliberate, keep it
AGENTS.md                    this file
source/
  conflicted.java.txt        the file exactly as received, conflict markers included
  ours.java.txt              the whole "ours" version, reconstructed
  theirs.java.txt            the whole "theirs" version, reconstructed
  base.java.txt              the whole base version — present only when a real base was known
  ours.diff / theirs.diff    unified diffs against base — present only when base was known
cases/
  case-<n>-<type>-<hash>/    one folder per conflict the existing resolvers could not fix
    conflict.json            type, handling, marker lines, what each resolver said, fix paths
    block/
      conflicted.txt         the exact conflict block, markers included
      ours.java.txt          the block's "ours" side
      theirs.java.txt        the block's "theirs" side
      base.java.txt          the block's base side — only when the file used the diff3 style
    whole/
      base/<File>.java.txt   three-way fixture layout (merge-java's ThreeWayFixture shape);
      ours/<File>.java.txt   base/ is absent when no real base was known
      theirs/<File>.java.txt
      ours.diff / theirs.diff
```

`run.json` records `"baseSource"`: `diff3` (the file carried `|||||||` base
sections), `git-index-stage-1` (the base came from the repository's unmerged
index) or `none`. With `none`, the base is genuinely unknown — read
`merge-java/docs/WHAT_IS_BASE.md` before inventing one, and see §2 step 5.

## 2. Anonymize each case into a separate fixture

For **every** `cases/case-…/` folder, create `anonymized/<shape-name>/` inside
this folder, mirroring the `whole/` layout (`base/`, `ours/`, `theirs/` with the
same `<File>.java.txt` names, plus `ours.diff` / `theirs.diff`).

1. **Invent a neutral domain.** For example `com.example.inventory` with types
   like `StockLedger`, `ReservationService` — or any obviously generic domain.
   The anonymized fixture must look like it was written for a tutorial, not
   extracted from a product.
2. **Replace everything identifying:** package names, type names, method /
   field / parameter / variable names, string and character literals, comments
   and javadoc text, log messages, numbers that carry domain meaning, file and
   type names in the layout itself.
3. **Preserve everything structural:** the syntactic shape of each side, the
   member order, the conflict `type` recorded in `conflict.json`, the shape of
   the disagreement (what each side did relative to base), the whitespace and
   formatting pattern, and roughly the size of each side. The case must remain
   an instance of the same problem — a shape a two-way text diff gets wrong
   (see `merge-java/docs/THREE_WAY_FIXTURES.md` §3 for what makes a case
   valuable).
4. **Name the directory for the change shape**, not the outcome:
   `method-add-both-same-body`, `constant-same-name-different-value`,
   `import-add-and-remove-different` (THREE_WAY_FIXTURES.md §Naming).
5. **If `base/` is absent** (`baseSource: none`), synthesize the minimal
   plausible base consistent with both sides, and record `synthesized base: true`
   plus your reasoning in `anonymized/<shape-name>/README.md`. Never fabricate a
   base silently: a wrong base invents conflicts that do not exist
   (`docs/WHAT_IS_BASE.md`).
6. **Self-check before moving on — all of these must hold:**
   - no identifier of four or more characters from the original appears in the
     anonymized fixture, except Java keywords and standard JDK names
     (`java.util.List`, `String`, …);
   - no comment, prose or literal text from the original survives, even
     translated or reworded;
   - detection classifies the anonymized three-way the same way as
     `conflict.json` records for the original:

     ```java
     var detection = new ConflictDetectionService().detect(
         fixturePath, baseText, oursText, theirsText, typeContext);
     // the expected ConflictType from conflict.json must appear
     ```
   - each side is a complete, compilable unit — whole files, not hunks
     (THREE_WAY_FIXTURES.md §1).

## 3. Build the new resolver from the anonymized fixture only

Follow `merge-java/ADDING_A_RESOLVER.md` exactly:

1. Copy `anonymized/<shape-name>/` into
   `merge-java/src/test/resources/fixtures/<shape-name>/`. **This copy — never
   anything from `source/` or `cases/` — is what enters the repository.**
2. Add a `ConflictType` with its `Handling` (or reuse the existing type when the
   gap is in the resolver, not the taxonomy).
3. Extend `AbstractConflictResolver`: three methods, stateless, declining
   (`null`) rather than guessing.
4. Register the resolver in `ConflictResolvers.defaultResolvers()` — one line,
   the registry test enforces it.
5. Extend `ConflictDetectionService` when detection cannot yet produce the type.
6. Write the tests: extend `AbstractResolverTest`, load the fixture through
   `ThreeWayFixture`, assert the computed change against the documented diffs,
   and assert the resolved output is structurally intact
   (`ResolutionVerifier.wasBalanced`). Every piece of test data comes from the
   anonymized fixture.
7. `mvn -f merge-java/pom.xml test` passes (JDK 25 on `JAVA_HOME`; or use
   `scripts/mvn-jdk25.cmd` from the repository root).

Optionally turn the anonymized fixture into a real git repository to inspect it
in a git GUI: `bun run merge-java/scripts/git-sample/sample-repo.js
<shape-name>`.

**Escape hatch — some shapes are not resolvable.** If the case is inherently a
human judgement (a preference, or semantics no syntactic rule can decide — see
`DESIGN_NEVER_AUTO_RESOLVED.md`), do **not** force a resolver. Write the verdict
and its reasoning, in shape language only, into
`anonymized/<shape-name>/VERDICT.md`, skip §4 for that case, and say so in the
report (§5).

## 4. Re-verify the new resolver on the ORIGINAL case

The anonymized fixture proves the resolver handles the shape; the original
proves it handles the real thing. The original stays in this folder and is read
**programmatically**, through merge-java's own re-verification entry point:

```java
MergeFileTool.Reverification check = MergeFileTool.reverify(
    Path.of("<this folder>/cases/case-1-structural_change-…"),  // never leaves this folder
    new YourNewResolver());

check.kind();      // AUTO    -> viable without asking
                   // REVIEW  -> viable, but a human confirms
check.viable();    // false   -> the resolver declined or produced nothing applicable
check.explanation();
```

- **`viable()` is true** — the loop is closed for this case. Report both halves:
  the anonymized test results and the original-case verdict.
- **`viable()` is false** — iterate on the resolver **using the anonymized
  fixture only**. You may use the *shape* of the failure (which kind came back,
  which structural property failed, which classification was missed) to reason
  about the fix, but no text, identifier, literal or path from the original may
  appear anywhere in the repository — not in code, not in a test, not in a
  "temporarily, for debugging" comment, not in a commit message. Express every
  fix as a structural rule and add an equivalent anonymized test case that
  reproduces the failure shape.
- **Never weaken the verification gate** (`ResolutionVerifier`) or a test
  assertion to make the original case pass. A resolver that only passes with the
  gate off is not viable.
- Re-run §4 after every change to the resolver, until it is viable or you have
  concluded (in shape language) that the case is not mechanically resolvable.

## 5. Report and clean up

Report one row per case:

| original case (folder name only) | anonymized fixture | resolver class | anonymized tests | re-verification on original |
|---|---|---|---|---|
| `case-1-structural_change-…` | `method-add-both-same-body` | `MethodAddBothResolver` | 12 passed | viable (AUTO) |

The folder name of an original case is safe to report; its **contents** are not.

This workspace is temporary by design. Once the resolver is merged and the
report above is delivered — or immediately, if the user asks — delete this
folder. Nothing in it needs archiving: the repository keeps the anonymized
fixture, and every fact in `run.json` is reproducible by re-running
`MergeFileTool` on the source file.
