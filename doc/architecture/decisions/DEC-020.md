# DEC-020: Cooperative codegen — preserve user-tweaked generated blocks, allow regen by deletion

## Context

JCodeBuddy's generators are source-visible (DEC-009) and frequently
re-run during development (live file watching, sidecar tooling, build
hooks). Today, every regeneration pass rewrites generated regions from
scratch. That works for output the user has not touched, but it
actively fights the user in three common situations:

1. **Local tweaks.** A developer reads the generated code, finds a
   place where the generator made a sub-optimal but functionally
   correct choice (a hand-tuned SQL fragment, a more descriptive log
   message, a custom exception type, a domain-specific validation),
   and edits the generated source to fix it. The next regeneration
   silently undoes the edit, often with no diff noise the developer
   notices until production breaks.

2. **Emergencies.** A generator bug ships; the user needs a local
   workaround that ships today. They edit the generated output, the
   workaround is in place, and then someone runs a regeneration
   later and the workaround is gone.

3. **Experimentation.** A developer wants to try a different
   dispatch table, error message, or generated constant to compare
   behavior, without having to disable the generator entirely or
   fork the generator.

DEC-018 (freeze markers) covers the **all-or-nothing** case: a
developer marks a whole file or whole element as frozen and the
generator leaves it alone. That is the right tool when the generator
is wrong everywhere for that element. It is the wrong tool when the
generator is right in 99% of the output and the user just wants to
keep one tweak.

This decision defines the **cooperative editing** pattern. The hard
rule is simple:

> *If the user has not deleted a piece of generated code, do not
> rewrite it on the next pass.*

The challenge is **finding** that piece again on the next pass
without rewriting the file from scratch. This decision chooses the
**lightest possible** mechanism for that — and explicitly
discourages a strict, mandatory `// generator:begin` /
`// generator:end` comment-marker scheme that adds noise to every
generated file.

## Decision

### 1. The user-edits-survive rule is mandatory

The hard rule:

> *For every block of generated code a generator might rewrite, if
> the user has not deleted the block, the next regeneration pass
> MUST preserve the existing source of that block verbatim —
> including any user edits inside it. Deleting the block is the
> user's explicit opt-in to regen.*

The user opts back into regeneration by **deleting the block**
(method body, case arm, builder method, etc.). When the generator
runs next, it sees the block is gone, and emits a fresh one at the
canonical location.

This is the **whole** of the user-facing contract. The next four
sections describe how generators find their previous output.

### 2. Default mechanism: implicit block detection, not strict markers

**Discouraged.** Requiring every generated block to be wrapped in
`// generator:begin <id> <key>` / `// generator:end <id> <key>`
markers is **discouraged** as the default. The reasoning:

- It adds two lines of noise to every block, on every regeneration,
  for the rest of the project's life.
- It is one more marker syntax for users to learn, even when they
  are not actively tweaking the generated output.
- It makes the generated code visually heavier, which fights the
  DEC-009 goal of "human-readable checked-in source".
- It only helps if the generator cannot otherwise find its previous
  output — and in practice, most generators can.

**Default.** Generators SHOULD find their previous output by
**recognition**, not by markers. The generator is the entity that
emitted the block in the first place, so it knows the shape of
what it emitted. On the next pass it parses the existing file with
JavaParser, walks to the canonical location for the block, and
asks "is the block I see here a block I previously emitted?" —
based on structural shape, not on a comment.

Examples of "block I previously emitted" recognition:

- A **switch entry** keyed by the JSON-RPC method name
  `users.get`: the generator scans the existing `switch` and looks
  for a `case "users.get":` arm. If present, it is the block;
  preserve the body (which may be a hand-written call into
  `usersService.get(...)`, a custom log message, whatever).
- A **builder method** on a record builder: the generator looks
  for a method whose name, parameter type, and return type match
  the canonical signature of the setter it would emit
  (`public Builder withName(String name)`). If present, preserve
  the body.
- A **loop-guard scaffolding** region around a particular entity
  type: the generator looks for a method whose name contains
  `recomputeDerivedTotalsFor` and whose parameter type is
  `Order`, etc.

In all three cases the user is free to edit the body. The
generator does not need a marker to find the block again; it
recognises the block by the same shape it used to emit it.

**Optional marker, not required.** A generator MAY emit a single
optional comment line at the top of a block — for example
`// generated by rpc-dispatcher — edit freely, delete to regen` —
as a **user-facing hint** that this block is owned by a generator.
This is a single line, scoped to the block, and it is *not*
required for the generator to find the block on the next pass. The
generator MUST NOT depend on this comment for recognition; it is a
UX aid, not a contract.

**Reporting mode.** A generator SHOULD support a
`--report-preserved-blocks` (or equivalent) mode that, after a
normal regeneration pass, prints the set of blocks it preserved
that differ from what it would have emitted. This is the
diagnostic surface that lets the user know "I kept something you
might want to look at" without burying the diff in marker
comments. The format is the same uniform format the brainstorm
file describes, so a future LSP / CI can parse it.

### 3. Strict-comment blocks are allowed, not forbidden, but discouraged

A generator MAY still choose to wrap its output in
`// generator:begin <id> <key>` / `// generator:end <id> <key>`
markers. The decision **does not forbid** this. Reasons a generator
might choose the strict form:

- The generator's blocks cannot be reliably recognised by shape
  (e.g. they are free-form Java statements inside a method body
  rather than a self-contained `case` arm or method).
- The user has asked for stricter behaviour after observing
  preservation bugs.
- A future codegen policy decides that strict markers are the
  right default (this decision explicitly leaves that door open).

When a generator does use strict markers, the marker syntax and
behaviour are exactly as the brainstorm file describes. But:

> The default for new generators is **implicit detection**. A
> generator that wants strict markers must justify the choice in
> its own README, and the project reserves the right to push back
> on it during review.

### 4. A small "marker" language is enough

The whole marker language, if a generator decides to use it,
consists of three things:

- A single optional user-facing comment at the top of a block:
  `// generated by <generatorId> — edit freely, delete to regen`.
  Not required. Not relied on for recognition.
- A pair of strict markers, only when the generator explicitly
  chooses them:
  `// generator:begin <generatorId> <stableBlockKey>` and the
  matching `// generator:end`. Optional, not the default.
- The hard user contract: "delete the block to regen" is a
  *property of every block*, not a property of the marker
  language. The marker language is only ever an aid to the
  generator in finding its previous output.

This is deliberately smaller than what the previous draft of
this decision proposed, where the strict marker pair was the
default for every block.

### 5. Compatibility with DEC-018 freeze markers

Freeze markers (DEC-018) are **higher priority** than cooperative
preservation. If a file or declaration is marked
`@GeneratedFrozen` or `// generator:freeze`, the generator MUST
NOT touch any block inside it, including the optional hint
comment. This lets a user escalate from "preserve this one tweak"
to "leave the whole file alone" without restructuring their code.

### 6. Compatibility with DEC-019 source-visible wiring

The cooperative pattern is itself **source-visible**: the
generator's recognition rules are ordinary Java, the preserved
blocks are ordinary Java, and the generator's behaviour is fully
specified by this decision. No runtime reflection, no bytecode
rewriting, no classpath scanning is involved on the
generator-to-preserved-block path. (See [DEC-019](DEC-019.md).)

### 7. The diff must be minimal and stable

Regeneration MUST NOT rewrite surrounding code (imports, package
declaration, other blocks, hand-written methods) just because a
single block changed. The patcher uses an AST-aware diff
(typically `com.github.javaparser` with
`LexicalPreservingPrinter`) and operates block-by-block. The
diff produced by a regeneration run is **the minimum set of
lines that actually changed**, not a rewritten file.

### 8. Idempotency

Running the generator twice in a row, with no source change in
between, MUST produce no diff on the second run. This is the
basic regeneration-consistency check from DEC-009; the
cooperative patcher must satisfy it.

## Worked examples

These show the **default** behaviour (implicit detection) for
the three patterns called out as motivation in the brainstorm.

### Example 1 — JSON-RPC dispatcher case arm

Hand-written orchestration:

```java
public class RpcDispatcher {

    public JsonRpcResponse dispatch(JsonRpcRequest req) {
        return switch (req.method) {
            case "users.get"    -> usersService.get(req.params, req.id);
            case "users.create" -> usersService.create(req.params, req.id);
            case "users.delete" -> usersService.delete(req.params, req.id);
            default             -> JsonRpcResponse.err(req.id, -32601,
                                            "Method not found: " + req.method);
        };
    }
}
```

User tweaks the `users.create` arm to add a log line:

```java
case "users.create" -> {
    log.info("creating user: {}", req.params);
    usersService.create(req.params, req.id);
}
```

On the next regen pass, the dispatcher generator:

1. Walks to the canonical location (the `switch` inside
   `dispatch`).
2. Sees a `case "users.create":` arm is already present.
3. Recognises it as the block it previously emitted.
4. **Preserves the body verbatim**, including the log line.
5. If a new method `users.update` is added to the dispatcher
   config, the generator **emits a new** `case "users.update":`
   arm at the canonical position; it does not touch the existing
   `users.create` arm.

The user opts back into the canonical body for `users.create` by
**deleting the arm**. On the next regen pass, the generator sees
the arm is gone and emits a fresh one.

### Example 2 — builder for a record

A `Person` view has a generated builder class. The generator
emits one `withXxx(...)` method per field, parameterised by the
field's name and type.

```java
public final class PersonBuilder {
    private final Person.Impl target = new Person.Impl();

    public PersonBuilder withName(String name) {
        target.setName(name);
        return this;
    }

    public PersonBuilder withAge(int age) {
        target.setAge(age);
        return this;
    }

    public Person build() { return target; }
}
```

The user adds a custom convenience method:

```java
public PersonBuilder withFullName(String first, String last) {
    target.setName(first + " " + last);
    return this;
}
```

The user's `withFullName` is **not** a block the generator
previously emitted, so the generator does not "preserve" it as a
generated block — it is simply a hand-written method. The
generator's recognition rule is "look for `with<Field>` methods
whose field name is in the canonical field set of `Person`". A
new field `email` added to `Person` makes the generator emit a
new `withEmail(...)` method; the user's `withFullName` is left
alone.

If the user edits the `withName` body to add validation:

```java
public PersonBuilder withName(String name) {
    if (name == null || name.isBlank()) {
        throw new IllegalArgumentException("name must not be blank");
    }
    target.setName(name);
    return this;
}
```

The generator still recognises `withName(String) → PersonBuilder`
as the block it emitted, **preserves the body verbatim**, and
does not regress the validation. The user opts back into the
canonical body by deleting `withName`; the next regen emits a
fresh one.

### Example 3 — loop-guard scaffolding for a business-process step

A `recomputeDerivedTotals` step is generated for the `Order`
entity type:

```java
@CoreChangeOnChange
void recomputeDerivedTotals(ProcessingUnit<OrderContext> unit) {
    for (var w : unit.coreWrites().updatesForType(Order.class)) {
        var order = w.entity();
        var derived = order.subtotal().plus(order.tax()).minus(order.discount());
        if (!derived.equals(order.derivedTotal())) {
            unit.coreWrites().update(order.id(), order.withDerivedTotal(derived));
        }
    }
}
```

The user changes the formula to exclude cancelled lines:

```java
@CoreChangeOnChange
void recomputeDerivedTotals(ProcessingUnit<OrderContext> unit) {
    for (var w : unit.coreWrites().updatesForType(Order.class)) {
        var order = w.entity();
        var activeLines = order.lines().stream()
            .filter(l -> !l.status().equals(LineStatus.CANCELLED))
            .toList();
        var derived = activeLines.stream()
            .map(Line::total)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        if (!derived.equals(order.derivedTotal())) {
            unit.coreWrites().update(order.id(), order.withDerivedTotal(derived));
        }
    }
}
```

The generator recognises the method by its annotation
(`@CoreChangeOnChange`), name, and parameter list. It **preserves
the body verbatim**. If a new entity type is added later, the
generator emits a new scaffolding method for it; it does not
touch the existing one.

## Alternatives considered

- **Option A — Always rewrite generated regions.** What the
  generator does today. Rejected: punishes every user tweak, makes
  local workarounds impossible, and creates churn on every
  regeneration.
- **Option B — Whole-file freeze markers only (DEC-018).** Already
  in place for the all-or-nothing case. Insufficient on its own:
  freeze a whole dispatcher to keep one case arm, and you freeze
  every other case arm too. This decision is the granular
  companion.
- **Option C — External override file (e.g.
  `dispatcher.overrides.java`).** Keep generated code pure, put
  user overrides in a separate file the generator composes at
  build time. Rejected: doubles the number of files the developer
  has to read to understand a single piece of behaviour, and the
  merge logic in the generator becomes a hidden DSL.
- **Option D — Runtime hooks / callbacks.** The generated code
  calls into a hand-written method the user provides. Rejected:
  it works for *one* level of customisation, but the user has to
  anticipate every place they might want a tweak. The cooperative
  pattern lets the user tweak anywhere without a generator
  change.
- **Option E — LSP / IDE plugin that intercepts the generator's
  writes and merges them with user edits at the IDE level.**
  Useful but orthogonal; the cooperative pattern is the on-disk
  contract that any IDE integration would have to honour anyway.
- **Option F — Strict `// generator:begin` /
  `// generator:end` markers around every block (the previous
  draft of this decision).** Now demoted to a discouraged
  option. Adds two lines of noise to every block, makes
  generated files visually heavier, and is unnecessary for the
  most common patterns (switch arms, builder methods, scaffolding
  methods), which the generator can recognise by shape. May
  still be the right choice for free-form blocks that cannot be
  recognised structurally; allowed, not the default.

## Consequences

### Positive

- Developers can keep local workarounds, hand-tuned defaults, and
  domain-specific tweaks across regenerations without disabling
  the generator.
- The generator remains the source of truth for the canonical
  version of every block; the user can opt back into the
  canonical version with a one-action gesture (delete the
  block).
- Regen diffs become small and reviewable: only the blocks the
  user has *not* tweaked actually change.
- The pattern composes with freeze markers (DEC-018) and with
  the source-visible wiring rule (DEC-019) without contradicting
  them.
- The default mechanism (implicit detection) adds **no** noise to
  generated files, satisfying the DEC-009 spirit of clean
  checked-in source.
- A single-line optional hint comment (`// generated by ... —
  edit freely, delete to regen`) is enough UX for the user to
  know what is and is not owned by the generator.
- The reporting mode (`--report-preserved-blocks`) gives the
  user a feedback loop without requiring the generator to
  annotate every block.

### Negative

- Implicit detection is **only as good as the generator's
  recognition rules**. A generator that fails to recognise a
  block it previously emitted will regenerate it (silently
  dropping the user's edit). The CI preservation fixture
  acceptance criterion exists to catch this class of bug.
- Generators that cannot reliably recognise their output by
  shape (free-form Java statements, mixed hand-written and
  generated code in the same block) need to either (a) choose
  the strict marker form, or (b) restrict themselves to a shape
  that is recognisable. Both are valid choices; neither is
  free.
- A bug in the recognition rule can cause the generator to
  *mis-recognise* a hand-written block as a generated one (and
  refuse to overwrite it, leaving an outdated block in place)
  or vice versa. The diagnostic and CI fixture are the
  defences.
- The marker language is now smaller and less uniform across
  generators. Reviewers must read each generator's README to
  know whether it uses strict markers, implicit detection, or
  both.
- The user has to know that "delete the block" is the opt-in.
  The single-line hint comment is the only on-disk signal; the
  LSP / IDE sidecar SHOULD surface it (highlight, hover with
  explanation).

### Follow-up

- Each generator's README publishes its recognition rule
  (which AST shapes it considers "blocks it previously emitted").
  This becomes part of the generator's contract and is reviewed
  on changes.
- Provide a small helper in the codegen module for the common
  recognition patterns (switch arm keyed by string literal,
  builder method keyed by name+signature, scaffolding method
  keyed by annotation+name+signature), so individual generators
  do not re-implement them.
- Add a CI check that runs the generator twice in a row and
  fails if the second run produces a non-empty diff
  (idempotency).
- Add a CI check that runs the generator on a fixture file with
  a known user tweak (e.g. a case arm with a custom log
  message) and asserts the tweak is preserved verbatim across
  regeneration, and that the reporting mode flags the
  difference.
- Update the LSP / IDE sidecar to highlight the optional
  `// generated by ...` hint comment, show a hover with the
  block's recognition rule, and offer a "regenerate this block"
  code action.

## Out of scope

- **Cross-generator recognition conflicts.** If two generators
  consider the same block "theirs", the conflict is a generator
  bug in either or both; let the user resolve it (typically by
  manual code).
- **Merge conflict resolution inside a block.** If two branches
  each tweak the same block, that is a regular git merge
  conflict and is resolved with the user's usual tool, not by
  the generator.
- **Visual diff UI.** The reporting mode and the optional hint
  comment give the developer the information; building a UI on
  top of them is a follow-up.
- **Reverting a tweak back to canonical automatically.** The
  pattern lets the user re-trigger regeneration on demand
  (delete the block); the generator does not auto-revert.
- **Generated metadata outside source files.** This decision
  governs *Java source*; binary metadata, JSON sidecars, and
  similar are out of scope.

## Acceptance criteria

- Every generator in the project MUST preserve, on the next
  regeneration pass, the body of every block it previously
  emitted that the user has not deleted.
- A user who edits the body of such a block does NOT lose those
  edits on the next regeneration.
- A user who deletes the block gets a fresh block emitted at
  the canonical location on the next regeneration.
- By default, no strict `// generator:begin` /
  `// generator:end` marker pair is required. A generator that
  uses them documents the choice in its README.
- A regenerated file with no user changes produces an empty
  diff on the next regeneration (idempotency).
- The generator's recognition rule (how it finds its previous
  output) is published in the generator's README and reviewed
  on changes.
- A CI fixture per generator asserts that a known user tweak is
  preserved verbatim across regeneration.
- Freeze markers (DEC-018) override cooperative preservation: a
  frozen file or declaration is not touched at all.
- The marker and reporting-mode patterns are documented at
  `doc/brainstorm/cooperative-codegen-preserve-user-tweaks.md`
  and reachable from every generator's own docs.
