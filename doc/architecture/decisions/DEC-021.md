# DEC-021: Generator class-file header — short id, JSON5 config, per-class options

- Status: Proposed
- Date: 2026-09-03

## Context

JCodeBuddy's generators are source-visible (DEC-009) and frequently
cooperative (DEC-020). The unit of generation is usually a whole
**class** (a dispatcher, a builder, a scaffolding helper, a
ProcessingUnit holder, …). For every such generated class, two
things are useful to the developer at a glance:

1. **What is this class, and which generator produced it?** Today,
   the developer has to read the surrounding context or follow the
   generator's id through a sidecar log to know which generator
   emitted the class. The file itself does not say.
2. **Can I tweak the generator's behaviour for *this* class
   specifically?** Some generators have options that affect what
   they emit: turn off a particular emission, switch the recognition
   style from implicit to strict, change a default, etc. Today the
   developer has to find the generator's project-level config and
   either hope it supports per-class options or accept the
   project-wide default.

The first draft of this decision put this information in a
class-body block comment. That was the wrong shape: it lived
inside the class, occupied a noticeable amount of vertical space,
was the first thing a reader saw, and competed with the
generator's own block-level cooperation per DEC-020.

This is the rewritten version. The header is now a **two-line
Java line-comment pair above the imports** of the file. The first
line is a short `{@link …}` reference plus a one-line description
of the class. The second line is a single-line JSON5 config blob
that the user can edit to customise the generator for that file
only.

## Decision

### 1. The header location and shape

Every generator that emits a whole class (or a top-level record,
or any other top-level type declaration) MUST emit a **two-line
Java line-comment pair as the first non-blank lines of the file,
above the `package` and `import` declarations**:

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generate builder for records.
// {enabled:true, blockMarker: "implicit"}

package hr.hrg.example;

import ...
```

Rules:

- The two lines MUST be ordinary Java line comments
  (`// …`), not block comments. The closing `//` ends the line.
- The two lines MUST appear immediately above the first
  `package` declaration, with at most blank lines between them.
  No other code or comment may appear before them in the file.
- The first line MUST start with `// {@link `, then the fully
  qualified class name of the generator (or its main entry
  point), then `}` and a single space, then a **one-line
  description** of the class. The whole first line, including
  the trailing period, MUST fit in 120 characters.
- The second line MUST start with `// {` and end with `}` and
  contain a single-line JSON5 config blob (see § 3).
- The header is generated source and follows the cooperative
  preservation rules from DEC-020. The user may edit it; deleting
  it (both lines) lets the generator re-emit a fresh pair on the
  next pass.

### 2. What the first line is for

The first line is the developer-facing note. It MUST be short
(one line, ≤ 120 characters) and it MUST link to the generator
so a developer can jump-to-definition from the comment to the
generator's source:

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generate builder for records.
// {@link hr.hrg.codebuddy.RpcDispatcher}  JSON-RPC dispatcher with explicit case-arm routing (DEC-019).
// {@link hr.hrg.codebuddy.LoopGuardGen}   Per-entity fixed-point loop guard for @CoreChangeOnChange steps.
```

The `{@link …}` target is the generator's main entry-point class.
Any IDE that supports the `{@link}` syntax will render it as a
clickable link. The class name does not need to live in the same
package; the import is implicit by the `{@link}` syntax (Java
resolves it against the project's classpath, the same way
Javadoc does).

The one-line description is **the description of the class in
this file**, not the description of the generator in general.
Generators are encouraged to keep it short enough to fit on one
line and end it with a period.

### 3. The second line is a single-line JSON5 config

The second line is a single-line JSON5 object literal:

```java
// {enabled:true, blockMarker: "implicit"}
// {enabled:true, blockMarker: 'strict', maxMethods: 64, dryRun: false}
// {enabled:false, note: 'see local tweaks; delete this line to re-enable generator'}
```

The project uses a **JSON5 subset**, kept as small as possible
and pinned to a specific list of Jackson features. The list of
supported features is the table in § 4. Anything outside that
table is **not** in the JSON5 subset and the generator MUST emit
a diagnostic if it encounters it.

Values are JSON values: strings, numbers, booleans, `null`, and
nested objects / arrays. Booleans MUST be written as
`true` / `false` (lowercase, no quotes). Numbers follow the
JSON5 rules in § 4.

### 4. The JSON5 feature subset, mapped to Jackson

The generator's config parser uses Jackson with the following
`JsonReadFeature`s enabled. Each row of the table below is a
JSON5 feature the project accepts and the Jackson feature the
parser enables to read it.

| JSON5 feature                                | Jackson `JsonReadFeature`                                |
| -------------------------------------------- | -------------------------------------------------------- |
| Single-quoted strings (`'foo'`)              | `ALLOW_SINGLE_QUOTES`                                    |
| Unquoted field names (`{foo: 1}`)            | `ALLOW_UNQUOTED_FIELD_NAMES`                             |
| Trailing commas (`{a:1, b:2,}`)              | `ALLOW_TRAILING_COMMA`                                   |
| Leading decimal point (`.8675`)              | `ALLOW_LEADING_DECIMAL_POINT_FOR_NUMBERS`                |
| Leading plus sign for numbers (`+42`)        | `ALLOW_LEADING_PLUS_SIGN_FOR_NUMBERS`                    |
| Non-numeric numbers (`Infinity`, `NaN`, hex) | `ALLOW_NON_NUMERIC_NUMBERS`                              |
| Backslash escaping of any character          | `ALLOW_BACKSLASH_ESCAPING_ANY_CHARACTER`                 |

The parser MUST NOT enable any Jackson feature outside this
list. If the project later wants to allow, say, multi-line
strings or comments inside the JSON5 blob, the table is the
single place to add them, and the parser is updated in lockstep.

### 5. Per-class config semantics

The user MAY edit a config value to change the generator's
behaviour for *this* file only. The generator MUST re-read the
header on every regeneration pass and honour the values it finds
there. The generator MUST also:

- Validate each value: an invalid value is a **diagnostic**, not
  a silent fallback to the default. The generator MUST NOT
  silently ignore a typo.
- Emit a diagnostic when a config value differs from the project
  default, so the user knows the file has been customised.
- Emit a diagnostic when a config key is unknown to this
  generator version (the user kept a key from an older
  generator; the new generator does not honour it).
- Preserve unknown keys on a best-effort basis (round-trip them
  in the regenerated header), so a downgrade to the previous
  generator version still works.

### 6. The `enabled` knob

Every generator MUST accept an `enabled` option (default `true`)
in its class-file header. When the user sets it to `false`:

- The generator MUST treat the file as if it were hand-written.
  It MUST NOT rewrite the file's class body, the imports, the
  package declaration, or the header on the next regeneration
  pass.
- The generator MUST emit a single diagnostic the first time it
  would have otherwise emitted into this file: "generator
  `<generatorId>` is disabled for this file via `enabled: false`".
- The generator MUST preserve the existing header (the user is
  using it as documentation of the disabled state), but it MUST
  NOT add or remove config keys without an explicit user action.

This is the per-file equivalent of DEC-018's whole-file freeze,
and the user opts back into generator output by setting the
value back to `true` (or by deleting the header, which the
generator treats as a request to re-emit everything in the
canonical layout).

### 7. The header is itself cooperative

The header is generated source and follows the cooperative
preservation rules from DEC-020. Concretely:

- The first line's description MAY be updated by the generator
  on a regen pass. If the user has edited the description, the
  generator MAY preserve the user's edit, but is not required
  to.
- The second line's config is treated as user-owned: the
  generator MUST preserve user edits verbatim, and only update a
  key's value if the user has reset it to the default (or if
  the project-wide default has changed, in which case the
  generator MAY update the value but MUST emit a diagnostic).
- If the user **deletes the header entirely** (both lines), the
  generator treats it as a request to re-emit a fresh header
  with project-wide defaults.

### 8. Compatibility with DEC-018 freeze markers

If the file is marked `@GeneratedFrozen` or carries
`// generator:freeze`, the generator MUST NOT touch the header
either. The header follows the same priority rule as everything
else in the file.

### 9. Compatibility with DEC-019 source-visible wiring

The header is plain Java line-comment text, navigable in any
IDE. The `{@link …}` reference points the developer at the
generator that produced the class, satisfying the DEC-019
"follow the program flow from entry point to leaf" rule for
the **generator side** of the same workflow. (See
[DEC-019](DEC-019.md).)

### 10. The generator MUST provide a way to read the header

Every generator MUST expose, in its public API, a way to read
the file's header and parse the JSON5 config line. The exact
shape (synchronous parser, streaming parser, codegen-module
helper) is left to the generator, but the parsed config MUST be
reachable from the generator's own code so that:

- Tests can assert on the config keys and defaults.
- LSP / IDE tooling can show a hover for any config key.
- CI fixtures can produce a file with a known config and assert
  the generator respects it.

The codegen module SHOULD provide a shared helper that builds
the Jackson `ObjectMapper` with the JSON5 features in § 4
enabled, and exposes a typed config object. Individual generators
extend the typed config with their own keys.

## Worked examples

### Example 1 — a fresh generated file

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generate builder for the Order record.
// {enabled:true, blockMarker: "implicit"}

package com.example.order;

import ...

public final class OrderBuilder { ... }
```

### Example 2 — the user disables the generator for this file

```java
// {@link hr.hrg.codebuddy.RecordBuilder} Generate builder for the Order record.
// {enabled:false, note: 'local tweaks; see PR #42'}

package com.example.order;

import ...

public final class OrderBuilder { ... }
```

On the next regen pass, the generator sees `enabled: false` and
does not rewrite the class body, the imports, the package
declaration, or the header. It emits one diagnostic: "generator
`hr.hrg.codebuddy.RecordBuilder` is disabled for this file via
`enabled: false`". The user opts back in by setting the value
back to `true`, or by deleting the header (both lines).

### Example 3 — the user customises one option

```java
// {@link hr.hrg.codebuddy.RpcDispatcher} JSON-RPC dispatcher for the user-facing API.
// {enabled:true, blockMarker: "strict", maxMethods: 128}

package com.example.api;

import ...

public final class RpcDispatcher { ... }
```

The generator honours `blockMarker: "strict"` and emits strict
`// generator:begin` / `// generator:end` markers around each
`case` arm in this file. The generator also honours
`maxMethods: 128`. The next regen pass for any other file still
emits the project default (implicit markers, 64 methods) because
the project-wide default is unchanged.

## Alternatives considered

- **Option A — Project-wide config files only.** The generator
  reads its options from a YAML / properties / TOML file in the
  project root. Per-class overrides require a separate mechanism
  (path globs, annotations, etc.). Rejected: the user cannot
  see the config next to the class that depends on it, and a
  per-class opt-out (the `enabled` case) requires its own
  annotation or marker scheme. The class-file header is the
  natural place for both.
- **Option B — Annotations on the class.** The generator reads
  per-class options from annotations on the generated class
  itself. Rejected: forces the generator to define a custom
  annotation per generator, requires an annotation class on
  the classpath, and the user has to discover the annotation's
  name. The class-file header is plain comments and works for
  any generator without any classpath machinery.
- **Option C — In-class-body block comment (the previous draft
  of this decision).** Rejected: occupies a noticeable amount
  of vertical space, is the first thing a reader sees, and
  competes with the generator's own block-level cooperation per
  DEC-020. The two-line header above imports is the smaller,
  less disruptive shape.
- **Option D — Sidecar JSON / YAML per generated class.** A
  `RpcDispatcher.options.json` file next to the generated class.
  Rejected: doubles the number of files, and the sidecar file
  is invisible to anyone reading the class. The header is in
  the same file the user is already reading.
- **Option E — Full JSON (not JSON5) in the second line.**
  Rejected: the user has to write `"enabled": true,` and
  `"blockMarker": "implicit"`, which is more noise for a
  single-line config that is read by humans first and machines
  second. The JSON5 subset in § 4 is the project-blessed
  compromise.

## Consequences

### Positive

- The user can see, in the file they are reading, which
  generator produced it, what it does, and what options are
  available — without leaving the file.
- The two-line header is small enough not to compete with the
  generator's own content; it lives above the imports where
  the reader's eye does not expect to see class-level detail.
- Per-class options give the user a way to tweak generator
  behaviour for one file without changing the project-wide
  default.
- The `enabled` knob is the per-file equivalent of DEC-018's
  whole-file freeze, and the user can opt back in by deleting
  the header (one action) or by setting the value back to
  `true` (also one action).
- The `{@link …}` reference in the first line is rendered as
  a clickable link by any IDE that supports the syntax, so the
  developer can jump to the generator's source in one click.
- The JSON5 subset is small, parseable, and human-friendly
  enough to be written by hand without tools.
- The header is generated source and follows the cooperative
  preservation rules from DEC-020; the user has a familiar
  mental model.

### Negative

- The JSON5 subset is a project-specific micro-language. A
  user who copies a header from another project (or from a
  blog post) may write a value that the project's subset does
  not support, and the diagnostic has to be clear about which
  Jackson feature is missing.
- Generators MUST implement a JSON5 parser or use the shared
  codegen-module helper. The helper itself depends on Jackson
  being on the classpath; that is acceptable because Jackson is
  already a project dependency for other reasons.
- The user has to know the header syntax. The LSP / IDE
  sidecar SHOULD surface it (highlight, hover with
  explanation, code action to reset a key to its default).
- A file that disables the generator via `enabled: false` is
  essentially a hand-written file. The user must remember
  that the next regen pass will leave it alone, even if the
  project's other files are regenerated. The diagnostic on
  first-emission-of-nothing is the only signal.
- A bug in the header parser can cause the generator to
  silently ignore a config key. The CI fixture for "generator
  honours per-class config" is the defence.

### Follow-up

- Each generator's README publishes its full list of config
  keys, value formats, and defaults, and a sample header.
- Provide a helper in the codegen module that builds the
  Jackson `ObjectMapper` with the JSON5 features in § 4
  enabled, parses the second line, validates the keys, and
  yields a typed config object. Individual generators extend
  the typed config with their own keys.
- Add a CI fixture per generator that writes a file with a
  known config, runs the generator, and asserts the generator
  honoured the per-file values.
- Update the LSP / IDE sidecar to highlight the two-line
  header, show a hover with the generator's id and a link to
  its README, and offer a "reset to default" code action for
  each config key.

## Out of scope

- **Cross-generator config conflicts.** If two generators
  consider the same file "theirs" and emit conflicting
  headers, that is a generator bug in either or both; let the
  user resolve it (typically by disabling one).
- **Generator orchestration across files.** A file's config
  affects only that file. Coordinated multi-file config (e.g.
  "dispatcher A and dispatcher B share a `maxMethods`
  setting") is a future concern.
- **Visual diff UI for config changes.** The diagnostic on
  "this value differs from the project default" is enough for
  the first iteration; a UI is a follow-up.
- **Encrypted / hidden config values.** The header is plain
  text in the source file. Secrets and per-file overrides
  that should not be checked in are not what this mechanism
  is for.
- **JSON5 features outside the table in § 4.** Multi-line
  strings, comments inside the JSON5 blob, and similar JSON5
  features are not in the project subset and the parser MUST
  reject them.

## Acceptance criteria

- Every generator in the project that emits a whole class
  (or a top-level type) emits a two-line Java line-comment
  header above the `package` declaration.
- The first line starts with `// {@link <fqn>}` and a
  one-line description ending in a period, ≤ 120 characters.
- The second line starts with `// {` and ends with `}` and
  contains a single-line JSON5 config blob.
- The JSON5 parser enables exactly the Jackson features
  listed in § 4 and no others.
- The generator re-reads the header on every regeneration
  pass and honours the values it finds.
- A user who edits a config value to a valid alternative
  sees that value respected on the next regeneration pass.
- A user who sets `enabled: false` sees the generator stop
  rewriting the file, with a single diagnostic the first time
  the generator would have emitted into that file.
- A user who sets a config value to an invalid alternative
  sees a diagnostic, not a silent fallback to the default.
- A user who deletes the header gets a fresh header
  re-emitted on the next regeneration pass.
- The header format and JSON5 subset are documented at
  `doc/brainstorm/generator-class-body-header.md` and the
  format is reachable from every generator's own docs.
