# DEC-019 — Source-Visible, IDE-Navigable Wiring

> **Status:** Accepted.
> **Applies to:** all JCodeBuddy codegen, all `project-automation` modules, and every
> pattern documented under `doc/brainstorm/`.

## Decision

JCodeBuddy does **not** behave like Spring, Quarkus, Guice or any
other Java framework that hides program flow behind runtime classpath
scanning, reflection, or proxy magic, even mapping strings to method calls via Map.
even Dagger that geenrates code has too many factories to allow any meaningful navigation through the code.

The project's preferred approach is:

1. A developer may use **annotations or other declarative syntax** to
   describe a connection between two pieces of code.
2. **Every declared connection must be materialized as ordinary Java
   source code that is committed to git.** The committed source is the
   source of truth, not the annotation, not the XML file, not the scan
   result, not the runtime container.
3. **The committed source must be navigable with any basic IDE** —
   jump-to-definition, find-usages, type hierarchy, "go to
   implementation". A developer (or an AI coding agent) who only has
   the committed sources and a stock IDE must be able to follow the
   program flow from entry point to leaf without running the
   application, reading generated bytecode, or reading framework
   documentation.

## Why

- **Debuggability.** Tracking the actual execution flow in a heavy-IOC
  codebase is famously hard (and slow). The project prioritizes
  program flow that can be followed on screen.
- **Reviewability.** PRs must show concrete wiring, not diffs of
  annotations that mean different things in different contexts.
- **AI-friendliness.** AI coding agents reason about explicit, linear
  code far more reliably than about scattered annotations and
  reflection-based discovery. See
  `hipster-ioc/doc/architecture-and-design.md` for the original
  rationale.
- **Longevity.** Comprehension must not depend on the framework's
  mental model surviving the next refactor of the framework itself.

## What this means concretely

- Generated wiring code lives in `src/main/java/...` or in
  `target/generated-sources/...` that is checked in (or is at least
  byte-identical to a checked-in template). It is **real Java code**,
  not bytecode generated at runtime by a container.
- A `@BusinessProcess` / `@CoreChange` / `@NotificationOnly`
  annotation is **only a marker**. The behavior it implies (which
  steps are scheduled, how the dispatcher commits, how the loop
  guard is wired) must be visible as a concrete method body
  somewhere in the committed source.
- The `project-automation` module is allowed to exist (it is how the
  materialization happens), but its output must always be
  inspectable, regenerable, and reproducible from the hand-written
  inputs.
- Hand written boilerplate is preferred as it allows easy migration to code-gen.
  Once the pattern is stable it can be tweaked for easier code-gen with keeping
  good readibility and navigability, and then codegen can be set-up to maintain the pattern.
- No reflection-driven discovery, no proxy classes that hide their
  targets behind interface lookups, no `META-INF/services` /
  `spring.factories`-style registries whose contents are the
  program's actual wiring.

## What this does *not* mean

- The project does not reject DI as a concept — it rejects the
  *invisible* part. Explicit constructor / parameter injection is
  fine and encouraged, as long as the wiring is in the source.
- The project does not reject annotations as syntax — it rejects
  annotations that *replace* the wiring instead of *labeling* it.
- The project does not reject code generation — it requires
  generation to be **reified into committed, navigable source**
  rather than emitted at runtime.

## Transport routing — REST and JSON-RPC dispatchers

This section is the **specific** application of the rule to the way
incoming transport requests (HTTP REST endpoints, JSON-RPC methods,
gRPC service methods, etc.) are bound to the Java code that handles
them. It is the single largest class of accidental "hash map of
reflection" wiring in typical Java services, so the project calls it
out explicitly.

### The anti-pattern (forbidden)

Do **not** implement a REST or JSON-RPC dispatcher by:

- defining an interface,
- annotating each implementation method with the route / method name,
- scanning the implementation at startup, and
- storing the result in a `Map<String, Method>` or
  `Map<String, ServiceInterface>` that the dispatcher then looks up
  and `invoke()`s at request time.

Concretely, this shape is **out**:

```java
// FORBIDDEN — do not write code like this
public class RpcDispatcher {
    private final Map<String, Method> methods = new LinkedHashMap<>();

    public void register(Object service) {
        for (Method m : service.getClass().getDeclaredMethods()) {
            if (m.isAnnotationPresent(RpcMethod.class)) {
                m.setAccessible(true);
                methods.put(m.getAnnotation(RpcMethod.class).value(), m);
            }
        }
    }

    public JsonRpcResponse dispatch(JsonRpcRequest req) {
        Method m = methods.get(req.method);          // string-keyed lookup
        try { m.invoke(service, req.params); }       // reflective call
        catch (Exception e) { ... }
    }
}
```

The same anti-pattern with REST looks like:

```java
// FORBIDDEN — do not write code like this
public class RestRouter {
    private final Map<String, Method> routes = new HashMap<>();

    public void registerController(Object controller) {
        for (Method m : controller.getClass().getDeclaredMethods()) {
            GetMapping g = m.getAnnotation(GetMapping.class);
            if (g != null) routes.put(g.value(), m);
            // ...same for PostMapping, PutMapping, DeleteMapping
        }
    }
}
```

Why this is forbidden here even though it is idiomatic in Spring /
Quarkus / express / many others:

1. The connection between the **string** `"users.get"` (or
   `"/users/{id}"`) and the **Java method** that handles it lives
   inside a runtime-populated map. A developer cannot jump-to-definition
   on the string and land on the handler — they have to know to look
   inside `register(...)` and read the `for` loop.
2. The handler call goes through `Method.invoke`, so the call site
   in the source (`m.invoke(...)`) is **not** the call site the IDE
   can navigate from. "Find usages" on the handler method does not
   return the dispatcher.
3. The wiring is filled in at runtime, so its contents are unknown
   from the source alone. Reviewing a PR that adds a new endpoint
   shows only the annotated method — the wiring changes that put it
   on the map are invisible.
4. AI coding agents cannot follow program flow across the map; they
   have to guess, which produces brittle suggestions.

The anti-pattern is forbidden **regardless of whether the annotations
are processed at compile time or scanned at runtime**. The forbidden
shape is the map + reflection call, not the use of an annotation per
se.

### The required shape (generator or hand-written)

A REST route or JSON-RPC method binding must be a **direct method
call** that the developer (or the IDE, or the AI agent) can navigate
to. Two equivalent ways to reach that shape:

**A. Hand-written explicit routing table.** A real Java method whose
body is a `switch` / `if-else` / table that calls each handler
directly. The IDE navigates from each branch to the handler.

```java
// GOOD — explicit, navigable, committed
public JsonRpcResponse dispatch(JsonRpcRequest req) {
    return switch (req.method) {
        case "users.get"    -> usersService.get(req.params, req.id);
        case "users.create" -> usersService.create(req.params, req.id);
        case "users.delete" -> usersService.delete(req.params, req.id);
        default             -> JsonRpcResponse.err(req.id, -32601,
                                        "Method not found: " + req.method);
    };
}
```

```java
// GOOD — explicit, navigable, committed
public void route(HttpExchange ex) throws IOException {
    String path = ex.getRequestURI().getPath();
    if (path.equals("/users/get"))    { usersGetHandler.handle(ex);   return; }
    if (path.equals("/users/create")) { usersCreateHandler.handle(ex);return; }
    // ...
    ex.sendResponseHeaders(404, -1);
}
```

The point is not the specific control structure (`switch`, `if-else`,
table lookup on an `Enum`, visitor, etc.) — the point is that
**each branch is a direct method call that the IDE can jump to from
the branch site**.

**B. Generator-written explicit routing table.** If the number of
routes is large and a hand-written table would be tedious, the
`project-automation` module may emit the table itself. The emitted
class must:

- live in `target/generated-sources/...` checked into git, or be
  byte-identical to a checked-in template,
- contain **direct method calls** in each branch — not a `Map<String,
  Method>` populated by scanning and not `Method.invoke(...)`,
- be human-readable, so a reviewer can still see the route-to-handler
  binding in a diff.

```java
// GOOD — generated, but still explicit and navigable
public JsonRpcResponse dispatch(JsonRpcRequest req) {
    return switch (req.method) {
        case "users.get"    -> usersService.get(req.params, req.id);
        case "users.create" -> usersService.create(req.params, req.id);
        case "orders.list"  -> ordersService.list(req.params, req.id);
        // ...generated from the project's @RpcMethod declarations
        default             -> JsonRpcResponse.err(req.id, -32601,
                                        "Method not found: " + req.method);
    };
}
```

The generator may read the `@RpcMethod` annotations to *learn* which
cases to emit, but the emitted code is the wiring, not the
annotations. If a developer deletes the `users.create` case, the
generator must regenerate it on the next run; if the developer
deletes the annotation, the generator removes the case. Either way,
the call site is in the emitted source.

### The two acceptance tests

For any REST or JSON-RPC dispatcher in the project, both must be
true:

1. **Navigate-by-string test.** Opening the dispatcher and
   Ctrl-clicking on the string `"users.get"` (or `/users/get`,
   or the case label in the `switch`) lands the developer on the
   handler method.
2. **Reflective-call absence test.** `grep -RIn "Method.invoke\\|getDeclaredMethod\\|Proxy.newProxy" src/main/java`
   returns nothing inside transport-routing code paths (a
   legitimate internal use of reflection in, say, a generic
   serializer is fine, but never on the route-to-handler path).

If either test fails, the dispatcher is not compliant with this
decision and must be refactored before merge.

### Why "just an annotation processor" does not satisfy the rule

A common push-back: "we'll keep the annotation, but process it at
compile time instead of scanning it at runtime — that should fix the
navigability problem." It does not, on two counts:

- Compile-time processing that emits a `Map<String, Method>` or
  `Method.invoke(...)` call still has the same problem: the wiring
  is a map populated by generated code, not a direct call.
- Compile-time processing that emits a `switch` over the annotation
  values *is* fine — that is shape (B) above. The decision is not
  about when the annotation is read; it is about whether the
  *result* of reading it is a direct call the IDE can navigate.
