# Phase 7 benchmarks — absolute read-path baselines

Generated by `bun run scripts/rewrite-migration/run-tooling-benchmarks.js`; the machine-readable results
are in [`benchmarks.json`](benchmarks.json) next to this file, and the numbers below are that file's table
with the interpretation added. Nothing here is handwritten — rerun the command and both change together.

## What was deliberately *not* measured

The plan sketched JavaParser-versus-OpenRewrite comparisons. **They are not here, and cannot be**: Phase 6
removed JavaParser from the build, so there is no alternative to measure against on this classpath. The
phase's re-scope decision was to keep absolute baselines only, which is what this file holds — cost per
read, cost per position lookup, and the share of a read that the F-34 validity guard accounts for. Anyone
who later wants a comparison needs a baseline captured *before* the next such removal; this file is that
capture for the current state.

One fork is a deliberate weakness: it is enough for an order of magnitude and for a diff against the next
run, and it keeps a full sweep under two minutes. It is not enough for a claim about a 5 % difference.

## The read path

`readFragment` reads a five-line interface. `readCommittedView` reads
`hipster-entity-example/.../PersonSummary.java` (2 KB). `readLargestFileInRepository` reads
`EntityMetadataGenerator.java` (206 KB, 3 391 lines). `read*` is `SourceReader.readSourceText` — OpenRewrite's
tree *plus* javac's validity check; `*SyntaxCheck*` is `JavaSyntaxCheck.inspect` alone, i.e. javac only.
"cold" means a text the memo cache has never seen, which is what a generator faces for each new file.

| Benchmark | Score | Unit | What it answers |
|---|---:|---|---|
| `readFragment` | 56 087 | µs/op | a whole read of a 5-line file |
| `readCommittedView` | 56 141 | µs/op | a whole read of a real 2 KB view |
| `readLargestFileInRepository` | 164 575 | µs/op | a whole read of the repo's largest source |
| `coldSyntaxCheckFragment` | 33 307 | µs/op | javac alone, cold, on 5 lines |
| `coldSyntaxCheckCommittedView` | 32 183 | µs/op | javac alone, cold, on 2 KB |
| `coldSyntaxCheckLargestFileInRepository` | 40 498 | µs/op | javac alone, cold, on 206 KB |
| `coldReadLargestFileInRepository` | 176 283 | µs/op | both halves cold, on 206 KB |
| `syntaxCheckFragment` | 0.002 | µs/op | the same call, answered from the cache |
| `syntaxCheckLargestFileInRepository` | 0.005 | µs/op | the cache, on the largest file |
| `syntaxCheckAlreadyInspected` | 0.009 | µs/op | two cached lookups (types + methods) |
| `stringConcatenationAlone` | 26.5 | µs/op | the control: the cost of building a cold variant |

### What the numbers say

1. **The cost of a read is fixed, not proportional to the file.** Five lines cost 56 ms and 206 KB costs
   165 ms — a 42 000-fold difference in input for a 3-fold difference in time. Both halves of the read are
   dominated by per-call setup: javac alone takes 33 ms on a fragment that has four declarations in it, and
   40 ms on a 3 391-line file. Whatever the read path would need optimising, it is not the parsing of large
   files; it is the ~30–55 ms a call spends getting to the parsing.
2. **The F-34 guard is roughly 60 % of a cold read** — 33 ms of the 56 ms a fragment costs. That is the
   number the migration owed itself. Read the second finding with it:
3. **The memo cache makes the guard's repeated cost vanish.** A cold `inspect` is 33 ms; a cached one is
   2 ns, four orders of magnitude cheaper, and it does not grow with the file (0.002 µs on the fragment,
   0.005 µs on the largest file). `JavaSyntaxCheck` is asked one question per declaration, so without that
   cache a 3 391-line file would cost roughly 90 parses × 40 ms. It is the cache, not the guard's cheapness,
   that makes the design affordable.
4. **The guard's cost is per distinct text, once.** `coldRead` (176 ms) minus `read` (165 ms) is the same
   ~11–33 ms javac delta, and the `stringConcatenationAlone` control (26 µs) is three orders of magnitude
   below both, so the cold variants measure a real parse rather than a copy.

## Position lookups

Per-declaration queries against an already-read file. The synthetic input is the 2 000-accessor interface
from `LargeSourceEdgeCaseTest`; the real input is `EntityMetadataGenerator.java`.

| Benchmark | Score | Unit | Per operation |
|---|---:|---|---|
| `accessorLinesOnTheSyntheticTree` | 2 775 | ns/op | 1.4 ns per member line (`@OperationsPerInvocation(2000)`) |
| `annotationLinesOnTheSyntheticTree` | 5 194 | ns/op | 2.6 ns per annotation line |
| `memberTextsOnTheSyntheticTree` | 5 143 | ns/op | 2.6 ns per verbatim member slice |
| `accessorLinesOnARealLargeFile` | 14 109 | ns/op | one pass over every method of the 3 391-line file |
| `typesWithEnclosingOnARealLargeFile` | 608 584 | ns/op | one full class-index walk of that file |
| `treeWalkOnlyOnARealLargeFile` | 1 582 013 | ns/op | `findAll(methods)` + `typeDeclarations` on the same file |

### What the numbers say

5. **A cached position lookup is nanoseconds.** 1.4 ns for a member's line, 2.6 ns for an annotation's,
   2.6 ns for a verbatim slice. Position resolution is free next to the 33 ms a cold read costs; a
   generator's per-field work is noise. Nothing in the location layer needs a faster data structure.
6. **The tree walks are the only query cost worth naming**: 0.6 ms for the class index's
   `typesWithEnclosing` and 1.6 ms for a whole-tree scan of the largest file. Against 165 ms to read that
   file, the walk is under 1 % — again, reading is the expensive part, not asking questions of a tree.
7. The synthetic lookups are an order of magnitude cheaper per member than a pass over the real file
   because the real file's members are spread across nested types and overloads, and a lookup is a linear
   walk of that file's declaration list. At these sizes that is invisible; a file with tens of thousands of
   members would want an index, and this is the measurement that would justify building one.

## Reproducing

```
bun run scripts/rewrite-migration/run-tooling-benchmarks.js
```

Compiles the module under `-Pjmh`, resolves the test classpath through the project's JDK 25 Maven launcher,
and runs JMH with that same JDK. `--include`, `--forks`, `--warmup`, `--measurement`, `--skip-compile` and
`--out` are documented in the script header. It refuses to run on a non-25 JDK rather than silently
measuring nothing, because JMH exits 0 with an empty result file when every fork dies on
`UnsupportedClassVersionError` — which is how the first run of this script produced a clean, empty table.

## Where this leaves the migration

The read path is affordable: a whole-repository sweep of the 283 main sources costs minutes, not hours
(`MigrationCompletenessTest` does three such sweeps inside the normal `clean test` gate), and the
per-declaration work the generators do is nanoseconds. The guard F-34 required is paid once per file and
then amortised by the cache. If the read path ever needs to be an order of magnitude faster, the target is
the per-call setup cost in finding 1, not the guard and not the queries.
