# AGENTS.md — Rules for AI Coding Agents Working in This Repository

> This file is read by AI coding agents (Kilo, codebuddy, and similar
> tools) at the start of every session. The rules below are
> **project-wide** and apply to anything you generate — code,
> documentation, tests, examples, or commit messages.

## 1. Source-Visible, IDE-Navigable Wiring (mandatory)

> **Status:** accepted project-wide rule, codified in
> [`doc/architecture/decisions/DEC-019.md`](doc/architecture/decisions/DEC-019.md).
> **Applies to:** all JCodeBuddy codegen, all `project-automation`
> modules, and every pattern documented under `doc/brainstorm/`.

JCodeBuddy does **not** behave like Spring, Quarkus, Dagger, Guice or
any other Java framework that hides program flow behind runtime
classpath scanning, reflection, or proxy magic. When you generate
code or documentation for this repository:

1. A developer may use **annotations or other declarative syntax** to
   describe a connection between two pieces of code.
2. **Every declared connection must be materialized as ordinary Java
   source code that is committed to git.** The committed source is
   the source of truth — not the annotation, not the XML file, not
   the scan result, not the runtime container.
3. **The committed source must be navigable with any basic IDE** —
   jump-to-definition, find-usages, type hierarchy, "go to
   implementation". A developer (or another AI agent) who only has
   the committed sources and a stock IDE must be able to follow the
   program flow from entry point to leaf without running the
   application, reading generated bytecode, or reading framework
   documentation.

### What this means concretely

- Generated wiring lives in `src/main/java/...` or in
  `target/generated-sources/...` that is checked in (or is at least
  byte-identical to a checked-in template). It is **real Java code**,
  not bytecode emitted at runtime by a container.
- A `@BusinessProcess` / `@CoreChange` / `@NotificationOnly` /
  `@CoreChangeOnChange` annotation is **only a marker**. The
  behavior it implies (scheduling, dispatch, loop guard) must exist
  as a concrete method body somewhere in the committed source.
- The `project-automation` module is allowed to exist (it is how the
  materialization happens), but its output must be inspectable,
  regenerable, and reproducible from the hand-written inputs.
- **Do not generate** reflection-driven discovery, proxy classes
  that hide their targets behind interface lookups, or
  `META-INF/services` / `spring.factories`-style registries whose
  contents are the program's actual wiring.
- **REST and JSON-RPC dispatchers are not exempt.** Routing a
  request by string name to a Java handler must be a **direct
  method call the IDE can navigate to** — not a
  `Map<String, Method>` populated by scanning annotations and
  invoked with `Method.invoke`. The accepted shapes and the two
  acceptance tests are spelled out in DEC-019 § "Transport routing
  — REST and JSON-RPC dispatchers". See
  [`doc/architecture/decisions/DEC-019.md`](doc/architecture/decisions/DEC-019.md).
- **Cooperative codegen — preserve user-tweaked generated blocks.**
  When you generate code that lives next to hand-written code
  (entity builders, dispatcher cases, loop-guard scaffolding,
  etc.), the default is **implicit block detection**, not strict
  marker comments: the generator recognises its previous output by
  the same structural shape it used to emit it (a `case "...":` arm,
  a `withXxx(...)` builder method, a `@CoreChangeOnChange` scaffold
  method, etc.) and preserves the body verbatim including any user
  edits. The user opts back into regeneration by **deleting the
  block**; the generator emits a fresh one at the canonical
  location. A single optional hint comment (`// generated by ... —
  edit freely, delete to regen`) may be emitted as a UX aid but
  must not be relied on for recognition. The strict
  `// generator:begin` / `// generator:end` pair is allowed but
  **discouraged** as a default because it adds noise to every
  block; use it only when a block cannot be recognised by shape.
  The full decision, three-state model, reporting mode, and
  robustness patterns are in
  [`doc/architecture/decisions/DEC-020.md`](doc/architecture/decisions/DEC-020.md)
  with a practical reference in
  [`doc/brainstorm/cooperative-codegen-preserve-user-tweaks.md`](doc/brainstorm/cooperative-codegen-preserve-user-tweaks.md).
  This complements DEC-018 (whole-file freeze markers) and DEC-019
  (source-visible wiring) without contradicting them.
- **Generator class-file header — short id, JSON5 config,
  per-file options.** When you generate a whole class, emit a
  **two-line `//` comment pair above the `package` declaration**,
  not a class-body block:
  `// {@link <fqn>} <one-line description>.`
  on the first line, and a single-line JSON5 config blob
  (`// {enabled:true, blockMarker: "implicit"}`) on the second.
  The JSON5 subset is **pinned** to the specific Jackson
  `JsonReadFeature`s listed in DEC-021 § 4 (single-quoted
  strings, unquoted field names, trailing commas, leading decimal
  point, leading plus sign, non-numeric numbers, backslash
  escaping of any character); anything else is rejected with a
  diagnostic. The header is generated source and follows the
  cooperative rules from DEC-020: the user may edit it, deleting
  it triggers regen. The mandatory `enabled` knob (default
  `true`) is the per-file equivalent of DEC-018's whole-file
  freeze — set it to `false` to take a file fully under manual
  control. The full decision, exact format, and patterns are in
  [`doc/architecture/decisions/DEC-021.md`](doc/architecture/decisions/DEC-021.md)
  with a practical reference in
  [`doc/brainstorm/generator-class-body-header.md`](doc/brainstorm/generator-class-body-header.md).
  This complements DEC-020 (cooperative blocks) and DEC-019
  (source-visible wiring): the `{@link …}` reference in the
  first line is the generator-side fulfilment of the same
  navigability rule.

### What this does *not* mean

- DI as a concept is fine — it is the *invisible* part that is
  rejected. Explicit constructor / parameter injection is encouraged.
- Annotations as syntax are fine — what is rejected is annotations
  that *replace* the wiring instead of *labeling* it.
- Code generation is fine — what is required is that generation is
  **reified into committed, navigable source** rather than emitted
  at runtime.

## 2. Other rules you are expected to follow

These come from existing project files; this section is a reminder
with pointers, not a new policy.

- **Modular multi-module Maven layout.** A `project-automation`
  module orchestrates dev-time codegen; the runtime app modules
  depend on released JCodeBuddy libraries, never on
  `project-automation`. See [`README.md`](README.md).
- **Cooperative codegen, not annotation processing.** Prefer
  generating committed source that coexists with hand-written
  code, rather than a processor that only runs at compile time.
  See [`doc/brainstorm/dec-009-source-visible-generation-strategy.md`](doc/brainstorm/dec-009-source-visible-generation-strategy.md).
- **JavaParser as the AST of choice.** Read, write, and reformat
  source through `com.github.javaparser` so generated code and
  parsed code share the same representation. See
  [`doc_knowledge/code.graph.md`](doc_knowledge/code.graph.md).
- **Memory and off-heap work go through `metadata-arena`.** Use
  `Arena` / `LongToLongsIndex` / mmap formats from that module
  rather than inventing your own. See
  [`metadata-arena/README.md`](metadata-arena/README.md).

## 3. How to use this file

- Read it before starting any non-trivial work in this repo.
- If a task description conflicts with rule §1, follow rule §1 and
  flag the conflict to the user in your final message.
- If you are unsure whether a specific piece of generated code
  satisfies rule §1, ask: "Could a developer with a stock IDE
  follow the program flow from entry point to leaf using only the
  committed sources?" If the answer is no, the generated code is
  not acceptable as-is.
