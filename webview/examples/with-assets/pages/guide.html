Five rules that make a page work in every host

A page is read in three places: the IDE's own webview, an ordinary browser, and possibly a CI artifact viewer or a PDF export. Only the first has window.openFile. These five rules are what make one page work in all of them.

  1. Feature-detect, never assume. typeof window.openFile === 'function' before every call. An unguarded call throws a TypeError inside a click handler and silently kills navigation for every later click in the page — the failure looks like "links stopped working", not like an error.
  2. Never render a dead-looking link. When there is no bridge, copy path:line to the clipboard and say so. A visible path string the user can paste beats an anchor that does nothing.
  3. Use the link base, not an absolute path. data-link-base plus the page's own location is the only spelling that survives a clone, a branch switch or a moved tree. An absolute path in a committed artifact is wrong on every machine but one.
  4. Resolve or leave alone. Emit a link only when you can point at a real file; when you claim a line, the thing you claim must be on that line. A page of plausible links that go nowhere is worse than plain text.
  5. No network at view time. No CDN, no bundler, no node_modules. The JCEF webview opens a local file with no server behind it. Local <script src="assets/…"> is fine; an https:// asset is not.
Rule 4 is the one a generator gets wrong, because a generator has a name and not a location. The answer this repository uses is the class index (.jcodebuddy/index/classes.json): a document names a type and the tool finds the declaring file and its declaration line, then drops the link if it cannot. See scripts/markdown-view/render.js.

Language samples

Highlighting is per block and needs nothing but a language-* class. microlighter scans pre > code, loads the grammar for the language it finds, and registers ranges on CSS.highlights. All five required languages, plus the two grammars they pull in as dependencies (HTML needs CSS/JSON/JS, Markdown needs YAML), are bundled in assets/microlighter.js.

JavaScript source.js

// The whole client ladder, in the order it must be tried.
const BRIDGE_PORT = 18881;

function openInIde(relativePath, line = 1) {
  const target = new URL(relativePath, PROJECT_ROOT).pathname;

  if (typeof window.openFile === 'function') {          // 1. injected by the IDE webview
    window.openFile(target, line, 1);
    return 'injected';
  }
  if (BRIDGE_PORT > 0) {                               // 2. loopback HTTP bridge
    const frame = document.createElement('iframe');
    frame.style.display = 'none';
    frame.src = `http://127.0.0.1:${BRIDGE_PORT}/open?filePath=${encodeURIComponent(target)}&line=${line}`;
    document.body.appendChild(frame);
    return 'bridge';
  }
  navigator.clipboard?.writeText(`${target}:${line}`);   // 3. the honest fallback
  return 'clipboard';
}

Java source.java

// A generated dispatcher: a direct method call per case, never Method.invoke.
// The routing a reader can follow with a stock IDE is the routing that counts.
package hr.hrg.example.dispatch;

public final class ReportDispatcher {

    private final EntityReport entityReport;
    private final CoverageReport coverageReport;

    public ReportDispatcher(EntityReport entityReport, CoverageReport coverageReport) {
        this.entityReport = entityReport;
        this.coverageReport = coverageReport;
    }

    /** Delegate the rendered model to the generator that owns the page. */
    public void dispatch(String kind, ReportModel model) {
        switch (kind) {
            case "entity-reference" -> entityReport.render(model);
            case "coverage" -> coverageReport.render(model);
            default -> throw new IllegalArgumentException("unknown report kind: " + kind);
        }
    }
}

Embedding generated blocks

A generated half does not need its own page. Emitting a table, a card grid or a code block into the manual page is often better, because the prose that explains it sits right next to it. The only rules are the five above plus one: a generated block must not carry its own copy of the client script, because the delegated handler already covers the whole document — including elements that arrive after load. 

// A generator's contract, in one function. Note what it does when it cannot
// resolve: it returns null, and the caller then prints the name as text.
export function linkFor(typeName, classIndex) {
  const entry = classIndex[typeName];          // .jcodebuddy/index/classes.json
  if (!entry) return null;                     // resolve or leave alone

  return `<span class="file-link" data-open="${escapeAttr(entry.path)}"`
    + ` data-line="${entry.declarationLine}" data-member="${escapeAttr(typeName)}"`
    + ` data-role="type">${escapeHtml(typeName)}</span>`;
}

Verifying before you ship

A page is a build output like any other, so test it like one. Two checks catch almost everything:

  • Every link resolves. Walk the emitted data-open values, resolve each against the link base, and assert the file exists — and where you claimed a data-member, assert that the member is on the claimed line. This repository's webview/examples/smoke-test.mjs does exactly that for both example pages, over all four pages and 40-odd links, and fails the run on the first unresolved target.
  • The page opens with no network. Grep the output for an https:// asset, a <script src> pointing off-box, or a CDN host, and fail. The renderer in scripts/entity-html/ asserts the same thing for the generated entity page. 
<!-- run from the repository root -->
node webview/examples/smoke-test.mjs

It renders each page in a real Chromium over file://, over the DevTools Protocol, and reads back document.body.dataset.syntaxReady — the <blocks>/<categories> marker assets/highlight-runner.js publishes. So the test does not merely assert that the HTML parsed: it asserts that microlighter ran and registered token ranges.
