One shell, several pages, four assets

This is the same navigator as the self-contained example, split into files. The manual landing page you are reading, a manual guide, and a generated entity reference all sit on one shell and one navigation client. Editing assets/site.css restyles all three; fixing assets/nav-client.js fixes all three; adding a language to assets/microlighter.js highlights it on all three.

That shared shell is the actual reason to pick this form. The self-contained twin is better when one file must travel alone; this form is better when a project has more than one page, which a project navigator always does.

That last row is the one that decides it for a project with generated pages. A generator that owns pages/entity-reference.html must be able to rewrite that file without touching the manual prose around it, and it must not have to re-emit a stylesheet to do it.

Both forms are offline and both keep absolute paths out. A <script src="assets/…"> is a local reference, not a network one — the rule the generated reports follow is "no network at view time", not "no separate files". What is forbidden is a CDN, a bundler (node_modules) or an http(s):// asset, because the JCEF webview opens the page with no server and no guarantee of a network.

The four lines of wiring

A page that joins this shell needs four tags. Two are the stylesheets, two are the scripts; the two scripts carry their configuration as attributes, so there is nothing to register and no initialisation call to remember. 

<link rel="stylesheet" href="assets/site.css">
<link rel="stylesheet" href="assets/syntax-theme.css">

<body data-syntax-theme="default">

<!-- data-link-base is resolved against THIS script's own src, so it is the
     same string on a page at the root and on a page three folders deep. -->
<script id="nav-client"
        src="assets/nav-client.js"
        data-link-base="../../../.."     <!-- from assets/ up to the repository root -->
        data-bridge-port="18881"></script>

<script id="highlight-runner" src="assets/highlight-runner.js"></script>
<script id="microlighter" src="assets/microlighter.js"></script>

Order matters for exactly one pair: microlighter.js defines window.microlighter, and highlight-runner.js calls it. Put the vendor script first. The nav client is independent of both and can go anywhere.

data-bridge-port is the loopback port of the IDE's HTTP bridge — 18881 for webview/webview-jetbrains, 18882 for webview/webview-vscode. It is a deployment detail, so do not invent it: GET /health answers without credentials and tells you whether a bridge is really listening.

Then put a location on whatever element you like — a table cell, a list item, a <code> span — and the delegated handler in the nav client does the rest: 

<span class="file-link"
      data-open="webview/webview-jetbrains/README.md"
      data-line="71"
      data-member="window.openFile"
      data-role="doc-section">webview/webview-jetbrains/README.md:71</span>

What the generator owns

pages/entity-reference.html is written as if a build step produced it: one <table> of types, every row carrying data-open/data-line, and the same four wiring tags. When your generator runs it overwrites that file and nothing else — which is the whole point of the split. The rule it must follow is "resolve or leave alone": a name it cannot resolve to a file and a line is printed as text.
