# jcodebuddy-core — finding generated code without knowing the generator

A generator commits its output as ordinary source, and it is **cooperative**: a member from an earlier
revision of the generator survives regeneration, so a developer's edit to generated code is kept. The
consequence is that a file in a real project is often **partly generated and partly hand-written**, and
until this module existed the boundary between the two was knowable only to the generator — because the
recogniser *was* the generator.

That is fine while the generator is the only consumer. It is not fine for the other three, which all need
the same answer and none of which can depend on a generator's internals:

- **an external static parser** — a linter, a migration tool, a diff policy, an IDE inspection;
- **an AI agent** reading the source, which has to know which parts it may edit freely and which parts its
  edit will be overwritten by;
- **a reviewer**, who is reading a diff and needs to see at a glance whether the changed lines are the
  developer's or the generator's.

This module is the answer. It has **no dependencies**: no generator, no JSON library, no parser library.
You hand it source text and it hands back line spans.

## Using it

```java
import hr.hrg.jcodebuddy.generated.GeneratedBlock;
import hr.hrg.jcodebuddy.generated.GeneratedCodeParser;

GeneratedCodeParser.Result result = GeneratedCodeParser.parse(
        Files.readString(path), path.toString());

if (result.hasUnknownMarkers()) {
    // A marker this parser does not implement. Do not edit the file: the code under that marker is
    // generated by a rule you cannot apply, and treating it as the developer's loses the edit.
    throw new IllegalStateException("refusing to edit: " + result.issues());
}

for (GeneratedBlock block : result.blocks()) {
    System.out.println(block.describe(path.toString()));
    // file      Thing_.java:1-40
    // member    OrderSummaryBuilderTracking.java:53-96
    // region    Router.java:12-30 (region routes)
    // block     Router.java:41-52
}

// Per line, when that is the question you actually have:
boolean generated = result.isGenerated(57);
result.innermostBlockAt(57).ifPresent(block -> ...);
```

Two decisions worth knowing before you read the spans:

- **A block's span includes its own marker line.** `fromLine()` is the marker, `toLine()` is the closing
  brace. A tool that rewrites the generator's output replaces exactly `fromLine()..toLine()` and does not
  leave the marker behind as an orphan or duplicate it.
- **`innermostBlockAt` is usually the one you want.** A file marker covers a member marker inside it, and
  the most specific answer is the one that tells you the smallest region you must not hand-edit.

## The four markers

Write this into your own tooling. It is the whole vocabulary; a parser that implements all four implements
them for **every** generator that follows the rules, including ones written later.

| Marker | Scope it claims |
| ------ | --------------- |
| `// @generated file <generator>` | the whole file |
| `// @generated member <generator>` | the declaration immediately below it, and its body |
| `// @generated region begin <id>` … `// @generated region end <id>` | the lines between the pair |
| `// @generated block` | the statement below it, bounded by the statement's own braces |

A marker is a Java line comment whose text **begins** with `@generated`. Nothing else about the comment
makes it a marker, and the generator's name is *advisory* — present so a human can jump to the generator,
never something you must interpret.

`block` is the one that would otherwise generate noise. A generated `switch` over REST routes gets **one**
marker before the switch, never one per `case` arm: the construct's braces already bound it, and a marker
per arm would add a line per route forever while telling you nothing you did not have.

## The rule to implement, if you implement nothing else

> **A marker you do not implement MUST be reported, never treated as hand-written.**

Three behaviours are possible when you meet a marker you do not know, and they are not equivalent:

| What you do | What happens |
| ----------- | ------------ |
| Treat the code as hand-written | **Wrong, and silently.** You will edit or migrate generated code and the edit is lost on the next pass |
| Treat the code as generated | Safe for edits, but you silently do not do what the marker asked |
| **Report it, and refuse to decide** | Correct: the code's status is unknown, and the operator is told which marker they need to support |

So the grammar after the keyword is deliberately loose, and this module accepts **any** word as a scope.
That is what lets you refuse rather than guess: a future `// @generated patchwork` is recognisable as *a
marker* by a parser that has never heard of patchwork, so it can say
`unsupported marker: @generated patchwork at Thing.java:412` instead of falling through to "hand-written".

`Result.hasUnknownMarkers()` is that check, and it is deliberately separate from `Result.hasIssues()`: a
parser that is only *reporting* can list every issue and carry on, while a parser that is about to *edit*
should refuse on either.

## Why the brace matching is a lexer

`block` and `member` are bounded by braces, and counting `{` and `}` characters is wrong on real Java — and
wrong **quietly**, reporting a span that is too long or too short with nothing to signal it. Every case
that breaks a counter is common:

```java
String s = "}";              // a brace that is text
return """
    }                        // a brace inside a text block
    """;
// }                          // a brace inside a comment
String escaped = "\\";       // an escaped quote that desynchronises a naive reader
```

So the parser tracks string literals, text blocks, character literals, line comments and block comments,
and skips their contents. It is deliberately **not** a full Java parser: it resolves braces, which is all a
boundary needs, and it treats anything it does not understand as ordinary text — the safe direction,
because the alternative is inventing a boundary.

## What it refuses to guess

Every one of these is reported as an issue, never resolved by extending a span to the end of the file or
to the next blank line. Guessing a boundary is worse than reporting a missing one, because a wrong span
looks exactly like a right one.

| `kind=` | Meaning |
| ------- | ------- |
| `unknown_marker` | A scope this parser does not implement, or a `region` with no direction and id |
| `marker_without_block` | A `block`/`member` whose construct has no braces — `private int value = 1;` |
| `unclosed_region` | A `region begin` with no matching `region end` by end of file |
| `unmatched_region_end` | A `region end` with no matching `region begin` |
| `unclosed_block` | The opening brace below a marker is never closed: the file does not parse |

The diagnostic shape is the one this project uses elsewhere:
`kind=…, location=<file>:<line>, cause=…, current=…, canonical=…, action=…`. The `action` is written for a
person or an agent that has to decide what to do next.

## Emitting markers

A generator should not type the spellings by hand — that is how two implementations of one vocabulary drift
apart. This module owns them:

```java
String header = GeneratedCodeMarkers.fileHeader("hr.hrg.example.Gen", "Thing metadata for the Thing view.");
// // @generated file hr.hrg.example.Gen — Thing metadata for the Thing view.
// // {enabled:true, blockMarker: "implicit"}

GeneratedCodeMarkers.member("hr.hrg.example.Gen");
GeneratedCodeMarkers.block("hr.hrg.example.Gen");
GeneratedCodeMarkers.regionBegin("routes", "hr.hrg.example.Gen");
GeneratedCodeMarkers.regionEnd("routes");
```

The **second** header line is the generator's JSON5 config, and a parser must never have to parse it: the
boundary is on the first line, and the options stay the generator's own business.

## Where the rules come from

- [`DEC-035`](../../doc-hipster-entity/architecture/decisions/DEC-035.md) — the vocabulary, the placement
  rules, and the unknown-marker rule this module implements.
- [`DEC-020`](../../doc-hipster-entity/architecture/decisions/DEC-020.md) — cooperative codegen, which is
  why a file can be partly generated in the first place.
- [`DEC-021`](../../doc-hipster-entity/architecture/decisions/DEC-021.md) — the class-file header's second
  line and its JSON5 config.
- [`DEC-019`](../../doc-hipster-entity/architecture/decisions/DEC-019.md) — generated code is committed,
  navigable source.

## Tests

`GeneratedCodeParserTest` (29 tests) and `GeneratedCodeMarkersTest` (15). Both are written **from a
consumer's side**: they build source text and read spans back through the public API, and no test
references a generator type. That is the property the module exists for, and it is the one a test can
quietly break by reaching for a convenience.

The awkward-Java cases each have a test that fails against a naive brace counter — braces in strings, text
blocks and comments, an escaped quote at the end of a string, an anonymous class inside a member, an array
initialiser, and a switch with nested braces in its arms.
